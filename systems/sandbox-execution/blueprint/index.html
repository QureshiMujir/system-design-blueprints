52 — Multi-Tier Sandbox Runtime

Project Number: 52

Project Name: Multi-Tier Sandbox Runtime

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a single-binary, multi-tier execution sandbox for untrusted code on Linux 6.x, exposing one TierImpl trait over four isolation backends — seccomp+namespaces+cgroups (Tier::Process), a Wasm/WASI engine (Tier::Wasm), a Firecracker microVM (Tier::MicroVm), and a ptrace-mediated usermode kernel (Tier::UserKernel) — so a caller selects an isolation/latency/fidelity tradeoff per workload instead of inheriting whatever a platform happens to expose.

Phase-0 deliverable (one line = one crate/service):

  1. sandbox-core — Tier, Capability, Budget, RunSpec, Outcome, TierImpl (no logic).
  2. sandbox-ns — namespace orchestrator (user/mount/pid/net/ipc/uts/cgroup, I3 order).
  3. sandbox-seccomp — BPF filter compiler, allowlist, notify-fd plumbing.
  4. sandbox-cg — cgroups v2 driver (memory, cpu, io, pids, freezer).
  5. sandbox-process — the Tier::Process backend.
  6. sandbox-runtime — the daemon binary; Unix-socket server; executor.
  7. sandbox-cli — operator CLI (run, exec, inspect).
  8. conformance/ runner — Python harness over the escape and isolation corpora.
  9. chaos/ — the documented escape corpus (11 scripts, §23 threat T1 coverage).

System boundaries:

  • Provides — process/Wasm/microVM/usermode-kernel isolation, quantified resource budgets, a signed append-only audit trail, one gRPC/REST control surface.
  • Delegates — TLS termination and tenant routing above the control plane to the operator's ingress; image persistence to an operator-supplied OCI registry; multi-region scheduling to the operator's orchestrator.
  • Does NOT provide — a full container orchestrator, a service mesh, a general VM manager, Windows/Solaris hosts, secrets management (§23.4).

Non-goals: a general multi-tenant PaaS; a Docker replacement; a build system; language runtimes beyond the five wrapped in Phase 8 (§20).

Deployment model: one sandbox-runtime daemon per host (bare metal, or a privileged VM with nested KVM for Tier::MicroVm), fronted by a stateless, horizontally scaled sandboxd control-plane deployment (Kubernetes-native).

Target users/operators: platform teams running code-evaluation, CI, agent-tool-execution, or FaaS-style products that need a legible, auditable isolation boundary rather than an opaque managed service.

What later phases unlock: Phase 5-7 (§17-§19) add tiers Tier::Process cannot safely serve (foreign-binary execution, kernel-Spectre-class threats, syscall-mediation research); Phase 8-10 (§20-§22) add language ergonomics, warm pools, and the audit/observability loop that makes the runtime operable at 3 a.m.

Recommended language: Rust 2024 for every privileged crate (sandbox-*) — the namespace orchestrator, seccomp compiler, and audit signer run with CAP_SYS_ADMIN, and a memory-safety bug in any of them is a sandbox-escape primitive (the fd-handling class of CVE-2024-21626, T2). Rejected: C (no memory safety; FFI to libseccomp/libcgroup would still be needed from Rust anyway, so C buys nothing); Go (a stop-the-world-capable GC runtime is the wrong trust boundary for a process holding raw namespace/cgroup fds mid-syscall, and goroutine scheduling complicates the fixed-OS-thread semantics clone3 and ptrace require). Go is used, deliberately scoped, for the control plane (sandboxd, ADR-02) since its Kubernetes fit outweighs the trust-boundary cost there — the control plane never touches a sandboxed process directly (§3 Common Substrate boundary).

Prerequisites: the Linux process model (fork/clone/execve, fd inheritance, controlling terminals, signal disposition); the namespace ABI and entry order (I3); the seccomp-BPF instruction set and action table; cgroups v2 unified hierarchy and delegation; the virtio device model and the Firecracker control protocol; the OCI Runtime/Image specs; async Rust (tokio/tower/tonic); AppArmor or SELinux policy authoring; on-call experience with a production container or VM fleet.

Estimated timeline: Phase 0 in 1 week (§12); the full 11-phase system in 4-6 months (16 weeks nominal, Appendix B §39).

Deferred features (full mapping: Deferred Features Register §36): MicroVM snapshot-restore PhaseDeferred("§18.7"); UserKernel systrap platform PhaseDeferred("§19.7"); WASI preview2/Component Model PhaseDeferred("§17.8"); macOS Tier::Process via Apple Hypervisor PhaseDeferred("§13.9"); GPU passthrough for Tier::MicroVm PhaseDeferred("§18.8"); Tier::Process CRIU snapshot PhaseDeferred("§13.7"); capability-token broker PhaseDeferred("§21.8"); K8s operator CRD PhaseDeferred("§21.10"); Cloud Hypervisor alternate backend PhaseDeferred("§18.6"); serverless billing surface PhaseDeferred("§22.10"); eBPF LSM alternate filter PhaseDeferred("§13.6").

2. Why Build This

  • The unique systems knowledge it teaches. Namespace/cgroup/seccomp choreography under real ordering constraints (I3); a Firecracker-class minimal-device-model hypervisor client; a ptrace-mediated usermode kernel (the gVisor Sentry/Gofer split); a Wasm engine's resource-limiter and fuel model — four isolation paradigms in one codebase, cross-compared instead of read about in isolation.
  • Why it matters architecturally. Every "just use Docker" retreat eventually meets a workload Docker's default isolation cannot serve; the industry's actual answer has been to run several of these four paradigms side by side (Replit Goval, e2b, Fly Machines). This project builds that multi-tier answer deliberately, not as an accreted afterthought.
  • Why it matters historically. Twenty years of container-escape research (Aqua's "Eight Ways to Escape a Container," CVE-2019-5736, CVE-2022-0492, the dirty-pipe family) is a corpus of specific, named mistakes; this runtime's chaos suite (§22, the chaos/ suite) runs every one of them as a regression test rather than trusting that "we did it differently."
  • The engineering muscles it builds. Fail-closed API design (P2); budget-as-contract thinking (P9); writing an audit trail as a first-class output rather than a log side-channel (P6); reasoning about a trust boundary that spans a host kernel, a hypervisor, and a usermode kernel simultaneously.
  • Concrete cross-links. gVisor (gvisor.dev) is Tier::UserKernel's direct ancestor; Firecracker (firecracker-microvm.github.io) is Tier::MicroVm's; Wasmtime (bytecodealliance.org) is Tier::Wasm's; bubblewrap/nsjail/minijail are sandbox-ns/sandbox-seccomp's. See §32 Comparative Architecture Table for the point-by-point comparison.
  • Calibration value. A working Tier::Process implementation that survives the chaos corpus (§22.3) is a defensible claim of security competence; a working Tier::UserKernel implementation is a defensible claim of systems-programming depth comparable to a mid-level gVisor contributor.

What Mastery Looks Like

  • Can explain, from memory, why CLONE_NEWUSER must be entered before every other namespace and what breaks if it is not (I3, Phase 1 §13).
  • Can write a seccomp-BPF allowlist from the syscall table and predict its ptrace interception cost without running it (Phase 1 §13, Phase 7 §19).
  • Can defend, with a concrete regime, why Tier::MicroVm is required and Tier::Process is insufficient for a specific threat model (ADR-08, §23 T4).
  • Can derive the sandbox-per-host ceiling from a memory budget and a concurrency target without looking it up (§33 Back-of-Envelope Capacity Model, Phase 2 §14).
  • Can trace a SIGKILL-by-budget event from the audit chain back to the cgroup that fired it (Phase 10 §22, I9).
  • Can redesign the runtime around a fundamentally different isolation primitive (eBPF LSM, a unikernel) and state exactly what tradeoff that redesign makes (§35 Alternative Architectures).

Control Plane — the only network-exposed surface (P8); terminates mTLS, resolves a capability token to a tenant, applies the quota engine, and forwards over the Unix socket. Never opens a socket on a sandbox's behalf.

Runtime Daemon — owns tier dispatch through the single TierImpl trait (§11.7, P1), the warm-pool (sandbox-pool, §21.3), and the signed audit chain (sandbox-audit, §22.1). Runs as a bounded service account holding exactly the capabilities in I5.

Tier 1-4 boxes — each implements TierImpl (§11.7) against the Common Substrate; none contains its own filesystem, network, or budget code (P4).

Common Substrate — sandbox-fs, sandbox-net, sandbox-cg, sandbox-ns, sandbox-seccomp; written once, consumed by every tier that needs the primitive (Tier 2 and Tier 3 skip sandbox-seccomp; Tier 3 skips sandbox-ns since Firecracker supplies its own VM boundary).

The one defining property: the isolation boundary is chosen per request, not per deployment — every other constraint above is a consequence of supporting all four boundaries in the same process without letting the weakest one set the host's risk floor.

6. Design Principles

  1. P1 — Tiers are a workload property, never a hidden default. The caller picks Tier::{Process,Wasm,MicroVm,UserKernel} per Run; the runtime never silently demotes a stronger tier to a weaker one. Tradeoff: a caller can request a tier the host cannot serve (no /dev/kvm) and must handle a closed failure. Operational implication: capacity planning is per-tier (§33). Violated: a "just make it work" demotion turns a security decision into an accident (§23 T4).
  2. P2 — Fail closed on every isolation hop. A namespace, cgroup attach, or seccomp load that fails is fatal for the sandbox under construction. Tradeoff: availability drops during host misconfiguration instead of degrading silently. Operational implication: Error::UnprivilegedUsernsDisabled-class errors must have runbooks (§25). Violated: a workload runs with fewer isolation layers than the caller believes (I2).
  3. P3 — The host is an authority; the sandbox is a subject. The daemon holds exactly the capabilities in I5; no sandbox inherits ambient capabilities; no_new_privs is unconditional. Tradeoff: some workloads that "just need CAP_NET_BIND_SERVICE" require an explicit RunSpec::capabilities grant, never an ambient one. Operational implication: capability grants are auditable per-run. Violated: an ambient-capability leak is a privilege-escalation primitive.
  4. P4 — One filesystem/network/budget builder. sandbox-fs, sandbox-net, sandbox-cg are written once and consumed by every tier that needs the primitive (P4 is why the Architectural Overview §3 has one Common Substrate box). Tradeoff: a tier-specific optimization must first be justified as a substrate change. Violated: tier-local forks of mount/network logic drift and reintroduce the bugs the shared code already fixed.
  5. P5 — No dynamic policy at runtime. Seccomp policy, AppArmor profile, capability set, and cgroup limits are resolved at construction and never mutated. Tradeoff: a long-running sandbox cannot be re-budgeted in place; it must be torn down and recreated. Operational implication: budget changes are a new Run, not a PATCH. Violated: a mutable policy is a TOCTOU window (§23 T6).
  6. P6 — Audit is a first-class output, not a side channel. Every sandbox produces a signed, append-only audit log (I9); it is part of the Outcome, not a best-effort log line. Tradeoff: audit-chain signing (M10) is on the critical path of every teardown. Operational implication: audit verification is a supported CLI command (sandbox-cli inspect --verify-audit). Violated: an unsigned or best-effort log cannot support a postmortem (§27).
  7. P7 — Determinism is the default. Same image, command, input, budget produces the same exit code, the same stdout up to scheduling interleavings, and the same audit shape (I10). Tradeoff: stochastic inputs (/dev/urandom, wall clock) must be explicitly opted into. Violated: a flaky conformance suite (§28) cannot distinguish a regression from noise.
  8. P8 — The control plane never speaks to user code. sandboxd hands a RunSpec to the runtime daemon over the Unix socket and reads an Outcome; it never opens a channel directly into a sandbox. Tradeoff: streaming output must be relayed, not proxied, adding one hop of latency (§4, gRPC Run p99 = 80 ms, M8 budget already includes this hop). Violated: a network-exposed process would gain a direct path into privileged code (§23 T5).
  9. P9 — Performance is a budget, not a goal. Cold-start targets are §4/§29 numbers; a regression > 10 % on any cold-start budget is a release blocker (ADR-24 in CI). Tradeoff: a correctness fix that regresses cold start needs an explicit budget-exception sign-off. Violated: unbounded performance drift erodes the product's viable workload set (interactive code-eval, §1) without anyone noticing until users complain.
  10. P10 — The runtime is one binary. All four tiers ship inside sandbox-runtime; operators install one binary and upgrade in one motion. Tradeoff: the binary is larger and a Tier 4-only deployment still links Tier 2/3 code. Violated: a daemon-per-tier topology reintroduces the "four things to upgrade in lockstep" operational burden this project exists to remove.
  11. P11 — Capability-oriented, not ambient, everywhere. The Capability bitflag type (§11.2) is the only way a sandbox gains a privilege; there is no path from "runs as root" to a privilege. Tradeoff: some legacy binaries that assume ambient root (e.g. binding port 80 without CAP_NET_BIND_SERVICE) require an explicit grant or fail. Violated: ambient capabilities are exactly the class of bug behind the 2019-era container-escape wave (§23 T2).
  12. P12 — Defense-in-depth layers are additive, never substitutive for the primary boundary. AppArmor and Landlock (§15.3) hardens Tier::Process; neither ever replaces the seccomp filter or the namespace boundary as the primary control. Tradeoff: policy authoring cost is paid twice (seccomp policy + AppArmor profile). Violated: treating a defense-in-depth layer as sufficient on its own reintroduces single points of failure the layering was meant to eliminate.
  13. P13 — The audit chain is append-only and externally verifiable. Every audit record chains the previous record's hash (I9); verification does not require trusting the runtime daemon that produced the chain, only the signing key. Tradeoff: a compromised signing key invalidates the trust model retroactively — key rotation (§26) must be planned for, not improvised. Violated: a mutable audit log cannot support a forensic reconstruction after A4 (§23).
  14. P14 — Warm reuse requires byte-identical provenance. A pooled sandbox is reused only if the new RunSpec is byte-identical to the one it was warmed for, modulo argv/env (§21.3). Tradeoff: warm-pool hit rate drops for workloads with high RunSpec cardinality. Violated: reusing a sandbox across differing budgets or images is a cross-tenant data-leakage vector (§23 T3).

11. Core Schema & Types

pub enum Tier { Process, Wasm, MicroVm, UserKernel }

pub struct Capability(u64); // bitflags over 20 POSIX capabilities(7); see §11 table

Compatibility: bit positions are ABI-fixed to capabilities(7) numbering; additive only, never renumbered.

11.8 TierImpl trait (sandbox-core/src/tier_trait.rs, §3, P1, P4)

pub trait TierImpl: Send + Sync + 'static {
    fn name(&self) -> Tier;
    async fn prepare(&self, spec: &RunSpec) -> Result<PreparedSandbox, Error>;
    async fn run(&self, prep: PreparedSandbox) -> Result<Outcome, Error>;
    async fn shutdown(&self) -> Result<(), Error>;
}
pub struct PreparedSandbox { pub id: SandboxId, pub tier: Tier /* + tier-private handle, opaque to sandbox-runtime */ }

Ownership: one Box<dyn TierImpl> per tier, held by sandbox-runtime::executor for the daemon's lifetime. Concurrency: Send + Sync required — prepare/run execute concurrently across sandboxes (§3 concurrency boundary: one tokio task per in-flight Run). Persistence: none; PreparedSandbox is an in-memory handle. 13. Phase 1 — Process Tier: Namespaces, Seccomp, Capabilities

13.1 Objectives

  • Land the full seven-namespace Tier::Process sandbox: a Run with Budget::strict(), the default seccomp allowlist, and an empty capability set runs an arbitrary statically linked binary against an OCI-style rootfs and cannot reach outside it.
  • Enforce I1-I5 (no_new_privs ordering, namespace ordering, setgroups-before-gid_map, capability ceiling, no ambient capabilities) as compiled-in, not best-effort.

13.2 Detailed Implementation Steps

  • sandbox-ns::unshare enters namespaces in the fixed order user → mount → pid → net → ipc → uts → cgroup (I2; the bubblewrap precedent, §5 Reference Implementations #4) via one clone3 call carrying all seven flags plus a CLOEXEC error pipe (extends §12.2).
  • The parent writes /proc/<pid>/uid_map and /proc/<pid>/gid_map only after writing setgroups deny to /proc/<pid>/setgroups (I3; kernel rejects the GID-map write otherwise).
  • sandbox-fs::pivot_root mounts a fresh tmpfs, bind-mounts the OCI rootfs read-only, layers an overlayfs (lower=rootfs, upper=scratch tmpfs), mounts a fresh procfs/sysfs(ro)/devtmpfs, pivot_roots in, and umount2(MNT_DETACH)s the old root (filesystem detail continues in §15).
  • sandbox-process::child drops the bounding set to RunSpec::capabilities via prctl(PR_CAPBSET_DROP), sets effective/permitted/inheritable to the same value, clears the ambient set unconditionally (I5, P11), then sets PR_SET_NO_NEW_PRIVS before sandbox-seccomp::bpf loads the filter (I1; illegal in the other order per the seccomp(2) man page, ADR-04).
  • sandbox-seccomp::allowlist ships the default policy: an allowlist of ~350 syscalls (roughly the Docker default, pruned) with KillProcess as the default action (never KillThread — that variant leaves zombies, a documented pitfall, §13.6). Architecture is checked first in the filter; a filter run on the wrong ABI is a kill.
  • sandbox-process::apparmor generates a per-sandbox AppArmor profile from the mount tree and exec allowlist (ADR-18); Landlock rules (kernel ≥5.13) layer under it (ADR-17) as defense-in-depth (P12), never as the primary boundary.

13.3 Deliverable

A Tier::Process run with Budget::evaluation() and the default seccomp policy runs a Python "hello world" against an OCI rootfs and is measurably contained (§13.5 corpus green).

13.4 Acceptance Criteria

  • Cold start ≤ 50 ms p99 (M1), warm reuse ≤ 10 ms p99 (M5), measured by benchmarks/cold_start_process.py over 1,000 runs.
  • 100 % of conformance/corpora/namespaces/ and conformance/corpora/seccomp/ fixtures pass (§13.5); zero escapes from the 11-script chaos/escapes/ corpus against Tier::Process (§22.3, M2).

Fixture Purpose Expected Output

13.6 Pitfalls

  • setgroups write ordering. Writing the GID map before setgroups deny is rejected by the kernel with EPERM; fix by reordering per I3. Debug signal: the specific EPERM on the GID-map write, not a generic namespace failure.
  • pivot_root over a non-fresh mount. Silently succeeds and leaves the host root reachable if the new root is not on its own mount point; always pivot into the fresh tmpfs sandbox-fs creates, never a bind mount of an existing directory.
  • PID 1 reaping. CLONE_NEWPID's PID 1 must reap orphans; use prctl(PR_SET_CHILD_SUBREAPER, 1) as a belt-and-braces measure against zombies.
  • Wrong-ABI filter (ADR-04) and KILL_THREAD vs. KILL_PROCESS. A filter built for the wrong syscall ABI silently no-ops rather than erroring — the architecture check at filter entry (§13.2) catches it; separately, KillThread leaves the rest of a multi-threaded victim alive as zombies — always use KillProcess (§11.6).

13.7 Performance Concerns

  • BPF filter depth: keep the compiled allowlist ≤ 64 effective classifier branches post-optimization, or per-syscall dispatch overhead exceeds the 3 % budget (§4).
  • The clone3 + pivot_root + overlay mount path is the dominant cost in cold start (§4 M1 50 ms budget); batch mount syscalls where the kernel allows combined flags rather than issuing one mount(2) per layer.
  • PhaseDeferred("§13.7"): CRIU-based snapshot/restore would amortize cold start further; deferred (§36).

13.8 Edge Cases

  • A host-absolute argv[0] that happens to also exist inside the rootfs by coincidence is a common misconfiguration; execve must resolve against the mounted rootfs path, never a host path.
  • A sandbox that never calls execve after a pre-exec failure must not leave a runnable process behind; the CLOEXEC-pipe error path (§12.2) always terminates it.
  • Racing cgroup-attach with process exit: if the child exits between clone3 and the cgroup-attach write, the write must be treated as "already gone," not an error.

13.9 Failure Analysis

  • What breaks: a namespace entry fails partway through the seven-flag clone3. Detection: the CLOEXEC pipe surfaces the specific errno. Blast radius: none — P2 fail-closed means no process ever runs half-isolated. Containment: construction aborts before execve. Recovery path: caller retries or surfaces Error::UnprivilegedUsernsDisabled/Error::NamespaceOrderViolation (§11.9) to the operator. Postmortem guidance: check docs/runbook/triage.md first — namespace failures cluster around sysctl drift on the host (§13.6).
  • PhaseDeferred("§13.9"): macOS Tier::Process via Apple Hypervisor is out of scope (ADR-03); failure here is "unsupported host," not a bug.

13.10 Operational Notes

  • Metrics: sandbox_cold_start_seconds{tier="process"}, sandbox_seccomp_deny_total{syscall} (§22.2). One OTel span per prepare() stage (namespace/filesystem/capability/seccomp) attributes a slow cold start to a stage. 14. Phase 2 — Resource Budgets: cgroups v2, rlimits, Timers, Signals

14.1 Objectives

  • Enforce every field of Budget (§11.3) with two independent layers where the literature shows one alone fails (I8): cgroups v2 as primary, rlimit as backstop.
  • Make budget-triggered kills classify correctly as KilledByBudget(BudgetReason), never a bare Signaled (I7).

14.2 Detailed Implementation Steps

  • sandbox-cg creates sandbox.slice/<id>.scope under a daemon-owned sandbox.slice (ADR-05); sets memory.max, memory.high, memory.swap.max, cpu.weight, cpu.max, io.max, pids.max from Budget fields. memory.high alone is a soft throttle — memory.max must also be set or an OOM-prone sandbox can blow the host (documented pitfall, §14.6).
  • sandbox-process::child sets RLIMIT_CPU, RLIMIT_AS, RLIMIT_NPROC, RLIMIT_NOFILE, RLIMIT_FSIZE, RLIMIT_CORE, RLIMIT_STACK — the backstop layer for cases (single-process memory blow-up) where cgroup measurement is coarser (I8).
  • Wall-clock budget: a timerfd armed at CLOCK_BOOTTIME (I13 — never CLOCK_MONOTONIC, which jumps on suspend/resume) delivers expiry to sandbox-runtime::executor's event loop, not to the sandbox; SIGTERM (or RunSpec::timeout_kill_signal) fires, escalating to SIGKILL after a 200 ms grace (§8.1 Draining state).
  • CPU-time budget is double-enforced: RLIMIT_CPU plus periodic sampling of cpuacct.usage in the cgroup.
  • The sandbox runs in its own process group; teardown kills the group, not just PID 1, so orphaned siblings cannot outlive accounting.
  • stdout/stderr captured via pipe2(O_CLOEXEC), truncated at Budget::stdout_bytes/stderr_bytes (flips Outcome::{stdout,stderr}_truncated rather than failing the run, §11.7).

14.3 Deliverable

A fork-bomb, a memory-bomb, and a wall-clock-runaway workload are each killed within their respective budgets with the correct BudgetReason, measured against the chaos/escapes/ corpus.

14.4 Acceptance Criteria

  • chaos/escapes/fork_bomb.py: killed by pids.max within 50 ms of the budget (I8); zero host-visible process-table pressure.
  • chaos/escapes/memory_bomb.py: killed by the cgroup OOM (memory.max), not the host OOM killer — verified by the audit record's BudgetReason::Memory.
  • Wall-clock-runaway: ExitStatus::KilledByBudget(WallClock) within Budget::wall_clock + 200 ms (§8.1), 100 % over 1,000 trials.

Fixture Purpose Expected Output

14.6 Pitfalls

  • memory.high without memory.max. A soft throttle alone lets a sandbox blow host memory; §14.2's construction-time check rejects a Budget that sets one without the other.
  • pids.max without RLIMIT_NPROC. Some workloads fork between the cgroup check and the rlimit check; I8 requires both layers, not either alone.
  • Hierarchical cpu.max surprises. Some kernels do not honour a child's cpu.max when the parent slice has a tighter limit; pin the parent to the superset of all children's limits.
  • RLIMIT_AS measures virtual address space, not RSS — a 4 GB mmap that is never touched is not caught by RLIMIT_AS alone; memory.max is ground truth.

14.7 Performance Concerns

  • cpuacct.usage sampling frequency trades detection latency against syscall overhead; sample every 10 ms (bounded by the 200 ms escape-detection budget, §4) rather than continuously.
  • cgroup-attach and rlimit-set are both on the cold-start critical path (M1 budget); batch them into the same pre-execve setup phase as the seccomp/capability work (§13.2) to avoid extra context switches.

14.8 Edge Cases

  • A child in uninterruptible sleep (D state) never observes SIGTERM or SIGKILL; this is an operator escalation, not a runtime bug — docs/runbooks/ stuck-sandbox.md covers it (§25).
  • A pty allocated but never drained by the caller can deadlock the runtime; the daemon must actively drain any pty it allocates on the sandbox's behalf.
  • Budget fields at their type's zero value (e.g. pids: 0) are rejected at validation (§8.3), not silently treated as "unlimited."

14.9 Failure Analysis

  • What breaks: cgroup OOM fires but the process group leaves a zombie sibling. Detection: sandbox_fork_bomb_kills_total/reaper metrics diverge from expected counts. Blast radius: contained to the one cgroup scope (the freezer, §14.2, prevents new forks during teardown). Recovery: cgroup.freeze then process-group SIGKILL, always in that order. Visibility: sandbox_budget_burn_total{kind} and the audit BudgetBurn record (§8.4).

14.10 Operational Notes

  • Metrics: sandbox_budget_burn_total{kind="memory|cpu|wall|fds|pids"}. Dashboards plot burn rate per tenant to catch a noisy-neighbor pattern before it becomes an incident (§25). No migration concern — budgets are per-RunSpec, never persisted across a runtime upgrade.

15. Phase 3 — Filesystem Isolation & Image Format

15.1 Objectives

  • Generalize §13.2's filesystem builder into sandbox-fs's full mount-kind set (§11.5 MountSpec) and the content-addressed image format.
  • Layer AppArmor/Landlock defense-in-depth (ADR-17, ADR-18, P12) on top of the primary namespace/overlay boundary.

15.2 Detailed Implementation Steps

  • Image format: a content-addressed tarball (manifest.json + layer tarballs), keyed by the xxh3 hash of the manifest (ADR-16); an ed25519 signature (ADR-15) carries integrity, checked before mount (I14). OCI images are translated in: unpacked into the content-addressed cache, then a manifest.json is emitted (§5 OCI Image Spec).
  • sandbox-fs::overlay builds MountSpec::Overlay{lower=rootfs, upper=scratch tmpfs, work=tmpfs, dst}; every bind mount carries MS_NOSUID|MS_NODEV|MS_NOEXEC unless MountSpec::Bind.recursive and an explicit executable opt-out are both set (P2: the safe default is closed).
  • sandbox-fs::fscrypt/fsverity support MountSpec::FsCrypt/FsVerity for workloads that need at-rest encryption or dm-verity-style integrity beyond the image signature (optional, not default).
  • AppArmor profile generation (sandbox-process::apparmor) derives its path rules directly from the mount tree and the exec allowlist — never hand-authored per sandbox, so it cannot drift from what was actually mounted.
  • Landlock (kernel ≥5.13, ADR-17) rules: rootfs path is LANDLOCK_ACCESS_FS_READ-only; /tmp is READ_FILE|WRITE_FILE|MAKE_FILE| TRUNCATE; nothing else is reachable — layered under, never instead of, the seccomp/namespace boundary (P12).

15.3 Deliverable

A Tier::Process sandbox mounts a signed, content-addressed image with a writable overlay scratch and a read-only rootfs; conformance/corpora/filesystem/ passes at 100 %.

15.4 Acceptance Criteria

  • Image signature verification (I14) rejects a tampered manifest 100 % of the time in filesystem/signature_mismatch.json.
  • Storage amplification ≤ 1.3x uncompressed layer size (§4), measured by benchmarks/overhead_per_tier.py.
  • Zero escapes from chaos/escapes/procfs_traversal.py and chaos/escapes/proc_self_exe_overwrite.py.

Fixture Purpose Expected Output

15.6 Pitfalls

  • overlayfs on tmpfs requires kernel ≥ 5.11. Older kernels need lowerdir on a real filesystem; surface Error::OverlayUnsupported, never a silent fallback to a weaker layout.
  • Read-only bind-mount flip. MS_BIND|MS_RDONLY in one call is silently ignored; the correct sequence is bind, then MS_REMOUNT|MS_BIND|MS_RDONLY.
  • Bind-mounting the host's /proc. An immediate escape (CVE-class mistake, §23); always mount a fresh procfs, never bind the host's.
  • Bind-mounting a directory containing setuid binaries. MS_NOSUID on the bind itself is mandatory; relying on the underlying filesystem's nosuid flag is wrong if that filesystem is also used elsewhere without it.

15.7 Performance Concerns

  • Content-addressed cache lookups are the xxh3-keyed hot path (ADR-16); a cache miss re-triggers a full layer unpack, which can push cold start past M1 — the cache must be warmed by the pool manager (§21.3) for common images.
  • fscrypt/fsverity are opt-in specifically because both add per-I/O overhead not needed by the majority of workloads (P9: performance is a budget).

15.8 Edge Cases

  • A manifest referencing a layer not present in the content-addressed cache: fail closed with a typed error before any mount, not a partial rootfs.
  • A MountSpec::FsVerity root hash that does not match the mounted content: mount fails at the kernel level, surfaced as a typed Error, not a silent read failure later.

15.9 Failure Analysis

  • What breaks: a compromised image passes hash validation but fails signature validation (A2, §23). Detection: I14's pre-mount check. Blast radius: zero — the sandbox is never constructed. Recovery: Error::ImageSignatureInvalid surfaced to the operator with the failing content hash for forensic follow-up.

15.10 Operational Notes

  • Metrics: cache hit/miss ratio, sandbox_image_signature_failures_total (I14). Deployment: the content-addressed cache is host-local; no cross-host cache invalidation protocol exists in Phase 0-10 (a scaling lever noted in §31).

16. Phase 4 — Network Isolation

16.1 Objectives

  • Build sandbox-net's five NetworkSpec variants (§11.5); default is None.
  • Enforce egress policy and DNS mediation without granting the sandbox any host-network-namespace capability directly (P3).

16.2 Detailed Implementation Steps

  • NetworkSpec::None (default): CLONE_NEWNET with only lo, brought up and nothing else — the safe default per P2.
  • NetworkSpec::Slirp{dns,mtu}: a usermode SLIRP-style TCP/IP+NAT stack runs inside the runtime daemon (re-implemented in Rust, not a slirp4netns subprocess, to avoid an extra process hop) and exposes a TUN device into the sandbox; no host-netns privilege needed.
  • NetworkSpec::Veth{bridge,ip4,mtu}: a veth pair is created, one end moved into the sandbox netns, the other attached to a host bridge with NAT configured via nftables; requires CAP_NET_ADMIN in the host netns, held only by the runtime daemon (P3), never by the sandbox.
  • NetworkSpec::MacVlan{parent,ip4}: a macvlan interface on the host parent, moved into the sandbox netns.
  • NetworkSpec::Vsock{cid} (Tier::MicroVm only): the sandbox sees a vsock device and nothing else — the network boundary and the VM boundary coincide.
  • Egress allowlist enforced via nftables on the host bridge (all network kinds) and, for Tier::UserKernel only, a connect()-address check inside the usermode netstack (§19.2) — Tier::Process cannot filter on address bytes in seccomp alone (the bytes live in the syscall payload, not the syscall number).
  • DNS is resolved by the runtime daemon's own stub resolver bound to the sandbox's loopback/slirp gateway, never the host's /etc/resolv.conf directly; every query is logged to the audit chain (§8.4).

16.3 Deliverable

A Tier::Process sandbox with NetworkSpec::Slirp reaches an allowlisted egress host and is denied a non-allowlisted one, with both outcomes in the audit chain.

16.4 Acceptance Criteria

  • Default (NetworkSpec::None) sandboxes: zero non-loopback interfaces present, 100 % over conformance/corpora/network/no_network.json.
  • Egress allowlist: 100 % of denied-destination attempts logged with a DNS-query audit trail, verified against network/egress_denylist.json.
  • Network RTT budget: host RTT + ≤ 2 ms NAT-hop overhead (§4), measured via benchmarks/overhead_per_tier.py.

16.5 Conformance Fixtures

Fixture Purpose Expected Output
network/no_network.json default isolation only lo, no route to host bridge
network/egress_allowlist.json allowed destination connection succeeds, audited
network/egress_denylist.json denied destination connection refused, audited
network/vsock_only.json Tier::MicroVm boundary no interface but vsock present

16.6 Pitfalls

  • veth requires host-netns CAP_NET_ADMIN. The runtime daemon holds it; a sandbox must never be granted it (P3) — a regression here is a direct namespace escape vector for network configuration.
  • Network-namespace teardown order. The veth end must be moved back to the host netns before the sandbox netns is destroyed, or the veth end is orphaned and leaks a host-side interface per sandbox lifecycle.
  • In-process SLIRP re-implementation risk. Reimplementing a TCP/IP+NAT stack in Rust (rather than shelling to slirp4netns) is a correctness surface of its own; the conformance corpus (§16.5) exists specifically to exercise it exhaustively.

16.7 Performance Concerns

  • The in-process SLIRP stack avoids a subprocess hop but adds an extra userspace-to-userspace copy per packet versus a kernel veth; budget the ≤ 2 ms NAT-hop RTT (§4) against this specifically for Slirp, not Veth.
  • Egress-allowlist nftables rules are evaluated per-packet on the host bridge; keep the ruleset small (< 100 rules per sandbox) to avoid linear nftables lookup cost compounding across thousands of concurrent sandboxes (§33).

16.8 Edge Cases

  • DNS query for a name that resolves to a denylisted IP after the allowlist check passed on the name alone (DNS rebinding): the nftables egress rule, evaluated on the actual connection, is the enforcement point of record, not the DNS decision.
  • A veth bridge attach that races with the bridge being torn down by an unrelated host-network reconfiguration: treated as a construction failure, not a silent no-network fallback (P2).

16.9 Failure Analysis

  • What breaks: the in-process SLIRP stack panics on a malformed packet. Detection: the panic is caught at the tokio task boundary and surfaced as Error::NetworkStackFault, not a daemon crash (task isolation, §3 concurrency boundary). Blast radius: one sandbox's network path; other sandboxes and the daemon itself are unaffected. Recovery: the sandbox continues with NetworkSpec::None-equivalent connectivity and the fault is audited.

16.10 Operational Notes

  • Metrics: sandbox_egress_denied_total{sandbox_id}, DNS-query audit volume. Runbook: a sudden spike in egress_denied_total for one tenant is the primary signal used in docs/runbooks/triage.md to distinguish a misconfigured allowlist from an active exfiltration attempt (§23 T1).

17. Phase 5 — Wasm Tier (WASI snapshot1)

17.1 Objectives

  • Land Tier::Wasm (ADR-06) as a structurally isolated alternative to Tier::Process — a module cannot express a raw syscall at all, unlike Native Client's verified-instruction-stream approach (Yee et al., §5 Papers #3).
  • Enforce WASI snapshot1's preopen-only filesystem model and a dual budget mechanism: fuel (CPU) and epoch interruption (wall clock).

17.2 Detailed Implementation Steps

  • sandbox-wasm::store creates one fresh Store per Run, carrying the WASI context and a Limits implementation enforcing Budget::memory_bytes via ResourceLimiter (§5 Reference Implementations #5).
  • sandbox-wasm::linker exposes only the host functions named in the manifest; an unresolved import fails module instantiation (fail-closed, P2) rather than linking a stub.
  • sandbox-wasm::fuel meters CPU via Wasmtime's fuel mechanism, calibrated per instruction class against a microbenchmark (documented in docs/architecture/tier-wasm.md); fuel exhaustion delivers a trap, not a process signal — the host must observe the trap and map it to ExitStatus::KilledByBudget(BudgetReason::Cpu) (I7 — a common miscue is treating the trap as Crashed).
  • sandbox-wasm::wasi mediates filesystem access through a per-Run preopen list; there is no path from inside the module to any directory outside it (structural, not policy-based, isolation — contrast with Tier::Process's seccomp+namespace policy layering).
  • Wall-clock budget: epoch_interruption, ticked from the runtime daemon's monotonic clock thread; a module must be killed within epoch_period + 50 ms of the wall budget expiring (§19.3 invariant analog for Tier::Wasm).
  • Networking is off by default; opted in only via NetworkSpec::Vsock when nested inside a Tier::MicroVm sandbox, or the Phase-1+ WASI preview2 surface (PhaseDeferred("§17.8")).

17.3 Deliverable

A WASI snapshot1 module compiled from Rust or C runs under Tier::Wasm with a preopen-scoped filesystem view and a calibrated fuel budget; conformance is measured against the upstream WASI test suite where importable.

17.4 Acceptance Criteria

  • Cold start ≤ 30 ms p99 (M2), measured over 1,000 runs.
  • 100 % WASI snapshot1 conformance on the imported upstream test suite (conformance/corpora/wasm/).
  • A module attempting to import an undeclared host function fails instantiation 100 % of the time — zero silent stub-linking.

Fixture Purpose Expected Output

wasm/fuel_exhaustion.json CPU budget breach trap mapped to KilledByBudget(Cpu), never Crashed
wasm/unresolved_import.json module importing an undeclared host fn instantiation fails closed

17.6 Pitfalls

  • Fuel exhaustion is a trap, not a kill signal — a naive implementation that treats every trap as Crashed misclassifies every CPU-budget kill (I7).
  • Cranelift/Winch parity. The fast-baseline Winch compiler's semantics must match Cranelift's exactly for determinism (P7); test both as a parity exercise, not just the default codegen.
  • Floating-point determinism. The relaxed-SIMD flag changes cross-host FP determinism; document the flag state in the ADR rather than leaving it implicit.

17.7 Performance Concerns

  • Fuel-per-instruction calibration drifts across Wasmtime versions; re-calibrate and re-record in docs/architecture/tier-wasm.md on every Wasmtime upgrade, or the CPU budget silently becomes looser or tighter than documented.
  • Store construction (not module compilation, which can be cached) dominates per-run cost; keep compiled-module caching keyed by content hash (ADR-16 pattern reused) to hit the 30 ms p99 (M2).

17.8 Edge Cases

  • A module that spins in a tight loop with no epoch checkpoints reachable (an optimizing compiler hoisted them out): Wasmtime's epoch mechanism inserts checks at loop back-edges by construction — verify this holds for the specific Cranelift version pinned in Cargo.toml.
  • PhaseDeferred("§17.8"): WASI preview2 / the Component Model frontend is deferred; a module requiring preview2 imports fails instantiation cleanly under the Phase-0-10 snapshot1-only surface (§36).

17.9 Failure Analysis

  • What breaks: a Cranelift/Winch codegen divergence produces different output for the same module. Detection: the parity test suite (§17.6) diffs both codegens' output per conformance run. Blast radius: a determinism guarantee (P7), not a security boundary — contained to conformance-suite red, not a production incident, if caught pre-release.

17.10 Operational Notes

  • Metrics: sandbox_cold_start_seconds{tier="wasm"}, fuel-burn histograms per module. No migration concern across a Wasmtime version bump beyond re-calibrating the fuel table (§17.7) and re-running the parity suite.

18. Phase 6 — MicroVM Tier (Firecracker)

18.1 Objectives

  • Land Tier::MicroVm (ADR-07): the tier that answers threats Tier::Process structurally cannot (Spectre-class cross-domain speculation, §23 T7) by giving each sandbox its own kernel.
  • Hold the minimal-device-model discipline (Agache et al., §5 Papers #1) that makes cold start dominated by kernel boot, not device probing.

18.2 Detailed Implementation Steps

  • sandbox-microvm::firecracker spawns Firecracker as a subprocess with a per-sandbox Unix-socket API endpoint in a per-sandbox directory (never /tmp — a stray shared-directory socket is a cross-sandbox leak, §18.6).
  • sandbox-microvm::kernel/initramfs ship a pre-built vmlinux (x86_64 + AArch64) and a small initramfs; sandbox-microvm::vsock is the sole control channel — no virtio-net in the Phase-0 surface (vsock-only networking, keeping the device count minimal per ADR-07).
  • sandbox-microvm::virtio_blk backs the rootfs as a read-mostly block device fed from the same content-addressed image cache sandbox-fs populates (§15.2 — the Common Substrate boundary, P4, holds even though Tier::MicroVm does not use sandbox-ns).
  • microvm-init (the in-VM agent, shipped in the initramfs, kept under 200 lines) receives the RunSpec over vsock, sets rlimits, mounts the rootfs, execves the user command, captures stdio, and ships the Outcome back over vsock — deliberately small so it can be code-reviewed in full, unlike a general-purpose init.
  • Boot-time budget (§4, M3: 250 ms p99 no-snapshot) is measured end to end: kernel boot + initramfs + microvm-init + vsock handshake + first user process.
  • KVM PT is disabled and IBRS is enabled by default (ADR-19) — the concrete Spectre/Meltdown-class mitigation this tier exists to provide relative to Tier::Process (§5 Papers #7, #8).

18.3 Deliverable

A Tier::MicroVm run boots a tiny initramfs, executes a command over vsock, and returns an Outcome within the M3 cold-start budget; conformance green on conformance/corpora/microvm/.

18.4 Acceptance Criteria

  • Cold start ≤ 250 ms p99 (M3, no snapshot), measured over 1,000 runs (benchmarks/cold_start_microvm.py).
  • Boot-time variance ≤ 30 ms over 1,000 runs given the same kernel/initramfs/spec (determinism invariant, §19.4 analog).
  • Max concurrent sandboxes > 200 per reference host (M12, §33 derivation).

18.5 Conformance Fixtures

Fixture Purpose Expected Output

microvm/kvm_unavailable.json no /dev/kvm Error::KvmUnavailable (§8.6), no partial VM left running
microvm/socket_isolation.json Firecracker API socket placement per-sandbox directory, never a shared path
microvm/vsock_only_net.json Phase-0 network surface no virtio-net device present

18.6 Pitfalls

  • Firecracker API socket exposure. A stray socket in a shared /tmp is a cross-sandbox leak; the socket must live in a per-sandbox directory the runtime daemon owns exclusively.
  • Rootfs block device permissions. The Firecracker subprocess must be able to read the staged rootfs image; the runtime daemon owns the staging directory and its permission bits explicitly, not via an ambient umask.
  • PhaseDeferred("§18.6"): Cloud Hypervisor as an alternate Tier::MicroVm backend is deferred (ADR-07's rejected alternative) — relevant once vhost-user or GPU passthrough device support is required (§35 Alternative Architectures).

18.7 Performance Concerns

  • Cold start is dominated by kernel boot, not device probing (the minimal-device- model argument, ADR-07) — adding a device "for convenience" must be re-measured against M3 before merging.
  • PhaseDeferred("§18.7"): snapshot-restore is the lever for a sub-100 ms cold start (M3's Phase-1+ successor target); deferred because the Phase-0 budget (250 ms) is met without it (§36).

18.8 Edge Cases

  • A kernel panic inside the guest during boot must be distinguishable from a vsock handshake timeout — both are boot failures but demand different runbooks (docs/runbooks/kvm-unavailable.md covers only the /dev/kvm case explicitly; a guest-kernel-panic runbook is a Phase-1+ gap tracked in §36).
  • PhaseDeferred("§18.8"): GPU passthrough (ROCm/CUDA) for compute-heavy Tier::MicroVm workloads is deferred; Firecracker's minimal device model does not support it without the Cloud Hypervisor alternative (§18.6).

18.9 Failure Analysis

  • What breaks: the guest kernel panics before the vsock handshake completes. Detection: vsock-handshake timeout at the runtime daemon. Blast radius: one sandbox; Firecracker's own VM boundary means a guest kernel panic cannot affect the host or sibling VMs. Recovery: the daemon tears down the failed Firecracker process and returns Error::MicroVmBootFailed with the captured serial-console log for forensics.

18.10 Operational Notes

  • Metrics: sandbox_cold_start_seconds{tier="microvm"}, KVM-device-availability gauge. Runbook: docs/runbooks/kvm-unavailable.md is the first stop for any Error::KvmUnavailable spike (§25).

19. Phase 7 — Usermode-Kernel Tier (Sentry/Gofer)

19.1 Objectives

  • Land Tier::UserKernel (ADR-08, ADR-09): a Sentry/Gofer split modeled on gVisor (§5 Papers #2) that mediates every syscall in a fixed 350-entry table, delegating filesystem access to a separate Gofer process the way Ostia delegates system-call interposition to a trusted agent (Garfinkel et al., §5 Papers #5) rather than interposing in-line in the Sentry itself.
  • Understand, by building it, the specific tradeoff (breadth vs. review surface) gVisor took — not to replace gVisor in production (§2 "Why Build This").

19.2 Detailed Implementation Steps

  • The user program runs in its own address space; the Sentry traps every syscall via ptrace(PTRACE_SYSEMU) (ADR-09's Phase-0 platform) and either services it from Sentry-local state, forwards a narrowed request to the Gofer, or denies it.
  • SyscallTable (350 entries, §11.9-adjacent, defined in sandbox-userkernel::policy): each entry is a policy tag plus a dispatch target. Arithmetic/introspection syscalls (getpid, clock_gettime, getuid) are serviced from Sentry-local state with no host syscall at all.
  • sandbox-userkernel::filesystem implements the Gofer side: a 9P-subset protocol over a Unix socket; path containment is enforced in the Gofer, not the Sentry — the Sentry is inside the trust boundary being tested, the Gofer is the defense-in-depth delegate (Ostia pattern, §5 Papers #5).
  • sandbox-userkernel::netstack services socket/connect/send/recv via a small in-process TCP/IP stack plus the NetworkSpec allowlist (reuses the address-level filtering §16.2 notes Tier::Process cannot do in seccomp alone).
  • Sentry-allocated pages are mapped into the user process via shared anonymous mappings; the host kernel never observes an mmap issued directly by the user program (memory model, distinguishing this from a bare-ptrace debugger).
  • An syscall not in the fixed 350-entry table produces a defined kill, never undefined behavior (I-analog: every syscall MUST produce a defined result — success, errno, or signal, §19.5 below formalizes this as a Tier invariant).

19.3 Deliverable

A Tier::UserKernel sandbox running the ptrace platform mediates the full documented syscall table with a measured, honestly reported overhead multiplier (§19.4).

19.4 Acceptance Criteria

  • Syscall-heavy workload overhead ≤ 5.0x baseline on the ptrace platform (M9), measured by benchmarks/overhead_per_tier.py; CPU-bound workload overhead is documented separately as negligible.
  • 100 % of the 350-entry SyscallTable produces a defined result (success, errno, or signal) — zero undefined-behavior escapes in conformance/corpora/userkernel/.
  • Path-containment violations at the Gofer are audited within the I6 200 ms bound.

19.5 Conformance Fixtures

Fixture Purpose Expected Output
userkernel/syscall_table_completeness.json every entry in the 350-table defined result for each
userkernel/undefined_syscall.json a syscall nr outside the table process killed, audited
userkernel/gofer_path_containment.json path traversal via the Gofer denied at the Gofer, not the Sentry
userkernel/ptrace_overhead.json M9 overhead measurement ≤ 5.0x on the named syscall-heavy corpus

19.6 Pitfalls

  • ptrace is slow and detectable. The systrap platform is faster but needs a more intricate signal-handler trick; shipped later behind PhaseDeferred("§19.7"), not a Phase-0 requirement.
  • Gofer trust placement. Enforcing path containment in the Sentry instead of the Gofer defeats the delegation model's entire purpose (§19.2) — the Sentry is part of the boundary under test, not a place to put the defense.
  • Sentry-local servicing correctness. A syscall wrongly marked "serviceable Sentry-local" (e.g. one whose semantics actually depend on host state) produces a subtly wrong result rather than a crash — the completeness fixture (§19.5) exists to catch exactly this class before it ships.

19.7 Performance Concerns

  • ptrace round-trips two context switches per intercepted syscall; this is the entire source of the ≤ 5.0x overhead ceiling (M9) — Sentry-local servicing of high-frequency syscalls (clock_gettime, getpid) is the primary mitigation available in the Phase-0 platform.
  • PhaseDeferred("§19.7"): the systrap platform (ADR-09's rejected-then-deferred alternative) targets ≤ 1.5x overhead (M9's Phase-1+ successor) via a signal-handler interception trick that avoids the ptrace round-trip entirely.

19.8 Edge Cases

  • A multi-threaded user program where two threads issue syscalls concurrently: the Sentry must serialize dispatch per-thread without serializing unrelated threads' syscalls against each other (a scalability concern, §31).
  • A Gofer process that crashes mid-request: the Sentry must surface a defined error to the syscall that triggered the request, never hang indefinitely.

19.9 Failure Analysis

  • What breaks: the Gofer process crashes. Detection: the Sentry's Unix socket read fails. Blast radius: the one sandbox whose Gofer crashed; other sandboxes each have their own Gofer process (no shared state). Recovery: the Sentry kills the sandboxed program with a defined error and the runtime daemon tears down the pair; no host-kernel involvement is required for containment.

19.10 Operational Notes

  • Metrics: sandbox_cold_start_seconds{tier="userkernel"}, syscall-dispatch latency histograms partitioned Sentry-local vs. Gofer-forwarded. This split is the primary tuning signal for future systrap work (§19.7).

20. Phase 8 — Language Runtimes

20.1 Objectives

  • Wrap the four most common code-eval workloads (Python, JavaScript, R, Shell) as pre-built RunSpec templates plus image manifests — not new tiers, compositions over the existing TierImpls (P1: the tier is still chosen by the caller).

20.2 Detailed Implementation Steps

  • sandbox-langs::python ships a python:3.12-slim-derived content-addressed image (§15.2), default Budget{memory: 256 MiB, wall: 5s, cpu: 4s, fds: 64, pids: 64, net: none}, and a pre-import allowlist (stdlib minus subprocess/ctypes/ socket unless the spec opts in) — layered on top of, not instead of, the seccomp/namespace boundary (P12).
  • sandbox-langs::javascript ships either a bun-based Tier::Process image or an isolate-vm-style embedding inside Tier::Wasm; the SES (Secure ECMAScript) lockdown() call runs at startup for the isolate-vm path, an additional language-level defense-in-depth layer above the tier boundary.
  • sandbox-langs::r wraps Rscript --vanilla against an r-base:4.4 image.
  • sandbox-langs::shell wraps a restricted-bash shim over a busybox:1.36 image, disabling built-ins the runtime does not intend to service (an explicit denylist, not an implicit one).
  • Each language runtime is a RunSpec template plus an image manifest, resolved by sandbox-cli run --lang <name>; none introduces a fifth TierImpl.

20.3 Deliverable

sandbox run --lang python --code 'print(1+1)' (and the JS/R/shell equivalents) each execute end to end against the default Tier::Process budget.

20.4 Acceptance Criteria

  • All four language templates pass their conformance/corpora/api/ fixture with the documented default budget, zero escapes against the shared chaos/ corpus.
  • Python's subprocess/ctypes/socket denial is enforced 100 % of the time under the default template (verified against the seccomp allowlist, §13.4).
  • Ruby is explicitly out of scope for Phase 0-10's default templates despite appearing in the repository layout's placeholder (sandbox-langs::ruby) — its acceptance criteria are deferred alongside PhaseDeferred("§21.8")'s broader multi-tenant template work.

Fixture Purpose Expected Output

20.6 Pitfalls

  • Template drift from the underlying tier's defaults. A language template that hand-rolls its own seccomp policy instead of composing the shared allowlist (§13.4) reintroduces the tier-local-fork risk P4 exists to prevent.
  • SES lockdown ordering. lockdown() must run before any user code executes in the isolate; a template that defers it is not actually providing the isolation it claims.

  • Each language template's cold start inherits its underlying tier's budget (M1 for the Python/shell Tier::Process templates); no additional per-language overhead budget is granted — a slow template is a Tier::Process regression, not a new category (§29).

20.8 Edge Cases

  • A user submission that imports an allowed stdlib module which itself transitively imports a denied one (e.g. http.client pulling in socket): the denial is enforced at the seccomp layer regardless of which Python-level module triggered the syscall — policy enforcement is below the language runtime, not inside it.

20.9 Failure Analysis

  • What breaks: a language template's default budget is too tight for a legitimate workload (e.g. a data-processing script needing > 256 MiB). Detection: elevated KilledByBudget(Memory) rate for one template in telemetry. Recovery: the caller supplies an explicit Budget override in the RunSpec, since the template is a default, not a ceiling on what the API allows.

20.10 Operational Notes

  • Metrics: per-language sandbox_runs_total{tier,outcome} breakdown (label added at the control-plane layer, not the runtime, since sandbox-core has no concept of "language" — P4 substrate purity is preserved).

21. Phase 9 — Control Plane, API Surface & Warm Pool

21.1 Objectives

  • Land sandboxd's gRPC/REST surface (P8: the only network-exposed component) and sandbox-pool's warm-reuse manager (P14).

21.2 Detailed Implementation Steps

  • gRPC service Sandbox{Run,Stream,Cancel,Inspect} (proto/sandbox/v1/sandbox.proto) over the Unix-socket transport to the runtime daemon (ADR-10, ADR-11).
  • REST: POST /v1/run (JSON RunSpec → Outcome), GET /v1/runs/{id}/events (Server-Sent Events for stdout/stderr/audit/lifecycle), DELETE /v1/runs/{id} (Cancel); OpenAPI documents both surfaces (docs/api/openapi.yaml).
  • internal/auth: mTLS terminates at sandboxd; a capability token (Macaroon-style) resolves to a tenant identity, checked before the request is forwarded over the Unix socket (P8 — the runtime daemon never itself parses a bearer token).
  • internal/quota: per-tenant and per-tier admission quotas enforced before a RunSpec reaches the runtime daemon at all — the control plane is the fail-fast layer, the runtime daemon's own budgets (§14) are the fail-safe layer.
  • sandbox-pool::prewarm keeps N pre-warmed sandboxes per (tier, image); reuse is granted only if the new RunSpec is byte-identical to the warmed one modulo argv/env (P14, I-analog to I10's determinism requirement). sandbox-pool::reaper retires a pooled sandbox after max_age or max_runs.

21.3 Deliverable

sandboxd accepts a gRPC Run and a REST POST /v1/run, both producing an Outcome; a warm pool measurably reduces p99 latency for repeat (tier, image) pairs.

21.4 Acceptance Criteria

  • gRPC Run end-to-end (Tier::Process): p50/p95/p99 = 15/45/80 ms (M8), measured under sustained load.
  • Warm-pool hit rate ≥ 80 % for a workload replaying the same (tier, image) pair at a Poisson-distributed 100 req/s, sandbox-pool reuse fixture.
  • Quota rejection at the control-plane layer completes in < 5 ms p99 (fail-fast, before any runtime-daemon resource is touched).

21.5 Conformance Fixtures

Fixture Purpose Expected Output
api/grpc_run_roundtrip.json gRPC Run happy path Outcome within M8
api/rest_sse_stream.json REST SSE event stream ordered stdout/stderr/lifecycle events
api/quota_rejection.json over-quota tenant rejected before runtime-daemon dispatch
api/pool_reuse_identity.json warm-pool byte-identity check (P14) reuse denied on budget/image mismatch

21.6 Pitfalls

  • Capability-token leakage to logs. The control plane MUST redact tokens before any log line is emitted — a documented pitfall carried forward from the original design review; a redaction-bypass here is a direct tenant-impersonation vector.
  • Warm-pool identity laxity. Granting reuse across differing budgets or images "close enough" is a cross-tenant data-leakage vector (§23 T3) — P14's byte-identity rule has no fuzzy-match exception.

21.7 Performance Concerns

  • The Unix-socket hop between sandboxd and the runtime daemon is on the critical path of every request; keep the wire format (protobuf, §8.2) small and avoid a second serialization round-trip for the SSE relay path.
  • Quota-check latency must stay ≤ 5 ms p99 (§21.4) or it becomes the dominant term in the M8 end-to-end budget rather than the sandbox construction itself.

21.8 Edge Cases

  • A Cancel racing a Run that has already transitioned to Completed: the control plane must treat this as a no-op, not an error, since the lifecycle state machine (§8.1) has no Cancel transition out of Completed.
  • PhaseDeferred("§21.8"): a capability-token broker for finer-grained multi-tenant delegation (beyond the flat per-tenant quota model) is deferred; today's model is a single quota engine per tenant, not a delegable-capability graph (§36).

21.9 Failure Analysis

  • What breaks: the warm pool reuses a sandbox whose prior run left residual state in a supposedly-fresh scratch overlay. Detection: the pool's byte-identity check (§21.2) combined with the per-run fresh-overlay guarantee (§15.2) — a violation here is a P0 defect, not a tunable. Blast radius: cross-tenant data exposure if it reaches production (§23 T3) — the reaper's max_runs ceiling bounds exposure window if the identity check itself has a bug.

21.10 Operational Notes

  • Metrics: sandbox_pool_size{tier,image}, request-latency histograms partitioned cold vs. warm. PhaseDeferred("§21.10"): a Kubernetes operator exposing SandboxRun as a CRD is deferred; Phase 0-10 operates sandboxd as a plain Deployment behind the admission webhook (§36).

22. Phase 10 — Audit, Observability & Chaos Engineering

22.1 Objectives

  • Close the loop: every sandbox produces a verifiable audit chain (P6, P13, I9), every daemon emits standard telemetry, and the 11-script escape corpus runs as a release gate, not a manual exercise.

22.2 Detailed Implementation Steps

  • sandbox-audit::log appends AuditRecords (§11.9, §8.4) for every lifecycle transition (§8.1): LifecycleStart, PrepareComplete/PrepareFailed, MountAttempt, SeccompDeny, BudgetBurn, RunStart, LifecycleEnd, ForceKilled, AuditFinalized.
  • sandbox-audit::signer computes the BLAKE3 hash chain and ed25519 signature per record (ADR-15, ADR-22, §8.4 layout); sandbox-audit::replay walks and verifies a chain offline, exposed via sandbox-cli inspect --verify-audit.
  • OpenTelemetry spans wrap every Run, every prepare() stage, and every tier-specific construction step (§13.10, §17.10, §18.10, §19.10's per-tier spans compose here into the full trace).
  • Prometheus metrics registered daemon-wide: sandbox_runs_total{tier,outcome}, sandbox_cold_start_seconds{tier} (histogram), sandbox_warm_reuse_seconds{tier} (histogram), sandbox_budget_burn_total{kind}, sandbox_seccomp_deny_total {syscall}, sandbox_pool_size{tier,image}.
  • chaos/escapes/ (11 scripts: runc_cve_2019_5736, cgroup_release_agent, proc_self_exe_overwrite, userns_overflow, procfs_traversal, tty_punchthrough, fork_bomb, fd_exhaustion, memory_bomb, disk_fill, time_travel) runs against every tier in CI (chaos.yml); any escape is a release blocker (§23 T1-coverage, Appendix A lists each script's one-line purpose).

22.3 Deliverable

The full escape corpus runs against all four tiers with zero escapes; an audit chain for any completed run verifies offline via sandbox-cli inspect --verify-audit.

22.4 Acceptance Criteria

  • Zero escapes across the 11-script corpus × 4 tiers = 44 combinations (M2).
  • Audit signing throughput > 100K records/sec (M10), measured under sustained load.
  • A 1M-record audit chain verifies offline with zero false positives/negatives (M8 milestone analog, Appendix B).

Fixture Purpose Expected Output

escape/cgroup_release_agent.json CVE-2022-0492 class denied by seccomp + cgroup delegation

  • Audit-record size for truncated output. Logging a full (truncated) stdout inline blows the audit chain's per-record size budget; cap and reference by offset instead of embedding.
  • Chaos-suite flakiness masking a real escape. A flaky chaos script that is "usually" green hides a real regression; chaos scripts must be deterministic (P7) — a flaky one is itself a defect to fix, never to retry-and-ignore.

  • Audit signing is on every teardown's critical path (P6); ed25519's fast verify (ADR-15) is why the 100K rec/s target (M10) is achievable without batching, but batching signature verification during sandbox-cli inspect bulk-replay is still worth doing for the 1M-record milestone.

  • What breaks: a new escape technique not yet in the 11-script corpus succeeds against one tier. Detection: external report or an internal red-team finding (audits/ process, referenced in §23). Recovery: the technique is added to chaos/escapes/ as script #12+ and the fix ships as a release-blocking patch.

  • Dashboards: cold-start/warm-reuse histograms per tier, budget-burn breakdown per tenant, seccomp-deny rate per syscall (spike = a probing attempt, §23 T1). 23. Threat Model

23.1 Adversaries

  • A1 — code submitted by an untrusted party. The primary adversary; the sandbox runs A1's code by design.
  • A2 — a compromised image modified between build and run.
  • A3 — a compromised neighbour sandbox attempting side-channel or cross-sandbox attacks.
  • A4 — a compromised runtime daemon, which runs with elevated privilege (I4).
  • A5 — a compromised control plane, the one network-exposed component (P8).

23.2 Assets

The host kernel and filesystem; the runtime daemon's signing key (ADR-15); other sandboxes' state and outputs; the audit chain (P13).

23.3 Boundaries

Host/sandbox (primary, per-tier, §3 trust boundary #1); runtime/control-plane (secondary, the SO_PEERCRED-gated Unix socket, §3 trust boundary #2); control-plane/network (mTLS + capability token, §21.2).

25. Operational Readiness

  • Metrics. Prometheus (ADR-14): sandbox_runs_total{tier,outcome}, sandbox_cold_start_seconds{tier}, sandbox_warm_reuse_seconds{tier}, sandbox_budget_burn_total{kind}, sandbox_seccomp_deny_total{syscall}, sandbox_pool_size{tier,image}, sandbox_egress_denied_total{sandbox_id}, sandbox_audit_chain_verify_failures_total.
  • Tracing. OpenTelemetry (ADR-13) spans per Run, per prepare() stage (namespace/filesystem/capability/seccomp), per tier construction step (§22.2).
  • Structured logging. JSON lines tagged with sandbox_id/run_id; capability tokens and env vars are redacted before any line is emitted (§21.6 pitfall).
  • Dashboards. Cold-start/warm-reuse histograms per tier; budget-burn breakdown per tenant; seccomp-deny rate per syscall (a spike is the primary probing-attempt signal, T9); KVM-availability gauge (T4/FM4).
  • Alerting philosophy. Alert on rate-of-change for security-relevant counters (seccomp_deny_total, egress_denied_total) rather than absolute thresholds — a sandbox runtime's baseline deny rate is workload-dependent; a step change is the signal.
  • SLOs. 99.9 % control-plane monthly availability (§4); M1/M2/M3/M4 cold-start budgets gated in CI (§29); escape-corpus zero-tolerance (§22.4) is a release gate, not an SLO with an error budget.
  • Incident response. docs/runbooks/triage.md is the single entry point, routing to oom.md, stuck-sandbox.md, seccomp-deny-storm.md, or kvm-unavailable.md per the Failure Modes table (§24).
  • Backup/restore. The only durable daemon-owned state is the audit chain (§3 persistence boundary); it is streamed to append-only object storage continuously, not backed up as a periodic snapshot — restore is chain replay from the last externally-persisted record.
  • Deployment topology. One sandbox-runtime per host (bare metal or a privileged nested-KVM VM); sandboxd as a stateless Kubernetes Deployment fronting N hosts.
  • Canary/rolling-upgrade/rollback. sandbox-runtime upgrades are host-by-host (drain via I11's shutdown(), then replace); sandboxd upgrades are a standard Kubernetes rolling deployment behind the admission webhook. A canary host runs the new sandbox-runtime build against a synthetic-traffic subset before fleet rollout; rollback is a binary swap plus a sandbox-seccomp policy-version pin (§13.10) if the regression is policy-shaped.

26. Compatibility & Versioning

  • Wire compatibility. RunSpec/Outcome protobuf messages (§8.2) are additive only; a new field ships with a zero-value default (SemVer minor). Removing a field, or renumbering a Tier/MountSpec/NetworkSpec/ExitStatus variant, is SemVer major (§11.5-11.7 compatibility notes).
  • Storage compatibility. The audit-chain record layout (§8.4) is versioned by a leading version byte in the manifest; AuditRecordKind is append-only (§11.9) so an older sandbox-cli can still parse newer records' known-kind prefix even if it cannot interpret a new kind's payload.
  • Schema evolution. Image manifest.json (§15.2) follows the OCI Image Spec's own versioning; the content-addressed hash (xxh3, ADR-16) is independent of the manifest schema version, so cache keys survive a schema bump.
  • API stability. The gRPC/REST surface (§21.2) follows SemVer; a REST endpoint is never removed within a major version, only deprecated with a documented sunset window (≥ 2 minor releases).
  • Migration. A RunSpec schema change that is not purely additive ships a translation shim in sandboxd::internal::api for one major version before the old shape is rejected.
  • Deprecation policy. Deprecated fields/endpoints are marked in docs/api/openapi.yaml and emit a structured warning in the response metadata for two minor releases before removal.
  • SemVer policy. sandbox-runtime, sandboxd, and the wire protocol version independently; the Makefile's release-check target refuses a release that bumps the wire protocol without a corresponding ADR.
  • Rolling-upgrade guarantees. A sandbox-runtime upgrade never interrupts an in-flight Run; shutdown() (I11) drains before the old binary exits, and the warm pool (§21.2) is deliberately not preserved across a daemon restart — correctness over pool-warmth continuity.

27. Testing & Verification Strategy

  • Unit tests. Per-crate, focused on sandbox-core type invariants and sandbox-seccomp/sandbox-cg policy-construction logic in isolation.
  • Integration tests. sandbox-test-util's deterministic simulator (§7 debugging methodology) drives full prepare→run→shutdown cycles per tier.
  • Property testing. proptest (ADR-23) over the seccomp policy compiler's input grammar (~350-entry allowlist), asserting the compiled BPF never permits a syscall outside the declared policy.
  • Differential testing. Cranelift vs. Winch parity (§17.6) for Wasm codegen; re-prepare() determinism diffing (I10) across all four tiers.
  • Fuzzing. cargo-fuzz targets (§10 fuzz/): seccomp-policy compilation, image-manifest parsing, audit-record decoding — a 30-day continuous target with zero panics (M7, ADR-23).
  • Chaos engineering. The 11-script escape corpus (§22.2) run against all four tiers in CI (chaos.yml), zero-tolerance release gate (§22.4).
  • Deterministic replay. The audit chain (§8.4) doubles as a replay log; sandbox-audit::replay reconstructs the lifecycle sequence of any completed run for debugging without re-executing the (possibly untrusted) workload.
  • Soak testing. benchmarks/throughput.py sustains 1K runs/sec for 30 minutes (M6) to surface slow leaks (fd, memory, cgroup-scope accumulation) invisible in short runs.
  • Fault injection. sandbox-test-util fixtures inject namespace-entry failures, cgroup-attach failures, and seccomp-load failures individually to verify each fails closed (P2) rather than degrading silently.
  • Conformance gating. conformance.yml runs every corpus bucket (the conformance/corpora/ layout, §10) on every PR; CI is red on any bucket with a non-zero fail count in report_schema.json.
  • Performance-regression gating. benchmarks/ results are compared against the M1-M12 targets (§29) nightly; a > 10 % regression on any cold-start budget blocks release (P9).
  • Traceability to invariants. Every I# (§7) has a named conformance fixture or sandbox-test-util assertion; the debugging methodology (§7 closing paragraph) is the authoritative mapping.

28. Build & Release Engineering

  • Reproducible builds. Nix flake pinning (ADR-21) for the release build path; cargo build --release remains available for local dev (§9 ADR-21's "when the rejected choice wins" regime).
  • Artifact signing. Release binaries are signed with the same ed25519 key family pattern as the audit chain (ADR-15), but a distinct release-signing key, never reused across the two purposes.
  • SBOM. Generated per release via cargo-cyclonedx (Rust) and syft (Go control-plane), attached to the GitHub release artifact.
  • Release channels. stable (fleet default), canary (one host subset, §25 canary policy), nightly (benchmarks + conformance only, never fleet-wide).
  • CI/CD topology. .github/workflows/{ci,conformance,chaos,kernels,security, release}.yml (§10); release.yml only fires on a signed, SBOM-attached, conformance-green, chaos-green tag.
  • Version stamping. Every binary embeds its git SHA, build timestamp, and wire-protocol version (§26); sandbox-cli inspect --version surfaces all three.
  • Provenance/attestation. SLSA-style provenance metadata (build platform, source commit, builder identity) is attached alongside the SBOM; the Nix flake lock file (ADR-21) is the reproducibility anchor an auditor re-derives against.
  • Dependency auditing. cargo audit and govulncheck run in security.yml on every PR; a new critical/high CVE in a dependency blocks merge, not just release.

29. Performance Engineering

Methodology. Every target below is measured by a named benchmarks/*.py script against the reference host (§4), gated in CI nightly, with a > 10 % regression on any cold-start budget blocking release (P9). Profiling uses perf record/perf stat for syscall-count and cache-miss analysis, and tokio-console for async-task scheduling contention in sandbox-runtime.

  • Allocation analysis. sandbox-seccomp::bpf and sandbox-fs::overlay are the two allocation-heaviest paths on cold start (BPF program buffer, mount-option strings); both use a pre-sized arena allocator to avoid per-run heap churn entering the M1 budget.
  • Lock contention. sandbox-pool is the only cross-sandbox shared-state structure (P4's substrate is per-sandbox, not shared); its prewarm/reaper queues use a sharded lock-free MPMC queue, not a single mutex, to avoid contention at M6's 1K runs/sec target.
  • Cache locality. Reference-host NUMA pinning (§4): one sandbox pinned within one NUMA node above 16 concurrent Tier::MicroVm guests avoids cross-node vsock latency, the dominant tail-latency contributor beyond that concurrency level.
  • Syscall analysis. Tier::Process's cold-start syscall count is tracked as a first-class regression signal (strace -c in benchmarks/cold_start_process.py) — a change that adds a syscall to the hot path is reviewed against the M1 budget explicitly, not just wall-clock time.
  • Tail-latency analysis. p99, not mean, is the gated metric for every cold-start target (M1-M4) because the interactive code-eval workload (§1) is latency-sensitive at the tail, not the average — a p50 win that worsens p99 is a regression, not an improvement.

30. Scalability Analysis

  • Constant regardless of scale: per-sandbox RAM floor (§4), the seven-namespace entry order (I2), the BPF filter depth ceiling (§13.7). Grows with load: daemon-wide FD count (O(n) in concurrent sandboxes, ~6 fds/sandbox against a raised 1,048,576 ulimit, §4 — not the binding constraint, §33), audit-chain length (O(n) in completed runs, unbounded — the reason it streams to external object storage, §25), nftables egress-rule count (O(n) in concurrent sandboxes with distinct allowlists, §16.7).
  • Named bottlenecks, in order: (1) per-host committed memory against the reference host's usable RAM (§33 M11 derivation) — the first ceiling hit as Tier::Process concurrency rises; (2) NUMA cross-node vsock latency above 16 concurrent Tier::MicroVm guests per node (§29, §33 M12 derivation); (3) content-addressed image cache contention on a cold cache (§15.7); (4) nftables per-packet egress-rule evaluation cost at high concurrent-sandbox counts with distinct allowlists (§16.7).
  • Horizontal scaling. Add hosts; sandboxd is stateless and scales independently of sandbox-runtime instances (§3 deployment model). No cross-host sandbox migration exists in Phase 0-10 (§4 scaling assumption) — a named limitation, not an oversight.
  • Vertical scaling. More RAM directly raises Tier::Process/Tier::Wasm concurrency ceilings (M11-class); more cores raise Tier::MicroVm concurrency (M12) since each guest wants a pinned vCPU budget above the NUMA threshold (§29).
  • Sharding/partitioning. Tenants are sharded across hosts by the control plane's quota engine (§21.2), not within a single sandbox-runtime instance — the daemon itself has no tenant concept (P4 substrate purity).
  • Coordination overhead. Zero cross-host coordination in the runtime daemon layer; sandboxd instances coordinate only through the shared quota state (external to this blueprint's Phase 0-10 scope — an operator-supplied backing store, §1 delegates).
  • Practical ceiling and the levers beyond it. ~4,000 Tier::Process sandboxes or ~200 Tier::MicroVm sandboxes per reference host (§33 derivation); beyond that, the levers are: more hosts (horizontal, no coordination cost added), snapshot- restore for Tier::MicroVm (PhaseDeferred("§18.7"), raising the practical density by amortizing cold start rather than raw concurrency), and the systrap platform for Tier::UserKernel (PhaseDeferred("§19.7"), raising sustainable syscall-heavy throughput per host).

31. Mental Models & First Principles

  1. MM1 — A namespace virtualizes a kernel identifier table; it is not a security boundary by itself. Predicts: a namespace-only sandbox (no seccomp filter) is escapable via any syscall the namespaced table doesn't cover. Bug class without it: engineers treat "namespaced" as a synonym for "secure" and skip the seccomp layer. Resolving: §13 (Phase 1), I1-I5.
  2. MM2 — A capability is the only legitimate path to privilege; ambient anything is a bug. Predicts: any code path that asks "am I root?" instead of "do I hold capability X?" is eventually wrong under this model. Bug class without it: privilege checks written against UID instead of the Capability bitflags (P11). Resolving: §11.2, §13.2, T2/T9.
  3. MM3 — Fuel meters instructions; epochs meter time; conflating the two misclassifies every CPU-vs-wall-clock kill. Predicts: an implementation that maps fuel exhaustion to a wall-clock BudgetReason will silently misreport "looped too long" as "took too long." Bug class without it: an incorrect ExitStatus::KilledByBudget reason in Outcome (I7). Resolving: §17.2, §17.6.
  4. MM4 — Delegated interposition: the process that decides is never the process with authority over the resource. The Ostia/Sentry-Gofer principle (§5 Papers #5). Predicts: any redesign folding Gofer logic into the Sentry silently loses the containment guarantee. Bug class without it: path-containment bypass (T12). Resolving: §19.2.
  5. MM5 — A hypervisor's larger interface is not automatically a smaller attack surface than a narrower usermode kernel (Garfinkel & Rosenblum, HotOS 2005). Predicts: choosing a VM tier "because VMs are more secure" without counting its actual device-model surface can be wrong — Firecracker's minimal device model, not "it's a VM," is why ADR-07 holds. Bug class without it: assuming any hypervisor gives Tier::MicroVm's properties, including ones with large device surfaces. Resolving: §18.2, §32.
  6. MM6 — Determinism is what makes an escape reproducible, and reproducibility is what makes an escape fixable. Predicts: flaky conformance tests correlate with real, not spurious, escape risk over time. Bug class without it: "we can't reproduce it" becomes a permanent excuse not to fix a reported escape. Resolving: I10, §22.6.
  7. MM7 — Fail-closed trades a silent security hole for a visible availability incident — almost always the correct trade for a sandbox. Predicts: an operator who "fixes" a fail-closed error by loosening the check has reintroduced exactly the bug class P2 exists to catch. Bug class without it: silently relaxing a check to make an alert stop firing. Resolving: §12.9, §13.9.
  8. MM8 — An audit chain's value is proportional to how independent its verification is from the thing it audits. Predicts: any "audit log" stored as a mutable, UPDATE-able database row provides zero forensic value against a compromised-daemon adversary (A4). Bug class without it: designing the audit store as a normal CRUD table instead of an append-only signed hash chain. Resolving: §11.9, T8.

gVisor made one decision differently: a single usermode-kernel tier for every workload, accepting ptrace/systrap overhead universally in exchange for one security model to reason about. That wins when an operator needs a single uniform isolation guarantee across a heterogeneous fleet and cannot audit four different tiers.

Firecracker made one decision differently: hardware virtualization as the only tier, with no lighter-weight fallback. That wins when every workload is already hostile-multi-tenant by default (public serverless) and the ~100-250 ms cold start is an acceptable fixed cost for a uniform, kernel-level guarantee.

runc/Docker made one decision differently: namespaces+cgroups+seccomp as the default and only isolation level, optimized for developer ergonomics and image portability over worst-case adversarial containment. That wins for CI and internal tooling where the "untrusted" code is actually semi-trusted (your own team's builds).

bubblewrap/nsjail made one decision differently: a single-shot, no-daemon process model with no lifecycle to manage. That wins for a CLI tool sandboxing one invocation (a linter, a formatter) where standing up a daemon is pure overhead.

V8 Isolates made one decision differently: push isolation into the language runtime entirely, with no OS-level boundary at all. That wins when the workload is guaranteed to be JavaScript/Wasm and per-isolate cold start must be sub-millisecond (edge compute, Cloudflare Workers-class deployments) — at the cost of trusting the JS engine itself as the entire security boundary, a much larger TCB-per-boundary tradeoff than any OS-primitive tier in this design.

33. Back-of-Envelope Capacity Model

Every number below chains from the §4 System Constraints table on the reference host (64 vCPU / 256 GiB RAM / NVMe / 25 GbE).

  1. Usable RAM for sandboxes. 256 GiB total − 32 GiB reserved (host OS, daemon, warm pool, Prometheus/Grafana sidecars) = 224 GiB usable.
  2. Tier::Process concurrency ceiling (M11). Per-sandbox all-in footprint = 4 MiB structural floor (§4) + 32 MiB typical interactive-eval commit (Budget::strict()-class workload) = 36 MiB. Ceiling = 224×1024 MiB ÷ 36 MiB ≈ 6,371 sandboxes. M11's stated target of > 4,000 keeps ~35 % headroom against non-uniform workload sizes — the memory-derived ceiling, not the FD ulimit (below), is the binding constraint (§30 bottleneck #1).
  3. Daemon FD headroom (not binding). At ~6 daemon-side bookkeeping fds/sandbox (§4) and 6,371 concurrent sandboxes: 6,371 × 6 ≈ 38,226 fds, well under the raised 1,048,576 ulimit (§4) — confirms the FD ceiling is not the constraint memory is.
  4. Tier::MicroVm NUMA-clean ceiling. 16 concurrent guests/NUMA node before cross-node vsock latency degrades tail latency (§29) × 2 NUMA nodes (typical dual-socket reference host) = 32 guests at full tail-latency quality.
  5. Tier::MicroVm oversubscribed ceiling (M12). 64 vCPU × 3.2 oversubscription ratio (lightweight, bursty guest workloads tolerating some scheduling latency beyond the NUMA-clean point) ≈ 205 guests, rounded to the stated floor of > 200 — accepting degraded-but-bounded tail latency beyond the 32-guest NUMA-clean ceiling (item 4).
  6. Tier::MicroVm RAM check (not binding). 224 GiB ÷ 128 MiB floor (§4) ≈ 1,792 guests by RAM alone — confirms vCPU/NUMA (item 5), not RAM, binds Tier::MicroVm concurrency.
  7. Cold-start budget breakdown for M1 (50 ms p99). clone3+namespace entry (~8 ms) + overlay/pivot_root mount (~15 ms) + seccomp compile+load (~5 ms) + cgroup attach (~4 ms) + capability drop (~1 ms) + execve+first instruction (~7 ms) + audit LifecycleStart write (~2 ms) = ~42 ms, leaving ~8 ms headroom against the 50 ms p99 target.
  8. Seccomp interception overhead (§4's ≤ 3 %). At a compiled-filter depth of 64 classifier branches (§13.7 ceiling) and an estimated ~2 ns/branch dispatch cost: 64 × 2 ns = 128 ns added per syscall. Against an unloaded average syscall cost of ~4,000 ns: overhead = 128 ÷ 4,000 ≈ 3.2 %, consistent with the stated ≤ 3 % target (the extra 0.2 % is the reason §13.7 caps filter depth rather than leaving it unbounded).
  9. Audit signing throughput (M10 ≥ 100K rec/s). At an estimated ~50 µs/sign (a conservative single-core ed25519-dalek-class figure) = ~20,000 signs/sec per core; a dedicated 6-thread signing pool (a small slice of the 64-vCPU host) ≈ 6 × 20,000 = 120,000 signs/sec, clearing the M10 100K floor with ~20 % headroom.
  10. Escape-detection latency budget (§4's ≤ 200 ms, I6). Seccomp-deny-to-audit path: kernel notify delivery (~1 ms) + sandbox-audit::log append (~1 ms) + BLAKE3 hash + ed25519 sign (~0.1 ms, item 9) = ~2.1 ms actual, against a 200 ms budget — the wide margin exists because I6's 200 ms is an operator alerting SLA (dashboard/alert propagation), not a raw signal-path latency.
  11. Storage amplification check (§4's ≤ 1.3x). A 500 MB rootfs layer set + overlay scratch tmpfs (bounded by Budget::disk_bytes, typically ≤ 128 MB for an evaluation workload) ÷ 500 MB uncompressed = 628 MB ÷ 500 MB ≈ 1.26x, under the 1.3x ceiling.
  12. Warm-pool memory tax (M6 context). Sustaining M6's 1,000 runs/sec with a pool of N pre-warmed Tier::Process sandboxes per hot (tier, image) pair at 36 MiB each (item 2): a pool of 50 warm sandboxes per image × 10 hot images = 500 sandboxes × 36 MiB ≈ 18 GiB, a small fraction of the 224 GiB usable budget (item 1) even before counting live traffic.

35. Alternative Architectures (Roads Not Taken)

A1 — Hardware-virt microVM everywhere.

Request ─▶ [Firecracker VM] ─▶ guest kernel ─▶ user code
             (every workload, no lighter tier)

Regime where it wins: every tenant is assumed hostile by default (public serverless). Real system: Fly.io Machines (Firecracker-only fleet). Rejected here because the interactive-eval workload's < 50 ms budget (M1) and the CI-build workload's semi-trusted threat model do not need — and cannot afford — a ~250 ms VM boot on every request (§1, §4).

A2 — Usermode kernel everywhere.

Request ─▶ [Sentry+Gofer] ─▶ syscall table ─▶ user code
             (one isolation level for all tenants)

Regime where it wins: an operator needs exactly one security model to audit across a heterogeneous fleet. Real system: Google Cloud Run's historical use of gVisor as its sole isolation layer. Rejected here because the ≤5.0x (ptrace) / ≤1.5x (systrap, deferred) syscall overhead (M9) is unacceptable for CPU-bound build/test workloads that Tier::Process serves natively at near-zero overhead (§4, §19.4).

A3 — OS-primitive containment only (no Wasm/microVM/usermode tiers).

Request ─▶ [namespaces+cgroups+seccomp] ─▶ user code
             (the plain-Docker/runc shape)

Regime where it wins: internal, semi-trusted CI where "untrusted" really means "our own team's build scripts." Real system: a plain runc/Docker fleet. Rejected here because it cannot safely serve the agent-tool-execution and hosted-webhook workloads (§1) against a genuinely hostile A1 adversary — it has no answer to Spectre-class co-residency risk (T7) the way Tier::MicroVm does.

A4 — Language VM only (Wasm/WASI everywhere, no native binaries).

Request ─▶ [Wasmtime Store] ─▶ WASI imports ─▶ compiled Wasm module
             (no Tier::Process/MicroVm/UserKernel at all)

Regime where it wins: edge compute where every workload is guaranteed Wasm-compilable and sub-millisecond cold start is the product's entire value proposition. Real system: Cloudflare Workers / Fastly Compute@Edge. Rejected here because the CI/build-and-test workload (§1) needs to run arbitrary, already-compiled native binaries that were never going to be recompiled to Wasm — a language-VM-only design cannot serve that workload at all, not just less efficiently.

37. Glossary

  • Tier — the caller-selected isolation backend (Process/Wasm/MicroVm/UserKernel, §11.1).
  • TierImpl — the trait every tier backend implements (prepare/run/shutdown, §11.8).
  • RunSpec — the immutable, fully-resolved request describing one sandboxed execution (§11.5).
  • Outcome — the terminal result of a Run, including the audit chain (§11.7).
  • Budget — the quantified resource ceiling set (memory/CPU/wall/pids/fds/io/net, §11.3).
  • Capability — the bitflag type gating every privileged operation a sandbox may perform (§11.2).
  • Namespace — a Linux kernel mechanism virtualizing one identifier table (PID, mount, net, …); not a security boundary alone (MM1).
  • cgroup v2 — the unified control-group hierarchy enforcing resource ceilings (§14, ADR-05).
  • seccomp-BPF — the Linux syscall-filtering mechanism compiled from a SeccompPolicy (§11.6, ADR-04).
  • no_new_privs — the process flag that must be set before a seccomp filter loads (I1).
  • Ambient capability — a capability inherited without an explicit grant; forbidden everywhere in this design (P11, I5).
  • Bounding set — the ceiling capability set a process (and its children) may ever hold.
  • pivot_root — the syscall that swaps a process's root filesystem, used to enter the sandbox rootfs (§13.2).
  • overlayfs — a union filesystem layering a read-only lower directory under a writable upper directory (§15.2).
  • Landlock — an unprivileged Linux LSM for per-process filesystem scoping, used as Tier::Process defense-in-depth (ADR-17).
  • AppArmor — a path-based Linux MAC system generating per-sandbox profiles from the mount tree (ADR-18).
  • Sentry — the usermode kernel process in Tier::UserKernel that mediates syscalls (§19.1).
  • Gofer — the delegate process holding filesystem authority for Tier::UserKernel (§19.2, MM4).
  • ptrace — the Linux syscall-tracing mechanism used as the Phase-0 Tier::UserKernel platform (ADR-09).
  • systrap — the deferred, faster Tier::UserKernel platform using signal-handler interception (§19.7).
  • vsock — a virtio socket address family used as the control channel between host and microVM guest (§18.2).
  • virtio — the paravirtualized device model Firecracker exposes to guests (virtio-blk, virtio-net, §18.2).
  • Firecracker — the microVM hypervisor backing Tier::MicroVm (ADR-07).
  • WASI — the WebAssembly System Interface; snapshot1 is the import surface Tier::Wasm conforms to (§17.2).
  • Wasmtime — the Wasm engine backing Tier::Wasm (ADR-06).
  • Fuel — Wasmtime's instruction-metering CPU-budget mechanism (§17.2, MM3).
  • Epoch interruption — Wasmtime's time-metering wall-clock-budget mechanism (§17.2, MM3).
  • Warm pool — the set of pre-constructed sandboxes reused across requests under strict byte-identity (§21.2, P14).
  • Cold start — the latency from Run request to first user instruction with no warm sandbox available (§4, M1-M4).
  • TOCTOU — time-of-check-to-time-of-use; the race class P5's static-policy rule exists to prevent (T6).
  • BLAKE3 — the hash function chaining audit records (§8.4, ADR-22).
  • ed25519 — the signature scheme securing the audit chain and release artifacts (ADR-15).
  • xxh3 — the non-cryptographic hash used for content-addressed image identity (ADR-16).
  • Content-addressed — identified by the hash of one's own content, not a mutable name (§15.2).
  • SBOM — Software Bill of Materials; generated per release (§28).
  • SLSA — Supply-chain Levels for Software Artifacts; the provenance model §28 follows.
  • OTel span — an OpenTelemetry trace unit wrapping one phase of sandbox construction or execution (§22.2, ADR-13).
  • nftables — the Linux packet-filtering framework enforcing egress allowlists (§16.2).
  • SLIRP — a usermode TCP/IP+NAT stack providing network access without host-netns privilege (§16.2).
  • NUMA — Non-Uniform Memory Access; the reference host's node topology bounds Tier::MicroVm concurrency (§33 item 4).
  • RTO — Recovery Time Objective; the bound on how fast service resumes after a failure (§4, §25).
  • Fail-closed — the design stance that any isolation-hop failure aborts construction rather than degrading silently (P2, MM7).
  • TCB — Trusted Computing Base; the set of components whose compromise breaks the security guarantee (§32, MM5).
  • Ostia delegation — the pattern of routing syscall interposition decisions to a separate trusted agent process (§5 Papers #5, MM4).
  • Spectre/Meltdown — cross-domain speculative-execution side channels; the reason Tier::MicroVm exists as an escape valve from Tier::Process (T7, §5 Papers #7-8).
  • CRIU — Checkpoint/Restore In Userspace; the deferred snapshot mechanism for Tier::Process (§13.7).
  • Oversubscription ratio — the number of lightweight guest workloads scheduled per physical vCPU beyond 1:1 (§33 item 5).
