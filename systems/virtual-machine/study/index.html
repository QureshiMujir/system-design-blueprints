Hard questions (§33)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why is a shared operand stack across all frames (P5) safe, given that a callee's Pop could in principle underflow into the caller's region — what exactly prevents this? (§15, §19, I1, I2)
  2. What specific property of this instruction set's codegen (not the verifier) makes the Phase 7 stack-effect simulation decidable in one static pass, without fixed-point iteration? (§16, §19, MM8)
  3. If the verifier (§19) and the compiler (§16) independently compute max_stack and disagree, which one is "right," and what does that disagreement actually indicate? (§16.10, §26)
  4. Why does the GC's root set (§18, I8) need to include the operand stack, not just frame locals — construct a concrete program where omitting it causes a use-after-free. (§17, §18, FM-4)
  5. Why is match/switch dispatch (ADR-01) not simply "slower" than computed goto — under what measured conditions (§21) would the reverse be true, per Ertl & Gregg (2003)? (§14, §21, MM3)
  6. What does Lua's move to a register-based VM (Ierusalimschy et al. 2005) actually save, and why does this project's scope (§1) make that saving not worth the compiler complexity it costs? (§9 ADR-02, §31, §34)
  7. Why is a bytecode verifier (§19) a meaningful trust boundary when the only producer of bytecode in this project's scope is its own compiler (§16) — what threat model justifies it anyway? (§9 ADR-09, §22)
  8. Trace exactly what happens, state-by-state (§8.4), when a Call opcode's argument count does not match the callee's arity, from dispatch through to the returned VmError. (§15, §19, I10)
  9. Why is GC safepoint placement restricted to Call/Return/backward-Jump (P8, ADR-22) rather than every instruction — what would break, and what would the pause-latency tradeoff become, if it were every instruction? (§18, §28 M4)
  10. What is the actual difference between "the verifier rejects malformed bytecode" (§19) and "the runtime guards reject malformed bytecode" (§14) — why does this project need both rather than just the cheaper one? (§14, §19, P6, P7)
  11. Why does interning Str constants once at module-load time (§17) rather than on every LoadConst execution matter for correctness, not just performance? (§11, §17, P4)
  12. Construct a program whose compiled bytecode passes the Phase 7 verifier but whose execution still triggers a documented VmError at runtime — is this a verifier bug, or expected behavior? Justify from first principles. (§19, §23 FM-7/FM-8)
  13. Why is heap allocation rate (M11) meaningfully bounded by GC pause latency (M4) rather than by raw allocator throughput — walk the causal chain. (§18, §28, §32)
  14. What concrete evidence would justify un-deferring inline caching (ADR-20, §35) for this instruction set, given that its current call sites are statically monomorphic? (§9 ADR-20, §21, §35)
  15. Why does this project's single-threaded-per-instance concurrency model (ADR-15) not simply mean "no concurrency support" — what is the actual scaling story for a host running many Vm instances? (§29, §9 ADR-15)
  16. If the disassembler (§20) and the execution loop (§14) ever disagree about what a given byte sequence means, which one is definitionally wrong, and how would you prove it? (§20, P10, §23 FM-9)
  17. Why is checked integer arithmetic (ADR-14, P12) a correctness requirement rather than a performance nicety, given that this is a from-scratch teaching VM with no untrusted numeric input beyond the bytecode itself? (§9 ADR-14, §12, T6)
  18. Walk through exactly how a value stored in local slot 3 of a frame 15 calls deep in a recursive fib computation survives a GC cycle triggered by an allocation in the 16th call — name every piece of state the collector must visit. (§15, §18, I8)

30. Mental Models & First Principles

MM1 — "Bytecode is a contract, not an implementation detail." Predicts that any opcode-meaning change is a compatibility event, not a refactor. Without it: engineers silently repurpose an opcode and break every previously-compiled Module. Resolves in §25 / P1.

MM2 — "The interpreter loop is a state machine over (ip, stack, frame), nothing more." Predicts that any bug must be traceable to one of those three pieces of state at one instruction boundary. Without it: engineers add hidden state (P11 violation) and debugging becomes non-reproducible. Resolves in §8.4 / §14.

MM3 — "Every dispatch is a branch-prediction problem before it is an algorithm problem." Predicts that match dispatch's cost is CPU-microarchitecture-dependent, not a fixed constant — per Ertl & Gregg (2003). Without it: engineers "optimize" dispatch without measuring, violating P9. Resolves in §14 / §21.

MM4 — "GC correctness is root-enumeration correctness, full stop." Predicts that every use-after-free bug traces to a missed root, never to the mark or sweep algorithm itself being wrong. Without it: engineers debug the wrong half of the collector. Resolves in §18 / I8.

MM5 — "A verifier is a proof-checker for a proof the compiler already computed." Per Leroy (2003): the verifier re-derives the same stack-effect proof the compiler's codegen implicitly relied on, independently. Without it: engineers treat verification as redundant with compilation and skip it, collapsing the trust boundary ADR-09 exists to draw. Resolves in §19 / ADR-09.

MM6 — "Register machines trade instruction count for register-allocation complexity." Per Ierusalimschy et al. (2005): a register VM is not "just faster," it moves cost from the dispatch loop into the compiler. Without it: engineers assume a register rewrite is a free performance win. Resolves in §14 / §31 / §34.

MM7 — "Threaded code turns dispatch into data." Per Bell (1973): direct/indirect threading replaces a decision (match/switch) with a memory read of the next handler's address. Without it: engineers cannot reason about why threaded dispatch's cost profile differs from switch dispatch's. Resolves in §21 / §34.

MM8 — "Stack depth is a static property when control flow is structured." The verifier's stack-effect simulation (I1) is only decidable in one static pass because this instruction set's codegen (Phase 4) never emits irreducible control flow. Without it: engineers would assume a fixed-point iteration is always required, over-engineering the verifier. Resolves in §19 / I1.

5. Required Reading

Books

  • Nystrom, R. Crafting Interpreters (2021). Part III, Ch. 14–30 ("A Bytecode Virtual Machine"): extract the chunk/constant-pool design and the single-pass Pratt-parser-to-bytecode pipeline. Applied in §8 / Phase 1 (§13).

  • Goldberg, A. & Robson, D. Smalltalk-80: The Language and Its Implementation (1983). Part IV, "The Virtual Machine": extract the byte-oriented stack-machine instruction format and object memory model. Applied in §8 / Phase 5 (§17).

  • Lindholm, T., Yellin, F., Bracha, G., Buckley, A., Smith, D. The Java Virtual Machine Specification, Java SE 17 Edition (2021). Ch. 4 (class file / constant pool), Ch. 6 (instruction set): extract the constant-pool indexing scheme and per-instruction operand-stack effect tables. Applied in §9 / Phase 1 (§13) and Phase 7 (§19).

  • Smith, J.E. & Nair, R. Virtual Machines: Versatile Platforms for Systems and Processes (2005). Ch. 3, "Process Virtual Machines": extract the interpreter-vs-emulator taxonomy this project sits in. Applied in §2 / Phase 0 (§12).

  • Aho, A., Lam, M., Sethi, R., Ullman, J. Compilers: Principles, Techniques, and Tools, 2nd ed. (2006). Ch. 8, "Code Generation": extract stack-machine code-generation patterns for expressions and control flow. Applied in §8 / Phase 4 (§16).

  • Appel, A.W. Modern Compiler Implementation in ML (1998). Ch. 6, "Activation Records": extract the activation-record / calling-convention design vocabulary. Applied in §11 / Phase 3 (§15).

Papers

  • Bell, J.R. "Threaded Code." Communications of the ACM 16(6), 1973: direct/indirect threaded dispatch as an alternative to switch dispatch. Applied in §21 / Phase 9 (§21).

  • Ertl, M.A. & Gregg, D. "The Structure and Performance of Efficient Interpreters." Journal of Instruction-Level Parallelism 5, 2003: quantifies switch vs. computed-goto vs. threaded dispatch branch-misprediction cost. Applied in §14 / Phase 2 and §21 / Phase 9.

  • Romer, T., Lee, D., Voelker, G., Wolman, A., Wong, W., Baer, J., Bershad, B., Levy, H. "The Structure and Performance of Interpreters." ASPLOS-VII, 1996: dispatch-loop instruction-cache and branch-target-buffer behavior. Applied in §21 / Phase 9.

  • Ertl, M.A. "Stack Caching for Interpreters." PLDI, 1995: caching top-of-stack values in registers to cut memory traffic. Applied in §14 / Phase 2 (§14).

  • Deutsch, L.P. & Schiffman, A.M. "Efficient Implementation of the Smalltalk-80 System." POPL, 1984: introduces inline caching for polymorphic call sites. Applied in §21 / Phase 9 (ADR-20).

  • Ierusalimschy, R., de Figueiredo, L.H., Celes, W. "The Implementation of Lua 5.0." Journal of Universal Computer Science 11(7), 2005: register-based bytecode design and instruction-count reduction versus a stack machine. Applied in §31 / §34.

  • Leroy, X. "Java Bytecode Verification: Algorithms and Formalizations." Journal of Automated Reasoning 30(3-4), 2003: static stack-effect and type-safety verification of bytecode prior to execution. Applied in §19 / Phase 7.

  • Bacon, D.F., Cheng, P., Rajan, V.T. "A Unified Theory of Garbage Collection." OOPSLA, 2004: the tracing/reference-counting duality; root-set correctness requirements. Applied in §18 / Phase 6.

  • Wilson, P.R. "Uniprocessor Garbage Collection Techniques." IWMM, 1992: survey of mark-sweep, copying, and generational collector tradeoffs. Applied in §18 / Phase 6 and §34.

Reference Implementations

  • CPython — Python/ceval.c, Include/opcode.h. Lesson: computed-goto dispatch (enabled by default under GCC/Clang) plus, since 3.11, adaptive specialization on hot opcodes. Pitfall: a monolithic switch grows unmaintainable without careful opcode grouping. Applied in §14 / Phase 2 and §21 / Phase 9.

  • Lua 5.4 — lvm.c, lopcodes.h. Lesson: a register-based instruction format collapses stack push/pop pairs into direct register references, cutting instruction count. Pitfall: the compiler needs a real register allocator, unlike a stack machine. Applied in §31 / §34.

  • OpenJDK HotSpot — share/interpreter/templateInterpreter.cpp. Lesson: per-opcode generated machine-code templates eliminate dispatch overhead entirely. Pitfall: platform-specific assembly multiplies maintenance cost per architecture. Applied in §31 / §34.

  • Wasm3 — source/m3_exec.h. Lesson: tail-call "next-instruction" dispatch via function pointers is portable across compilers and competitive with computed goto. Pitfall: relies on the host C compiler actually performing tail-call optimization, which is not guaranteed by the C standard. Applied in §14 / Phase 2 and §31.

  • CRuby YARV — insns.def, vm_insnhelper.c. Lesson: replacing an AST-walking interpreter with a compiled stack-bytecode VM (Ruby 1.9) is itself the historical case study for why bytecode beats tree-walking. Pitfall: migrating an existing language's semantics onto a new instruction set surfaces edge cases the tree-walker had papered over. Applied in §34.

RFCs / Specifications

  • W3C WebAssembly Core Specification, Ch. 3 "Validation": the closest standardized analogue to this project's Phase 7 verifier — a structured type-and-stack-effect validation algorithm run before execution. Applied in §19 / Phase 7.

  • ECMA-335, Common Language Infrastructure (CLI), Partition III "CIL Instruction Set": a second real-world stack-based bytecode instruction set for comparison against the opcode table in §11. Applied in §8 / §31.

Glossary (§36) · 37 terms · site-wide glossary

AST
Abstract Syntax Tree; the tree-shaped source representation accepted directly as this VM's compiler input (§1).
Arity
the declared number of parameters a function accepts; checked both statically (§19) and dynamically (§15).
Backward jump
a Jump/JumpIf/JumpNot whose target offset is less than the current ip; the designated GC safepoint location besides Call/Return (P8).
Base pointer (base_sp)
the operand-stack index below which a Frame may not read or pop (§11, P5).
Bytecode
the flat, linear instruction stream a Function executes; the compiled form of an AST (§8).
Call frame (Frame)
the per-invocation record holding a function's locals, instruction pointer, and operand-stack base (§11).
Calling convention
the fixed protocol for how arguments, return values, and control transfer between caller and callee (§8.3, ADR-05).
Computed goto
a dispatch technique using labels-as-values to jump directly to a handler address, bypassing a central switch (§34, Bell 1973).
Conformance fixture
a named, checked-in input/expected-output pair proving one specific behavior (§26).
Constant pool
the per-module deduplicated table of literal values referenced by index from bytecode (§8.2, ADR-04).
Dispatch
the step that maps a decoded opcode to the code that executes it (§8.4, ADR-01).
Direct threading
a dispatch technique where each instruction slot directly holds the address of its handler (§5, Bell 1973).
Fetch-decode-dispatch loop
the core execution cycle: read the opcode, read its operands, select and run its handler (§8.4).
Frame push/pop
the act of entering/leaving a function call by adding/removing a Frame from call_stack (§15).
Garbage collection (GC)
automatic reclamation of heap objects no longer reachable from any root (§18).
Heap object
a reference-counted-free, GC-managed value living outside the operand stack/locals, referenced via Value::Ref (§11, §17).
Immediate operand
a fixed-width value encoded directly after an opcode byte, as opposed to a constant-pool reference (§8.1).
Inline caching
caching the resolved target of a polymorphic call site to skip repeated lookup (§5, Deutsch & Schiffman 1984; deferred here per ADR-20).
Instruction-boundary bitmap
the verifier's static record of every valid instruction-start offset, used to validate jump targets (§19, I7).
Instruction pointer (ip)
the offset into a function's code of the next instruction to fetch (§11, I3).
Locals
a frame's fixed-size array of local variable slots, addressed by u8 index (§11, ADR-06).
Mark-sweep
a tracing GC algorithm: mark all reachable objects from roots, then free all unmarked objects (§18, ADR-08/21).
Mnemonic
the human-readable name for an opcode (e.g., IAdd) used in disassembly (§20).
Module
the compiled, unverified unit of functions plus a constant pool (§8.2, §11).
Operand stack
the shared value stack all frames push to and pop from during execution (§11, P5).
Opcode
the single byte identifying which instruction to execute (§8.1, ADR-03).
Register-based VM
an instruction set addressing operands via named registers rather than an implicit stack (§9 ADR-02, §31, §34).
Root set
the set of Values a GC must treat as definitely reachable: the operand stack, all live frames' locals, and the constant pool (§18, I8).
Safepoint
a well-defined point in execution where GC is permitted to run (§18, P8, ADR-22).
Stack-effect simulation
the verifier's static computation of operand-stack depth at every instruction, without executing anything (§19, I1).
Subroutine threading
a dispatch technique compiling each instruction as a call to its handler subroutine (§5, Bell 1973).
Tagged union / tagged enum
a value representation carrying an explicit type discriminant alongside its payload, as used by Value (§11, ADR-07).
Threaded code
any dispatch technique replacing a central switch with data-driven control transfer between handlers (§5, Bell 1973; §21, §34).
Trust boundary
the point past which input is assumed safe; here, the verifier's approval gate before Vm::run (§19, ADR-09, I9).
Verifier
the static analysis pass proving stack-effect balance, jump-target validity, and index bounds before execution (§19).
Verified module
a Module with verified == true, the only kind Vm::run accepts (§11, I9).
Vm
the execution engine instance owning the operand stack, call stack, heap, and GC state (§11). ---
