31 — Virtual Machine (Bytecode Interpreter) from Scratch

Project Number: 31

Project Name: Virtual Machine (Bytecode Interpreter) from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from first principles, a general-purpose stack-based bytecode virtual machine: a fixed opcode set with a constant pool, a compiler that lowers an AST into that bytecode, a fetch-decode- dispatch execution loop with call frames and a defined calling convention, a mark-sweep garbage collector for heap objects, a static bytecode verifier that gatekeeps untrusted bytecode before execution, and a disassembler/debugger for tooling. The deliverable is a four-crate Rust workspace that reproduces, at teaching scale, the architecture shared by the JVM, CPython's ceval loop, Lua's VM, and the CLR: AST → bytecode → verified module → executing VM.

Phase 0 deliverable

  1. vm-core — Opcode, Value, Module, Function, Frame, Vm execution loop (correctness kernel, ADR-01, ADR-07).
  2. vm-compiler — AST types + single-pass codegen (AST → bytecode, ADR-02).
  3. vm-stdlib — built-in functions (abs, max, min) as compiled fns.
  4. vm-cli — vmrun binary: demo runner (fib, fact, floats, print).
  5. conformance/ — per-opcode fixture harness skeleton (ADR-17).

System boundaries

  • Provides: opcode set + encoding, constant pool, call frames, execution loop, single-pass compiler, mark-sweep GC (Phase 6), static verifier (Phase 7), disassembler (Phase 8), dispatch benchmarking (Phase 9).
  • Delegates: OS process/thread scheduling, native code generation (no JIT), file I/O beyond Print/Println.
  • Does NOT provide: a textual parser, a JIT compiler, on-disk bytecode serialization, inline caching, generational/moving GC, tail-call elimination — each individually flagged PhaseDeferred below and registered at §35 with a concrete anchor.

Non-goals

Not a production language runtime. Not a JIT. Not a general-purpose scripting language product. Not a distributed or networked system — this is a single-process, embeddable execution engine.

Deployment model

Statically linked Rust library (vm-core) embedded in a host process (vm-cli demo binary or a future embedder). No daemon, no network surface, no persistence layer in Phase 0-9 scope.

Target users

Systems and language-implementation engineers studying interpreter/runtime construction: bytecode design, dispatch technique tradeoffs, calling conventions, GC integration, and bytecode safety.

Language + rationale

Rust (stable channel). Rationale: memory safety without a host GC for the implementation itself, enum-based tagged unions for Value/Opcode without unsafe bit tricks, a Cargo workspace matching the crate boundaries salvaged from the seed draft (ADR-11). Rejected: C (no safety net around tagged-union discipline — see ADR-07); C++ (header/build complexity disproportionate to scope); Zig (immature ecosystem for the conformance/fuzzing tooling needed at Phase 9).

Prerequisites

Stack machines vs. register machines; IEEE-754 floating point; two's-complement arithmetic; basic tracing garbage collection theory; AST-to-IR lowering; assembly-level calling conventions.

2. Why Build This

A bytecode VM is the load-bearing abstraction underneath every managed-language runtime in production use: the JVM (Lindholm et al., The Java Virtual Machine Specification), CPython's ceval.c, Lua's lvm.c, the CLR, and WebAssembly engines (Wasm3, wasmtime) all share the same skeleton — a compiler lowers a tree/graph IR into a flat instruction stream, and an execution loop walks that stream one instruction at a time against an operand stack or register file and a call stack of frames. Building one from scratch is the only way to internalize dispatch-technique tradeoffs (switch vs. threaded code, Bell 1973; Ertl & Gregg 2003), why Smalltalk-80 (Goldberg & Robson 1983) chose a byte-oriented stack machine over a tree-walker, why Lua moved from a stack machine to a register machine in 5.0 (Ierusalimschy, de Figueiredo & Celes 2005) and cut its average instruction count roughly in half, and why a bytecode verifier (Leroy 2003) exists as a distinct trust boundary from the compiler in the JVM but not in CPython. Cross-links: this project's Value/heap-object split is the same shape as a Garbage Collector project's root-set problem; its verifier is the same shape as a Taint Analysis Engine's static dataflow pass; its calling convention is the shape every compiler backend (register allocation, stack frame layout) targets.

What Mastery Looks Like

  • Explain why a stack-based operand model needs no register allocator in the compiler, and name the instruction-count cost that Lua's register model (Ierusalimschy et al. 2005) pays to avoid it (Phase 2, §14; Phase 4, §16).

  • Derive, from the opcode table alone, whether a given bytecode sequence can ever underflow the operand stack — the exact static analysis a verifier performs (Phase 7, §19; I1, I7).

  • Explain the difference between direct threading, indirect threading, subroutine threading, and computed-goto dispatch (Bell 1973; Ertl & Gregg 2003), and why Rust's stable channel forces ADR-01's switch/match-based choice (Phase 2, §14; Phase 9, §21).

  • Trace a function call end-to-end: argument push, Call, frame push, LoadLocal, Return, frame pop, and state the invariant that makes it safe (Phase 3, §15; I2, I5).

  • Explain why the GC's root set must include the operand stack and every live frame's locals, not just the constant pool, and what breaks if it does not (Phase 6, §18; I8).

  • Explain what a bytecode verifier proves before the first instruction executes, and why that proof is a distinct trust boundary from "the compiler already checked it" (Phase 7, §19; MM5).

  • Read a disassembly listing and reconstruct the source-level control flow (loop, branch, call) it was compiled from (Phase 8, §20).

Front End: accepts an AST directly (§1 non-goal: no textual parser). Module: the compiled, unverified artifact — flat per-function bytecode plus a deduplicated constant pool (ADR-04). Verifier: a static pass over Module proving stack-effect balance, jump-target validity, and constant-index bounds before any bytecode executes (ADR-09, I9) — the sole trust boundary between untrusted bytecode and the execution loop. Vm: owns the shared operand stack, the call stack of Frames, the heap (Phase 5+), and the tracing collector (Phase 6+); runs the fetch-decode-dispatch loop (ADR-01). Disassembler: read-only tooling sharing the verifier's bounds-checked decoder (ADR-10, T10), never a second source of truth for instruction layout.

6. Design Principles

P1 — Bytecode Is a Versioned Contract. The Module format is the stable interface between vm-compiler and vm-core; it is never informally extended. Tradeoff: every opcode addition is a compatibility event (§25). Violating it: compiler and VM silently drift, producing FM-9.

P2 — Stack Discipline Over Registers (for this project's scope). Operands live on a shared stack, not in named registers. Tradeoff: more instructions per operation than Lua's register model (Ierusalimschy et al. 2005) in exchange for a codegen pass with no register allocator. Violating it: mixing register and stack addressing in one instruction set breaks the verifier's single stack- effect model (I1).

P3 — Fixed-Width Opcode, Explicit Operand Widths. Each opcode is one byte; each opcode's immediate operands have a fixed, opcode-specific width (u8/u16/u32). Tradeoff: no LEB128 density (WebAssembly's choice) in exchange for O(1) decode. Violating it breaks the disassembler's and verifier's shared decoder (ADR-10).

P4 — Constant Pool Deduplication. Identical constants compile to one pool entry. Tradeoff: compiler must intern during codegen. Violating it wastes pool slots and risks exceeding the 65,536 u16 ceiling (§4) sooner than necessary.

P5 — Frame-per-Call, Shared Operand Stack. Each call pushes one Frame; all frames share one Vec<Value> operand stack sliced by base_sp. Tradeoff: a corrupted base_sp leaks one frame's values into another's view (FM-11) in exchange for avoiding N separate stack allocations.

P6 — Fail Loud, Never Undefined. Every fault (stack underflow, type mismatch, division by zero, OOB constant index) returns a typed VmError; none is ever a silent wrong answer or undefined behavior. Tradeoff: a per-instruction tag check (ADR-14) costs cycles the verifier could otherwise eliminate statically. Violating it converts a programming error into a security bug (T6).

P7 — Verify Before Execute. Bytecode from any source (compiler or otherwise) passes the Phase 7 verifier before Vm::run fetches its first instruction (I9). Tradeoff: verification is a second pass over the whole function body. Violating it removes the only trust boundary between untrusted bytecode and memory-safe execution (ADR-09, T2/T4/T5).

P8 — GC Safepoints at Well-Defined Points Only. The collector may run only at Call, Return, and backward Jump — never mid-instruction (ADR-22). Tradeoff: worst-case pause latency is bounded by the longest safepoint-free instruction run, not by per-instruction granularity. Violating it requires re-deriving the root set inside every opcode handler.

P9 — Dispatch Technique Chosen by Measurement. The Phase 2 dispatch loop starts as match (switch) dispatch (ADR-01) and is only replaced if Phase 9 benchmarks (M1) show a measured, not assumed, win — per Ertl & Gregg (2003), the "obviously faster" technique varies by compiler and CPU. Violating it means shipping a dispatch rewrite with no measured justification.

P10 — One Canonical Disassembly Format. The disassembler (Phase 8) and any future trace/debug tooling render instructions identically; there is exactly one textual mnemonic table (ADR-10). Violating it produces divergent debug output that cannot be diffed against itself.

P11 — No Hidden Global Mutable State. All execution state lives in one Vm instance (operand_stack, call_stack, heap); no static/thread-local interpreter state. Tradeoff: every call site must thread a &mut Vm. Violating it makes multiple concurrent Vm instances (ADR-15) unsafe to run in the same process.

P12 — Deterministic Numeric Semantics. Integer arithmetic is checked (overflow → VmError, ADR-14); float arithmetic is IEEE-754 double, no fast-math flags. Tradeoff: checked-arith overhead on every IAdd/ISub/IMul. Violating it makes fib/fact conformance fixtures (§13, §26) non-reproducible across builds.

P13 — Deferred Features Get a Registered Anchor. Any capability out of Phase 0-9 scope is flagged PhaseDeferred with a concrete section anchor and appears in §35 with a building phase and an un-defer trigger; it is never silently dropped. Violating it hides scope decisions from the record this document is.

8. Domain Model / Protocol / Data Model

8.1 Bytecode encoding

Instruction := Opcode:u8 [Operand]*
Operand widths are opcode-specific, one of: u8, u16, u32 (little-endian)

Example — LoadLocal (u8 slot) followed by IAdd (no operand):
  offset  bytes        mnemonic
  0x00    0x10 0x00    LoadLocal 0
  0x02    0x10 0x01    LoadLocal 1
  0x04    0x20         IAdd
  0x05    0x40         Return

8.2 Module layout

Module {
  constants: Vec<Constant>          ; Constant = Int(i64) | Float(f64) | Str(String)
  functions: Vec<Function>          ; indexed by u16 function index (ADR-16)
}
Function {
  name: String
  arity: u8
  local_count: u8
  max_stack: u16                    ; computed by compiler + confirmed by verifier (I1)
  code: Vec<u8>
}

8.3 Worked example — compiling fn add(a, b) { return a + b; }

Step AST node Emitted bytecode
1 param a → slot 0, param b → slot 1 (no emission; arity=2, local_count=2)
2 a (Identifier) LoadLocal 0
3 b (Identifier) LoadLocal 1
4 a + b (BinaryOp Add) IAdd
5 return a + b; Return

Resulting code: [LoadLocal 0, LoadLocal 1, IAdd, Return], max_stack = 2 (peak depth after step 3, before IAdd consumes both operands).

8.4 Execution-loop state machine

State Entry condition Action Next state
Fetch frame active, ip valid (I3) read Opcode byte at ip Decode
Decode opcode fetched read fixed-width operands, advance ip Dispatch
Dispatch operands decoded match on opcode (ADR-01) → handler Execute
Execute handler selected mutate operand stack / locals / ip Safepoint-check
Safepoint-check at Call/Return/backward-Jump only (P8) run GC if heap threshold crossed Fetch
Halt Halt opcode executed return top-of-stack as program result terminal
Fault any VmError raised unwind call stack, return error terminal

8.5 Malformed-input example

Adversarial bytecode: Jump 0x03 where offset 0x03 falls inside the 2-byte operand of a preceding LoadLocal instruction (mid-instruction jump target). The Phase 7 verifier's instruction-boundary bitmap (I7) flags offset 0x03 as "not an instruction start" and rejects the module with VerifyError::JumpTargetInvalid — the fault never reaches the execution loop.

8.6 Failure-path example

Bytecode [LoadLocal 0, IAdd, Return] with only one push before IAdd (which needs two operands). The verifier's static stack-effect simulation (I1) computes a stack depth of 1 immediately before IAdd, which requires depth ≥ 2, and rejects with VerifyError::StackEffectMismatch before any instruction executes — no runtime underflow is possible on verified bytecode.

11. Core Schema & Types

enum Opcode {                     // 1 byte discriminant, ADR-03
  PushInt(i64), PushFloat(f64), PushTrue, PushFalse, PushNull,
  LoadConst(u16),                 // constant-pool load, ADR-04
  Pop, Dup,
  LoadLocal(u8), StoreLocal(u8),  // ADR-06
  IAdd, ISub, IMul, IDiv, IMod, INeg,
  FAdd, FSub, FMul, FDiv, FNeg,
  CmpEq, CmpNe, CmpLt, CmpLe, CmpGt, CmpGe,
  And, Or, Not,
  Jump(u32), JumpIf(u32), JumpNot(u32),
  Call(u16), Return,              // ADR-16
  IntToFloat, FloatToInt,
  Print, Println,
  Halt,
}
enum Value {                      // ADR-07: tagged enum, no NaN-boxing
  Int(i64), Float(f64), Bool(bool), Null,
  Ref(HeapRef),                   // Phase 5+, points into Heap
}

enum Constant { Int(i64), Float(f64), Str(String) }   // pool entry, distinct from Value

struct HeapRef(u32);               // opaque index into Heap, no raw pointers exposed

enum HeapObject { Str(String) }    // Phase 5 scope; Array/Map deferred (§35)

struct GcHeader { mark: bool, size: u32 }   // Phase 6, ADR-21 non-moving mark-sweep
struct Function {
  name: String, arity: u8, local_count: u8,
  max_stack: u16,                 // computed by compiler, confirmed by verifier (I1)
  code: Vec<u8>,
}

struct Module { constants: Vec<Constant>, functions: Vec<Function>, verified: bool }  // I9

struct Frame { func_index: u16, ip: u32, locals: Vec<Value>, base_sp: u32 }  // ADR-05, P5
struct Vm {
  operand_stack: Vec<Value>, call_stack: Vec<Frame>,
  module: Module, heap: Heap, gc: GcState,            // heap/gc from Phase 5/6
}

enum VmError {                     // ADR-13, P6
  StackUnderflow, StackOverflow, TypeMismatch { expected: &'static str, found: &'static str },
  DivisionByZero, ConstantPoolOob, ArityMismatch, NotVerified,
  VerificationFailed(VerifyError), OutOfMemory, MalformedBytecode, NativeCallPanic,
}

enum VerifyError {                 // ADR-09, §19
  JumpTargetInvalid, StackEffectMismatch, ConstIndexOob, ArityMismatch, UnreachableCode,
}
struct DisassembledInstr {         // §20, ADR-10, shared decoder
  offset: u32, mnemonic: &'static str, operands: Vec<i64>, resolved_const: Option<String>,
}

Ownership: Vm owns Module, Heap, GcState exclusively (P11 — no hidden global state). Concurrency: single-threaded per Vm instance (ADR-15). Serialization: none in Phase 0-9 scope (ADR-19); all types are in-memory only.

14.1 Objectives

  • Implement the full fetch-decode-dispatch loop (§8.4 state machine) for all non-call, non-jump opcodes.

14.2 Detailed Implementation Steps

  1. Implement the Fetch → Decode → Dispatch → Execute loop per §8.4, one match arm per opcode (ADR-01).

  2. Implement operand-stack push/pop with a debug-mode depth assertion against max_stack (I1) and a release-mode guard that returns VmError::StackOverflow/StackUnderflow rather than panicking (P6).

  3. Implement Dup/Pop and confirm they interact correctly with the depth guard from step 2.

  4. Wire I6's tag check into every arithmetic/comparison/logical opcode handler — read the operand, confirm its Value tag, else VmError::TypeMismatch.

  5. Apply Ertl's stack-caching insight (Ertl 1995, §5) as a documented future optimization opportunity — not implemented this phase (measured, not assumed, per P9); record as a Phase 9 candidate.

  6. Add per-opcode dispatch counters (ADR-24 telemetry) for later use in §21/§28 benchmarking.

  7. Extend fixtures (14.5) exercising stack depth at its exact max_stack boundary.

14.3 Deliverable

A complete dispatch loop for all opcodes except Call/Return/Jump/JumpIf/JumpNot (deferred to Phase 3/4), passing all Phase 0/1 fixtures plus this phase's stack-discipline fixtures.

14.4 Acceptance Criteria

14.6 Pitfalls

  • Implementing Call/Jump "just to test the loop" — out of scope until frames (Phase 3) and compiler codegen (Phase 4) exist; keeps this phase within the 40-120 line ceiling.

  • Skipping the debug-mode depth assertion because the release-mode guard "already covers it" — the assertion catches compiler/verifier bugs earlier and more cheaply (P7's spirit extended to internal invariants).

15. Phase 3 — Call Frames & Calling Convention

15.1 Objectives

  • Implement Call/Return and the Frame push/pop discipline per §11 and the calling convention in §8.3/ADR-05.

  • Confirm the shared-operand-stack, base_sp-sliced frame model (P5) end-to-end.

15.2 Detailed Implementation Steps

  1. Implement Call(fn_index): pop arity arguments left-to-right per ADR-05, verify arity == callee.arity (I10), push a new Frame with locals[0..arity) = args, remaining locals Null (§8.3).

  2. Implement call-depth guard before frame push: reject with VmError::StackOverflow if call_stack.len() >= max_call_depth (I5, §4, T3).

  3. Implement Return: leave top-of-operand-stack as the return value, pop the current frame, restore the caller's ip/base_sp (P5).

  4. Implement base_sp slicing so a callee's Pop/Dup/arithmetic never observes the caller's operand-stack contents below base_sp (I2, P5) — a debug-mode assertion enforces this boundary.

  5. Wire recursive self-calls (needed for fib/fact per §1's "done" definition) through the same Call path — no special-casing recursion.

  6. Extend VmError usage: ArityMismatch (I10) on mismatched call-site argument count.

  7. Extend fixtures (15.5) with fib/fact recursive-call fixtures per §1's Done criterion.

16. Phase 4 — Control Flow, Jumps & Compiler Codegen

16.1 Objectives

  • Implement Jump/JumpIf/JumpNot in the execution loop.

  • Implement vm-compiler's single-pass AST-to-bytecode codegen: let, assignment, if/else, while, expression statements, binary/unary operators (ADR-02, P2).

  • Implement forward-jump patching for if/while codegen.

16.2 Detailed Implementation Steps

  1. Implement Jump(target)/JumpIf(target)/JumpNot(target) in Vm::run: absolute u32 byte offset into the current function's code (P3, §8.1).

  2. Implement vm-compiler::ast: Program { functions: Vec<FnDecl> }, Stmt (Let, Assign, Return, If, While, ExprStmt), Expr (literals, identifiers, binary/unary ops, calls) — signatures only, per Aho et al. Ch. 8 (§5) code-generation patterns.

  3. Implement a pre-scan pass assigning each FnDecl a u16 function index before codegen, enabling forward calls (Nystrom 2021, §5) — same technique the seed draft's compiler already used.

  4. Implement per-function codegen: a FnCtx tracking a locals table (name → u8 slot) and a CodeBuilder emitting opcodes + patching forward-jump placeholders (patch_u32, per the salvaged seed-draft technique).

  5. Implement if/else codegen: condition → JumpNot(else_label) → then-block → Jump(end_label) → else-block, with both labels backpatched (ADR-02).

  6. Implement while codegen: loop-top label → condition → JumpNot(end_label) → body → Jump(loop_top) → end-label backpatched — note the backward Jump(loop_top) is a GC safepoint (P8, ADR-22).

  7. Extend fixtures (16.5) with if/while/nested-control-flow programs compiled end-to-end from AST.

16.3 Deliverable

A working vm-compiler producing verified-shape bytecode from AST input, and a Vm executing if/while-bearing programs correctly, including backward jumps hitting GC safepoints.

16.4 Acceptance Criteria

  • if_else.json: AST for if (x > 0) { return 1; } else { return -1; } compiles and both branches execute correctly for x = 5 and x = -5.

  • while_loop.json: AST for a summing while loop over 1..100 compiles and returns 4950.

  • forward_call.json: a function calling another function declared later in the AST compiles and executes correctly (pre-scan pass, step 3).

  • Empty if branch ({}) — must still emit a valid (possibly zero-instruction) block with correct jump targets around it.

  • while (false) { ... } — body never executes; loop-top jump still compiles correctly (dead code is not eliminated in this scope, out of Phase 0-9 optimization scope).

  • Deeply nested if/while (10+ levels) — backpatch bookkeeping must not leak or mis-associate labels across nesting levels.

16.9 Failure Analysis

Maps to FM-9 (dispatch table desync) if a codegen bug emits an opcode/operand pairing the decode table (Phase 1) doesn't expect — caught by dispatch_all_opcodes.json-style fixtures re-run against compiler output, not just hand-written bytecode.

16.10 Operational Notes

The compiler produces Function.max_stack via the same stack-effect simulation the Phase 7 verifier will independently re-derive (I1) — this phase's codegen and Phase 7's verifier must never diverge on this computation; a shared helper is the single source of truth (P1).

17. Phase 5 — Heap Objects, Strings & Reference Types

17.1 Objectives

  • Introduce Value::Ref(HeapRef) and HeapObject (starting with Str, per §11 and domain guidance's scope).

  • Implement a Heap allocator (no reclamation yet — GC lands Phase 6) with GcHeader bookkeeping.

  • Extend the constant pool and LoadConst to intern Str constants onto the heap at module-load time.

17.2 Detailed Implementation Steps

  1. Implement HeapRef(u32) as an opaque index into Heap's backing storage — no raw pointers exposed outside vm-core (ADR-07's safety discipline extended to heap objects).

  2. Implement Heap { objects: Vec<Option<(GcHeader, HeapObject)>> } — a slot-indexed arena; freed slots become None starting Phase 6 (I13: every allocation reachable from exactly one owning slot at allocation time).

  3. Implement module-load-time interning: every Constant::Str becomes one heap HeapObject::Str allocation, referenced by a Value::Ref pushed on LoadConst (extends Phase 1's LoadConst without changing its opcode encoding).

  4. Extend CmpEq/CmpNe to support Value::Ref string comparison (value equality on the underlying String, not HeapRef identity) — document this as the chosen semantics (a design choice, not yet an ADR row since it doesn't reach the ≥20-row bar as a distinct decision, but recorded here for terminology lock).

  5. Extend Print/Println to render Value::Ref(Str) as the string's contents, not its HeapRef index.

  6. Extend fixtures (17.5) with string literal, string comparison, and string print programs.

  7. Document in docs/adr/ that array/map heap types are PhaseDeferred("§17") (§35) — this phase ships Str only, per the domain-guidance scope boundary.

17.3 Deliverable

Value::Ref-backed string constants: literals, comparison, and printing all work correctly with no reclamation yet (that is Phase 6's job).

17.4 Acceptance Criteria

  • string_literal.json: a Str("hello") constant loads and prints as hello, not a HeapRef index.

  • string_eq.json: two distinct heap allocations holding equal string contents compare equal via CmpEq (value semantics, not identity).

  • heap_growth_unbounded.json (documented expectation only, not yet enforced): heap grows without bound in this phase — Phase 6 is required before the §4 256 MiB ceiling is enforced.

17.5 Conformance Fixtures

Fixture Assertion
string_literal.json Str("hello") constant prints as hello
string_eq.json two heap-distinct equal strings compare equal via CmpEq
string_dedup_pool.json identical string constants in one module share one pool entry (P4)
print_ref_value.json Println on a Value::Ref never prints a raw HeapRef index

17.6 Pitfalls

  • Printing HeapRef's internal u32 instead of resolving through Heap — a debugging-experience regression, not a safety bug, but violates P10's "one canonical" rendering discipline extended to runtime print output.

  • Comparing Value::Ref by HeapRef identity instead of contents — breaks the intuitive semantics a source-language user expects from == on strings.

  • Allocating a new heap object for every LoadConst of the same string constant instead of interning once at module load — defeats P4's dedup principle at the heap layer.

17.7 Performance Concerns

Heap allocation is currently unbounded and never reclaimed (Phase 6 adds reclamation); this phase does not yet gate on M11 (heap allocation rate) — that gate activates once Phase 6's GC exists to respond to allocation pressure.

17.8 Edge Cases

  • Empty string constant (Str("")) — must intern and compare correctly like any other string.

  • Very large string constant near a size that would matter for the future §4 heap ceiling — no special casing yet, but the fixture documents the boundary for Phase 6.

  • Two identical strings originating from different modules (out of scope: this project has one module per Vm instance, so this edge case does not arise — documented here to close the question, not deferred).

17.9 Failure Analysis

Maps to FM-4 (GC root-scan miss / use-after-free) only once Phase 6 exists; this phase's own failure mode is unbounded heap growth, which is an expected, documented limitation (17.4) rather than a defect — it becomes FM-5 territory (heap exhaustion) only after Phase 6's ceiling is wired.

17.10 Operational Notes

heap_alloc_total (I13 telemetry) begins incrementing this phase with no corresponding free counter until Phase 6 — operators should expect monotonic heap growth as the correct behavior for this phase alone, not a leak signal yet.

18. Phase 6 — Garbage Collection Integration

18.1 Objectives

  • Implement a non-moving mark-sweep collector (ADR-08, ADR-21) over Heap.

  • Implement root-set enumeration covering the operand stack, every live frame's locals, and the constant pool (I8).

  • Wire GC safepoints at Call/Return/backward-Jump only (P8, ADR-22).

18.2 Detailed Implementation Steps

  1. Implement GcState { threshold: usize, bytes_allocated: usize } tracking allocation pressure against the §4 256 MiB ceiling.

  2. Implement the mark phase: walk roots (operand stack, every Frame.locals, Module.constants) and transitively mark reachable HeapObjects via their GcHeader.mark bit (I8, Bacon et al. 2004's root-set correctness requirement).

  3. Implement the sweep phase: scan Heap.objects, free (None) every unmarked slot, reset all mark bits for the next cycle (ADR-21 non-moving, free-list reuse of freed slots).

  4. Wire the safepoint check into Call/Return/backward-Jump handlers only (P8, ADR-22) — triggering a GC cycle when bytes_allocated > threshold.

  5. Extend VmError with OutOfMemory (T8): if a GC cycle does not free enough to satisfy a pending allocation and the heap is at the §4 ceiling, allocation fails closed.

  6. Add debug-build canary-pattern writes to freed slots to make use-after-free detectable in tests (I8 detection column).

  7. Extend fixtures (18.5) exercising root-set completeness (values reachable only via a deep call stack must survive a GC cycle).

18.3 Deliverable

A working mark-sweep collector that reclaims unreachable string objects without corrupting any value reachable from the stack, frames, or constant pool, running only at documented safepoints.

18.4 Acceptance Criteria

  • gc_reclaims_unreachable.json: an unreachable string allocation is freed after one GC cycle (heap byte count decreases).

  • gc_preserves_reachable_deep.json: a string held only in a locals slot 20 call-frames deep survives a GC cycle triggered mid-recursion.

  • gc_pause_p99.json (informal at this phase, formalized as M4 in §21/§28): GC pause stays under the §4 5 ms p99 target at a 64 MiB live set on reference hardware.

18.5 Conformance Fixtures

Fixture Assertion
gc_reclaims_unreachable.json unreachable heap object freed after one cycle
gc_preserves_reachable_deep.json value 20 frames deep survives a GC cycle (I8)
gc_preserves_operand_stack.json value only on the operand stack (not yet stored to a local) survives
gc_safepoint_only_at_call_return_jump.json no GC cycle runs mid-instruction (P8, ADR-22)
oom_at_ceiling.json allocation past the 256 MiB ceiling after a failed GC cycle returns VmError::OutOfMemory

18.6 Pitfalls

  • Missing the operand stack from the root set (only scanning frame locals) — the single most common tracing-GC bug class (I8); gc_preserves_operand_stack.json exists specifically to catch this.

  • Running a GC cycle at an arbitrary instruction instead of only at the three documented safepoints (P8) — breaks the bounded-pause-latency argument in ADR-22.

  • Forgetting to reset GcHeader.mark bits after sweep, causing the next cycle's mark phase to see stale marks and under-collect.

18.7 Performance Concerns

M4 (GC pause p99) is formally gated starting §21/§28; this phase's mark phase is O(live set), sweep phase is O(heap slot count) — Wilson (1992, §5) documents this as mark-sweep's characteristic tradeoff against copying GC's O(live set)-only sweep cost (§29, §34 alternative).

18.8 Edge Cases

  • A GC cycle triggered with zero live heap objects — sweep phase must complete without error, not assume at least one object exists.

  • A value stored in a local slot that is later overwritten (StoreLocal to the same slot) before a GC cycle — the old value must not be treated as still-reachable from that slot.

  • Recursive fib/fact (Phase 3 fixtures) triggering a GC cycle mid-recursion — every frame's locals in the entire call stack, not just the topmost frame, must be scanned (I8).

18.9 Failure Analysis

Maps to FM-4 (GC root-scan miss / use-after-free) directly — detection via the debug-build canary pattern (18.2 step 6) and the gc_preserves_reachable_deep.json/gc_preserves_operand_stack.json fixtures; also maps to FM-5 (heap exhaustion) via oom_at_ceiling.json.

18.10 Operational Notes

gc_use_after_free_detected (I8 telemetry) must be zero in every CI run; a nonzero count blocks release per §26/§27. heap_bytes_used (T8 telemetry) feeds the §24 dashboard alongside GC cycle count and pause duration.

19. Phase 7 — Bytecode Verifier & Safety Checks

19.1 Objectives

  • Implement the static verifier (ADR-09) proving, before any execution: stack-effect balance (I1), jump-target validity (I7), constant-index bounds (I4), and arity consistency (I10).

  • Set Module.verified = true only on a fully passing verification (I9) and gate Vm::run on it.

  • Ensure the verifier and disassembler (Phase 8) share one decoder (P10, ADR-10).

19.2 Detailed Implementation Steps

  1. Implement an instruction-boundary bitmap per function: one static pass over code recording every valid instruction-start offset (I7's enforcement mechanism, per Leroy 2003's verification algorithm shape).

  2. Implement static stack-effect simulation: walk the instruction stream (respecting all jump edges, not just fallthrough) tracking stack depth at each point; reject if any point's depth would go negative or exceed max_stack (I1), or if two control-flow paths reach one instruction with different simulated depths (Leroy 2003's merge-point consistency rule).

  3. Implement jump-target validation against the boundary bitmap from step 1 (I7) — reject any Jump/JumpIf/JumpNot target that is not a recorded instruction start.

  4. Implement constant-index bounds checking for every LoadConst operand against Module.constants.len() (I4).

  5. Implement arity consistency checking for every Call operand against the target function's declared arity (I10) — this is the static counterpart to Phase 3's dynamic runtime check.

  6. Implement reachability checking: every function must end in a Return or Halt on every control-flow path reachable from entry, or the verifier rejects with VerifyError:: UnreachableCode/incomplete-path (I11).

  7. Set Module.verified = true only if every function passes all five checks; wire Vm::run's entry guard (I9) to refuse unverified modules with VmError::NotVerified.

  8. Extend fixtures (19.5) with the conformance/invalid/ malformed-bytecode corpus, one fixture per rejection reason.

19.3 Deliverable

A verifier that accepts every fixture produced by vm-compiler (Phases 1-4) and rejects every hand-crafted malformed-bytecode fixture in conformance/invalid/, with Vm::run refusing to execute anything the verifier has not approved.

19.4 Acceptance Criteria

  • 100% of conformance/valid/ fixtures (Phases 0-6) pass verification unchanged.

  • 100% of conformance/invalid/ fixtures are rejected with the documented VerifyError variant.

  • Vm::run on an unverified Module (bypassing Verifier::verify) returns VmError::NotVerified in 100% of attempts, never executes instruction 0.

19.5 Conformance Fixtures

Fixture Assertion
verify_all_valid_fixtures.json every Phase 0-6 valid fixture passes verification unchanged
invalid/bad_jump_target.json jump into a multi-byte operand rejected (I7, §8.5)
invalid/stack_underflow_static.json statically-detectable underflow rejected (I1, §8.6)
invalid/const_index_oob.json out-of-range LoadConst index rejected (I4)
invalid/arity_mismatch_static.json Call with wrong static argument count rejected (I10)
invalid/unreachable_return.json a control-flow path missing a terminal Return/Halt rejected (I11)
unverified_run_refused.json Vm::run on verified == false returns VmError::NotVerified (I9)

19.6 Pitfalls

  • Only checking the fallthrough path's stack effect and skipping jump-target paths — the classic verifier gap (Leroy 2003 explicitly calls out merge-point consistency for exactly this reason).

  • Treating verification as a compiler-only concern and skipping the Vm::run entry guard (I9) — removes the trust boundary the entire phase exists to establish (ADR-09).

  • Sharing most but not all of the decoder logic with Phase 8's disassembler — any divergence reintroduces the class of bug P10 exists to prevent.

19.7 Performance Concerns

M5 (verifier throughput floor, §4: ≥50M opcodes/sec) is formally gated starting §21/§28; the stack- effect simulation is O(instructions) with one pass per function (no fixed-point iteration needed because this instruction set has no irreducible control flow by construction — codegen, Phase 4, never emits it).

19.8 Edge Cases

  • A function with zero instructions (degenerate empty body) — must be rejected (no terminal Return/Halt, I11), not silently accepted as trivially valid.

  • A jump target equal to code.len() (one past the end) — must be rejected as not an instruction start, even though it is a valid array index for other purposes.

  • Two merge-point paths reaching the same jump target with equal simulated stack depth — must be accepted; only unequal merge depths are a rejection (I1's precise boundary).

19.9 Failure Analysis

Maps to FM-8 (verifier false negative — bad bytecode admitted) directly; detection is the conformance/invalid/ corpus achieving 100% rejection (19.4) plus differential testing against the Phase 2-4 execution loop's own dynamic guards (I1/I4/I7/I10 dynamic checks must never fire on verified bytecode — if they do, that is itself evidence of a verifier false negative, §26).

19.10 Operational Notes

verifier_reject_total{reason=...} (I1/I4/I7/I10 telemetry columns) is the primary operational signal for a misbehaving upstream compiler or an attempted adversarial-bytecode load; a nonzero rate in a trusted-compiler-only deployment is itself an incident (§22/§24).

21. Phase 9 — Performance: Dispatch Tuning, Backlog Measurement & Benchmarking

21.1 Objectives

  • Formally gate M1-M11 (§28) in CI on reference hardware.

  • Measure match dispatch (ADR-01) against at least one alternative technique to resolve P9's "measured, not assumed" mandate.

  • Produce the recorded baseline that any future inline-caching or JIT work (ADR-20, PhaseDeferred) would need to beat.

21.2 Detailed Implementation Steps

  1. Implement benchmarks/ wall-clock micro-benchmarks for M1 (dispatch overhead/instruction), M2 (fib(30) wall time), M3 (call overhead), M9 (constant-pool lookup latency) — no external benchmarking crate invented beyond what ADR-24's telemetry already provides plus std::time.

  2. Implement an experimental computed-goto-style alternative dispatch path behind a feature flag, strictly for measurement (P9) — per Ertl & Gregg (2003) and Romer et al. (1996)'s methodology of comparing dispatch techniques on identical hardware.

  3. Record M1 results for both dispatch paths; per P9, only promote the alternative to the default if it measurably beats the §4 3 ns/instruction ceiling by a documented margin — otherwise match dispatch (ADR-01) remains locked.

  4. Implement M4 (GC pause p99) and M11 (heap allocation rate) benchmarks exercising Phase 6's collector under sustained allocation pressure.

  5. Implement M5 (verifier throughput) and M6 (disassembler throughput) benchmarks over the full conformance/valid/ corpus.

  6. Implement M7 (startup time) and M8 (frame memory overhead) benchmarks.

  7. Wire all M1-M11 targets into CI as a perf-regression gate (§26/§28): a build failing any target by more than a documented tolerance fails CI.

  8. Document, per ADR-20, that inline caching remains deferred — this phase's data (call-site monomorphism is total in this instruction set; there is no polymorphic dispatch to cache) is the evidence closing that question rather than leaving it open.

21.3 Deliverable

A CI-gated performance suite covering M1-M11, a resolved dispatch-technique decision (measured, not assumed), and a documented closure of the inline-caching question for this instruction set's scope.

21.4 Acceptance Criteria

  • All eleven M1-M11 targets (§28) pass on reference hardware in CI.

  • The dispatch-technique decision (match vs. measured alternative) is recorded in docs/adr/ with the actual measured numbers, not a qualitative claim.

  • fib(30) (M2) completes within the documented target with the locked, measured dispatch technique.

21.5 Conformance Fixtures

Fixture Assertion

bench_fib30_m2.rs fib(30) wall time ≤ M2 target

perf_regression_gate.rs CI fails if any M1-M11 target regresses beyond documented tolerance

21.6 Pitfalls

  • Benchmarking on a noisy/shared CI runner and treating the result as authoritative — Ertl & Gregg's (2003) own methodology insists on isolated, repeated measurement.

  • Promoting the experimental dispatch path (21.2 step 2) on a marginal, noise-level improvement, violating P9's "measurable, documented margin" bar.

  • Conflating M2 (fib(30) wall time, an end-to-end proxy) with M1 (per-instruction dispatch overhead, a micro-metric) when diagnosing a regression — they can move independently.

21.7 Performance Concerns

This entire phase is the performance-concerns phase; every M1-M11 target in §28 is defined, measured, and CI-gated here. No further performance work is in scope for Phase 0-9; JIT compilation and inline caching remain PhaseDeferred per ADR-20/§35.

  • A benchmark that passes on the author's machine but fails the documented CI tolerance on the reference hardware profile — the CI result is authoritative, not the local run (§27 reproducible- build discipline extended to benchmarking).

  • GC pause measurement (M4) taken mid-benchmark vs. at benchmark start — must exclude any warmup- phase GC cycle from the p99 calculation to avoid skew.

21.9 Failure Analysis

Maps to no single FM class directly; a regression here is a leading indicator that manifests later as FM-1 (call-depth exhaustion under load) or FM-5 (heap exhaustion) if M2/M4 regress silently without this phase's CI gate catching it first.

21.10 Operational Notes

Dashboards: (1) verifier rejection rate by reason, (2) GC pause p50/p99 and cycle frequency, (3) call-depth and heap-usage headroom against §4 ceilings, (4) native-call panic rate.

SLOs: verifier throughput ≥ M5 target; GC pause p99 ≤ M4 target; zero gc_use_after_free_detected events in any release build.

Runbooks: "Verifier rejection spike" (§22 T1/T2/T4/T5 correlation, check upstream compiler version) — "GC pause regression" (§28 M4, bisect against §21 baseline) — "Heap ceiling approaching" (§4/T8, review allocation-heavy fixtures, consider raising the configured ceiling).

Backup/restore: not applicable — no persistent state (ADR-19, in-memory only per Vm instance); a crashed embedder simply restarts a fresh Vm.

Deployment topology: embedded library, one Vm instance per logical execution context, no shared mutable state across instances (ADR-15, P11).

Canary/rollback/migration: a new vm-core release is canaried by running the full conformance/ corpus (valid + invalid) plus the M1-M11 perf gate (§21) before promotion; rollback is a Cargo version pin revert (§25/§27).

25. Compatibility & Versioning

Bytecode format versioning: the opcode encoding (§8.1, P3/ADR-03) is versioned implicitly by the vm-core crate's SemVer major version; a breaking opcode change (width, meaning, or removal) is a major-version bump.

Module compatibility: Module produced by one vm-compiler minor version must load and verify correctly against any vm-core release sharing the same major version (P1's "versioned contract").

API stability: vm-core's public Vm/Module/Function/Value/VmError types follow Rust SemVer conventions; adding a new VmError variant is a minor-version-compatible additive change (non-exhaustive enum discipline) per ADR-13.

Opcode deprecation: an opcode is never silently repurposed; deprecation is a documented ADR superseding an existing ADR-03-family row, with the old opcode value reserved (never reused) for at least one major version.

Rolling-upgrade guarantees: not applicable in this embedded, single-process deployment model (§1); a future networked/persisted extension (ADR-19's deferred file format) would need to define this explicitly before shipping.

Deferred persistence versioning: once PhaseDeferred("§25")'s on-disk bytecode format lands, it requires its own magic-number + version-field scheme (comparable to .class's major/minor version fields, Lindholm et al. §5) — not designed yet, flagged here so the un-defer trigger in §35 is explicit.

26. Testing & Verification Strategy

Unit tests: per-opcode handler correctness (Phase 0-4 fixtures), per-verifier-check correctness (Phase 7 fixtures), tied directly to I1-I13.

Integration tests: full AST → compile → verify → execute pipelines (fib_recursive.json, while_loop.json), tied to Phase 3/4 deliverables.

Property-based testing: randomized stack-effect-neutral instruction sequences checked against the verifier's static simulation matching the execution loop's dynamic depth at every point (I1 cross-check between Phase 2's dynamic guard and Phase 7's static one).

Differential testing: verifier's static stack-depth computation vs. the compiler's own max_stack computation (16.10) must never diverge — any divergence is a build-blocking test failure.

Fuzzing: cargo-fuzz targets over the verifier's decoder (T1/T2/T5) and over raw byte streams fed directly to Verifier::verify — the primary defense against T1-T5 threat-model classes beyond the hand-written conformance/invalid/ corpus.

Chaos/fault injection: forced native-stdlib-panic injection to confirm the ADR-23 catch-unwind boundary converts every panic to a VmError (T9/FM-10).

Deterministic replay: any VmError-returning execution is replayable from the same Module + initial arguments — no hidden global state (P11) makes this trivially true by construction; a regression test asserts it.

Soak testing: sustained allocation-and-recursion workload for 1 hour+ confirming gc_use_ after_free_detected stays zero and heap_bytes_used stays bounded (Phase 6/9 fixtures at scale).

Conformance: the conformance/valid/ + conformance/invalid/ corpora (per-phase §N.5 tables) are the canonical conformance suite; 100% pass is a release gate (§27).

Perf-regression gating: M1-M11 (§21/§28) enforced in CI with documented tolerances; any regression beyond tolerance blocks merge.

Reproducible builds: Cargo.lock committed, rust-toolchain.toml pins the exact toolchain version (§10); cargo build --locked in CI and release pipelines.

Signing: release binaries (the vm-cli demo binary) signed with a project GPG key; checksums published alongside each GitHub release.

SBOM: cargo-cyclonedx generates a Software Bill of Materials per release, auditing every transitive dependency (T11).

Release channels: main (unreleased), tagged SemVer releases per §25's versioning policy; no nightly/beta channel — stable Rust only (ADR-11).

29. Scalability Analysis

Constant regardless of program size: dispatch cost per instruction (M1); constant-pool lookup (M9, O(1) Vec index); local-variable access (O(1) slot index, ADR-06).

Grows with program size: verifier pass time (O(instructions), M5); disassembly time (O(instructions), M6); compiled bytecode size (O(AST nodes), M10).

Grows with runtime behavior: call-stack depth (O(recursion depth), bounded by §4's 1,024 ceiling); heap live-set size (O(live allocations), drives GC pause per M4); operand-stack depth (O(expression nesting), bounded by §4's 4,096 ceiling).

Named bottlenecks, in order: (1) dispatch overhead (M1) — the per-instruction tax paid by every program; (2) GC pause (M4) — grows with live-set size, the dominant cost under allocation-heavy workloads; (3) native-call boundary (ADR-23's catch-unwind) — fixed per-call overhead on top of M3; (4) constant-pool lookup (M9) — negligible in isolation but compounds at high LoadConst density.

Horizontal scaling: not applicable to a single Vm instance; the unit of horizontal scale-out is the process running many independent Vm instances (shared-nothing, ADR-15) — no inter-instance coordination exists or is needed.

Vertical scaling: single-threaded execution loop per instance (ADR-15) means vertical scaling (more cores) does not speed up one program's execution; it only increases the number of concurrent Vm instances a host can run.

Practical ceiling: single-instruction-stream throughput bound by host CPU IPC and branch- prediction accuracy on the dispatch match (M1) — Ertl & Gregg (2003) document this ceiling as inherent to any switch/threaded-dispatch interpreter, only escaped by a JIT (PhaseDeferred("§21")).

Levers beyond the ceiling: JIT compilation, inline caching (ADR-20), a register-based instruction set (§34), superinstructions combining common opcode pairs — all out of Phase 0-9 scope, registered in §35.

30. Mental Models & First Principles

MM1 — "Bytecode is a contract, not an implementation detail." Predicts that any opcode-meaning change is a compatibility event, not a refactor. Without it: engineers silently repurpose an opcode and break every previously-compiled Module. Resolves in §25 / P1.

MM2 — "The interpreter loop is a state machine over (ip, stack, frame), nothing more." Predicts that any bug must be traceable to one of those three pieces of state at one instruction boundary. Without it: engineers add hidden state (P11 violation) and debugging becomes non-reproducible. Resolves in §8.4 / §14.

MM3 — "Every dispatch is a branch-prediction problem before it is an algorithm problem." Predicts that match dispatch's cost is CPU-microarchitecture-dependent, not a fixed constant — per Ertl & Gregg (2003). Without it: engineers "optimize" dispatch without measuring, violating P9. Resolves in §14 / §21.

MM4 — "GC correctness is root-enumeration correctness, full stop." Predicts that every use-after-free bug traces to a missed root, never to the mark or sweep algorithm itself being wrong. Without it: engineers debug the wrong half of the collector. Resolves in §18 / I8.

MM5 — "A verifier is a proof-checker for a proof the compiler already computed." Per Leroy (2003): the verifier re-derives the same stack-effect proof the compiler's codegen implicitly relied on, independently. Without it: engineers treat verification as redundant with compilation and skip it, collapsing the trust boundary ADR-09 exists to draw. Resolves in §19 / ADR-09.

MM6 — "Register machines trade instruction count for register-allocation complexity." Per Ierusalimschy et al. (2005): a register VM is not "just faster," it moves cost from the dispatch loop into the compiler. Without it: engineers assume a register rewrite is a free performance win. Resolves in §14 / §31 / §34.

MM7 — "Threaded code turns dispatch into data." Per Bell (1973): direct/indirect threading replaces a decision (match/switch) with a memory read of the next handler's address. Without it: engineers cannot reason about why threaded dispatch's cost profile differs from switch dispatch's. Resolves in §21 / §34.

MM8 — "Stack depth is a static property when control flow is structured." The verifier's stack-effect simulation (I1) is only decidable in one static pass because this instruction set's codegen (Phase 4) never emits irreducible control flow. Without it: engineers would assume a fixed-point iteration is always required, over-engineering the verifier. Resolves in §19 / I1.

CPython made the opposite verifier decision from the JVM: it trusts its own compiler entirely and performs no bytecode verification, because .pyc files are treated as trusted artifacts of the same toolchain that will run them — a niche this project's ADR-09 explicitly rejects for bytecode of uncertain provenance. Lua 5.4 made the opposite operand-model decision (ADR-02): its register-based instructions cut instruction count roughly in half versus a stack machine (Ierusalimschy et al. 2005), winning in embedded/scripting contexts where every dispatch cycle on a slow host CPU matters. HotSpot made the opposite dispatch decision: generating real machine code per opcode (template interpreter) eliminates dispatch overhead entirely at the cost of per-architecture assembly maintenance — it wins when the JVM's install base justifies that maintenance cost across every supported ISA. Wasm3 made the same stack-based, no-JIT choice this project makes for its interpreter tier, but wins in a different niche: it is a portable, embeddable interpreter for an already-verified, already-standardized bytecode format (WebAssembly) rather than a from-scratch teaching instruction set.

32. Back-of-Envelope Capacity Model

  1. Max instructions addressable per function: 64 KiB code ceiling (§4) ÷ 1 byte/opcode minimum = 65,536 instructions worst case (all zero-operand opcodes); realistic average with 1-2 byte operands ≈ 20,000-30,000 instructions/function.

  2. Max call depth from native stack budget: assume an 8 MiB OS thread stack, ~200 bytes of native stack frame per Vm::run recursive dispatch call (if the loop itself recurses on nested calls) → 8 MiB / 200 B ≈ 41,000 theoretical max; §4's documented 1,024 ceiling is chosen with a 40x safety margin, not the hardware limit itself.

  3. Max operand stack memory: 4,096 slots (§4) × 24 bytes/Value (tag + 8-byte payload, ADR-07) ≈ 96 KiB per Vm instance for the operand stack alone.

  4. Frame memory at max call depth: M8's ≤128 B fixed + local_count * 24 B, worst case 256 locals (§4 ADR-06 ceiling) → ~6,272 B/frame × 1,024 max frames ≈ 6.4 MiB call-stack memory ceiling.

  5. GC pause budget derivation: M4 target 5 ms p99 at 64 MiB live set (§4) → implies a required mark-phase throughput of ≥ 64 MiB / 5 ms ≈ 12.8 GB/sec of live-object graph traversal, a sanity check against M11's 5M allocs/sec target (each mark-phase visit is cheaper than an allocation).

  6. Verifier pass cost at startup: M7's 10 ms startup target (§4) for a 10 KiB module ÷ M5's 50M opcodes/sec floor → 10 KiB / ~2 bytes/opcode average = 5,000 opcodes → 5,000 / 50M/sec = 0.1 ms, leaving 9.9 ms of the 10 ms budget for module parsing/loading overhead, not verification.

  7. Constant pool max memory footprint: 65,536 entries (§4 u16 ceiling) × worst case 32 bytes/ Constant (a Str with inline small-string storage) ≈ 2 MiB worst-case pool size per module.

  8. Bytecode density vs. AST: M10's ≤4 bytes/AST-node target implies a 10,000-node AST program compiles to ≤ 40 KB of bytecode, comfortably inside the 64 KiB per-function ceiling for any single function under ~16,000 AST nodes.

  9. Dispatch throughput ceiling from M1: M1's ≤3 ns/instruction target implies a theoretical ceiling of ~333M instructions/sec single-threaded; M2's fib(30) (~2.7M calls, each ~10 instructions ≈ 27M instructions) at that ceiling would take ~81 ms, comfortably inside M2's 150 ms target with headroom for call overhead (M3).

  10. Heap ceiling exhaustion time under M11's allocation rate: §4's 256 MiB heap ceiling ÷ an average 64-byte HeapObject::Str allocation ≈ 4M live objects max; at M11's 5M allocs/sec with zero reclamation, exhaustion would occur in <1 second — confirming Phase 6's GC (not merely a ceiling check) is load-bearing, not optional, under any sustained allocation workload.

33. Hard Questions (Self-Examination)

  1. Why is a shared operand stack across all frames (P5) safe, given that a callee's Pop could in principle underflow into the caller's region — what exactly prevents this? (§15, §19, I1, I2)

  2. What specific property of this instruction set's codegen (not the verifier) makes the Phase 7 stack-effect simulation decidable in one static pass, without fixed-point iteration? (§16, §19, MM8)

  3. If the verifier (§19) and the compiler (§16) independently compute max_stack and disagree, which one is "right," and what does that disagreement actually indicate? (§16.10, §26)

  4. Why does the GC's root set (§18, I8) need to include the operand stack, not just frame locals — construct a concrete program where omitting it causes a use-after-free. (§17, §18, FM-4)

  5. Why is match/switch dispatch (ADR-01) not simply "slower" than computed goto — under what measured conditions (§21) would the reverse be true, per Ertl & Gregg (2003)? (§14, §21, MM3)

  6. What does Lua's move to a register-based VM (Ierusalimschy et al. 2005) actually save, and why does this project's scope (§1) make that saving not worth the compiler complexity it costs? (§9 ADR-02, §31, §34)

  7. Why is a bytecode verifier (§19) a meaningful trust boundary when the only producer of bytecode in this project's scope is its own compiler (§16) — what threat model justifies it anyway? (§9 ADR-09, §22)

  8. Trace exactly what happens, state-by-state (§8.4), when a Call opcode's argument count does not match the callee's arity, from dispatch through to the returned VmError. (§15, §19, I10)

  9. Why is GC safepoint placement restricted to Call/Return/backward-Jump (P8, ADR-22) rather than every instruction — what would break, and what would the pause-latency tradeoff become, if it were every instruction? (§18, §28 M4)

  10. What is the actual difference between "the verifier rejects malformed bytecode" (§19) and "the runtime guards reject malformed bytecode" (§14) — why does this project need both rather than just the cheaper one? (§14, §19, P6, P7)

  11. Why does interning Str constants once at module-load time (§17) rather than on every LoadConst execution matter for correctness, not just performance? (§11, §17, P4)

  12. Construct a program whose compiled bytecode passes the Phase 7 verifier but whose execution still triggers a documented VmError at runtime — is this a verifier bug, or expected behavior? Justify from first principles. (§19, §23 FM-7/FM-8)

  13. Why is heap allocation rate (M11) meaningfully bounded by GC pause latency (M4) rather than by raw allocator throughput — walk the causal chain. (§18, §28, §32)

  14. What concrete evidence would justify un-deferring inline caching (ADR-20, §35) for this instruction set, given that its current call sites are statically monomorphic? (§9 ADR-20, §21, §35)

  15. Why does this project's single-threaded-per-instance concurrency model (ADR-15) not simply mean "no concurrency support" — what is the actual scaling story for a host running many Vm instances? (§29, §9 ADR-15)

  16. If the disassembler (§20) and the execution loop (§14) ever disagree about what a given byte sequence means, which one is definitionally wrong, and how would you prove it? (§20, P10, §23 FM-9)

  17. Why is checked integer arithmetic (ADR-14, P12) a correctness requirement rather than a performance nicety, given that this is a from-scratch teaching VM with no untrusted numeric input beyond the bytecode itself? (§9 ADR-14, §12, T6)

  18. Walk through exactly how a value stored in local slot 3 of a frame 15 calls deep in a recursive fib computation survives a GC cycle triggered by an allocation in the 16th call — name every piece of state the collector must visit. (§15, §18, I8)

34. Alternative Architectures (Roads Not Taken)

Register-based bytecode.

[Stack VM]                    [Register VM]
LoadLocal 0  ; push a         ADD r2, r0, r1   ; r2 = a + b, one instruction
LoadLocal 1  ; push b
IAdd         ; pop,pop,push
StoreLocal 2 ; pop, store

Wins in throughput-sensitive embedded/scripting deployments where dispatch-cycle count dominates — the real system embodying it is Lua 5.0+ (Ierusalimschy, de Figueiredo & Celes 2005), which halved average instruction count versus its own prior stack-based design. Rejected here (ADR-02) because this project's scope (§1) prioritizes a codegen pass with no register allocator over raw dispatch throughput — the pedagogical value of a simple compiler outweighs the performance win at this project's scale.

Template/JIT interpreter (generated machine code per opcode).

dispatch table: [opcode] -> pointer to generated native code stub
execution: jump directly into generated code, no interpretive decode step

Wins in high-install-base production runtimes where per-architecture assembly maintenance cost is justified by aggregate throughput gains across billions of executions — the real system is OpenJDK HotSpot's template interpreter. Rejected here (§9 ADR-01/ADR-11) because it requires per-target assembly generation entirely out of a from-scratch, portable, stable-Rust teaching project's scope.

Direct AST-walking tree interpreter (no bytecode at all).

eval(node):
  match node { BinaryOp(op, l, r) -> apply(op, eval(l), eval(r)), ... }

Wins in implementation simplicity and fast time-to-first-execution for small scripting embeddings — the real system is pre-1.9 CRuby (MRI), which walked the AST directly. Rejected here because CRuby's own history is the counter-argument: Ruby 1.9 replaced the tree-walker with YARV, a compiled stack-bytecode VM, precisely because AST-walking could not compete on performance and because this project's explicit purpose (§2) is to teach bytecode design, which a tree-walker has none of.

Indirect/subroutine-threaded code (Forth-style, GNU-extension-dependent).

handler table: [opcode] -> code-address; NEXT: fetch, indirect-jump to handler, handler ends with
                                          a jump back to NEXT (no central switch)

Wins on architectures/compilers without good switch-to-jump-table optimization, where a labels-as- values / computed-goto extension turns dispatch into a data-driven jump chain — the real systems are classic Forth implementations and Smalltalk-80's original virtual machine (Goldberg & Robson 1983). Rejected here (ADR-01, ADR-11) because it relies on the GNU C "labels as values" extension with no equivalent in stable Rust, directly conflicting with §1's language rationale.

36. Glossary

AST — Abstract Syntax Tree; the tree-shaped source representation accepted directly as this VM's compiler input (§1).

Arity — the declared number of parameters a function accepts; checked both statically (§19) and dynamically (§15).

Backward jump — a Jump/JumpIf/JumpNot whose target offset is less than the current ip; the designated GC safepoint location besides Call/Return (P8).

Base pointer (base_sp) — the operand-stack index below which a Frame may not read or pop (§11, P5).

Bytecode — the flat, linear instruction stream a Function executes; the compiled form of an AST (§8).

Call frame (Frame) — the per-invocation record holding a function's locals, instruction pointer, and operand-stack base (§11).

Calling convention — the fixed protocol for how arguments, return values, and control transfer between caller and callee (§8.3, ADR-05).

Computed goto — a dispatch technique using labels-as-values to jump directly to a handler address, bypassing a central switch (§34, Bell 1973).

Conformance fixture — a named, checked-in input/expected-output pair proving one specific behavior (§26).

Constant pool — the per-module deduplicated table of literal values referenced by index from bytecode (§8.2, ADR-04).

Dispatch — the step that maps a decoded opcode to the code that executes it (§8.4, ADR-01).

Direct threading — a dispatch technique where each instruction slot directly holds the address of its handler (§5, Bell 1973).

Fetch-decode-dispatch loop — the core execution cycle: read the opcode, read its operands, select and run its handler (§8.4).

Frame push/pop — the act of entering/leaving a function call by adding/removing a Frame from call_stack (§15).

Garbage collection (GC) — automatic reclamation of heap objects no longer reachable from any root (§18).

Heap object — a reference-counted-free, GC-managed value living outside the operand stack/locals, referenced via Value::Ref (§11, §17).

Immediate operand — a fixed-width value encoded directly after an opcode byte, as opposed to a constant-pool reference (§8.1).

Inline caching — caching the resolved target of a polymorphic call site to skip repeated lookup (§5, Deutsch & Schiffman 1984; deferred here per ADR-20).

Instruction-boundary bitmap — the verifier's static record of every valid instruction-start offset, used to validate jump targets (§19, I7).

Instruction pointer (ip) — the offset into a function's code of the next instruction to fetch (§11, I3).

Locals — a frame's fixed-size array of local variable slots, addressed by u8 index (§11, ADR-06).

Mark-sweep — a tracing GC algorithm: mark all reachable objects from roots, then free all unmarked objects (§18, ADR-08/21).

Mnemonic — the human-readable name for an opcode (e.g., IAdd) used in disassembly (§20).

Module — the compiled, unverified unit of functions plus a constant pool (§8.2, §11).

Operand stack — the shared value stack all frames push to and pop from during execution (§11, P5).

Opcode — the single byte identifying which instruction to execute (§8.1, ADR-03).

Register-based VM — an instruction set addressing operands via named registers rather than an implicit stack (§9 ADR-02, §31, §34).

Root set — the set of Values a GC must treat as definitely reachable: the operand stack, all live frames' locals, and the constant pool (§18, I8).

Safepoint — a well-defined point in execution where GC is permitted to run (§18, P8, ADR-22).

Stack-effect simulation — the verifier's static computation of operand-stack depth at every instruction, without executing anything (§19, I1).

Subroutine threading — a dispatch technique compiling each instruction as a call to its handler subroutine (§5, Bell 1973).

Tagged union / tagged enum — a value representation carrying an explicit type discriminant alongside its payload, as used by Value (§11, ADR-07).

Threaded code — any dispatch technique replacing a central switch with data-driven control transfer between handlers (§5, Bell 1973; §21, §34).

Trust boundary — the point past which input is assumed safe; here, the verifier's approval gate before Vm::run (§19, ADR-09, I9).

Verifier — the static analysis pass proving stack-effect balance, jump-target validity, and index bounds before execution (§19).

Verified module — a Module with verified == true, the only kind Vm::run accepts (§11, I9).

Vm — the execution engine instance owning the operand stack, call stack, heap, and GC state (§11).
