⬜ Phase 0 — Repo Skeleton, Value Representation & Correctness Kernel §12

Objectives

  • Stand up the Cargo workspace with all four crates (§10) building green in CI.

  • Implement Value, Constant, Opcode (integer/float/bool/null subset only — no Ref/heap yet), Module, Function, Frame per §11.

  • Implement a minimal Vm::run covering PushInt, PushFloat, arithmetic, Return, Halt — the correctness kernel.

  • Seed docs/adr/ with ADR-01, ADR-02, ADR-07, ADR-11, ADR-18.

Deliverable

A Cargo workspace compiling on stable Rust; a Vm capable of executing straight-line arithmetic bytecode (no calls, no branches) and returning a correct Value.

Acceptance

  • cargo test --workspace returns 0.

  • arith_smoke.json fixture: [PushInt 2, PushInt 3, IAdd, Return] evaluates to Int(5).

  • Division by zero on IDiv returns VmError::DivisionByZero, not a panic.

Fixtures
Fixture Assertion
arith_smoke.json 2 + 3 == 5 via PushInt/IAdd/Return
float_smoke.json 2.5 * 4.0 == 10.0 via PushFloat/FMul/Return
div_zero.json IDiv by zero returns VmError::DivisionByZero
underflow.json IAdd with one prior push returns VmError::StackUnderflow
Pitfalls

  • Reaching for unsafe/bit-tricks for Value before measuring any need (ADR-07) — resist until Phase 9 data justifies it.

  • Wiring Call/Jump opcodes early "for completeness" — out of Phase 0 scope (deferred to Phase 3/4), inflates this phase's line budget past the 40-120 line ceiling (§16's H7 rule).

  • Skipping checked-arithmetic wiring "for now" — retrofitting it after Phase 4's compiler exists is a breaking change to every fixture (P12).

⬜ Phase 1 — Opcode Set, Constant Pool & Bytecode Format §13

Objectives

  • Complete the full Opcode enum per §11 (comparisons, logical ops, conversions, I/O, LoadConst).

  • Implement the constant pool (Module.constants: Vec<Constant>) with compile-time deduplication (P4, ADR-04).

  • Freeze the bytecode encoding: 1-byte opcode + fixed-width operands (P3, ADR-03), matching §8.1.

Deliverable

A frozen, documented bytecode encoding (§8.1) with a constant pool, full non-control-flow opcode set, and a shared decode table ready for Phase 2's dispatch loop and Phase 8's disassembler.

Acceptance

  • const_pool_dedup.json fixture: two identical Str("x") constants compile to one pool entry.

  • LoadConst with an out-of-range index returns VmError::ConstantPoolOob (I4), never a panic.

  • All opcodes added this phase have at least one fixture in conformance/valid/.

Fixtures
Fixture Assertion
const_pool_dedup.json duplicate constants collapse to one pool slot (P4)
cmp_ops.json CmpLt/CmpGe etc. produce correct Bool for int and float operands
logical_ops.json And/Or/Not short-circuit-free truth table matches spec
conv_ops.json IntToFloat/FloatToInt round correctly at boundary values
const_oob.json LoadConst 9999 on a 2-entry pool returns VmError::ConstantPoolOob
Pitfalls

  • Letting the decode table drift between vm.rs and a future disasm.rs — P10 mandates one shared table from this phase forward.

  • Implicit numeric coercion in comparison opcodes — violates I6 and produces silent wrong answers instead of a typed error.

  • Growing the constant pool past u16 range untested — the verifier (Phase 7) must catch this, but a fixture should exist here too (13.5).

⬜ Phase 2 — Stack-Based Execution Loop & Dispatch §14

Objectives

  • Implement the full fetch-decode-dispatch loop (§8.4 state machine) for all non-call, non-jump opcodes.

  • Lock the dispatch technique to match-based switch dispatch (ADR-01, P9), instrumented so Phase 9 can measure alternatives.

  • Establish the operand-stack push/pop discipline and its bounds guard (I1).

Deliverable

A complete dispatch loop for all opcodes except Call/Return/Jump/JumpIf/JumpNot (deferred to Phase 3/4), passing all Phase 0/1 fixtures plus this phase's stack-discipline fixtures.

Acceptance

  • stack_depth_boundary.json: a sequence reaching exactly max_stack succeeds; one more push returns VmError::StackOverflow.

  • dispatch_all_opcodes.json: every non-control-flow opcode has at least one passing fixture.

  • Dispatch loop overhead measured (informally, formal gate in §21) at this phase to establish a Phase 9 baseline.

Fixtures
Fixture Assertion
stack_depth_boundary.json push to exactly max_stack succeeds; one more overflows (I1)
dup_pop_roundtrip.json Dup then Pop leaves stack depth unchanged
type_mismatch.json IAdd on (Int, Bool) returns VmError::TypeMismatch (I6)
dispatch_all_opcodes.json every Phase 0/1 opcode dispatches to the correct handler
Pitfalls

  • Implementing Call/Jump "just to test the loop" — out of scope until frames (Phase 3) and compiler codegen (Phase 4) exist; keeps this phase within the 40-120 line ceiling.

  • Skipping the debug-mode depth assertion because the release-mode guard "already covers it" — the assertion catches compiler/verifier bugs earlier and more cheaply (P7's spirit extended to internal invariants).

  • Premature dispatch-technique switching (computed goto via an unsafe extension) before Phase 9 measurement — violates P9 directly.

⬜ Phase 3 — Call Frames & Calling Convention §15

Objectives

  • Implement Call/Return and the Frame push/pop discipline per §11 and the calling convention in §8.3/ADR-05.

  • Enforce arity checking (I10) and call-depth bounding (I5, T3).

  • Confirm the shared-operand-stack, base_sp-sliced frame model (P5) end-to-end.

Deliverable

Full support for direct (non-forward-reference-dependent) function calls including recursion, with arity- and depth-checked Call/Return.

Acceptance

  • fib_recursive.json: fib(10) == 55 via direct recursive Call.

  • fact_recursive.json: fact(10) == 3628800 via direct recursive Call.

  • call_depth_exceeded.json: unbounded recursion returns VmError::StackOverflow at exactly max_call_depth (§4), never a native stack overflow / process crash (T3).

Fixtures
Fixture Assertion
fib_recursive.json fib(10) == 55
fact_recursive.json fact(10) == 3628800
arity_mismatch.json calling a 2-arity function with 1 argument returns VmError::ArityMismatch
call_depth_exceeded.json recursion past max_call_depth returns VmError::StackOverflow, no crash
base_sp_isolation.json callee's Pop cannot underflow into caller's operand-stack region
Pitfalls

  • Forgetting to restore the caller's ip on Return, corrupting the caller's fetch loop (maps to FM-11).

  • Allowing a callee to Pop past its base_sp boundary in release builds without a guard — the debug assertion (15.2 step 4) must have a release-mode equivalent returning VmError, not just a debug-only check (P6).

  • Off-by-one in max_call_depth comparison (>= vs >) silently permitting one frame past the documented §4 ceiling.

⬜ Phase 4 — Control Flow, Jumps & Compiler Codegen §16

Objectives

  • Implement Jump/JumpIf/JumpNot in the execution loop.

  • Implement vm-compiler's single-pass AST-to-bytecode codegen: let, assignment, if/else, while, expression statements, binary/unary operators (ADR-02, P2).

  • Implement forward-jump patching for if/while codegen.

Deliverable

A working vm-compiler producing verified-shape bytecode from AST input, and a Vm executing if/while-bearing programs correctly, including backward jumps hitting GC safepoints.

Acceptance

  • if_else.json: AST for if (x > 0) { return 1; } else { return -1; } compiles and both branches execute correctly for x = 5 and x = -5.

  • while_loop.json: AST for a summing while loop over 1..100 compiles and returns 4950.

  • forward_call.json: a function calling another function declared later in the AST compiles and executes correctly (pre-scan pass, step 3).

Fixtures
Fixture Assertion
if_else.json both branches of an if/else execute correctly
while_loop.json summing loop 1..100 returns 4950
forward_call.json calling a function declared later in source compiles and runs
nested_control_flow.json while containing if compiles with correct jump targets
jump_patch_boundary.json a jump target exactly at function end patches correctly
Pitfalls

  • Unpatched forward-jump placeholders left as 0x00000000 reaching the verifier (Phase 7) — must be caught by this phase's own fixtures, not deferred to the verifier.

  • Off-by-one in backward-jump target computation (loop_top pointing one instruction early/late).

  • Forgetting that the backward while jump is a GC safepoint (P8) — irrelevant until Phase 6 exists but must be documented now so Phase 6 doesn't need a codegen change.

⬜ Phase 5 — Heap Objects, Strings & Reference Types §17

Objectives

  • Introduce Value::Ref(HeapRef) and HeapObject (starting with Str, per §11 and domain guidance's scope).

  • Implement a Heap allocator (no reclamation yet — GC lands Phase 6) with GcHeader bookkeeping.

  • Extend the constant pool and LoadConst to intern Str constants onto the heap at module-load time.

Deliverable

Value::Ref-backed string constants: literals, comparison, and printing all work correctly with no reclamation yet (that is Phase 6's job).

Acceptance

  • string_literal.json: a Str("hello") constant loads and prints as hello, not a HeapRef index.

  • string_eq.json: two distinct heap allocations holding equal string contents compare equal via CmpEq (value semantics, not identity).

  • heap_growth_unbounded.json (documented expectation only, not yet enforced): heap grows without bound in this phase — Phase 6 is required before the §4 256 MiB ceiling is enforced.

Fixtures
Fixture Assertion
string_literal.json Str("hello") constant prints as hello
string_eq.json two heap-distinct equal strings compare equal via CmpEq
string_dedup_pool.json identical string constants in one module share one pool entry (P4)
print_ref_value.json Println on a Value::Ref never prints a raw HeapRef index
Pitfalls

  • Printing HeapRef's internal u32 instead of resolving through Heap — a debugging-experience regression, not a safety bug, but violates P10's "one canonical" rendering discipline extended to runtime print output.

  • Comparing Value::Ref by HeapRef identity instead of contents — breaks the intuitive semantics a source-language user expects from == on strings.

  • Allocating a new heap object for every LoadConst of the same string constant instead of interning once at module load — defeats P4's dedup principle at the heap layer.

⬜ Phase 6 — Garbage Collection Integration §18

Objectives

  • Implement a non-moving mark-sweep collector (ADR-08, ADR-21) over Heap.

  • Implement root-set enumeration covering the operand stack, every live frame's locals, and the constant pool (I8).

  • Wire GC safepoints at Call/Return/backward-Jump only (P8, ADR-22).

Deliverable

A working mark-sweep collector that reclaims unreachable string objects without corrupting any value reachable from the stack, frames, or constant pool, running only at documented safepoints.

Acceptance

  • gc_reclaims_unreachable.json: an unreachable string allocation is freed after one GC cycle (heap byte count decreases).

  • gc_preserves_reachable_deep.json: a string held only in a locals slot 20 call-frames deep survives a GC cycle triggered mid-recursion.

  • gc_pause_p99.json (informal at this phase, formalized as M4 in §21/§28): GC pause stays under the §4 5 ms p99 target at a 64 MiB live set on reference hardware.

Fixtures
Fixture Assertion
gc_reclaims_unreachable.json unreachable heap object freed after one cycle
gc_preserves_reachable_deep.json value 20 frames deep survives a GC cycle (I8)
gc_preserves_operand_stack.json value only on the operand stack (not yet stored to a local) survives
gc_safepoint_only_at_call_return_jump.json no GC cycle runs mid-instruction (P8, ADR-22)
oom_at_ceiling.json allocation past the 256 MiB ceiling after a failed GC cycle returns VmError::OutOfMemory
Pitfalls

  • Missing the operand stack from the root set (only scanning frame locals) — the single most common tracing-GC bug class (I8); gc_preserves_operand_stack.json exists specifically to catch this.

  • Running a GC cycle at an arbitrary instruction instead of only at the three documented safepoints (P8) — breaks the bounded-pause-latency argument in ADR-22.

  • Forgetting to reset GcHeader.mark bits after sweep, causing the next cycle's mark phase to see stale marks and under-collect.

⬜ Phase 7 — Bytecode Verifier & Safety Checks §19

Objectives

  • Implement the static verifier (ADR-09) proving, before any execution: stack-effect balance (I1), jump-target validity (I7), constant-index bounds (I4), and arity consistency (I10).

  • Set Module.verified = true only on a fully passing verification (I9) and gate Vm::run on it.

  • Ensure the verifier and disassembler (Phase 8) share one decoder (P10, ADR-10).

Deliverable

A verifier that accepts every fixture produced by vm-compiler (Phases 1-4) and rejects every hand-crafted malformed-bytecode fixture in conformance/invalid/, with Vm::run refusing to execute anything the verifier has not approved.

Acceptance

  • 100% of conformance/valid/ fixtures (Phases 0-6) pass verification unchanged.

  • 100% of conformance/invalid/ fixtures are rejected with the documented VerifyError variant.

  • Vm::run on an unverified Module (bypassing Verifier::verify) returns VmError::NotVerified in 100% of attempts, never executes instruction 0.

Fixtures
Fixture Assertion
verify_all_valid_fixtures.json every Phase 0-6 valid fixture passes verification unchanged
invalid/bad_jump_target.json jump into a multi-byte operand rejected (I7, §8.5)
invalid/stack_underflow_static.json statically-detectable underflow rejected (I1, §8.6)
invalid/const_index_oob.json out-of-range LoadConst index rejected (I4)
invalid/arity_mismatch_static.json Call with wrong static argument count rejected (I10)
invalid/unreachable_return.json a control-flow path missing a terminal Return/Halt rejected (I11)
unverified_run_refused.json Vm::run on verified == false returns VmError::NotVerified (I9)
Pitfalls

  • Only checking the fallthrough path's stack effect and skipping jump-target paths — the classic verifier gap (Leroy 2003 explicitly calls out merge-point consistency for exactly this reason).

  • Treating verification as a compiler-only concern and skipping the Vm::run entry guard (I9) — removes the trust boundary the entire phase exists to establish (ADR-09).

  • Sharing most but not all of the decoder logic with Phase 8's disassembler — any divergence reintroduces the class of bug P10 exists to prevent.

⬜ Phase 8 — Disassembler, Debugger & Tooling §20

Objectives

  • Implement disasm.rs's DisassembledInstr output sharing Phase 1's decode table and Phase 7's instruction-boundary bitmap (P10, ADR-10, T10).

  • Implement a vm-cli disasm subcommand rendering a full function's bytecode as human-readable text.

  • Implement constant-pool resolution in disassembly output (resolved string/int/float values, not raw pool indices).

Deliverable

A vmrun disasm subcommand producing deterministic, constant-resolved, human-readable disassembly for any verified Module, sharing its decoder with the Phase 7 verifier.

Acceptance

  • disasm_golden.json: disassembling the fib_recursive fixture (Phase 3) produces output byte-for-byte identical across two independent runs (I12).

  • Every opcode category in §11 (stack, locals, arithmetic, comparison, logical, jumps, calls, conversions, I/O, control) appears at least once in conformance/valid/disasm_* fixtures.

  • vm-cli disasm on an unverified Module returns an error, not a decode attempt (mirrors I9's spirit — T10).

Fixtures
Fixture Assertion
disasm_golden.json disassembly is byte-for-byte reproducible across runs (I12)
disasm_const_resolution.json LoadConst renders the resolved constant, not a bare index
disasm_all_categories.json every §11 opcode category appears in disassembly output
disasm_refuses_unverified.json disassembling an unverified Module is refused (T10)
Pitfalls

  • Writing a second, "quick" decoder for the disassembler instead of reusing Phase 1/7's shared table — the exact drift P10/T10 exist to prevent.

  • Rendering raw pool indices instead of resolved constants — technically correct but defeats the human-readability goal this phase exists for.

  • Allowing disassembly of unverified bytecode "just for debugging" — reopens the OOB/malformed- input classes (T10) that Phase 7 closed for execution.

⬜ Phase 9 — Performance: Dispatch Tuning, Backlog Measurement & Benchmarking §21

Objectives

  • Formally gate M1-M11 (§28) in CI on reference hardware.

  • Measure match dispatch (ADR-01) against at least one alternative technique to resolve P9's "measured, not assumed" mandate.

  • Produce the recorded baseline that any future inline-caching or JIT work (ADR-20, PhaseDeferred) would need to beat.

Deliverable

A CI-gated performance suite covering M1-M11, a resolved dispatch-technique decision (measured, not assumed), and a documented closure of the inline-caching question for this instruction set's scope.

Acceptance

  • All eleven M1-M11 targets (§28) pass on reference hardware in CI.

  • The dispatch-technique decision (match vs. measured alternative) is recorded in docs/adr/ with the actual measured numbers, not a qualitative claim.

  • fib(30) (M2) completes within the documented target with the locked, measured dispatch technique.

Fixtures
Fixture Assertion
bench_dispatch_m1.rs dispatch overhead per instruction ≤ M1 target
bench_fib30_m2.rs fib(30) wall time ≤ M2 target
bench_gc_pause_m4.rs GC pause p99 ≤ M4 target at 64 MiB live set
bench_verifier_throughput_m5.rs verifier throughput ≥ M5 target
perf_regression_gate.rs CI fails if any M1-M11 target regresses beyond documented tolerance
Pitfalls

  • Benchmarking on a noisy/shared CI runner and treating the result as authoritative — Ertl & Gregg's (2003) own methodology insists on isolated, repeated measurement.

  • Promoting the experimental dispatch path (21.2 step 2) on a marginal, noise-level improvement, violating P9's "measurable, documented margin" bar.

  • Conflating M2 (fib(30) wall time, an end-to-end proxy) with M1 (per-instruction dispatch overhead, a micro-metric) when diagnosing a regression — they can move independently.
