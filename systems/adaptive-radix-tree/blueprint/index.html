403 — Adaptive Radix Tree (ART) + Trie Family

Goal: Implement, from scratch in Rust, an in-memory ordered-index library covering the trie family and culminating in the Adaptive Radix Tree — a baseline 256-way trie, a compressed radix/PATRICIA tree with path compression, and the ART with four adaptive inner node types (Node4/Node16/Node48/Node256), header prefixes (pessimistic + optimistic), lazy expansion, SIMD node dispatch (Node16 via SSE), and a lock-free-read concurrent variant using Optimistic Lock Coupling with epoch-based reclamation. Order-preserving binary-comparable key encoding makes it a true ordered index supporting point get/insert/delete, range scan, prefix scan, and ordered iteration, benchmarked against BTreeMap and HashMap. It is the in-memory index primitive, not a durable storage engine.

1. Goal

Build a production-grade, from-scratch, in-memory ordered index library in Rust progressing through the full trie family — baseline 256-way trie → radix/PATRICIA with path compression → the Adaptive Radix Tree (ART) with adaptive node types, SIMD dispatch, and a concurrent lock-free-read variant — exposing all operations over order-preserving binary-comparable keys so it functions as a true range/prefix-capable ordered map, not merely a hash-map substitute.

Engineering definition

  • What it is: an embeddable in-memory index library, Art<V>, implementing the OrderedMap<V> trait; keys are byte strings produced by KeyEnc (order-preserving encoding of u64/i64/f64/str/composite); operations: point get/insert/remove, range(lo, hi), prefix_iter(prefix), ordered iteration (successor/predecessor).
  • Core structure progression:
    1. Trie256 — baseline 256-way per-byte trie; establishes height + memory baselines.
    2. RadixTree — compressed edge labels + split-on-mismatch path compression; Patricia binary-radix variant.
    3. Art<V> — adaptive inner nodes (Node4 / Node16 / Node48 / Node256) + Leaf + NodeHeader prefix; pessimistic + optimistic path compression; lazy expansion; grow/shrink transitions.
    4. art-simd — Node16 key search via _mm_cmpeq_epi8 + movemask; scalar fallback.
    5. ArtOlc<V> — Optimistic Lock Coupling (OLC); per-node Version counters; lock-free reads; restart-on-conflict; epoch-based reclamation (Ebr).
  • Key invariant: memcmp(KeyEnc(a), KeyEnc(b)) == cmp(a, b) — byte-wise traversal order equals logical order; range/prefix scans are correct without extra comparison logic.
  • Height bound: O(key_len) in bytes, not O(n); u64 keys ≤ 8 levels.
  • Memory bound: node size proportional to actual fanout (Node4 ~ 56 B, Node256 ~ 2 KB); avoids the 256-pointer-per-node waste of a flat trie.

  • Precise control over struct layout (repr(C), field ordering) for cache-line packing.

Why ART matters historically and architecturally

  • HyPer (TU Munich) adopted ART as its primary index structure; DuckDB ships an ART implementation for ordered scans on primary keys and secondary indices — it is production-proven at large scale.
  • The 2013 ICDE paper benchmarked ART against B+-trees, hash tables, a red-black tree, and a judy array on both integer and string keys; ART wins on memory and latency for main-memory workloads.
  • ART unifies two orthogonal ideas — (1) radix decomposition giving O(key_len) height and order-preserving iteration, (2) adaptive fanout giving memory proportional to density — that B-trees and hash tables address separately and incompletely.
  • For IP routing (longest-prefix match), ART is a natural replacement for the classical Lulea/DIR-24-8 structures; for autocomplete / dictionary workloads, prefix_iter is native, not an afterthought.

Engineering muscles built

  • cache-aware layout: reasoning about sizeof(Node4) = ~56 B, cache-line packing, arena fragmentation.
  • unsafe-behind-safe-API discipline: NodePtr raw pointer wrapped in safe find_child/add_child; miri-clean.
  • SIMD: intrinsic-level programming without C; cfg-gated fallback; cycle-accurate benchmarking.
  • lock-free concurrency: OLC is simpler than full lock-free but subtler than coarse locking; version counters, memory ordering, restart-on-conflict — transferable to any optimistic concurrency scheme.
  • differential testing at the trait level: OrderedMap abstraction lets Trie256, Art, and ArtOlc all be property-tested against BTreeMap with the same harness.

Calibration value

  • Builds intuition for why DuckDB chose ART over a B-tree for its main-memory index: height, cache efficiency, memory proportionality.
  • Demonstrates that "ordered map" and "hash map" are not equivalent even in main memory — ordered iteration, range, and prefix require ART-style structure.
  • The OLC + EBR concurrency section is directly applicable to any optimistic concurrent data structure (HTM, MVCC, lock-free skip-lists).

What Mastery Looks Like

  • Phase 1 — KeyEnc authorship: Given an arbitrary type (e.g., a signed 128-bit integer or a UUID), you can derive its order-preserving byte encoding from first principles, prove the memcmp invariant, and identify the edge cases (NaN, negative zero, composite ambiguity) before writing a single test.
  • Phase 5 — Node-type transition design: You can state precisely why the four node types exist (not three, not five), derive the grow/shrink thresholds from the fanout distribution in the 2013 ICDE paper, and predict which node type dominates a given key-distribution workload.
  • Phase 6 — Prefix compression tradeoffs: You can explain, without consulting code, why optimistic prefix requires a full leaf key, why MAX_PREFIX_LEN=8 was chosen, and what failure mode each shortcut produces — then audit a prefix-split implementation for the three canonical bugs.
  • Phase 9 — SIMD intrinsic-level reasoning: You can translate the _mm_cmpeq_epi8 + movemask + tzcnt pipeline into cycle counts on a Skylake core, identify when SIMD overhead exceeds scalar benefit (num_children < 4), and write the scalar fallback from the same spec without referencing the SIMD version.
  • Phase 11 — OLC correctness argument: Given a concurrent traversal scenario (concurrent insert causing a Node4→Node16 grow), you can trace the version-counter sequence, identify the exact instruction window where a reader can observe an inconsistent state, and confirm that check_or_restart closes it.
  • Phase 12 — EBR epoch reasoning: You can derive the minimum number of epochs needed for safe reclamation (three), explain why two is insufficient, and identify the class of workloads (long-pinned threads) that defeat EBR's reclamation progress guarantee.
  • Phase 13 — Differential test design: You can identify which properties of OrderedMap cannot be expressed as a single BTreeMap comparison (e.g., prefix iteration semantics) and design a faithful oracle for each.
  • Cross-cutting — cache-line arithmetic: Given any node type, you can predict its L1/L2 miss budget per lookup, reason about alignment-padding choices, and estimate the memory-footprint ratio between ART and BTreeMap for a given key distribution without running code.

Component responsibilities

art-core

  • Key(Vec<u8>) — logical key; KeyEnc trait — encode(&self, out: &mut Vec<u8>); order-preserving contract.
  • OrderedMap<V> — trait with get / insert / remove / range / prefix_iter; all trie variants + Art<V> + ArtOlc<V> implement it.
  • ArtError — KeyTooLong | PrefixOverflow; returned from fallible ops; no panics.
  • Invariant: memcmp(enc(a), enc(b)) == cmp(a, b) for all KeyEnc impls.

Trie256 (art-trie)

  • 256-way per-byte inner nodes; each node is an array of 256 optional child pointers.
  • insert / get / remove / ordered iteration via in-order traversal.
  • Role: pedagogic baseline; documents height = key_len levels, memory = 256 pointers per node regardless of fanout.
  • Output: memory waste figures and height measurements feed Phase-3 motivation.

RadixTree / Patricia (art-trie)

  • RadixTree: compressed edge labels; split-on-mismatch insert creates new inner node with shared prefix.
  • Patricia: binary radix (one bit per level); nodes store only the discriminating bit position; no edge-label storage.
  • Quantify: height reduction, memory saving vs Trie256; compare on uniform random u64 keys and skewed string sets.
  • Invariant: in-order traversal of RadixTree matches BTreeMap order.

Art<V> + node types (art-art)

  • NodePtr(*mut ()): tagged pointer; low 3 bits (or a header byte) encode NodeType; alignment of all node structs ≥ 8.
  • NodeHeader: node_type: NodeType, num_children: u16, prefix_len: u32, prefix: [u8; 8]; prefix_len may exceed 8 (optimistic mode).
  • Node4: keys: [u8; 4] sorted; children: [NodePtr; 4]; linear scan; ~56 B.
  • Node16: keys: [u8; 16] sorted; children: [NodePtr; 16]; SIMD scan via art-simd; ~160 B.
  • Node48: child_index: [u8; 256] (0xFF = empty); children: [NodePtr; 48]; ~432 B.
  • Node256: children: [NodePtr; 256]; direct index; ~2 KB.
  • Leaf<V>: key: Box<[u8]> (full key, needed for optimistic prefix verification); value: V.
  • find_child(node, byte) -> Option<NodePtr> — dispatches by NodeType.
  • add_child(&mut node, byte, child) — may trigger grow (Node4→Node16, Node16→Node48, Node48→Node256).
  • remove_child(&mut node, byte) — may trigger shrink (reverse transitions).
  • Capacity thresholds: grow Node4 when num_children == 4; Node16 at 16; Node48 at 48. Shrink Node16 when num_children < 5; Node48 < 17; Node256 < 49.

NodeHeader prefix machinery (art-art)

  • Pessimistic prefix: up to MAX_PREFIX_LEN = 8 bytes stored inline; compared byte-by-byte during traversal; always correct.
  • Optimistic prefix: prefix_len > 8; only first 8 bytes stored; extra bytes NOT stored; at leaf, verify full key matches the claimed prefix length by comparing against the leaf's key: Box<[u8]>.
  • Lazy expansion: a single-descendant path is represented as a lone Leaf placed directly at the parent slot; only when a second key diverges does an inner node split materialize.
  • Invariant: every Leaf stores its complete key so optimistic-prefix verification can always proceed.

art-simd (art-simd)

  • node16_find_child(keys: *const u8, byte: u8, num_children: u8) -> Option<usize> — SSE2: broadcast byte into a 16-byte vector; _mm_cmpeq_epi8 vs keys[0..16]; _mm_movemask_epi8 → bitmask; trailing_zeros gives slot index; mask against (1 << num_children) - 1 to exclude garbage slots.
  • cfg(target_feature = "sse2") gate; scalar fallback (linear scan) compiled otherwise.
  • AVX2 variant for Node48 helpers: PhaseDeferred("Deferred Features Register").
  • Benchmark: SIMD vs scalar Node16 on random byte lookups; expected ≥ 2× throughput gain at num_children = 16.

ArtOlc<V> (art-concurrent)

  • Same node layout as Art<V> plus an AtomicU64 version per node (embedded in NodeHeader).
  • Version encoding: bit 0 = obsolete (node freed), bit 1 = write-locked, bits 2..63 = monotone counter.
  • Read path: read_lock_or_restart(node) -> Version — spin while lock bit set; return version. Descend. check_or_restart(node, v) — CAS-free version re-read; if changed → restart.
  • Write path: upgrade_to_write_lock_or_restart(node, v) — CAS bit 1 from 0→1; if CAS fails → restart. On release, increment counter and clear bit 1.
  • Invariant: writers couple parent→child locks (parent locked before child accessed for structural modification).
  • Lock-free reads: readers never set any lock bit; worst case is a restart loop, not a block.

Ebr (art-concurrent)

  • Global epoch (AtomicU64, values 0/1/2 cycling); per-thread local epoch + retire list.
  • Quiescent state: when a read-side critical section ends, thread updates its local epoch to global; when all threads observe epoch E, epoch E-2's retire list is safe to free.
  • retire(node_ptr) — adds to thread-local list; checked for collection on each quiescent state.
  • ABA avoidance: version counter increment on every write; a reader sees a stale version before a node is freed (obsolete bit) → restarts before using freed memory.

art-cli (art-cli)

  • Binary: artdb; subcommands: insert <key> <value>, get <key>, del <key>, scan <lo> <hi>, prefix <prefix>, load <file> (bulk import), stats (node-type histogram, height, memory bytes), bench (throughput vs BTreeMap + HashMap), viz (ASCII tree dump).
  • Drives all five library crates; the integration harness for manual testing.
  • Key encoding CLI flags: --enc u64|i64|f64|str|raw; internally calls the appropriate KeyEnc impl.

5.4 Specifications and Notes

ART node-layout and grow/shrink rules (from ICDE 2013):

Node4:   capacity ≤ 4;  keys[4] sorted; children[4]; grow  → Node16  when full (num_children == 4)
Node16:  capacity ≤ 16; keys[16] sorted; children[16]; grow → Node48  when full (num_children == 16)
Node48:  capacity ≤ 48; child_index[256] (0xFF = empty) → slot in children[48]; grow → Node256 when full
Node256: capacity ≤ 256; children[256] direct; shrink → Node48 when num_children < 37
Node48 shrink → Node16 when num_children < 13; Node16 shrink → Node4 when num_children < 5

OLC protocol (DaMoN 2016 §3), described procedurally: a read snapshots the node's version (v = node.version.load(Acquire)), restarting immediately if it observes the lock bit set; it then accesses the node's fields and restarts if a subsequent re-read of the version differs from v. A write (upgrade) performs the same version snapshot and lock-bit check, then attempts CAS(node.version, v, set_lock(v)) — restarting on CAS failure — mutates the node, and finally stores unlock_and_bump(v) with Release ordering. A delete (obsolete) sets the obsolete bit, bumps the version, and retires the node to EBR.

Binary-comparable encoding rules:

Type Encoding Correctness invariant
u32/u64 big-endian bytes memcmp == numeric order
i64 flip sign bit, then big-endian negative values sort below positive
f64 if sign bit set: flip all bits; else flip sign bit only IEEE total order; NaN sorts consistently
str UTF-8 bytes as-is + 0x00 terminator no key is a prefix of another value key; lexicographic == memcmp order
composite encode each component in order, concatenate components must be individually non-ambiguous (fixed-width or terminated)

6. Design Principles

P1 — Adapt representation to fanout

  • Inner nodes select type (Node4/Node16/Node48/Node256) based on actual child count, not worst-case 256.
  • Tradeoff: per-node type check overhead vs 10–50× memory reduction vs fixed-256.
  • Operational: grow on insertion when at-capacity; shrink on deletion when below threshold.
  • Violation: a fixed Node256 everywhere uses 2 KB/node; 1 M keys ≈ 2 GB wasted vs ~30 MB with ART.

P2 — Keys are order-preserving bytes

  • All user keys pass through KeyEnc before entering the tree; memcmp(encode(a), encode(b)) == cmp(a, b) for all supported types.
  • Tradeoff: encoding cost (one pass over key) vs ability to do range/prefix scans using byte-wise traversal.
  • Operational: range scan and prefix_iter are correct by construction; no per-key comparator needed at traversal time.
  • Violation: a signed integer encoded as native-endian or without sign-bit flip silently reverses the ordering of negative values; range queries return wrong results with no error.

P3 — Path compression + lazy expansion

  • Pessimistic prefix: up to MAX_PREFIX_LEN (8) bytes stored inline and compared on traversal.
  • Optimistic prefix: prefix_len may exceed 8; extra bytes NOT stored — verified via a leaf's full key at query end.
  • Lazy expansion: a path leading to a single leaf is not materialized as inner nodes; the leaf is placed directly.
  • Tradeoff: prefix-mismatch requires a leaf dereference (cache miss) for verification; saves inner-node allocations for long shared prefixes.
  • Violation: omitting path compression → tree height = key_length_bytes for every key → O(key_len × n) nodes.

P4 — A leaf stores its full key

  • Every Leaf<V> holds key: Box<[u8]> — the complete original encoded key.
  • Required for: (a) optimistic prefix verification (compare stored prefix_len bytes against the leaf), (b) key reconstruction during ordered iteration without re-encoding.
  • Tradeoff: per-leaf allocation proportional to key length vs correctness of optimistic traversal.
  • Violation: omitting full key → optimistic-prefix queries return stale/wrong values silently; leaf lookup succeeds against the wrong key.

P5 — Safe API over unsafe layout

  • All raw-pointer dereferences, tag-bit manipulation on NodePtr, and transmute-style casts are confined to unsafe blocks inside art-art and art-concurrent; all public APIs are safe.
  • Tradeoff: encapsulation overhead (one level of indirection at module boundary) vs soundness and auditability.
  • Operational: the unsafe surface is a documented invariant checklist; Miri runs the test suite.
  • Violation: leaking NodePtr as a public type allows callers to forge tags → undefined behavior, no detection.

P6 — Lock-free reads (OLC restart discipline)

  • Readers read a node's Version, proceed without acquiring a lock, then re-validate before using results; on mismatch, RESTART the traversal.
  • Tradeoff: read-side overhead = two atomic loads per node level vs no reader–reader contention; write-heavy workloads cause reader starvation (bounded by tree height = key_len).
  • Operational: read_lock_or_restart + check_or_restart are the ONLY sanctioned read patterns in art-concurrent; bypassing them produces torn reads.
  • Violation: a reader that skips check_or_restart may dereference a pointer whose target has been freed → use-after-free.

P7 — Reclaim with epochs (EBR)

  • Freed nodes enter the Ebr retire list; a node is actually deallocated only after all threads have passed through a quiescent state (epoch advance).
  • Tradeoff: reclamation lag (memory held longer than strictly needed) vs ABA freedom and use-after-free prevention.
  • Operational: Ebr is integrated with ArtOlc; writers call Ebr::retire rather than freeing directly; readers register epochs on entry/exit.
  • Violation: direct dealloc of a retired node → a concurrent reader mid-traversal dereferences freed memory; detected by Miri / AddressSanitizer, not at runtime in production.

P8 — Bench against real baselines

  • Every performance claim is validated against std::collections::BTreeMap, std::collections::HashMap, and the throughput numbers cited in the ICDE 2013 paper.
  • Tradeoff: benchmark maintenance cost vs preventing regression to "worse than BTreeMap" — which has happened in prior art-tree crates.
  • Operational: Criterion benchmarks for get/insert/scan/prefix are non-optional in Phase 13; CI fails if ART get-throughput regresses below BTreeMap on the dense-integer fixture.
  • Violation: shipping without BTreeMap comparison makes "ART is faster" an unverified claim.

P9 — Determinism modulo concurrency

  • Single-threaded Art<V> operations are fully deterministic: same sequence of inserts/removes → identical tree shape (node types, prefix split points).
  • Tradeoff: a stable tree shape requires deterministic grow/shrink thresholds (no probabilistic rebalancing).
  • Operational: differential fuzzing against BTreeMap is feasible because both are deterministic; property tests are reproducible with a fixed seed.
  • Violation: any randomness in node-type selection or prefix handling makes differential tests unreliable.

P10 — Height is key-length-bounded, not n-bounded

  • Lookup traverses at most key_len inner nodes regardless of n; each node dispatches on one byte of the key.
  • Tradeoff: keys with shared long prefixes produce deeper trees (bounded by prefix length, not n); very short keys produce very flat trees.
  • Operational: height reported by artdb stats should never exceed the longest key length in bytes; a violation signals a path-compression bug.
  • Violation: a split that increments depth without consuming a key byte creates unbounded growth.

P11 — Node children sorted in Node4/Node16

  • Node4 and Node16 maintain keys[] in ascending byte order at all times.
  • Required for: ordered iteration (in-order traversal with no re-sort); binary search in Node16 find_child; SIMD mask interpretation.
  • Tradeoff: insertion maintains sort order (shift cost O(n), n≤16) vs a hash-map child store.
  • Violation: unsorted keys in Node16 → binary search returns wrong child → silent key mismatch; SIMD movemask result misinterpreted.

P12 — No-std + alloc; only art-cli requires std

  • art-core, art-trie, art-art, art-simd, art-concurrent: #![no_std] + extern crate alloc.
  • Enables embedding in kernel modules, WASM, or a storage engine's no-std context.
  • Tradeoff: cannot use std::io, std::thread in library crates; art-concurrent uses core::sync::atomic only.
  • Violation: a use std:: in a library crate breaks embedded/WASM build targets silently (depends on toolchain).

P13 — Explicit capacity-band invariant as an assert

  • After every add_child / remove_child the node's (NodeType, num_children) pair must satisfy the band table; a debug_assert! fires immediately in test builds.
  • Operational: invariant is the grow/shrink trigger; the assert is the detection mechanism; recovery is "never get there" (grow before the assert fires).
  • Violation: a node outside its band is either wasteful (should have shrunk) or corrupt (more children than its array can hold → buffer overwrite).

  +1.0 → IEEE bits = 0x3FF0_0000_0000_0000 (bit63=0) → flip bit63 → 0xBFF0_0000_0000_0000

memcmp order: 0x400F... < 0x8000... < 0xBFF0...  ✓ (-1.0 < 0.0 < +1.0)

str terminator necessity: "ant" encodes as 61 6E 74 00; without terminator "ant" would be a byte prefix of "anti" at the byte level, breaking radix traversal (two distinct keys would share a full traversal path). The 0x00 terminator guarantees no encoded key is a prefix of another.

8.3 ART Node Layouts

NodeHeader — common prefix; embedded at byte offset 0 of every inner node:

struct NodeHeader {
    version:     AtomicU64,      //  8 B  (used by ArtOlc; zero in single-threaded Art)
    node_type:   NodeType,       //  1 B  (Node4=0, Node16=1, Node48=2, Node256=3, Leaf=4)
    num_children: u16,           //  2 B
    prefix_len:  u32,            //  4 B  (may exceed MAX_PREFIX_LEN for optimistic)
    prefix:      [u8; 8],        //  8 B  MAX_PREFIX_LEN = 8
}                                // = 23 B; padded to 24 B

Node4 — capacity 1–4 children; linear scan:

struct Node4 {
    hdr:      NodeHeader,        // 24 B
    keys:     [u8; 4],           //  4 B  sorted partial-key bytes (unused slots = 0)
    _pad:     [u8; 4],           //  4 B  align children to 8 B
    children: [NodePtr; 4],      // 32 B  (4 × 8 B)
}                                // = 64 B total (one cache line)

Node16 — capacity 5–16 children; SIMD scan (SSE2 on 16-byte aligned keys):

struct Node16 {
    hdr:      NodeHeader,        // 24 B
    keys:     [u8; 16],          // 16 B  sorted, 16-byte aligned for SSE load
    children: [NodePtr; 16],     //128 B
}                                // = 168 B ≈ 3 cache lines

Node48 — capacity 17–48 children; 256-byte index + 48 child slots:

struct Node48 {
    hdr:         NodeHeader,     //  24 B
    child_index: [u8; 256],      // 256 B  key_byte -> slot (0xFF = empty)
    children:    [NodePtr; 48],  // 384 B
}                                // = 664 B ≈ 11 cache lines

Node256 — capacity 49–256 children; direct index:

struct Node256 {
    hdr:      NodeHeader,        //   24 B
    children: [NodePtr; 256],    // 2048 B
}                                // = 2072 B ≈ 33 cache lines

Leaf — stores the FULL original key (required for optimistic-prefix verification):

struct Leaf<V> {
    hdr:   NodeHeader,   // 24 B  (node_type = Leaf; prefix/num_children unused)
    key:   Box<[u8]>,    //  pointer + len
    value: V,
}

NodePtr — tagged pointer, 8 B. Low 3 bits encode NodeType (Node4=0b000…Node256=0b011, Leaf=0b100); the upper bits are the real pointer >> 3. On 64-bit targets with 8-B-aligned nodes the bottom 3 bits are always 0 before tagging. Null = 0.

Node type Capacity band Bytes Cache lines
Node4 1–4 64 1
Node16 5–16 168 3
Node48 17–48 664 11
Node256 49–256 2072 33

8.5 Path Compression: Pessimistic, Optimistic, Lazy Expansion

Pessimistic prefix — up to MAX_PREFIX_LEN=8 bytes stored inline in NodeHeader.prefix. During traversal: compare prefix[0..min(prefix_len, 8)] byte by byte. If mismatch → key not present (for get) or split node (for insert). All bytes are verified on every traversal step; no false-positive traversal.

Optimistic prefix — when the shared prefix exceeds 8 bytes, prefix_len is stored accurately but only the first 8 bytes are in prefix. During traversal, skip over prefix_len bytes without checking the hidden tail. At the leaf, do a full key comparison to verify; if mismatch, the key is absent. Avoids storing long prefixes at every node; costs one extra leaf-key comparison.

Lazy expansion — when only a single descendant exists below a branch point, skip creating inner nodes; store the leaf directly. When a second key arrives that diverges, materialize the inner node(s) at that point.

Worked prefix-split insert — keys "antidote" and "antelope" share prefix "ant":

State before: root → Node4[key='a'] → Node4[key='n'] → Node4[key='t']
              → Leaf("antidote") [lazy, no inner node for 'idote']

Insert "antelope":
1. Traverse: root→'a'→'n'→'t', reach Leaf("antidote")
2. Compare "antelope" vs stored key "antidote" byte-by-byte from position 3:
   pos3: 'i' vs 'e' → mismatch at pos 3
3. Create new Node4 at this point, prefix = "" (no common bytes after 'ant')
4. Node4.add_child('i', Leaf("antidote"))
5. Node4.add_child('e', Leaf("antelope"))
6. Replace the slot in parent that pointed to Leaf("antidote") with new Node4.

Result:
  ...→'t'→ Node4[keys='e','i']
            ├─'e'→ Leaf("antelope")
            └─'i'→ Leaf("antidote")

8.6 find_child Semantics Per Node Type

Node find_child(byte) strategy Complexity
Node4 linear scan keys[0..num_children]; branchless compare with early exit O(4)
Node16 SIMD: load keys[0..16] into XMM, _mm_cmpeq_epi8(xmm, broadcast(byte)), movemask→ctz; scalar fallback: binary search O(1) / O(log16)
Node48 child_index[byte]; if != 0xFF: children[child_index[byte]] O(1)
Node256 children[byte]; if non-null: return O(1)

Node4 linear scan is branchless (compare all 4, mask with num_children, find first match) to avoid branch mispredictions on tiny arrays.

8.8 Worked RANGE Scan

range(lo=Bound::Included("ant"), hi=Bound::Excluded("bee")):

In-order DFS from root; at each node:
1. If current_key_prefix > hi → prune entire subtree
2. If node is Leaf → emit if lo <= leaf.key < hi
3. For inner node: iterate children in sorted key-byte order (ascending)
   Node4/Node16: already sorted by keys[] array
   Node48: iterate 0..=255, emit child_index[b] != 0xFF slots in order
   Node256: iterate 0..=255

Traversal result (ascending):
  "ant"  → included (>= lo, < hi)  ✓
  "anti" → included                 ✓
  "be"   → "be" < "bee" so included ✓
  "bee"  → excluded (== hi, Excluded bound)

Emitted: ["ant", "anti", "be"]

The iterator reconstructs full keys by tracking the current byte-path as it descends (stack of (NodePtr, child_index) pairs); each Leaf emits leaf.key directly.

// key.rs
/// Logical key: order-preserving byte string produced by KeyEnc.
/// Byte-wise (memcmp) order == logical key order — the ART traversal invariant.
#[derive(Clone, PartialEq, Eq, PartialOrd, Ord)]

impl Key {
    pub fn as_bytes(&self) -> &[u8];
    pub fn len(&self) -> usize;

// encode.rs
/// Implementors must satisfy: memcmp(encode(a), encode(b)) == a.cmp(b) for all a, b.
pub trait KeyEnc {
    fn encode(&self, out: &mut Vec<u8>);
}

// u32/u64: big-endian 4/8 bytes — already memcmp-ordered (ADR-06).
impl KeyEnc for u64;
impl KeyEnc for u32;

// i64: flip sign bit so negatives sort before positives in unsigned byte comparison (ADR-07).
impl KeyEnc for i64;

// f64: IEEE 754 total-order transform — if sign bit set, flip all bits; else flip only sign bit (ADR-08, IEEE 754-2008 §5.10).
impl KeyEnc for f64;

// &str: UTF-8 bytes as-is + 0x00 terminator (ADR-09).
// Invariant: no embedded NUL → no key is a byte-prefix of another at value level.
impl KeyEnc for str;

// Composite: encode each component in order; separator bytes may be inserted per type boundary (ADR-10).
// Usage: encode_composite!(out, &key.part1, &key.part2)
// ordered_map.rs
use core::ops::Bound;

/// Ordered-index contract implemented by Trie256, RadixTree, Patricia, Art, ArtOlc.
pub trait OrderedMap<V> {
    /// Point lookup. O(key_len).
    fn get(&self, key: &[u8]) -> Option<&V>;
    /// Insert; returns old value if key existed. O(key_len) amortised.
    fn insert(&mut self, key: &[u8], value: V) -> Option<V>;
    /// Delete; returns removed value. O(key_len) amortised.
    fn remove(&mut self, key: &[u8]) -> Option<V>;
    /// Ordered range scan; yields (key_bytes, &V) in ascending order.
    fn range<'a>(&'a self, lo: Bound<&[u8]>, hi: Bound<&[u8]>) -> RangeIter<'a, V>;
    /// All entries whose key starts with `prefix`; ascending order.
    fn prefix_iter<'a>(&'a self, prefix: &[u8]) -> PrefixIter<'a, V>;
}

pub type RangeIter<'a, V>  = Box<dyn Iterator<Item = (&'a [u8], &'a V)> + 'a>;
pub type PrefixIter<'a, V> = Box<dyn Iterator<Item = (&'a [u8], &'a V)> + 'a>;

11.2 art-art — Core ART Types

// node.rs — NodeType + NodePtr
pub const MAX_PREFIX_LEN: usize = 8; // pessimistic inline bytes in NodeHeader.prefix

/// Discriminant stored in tagged pointer low bits (2 bits) + NodeHeader.node_type.
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum NodeType { Node4, Node16, Node48, Node256, Leaf }

/// Fat raw pointer; low 3 bits = NodeType tag; upper bits = aligned heap address.
/// SAFETY: all construction/dereference paths are encapsulated; never pub-dereferenced outside art-art.
#[derive(Copy, Clone)]
pub struct NodePtr(*mut ());

impl NodePtr {
    pub const NULL: NodePtr = NodePtr(core::ptr::null_mut());
    pub fn is_null(self) -> bool;
    /// Encode: align heap ptr (>= 8-byte aligned) + tag in low 3 bits.
    pub unsafe fn encode(ptr: *mut (), tag: NodeType) -> NodePtr;
    pub unsafe fn node_type(self) -> NodeType;
    /// SAFETY: caller ensures self points to a live T with matching NodeType tag.
    pub unsafe fn as_ref<T>(self) -> &'static T;
    pub unsafe fn as_mut<T>(self) -> &'static mut T;
}
// header.rs — NodeHeader
/// Shared prefix of every inner node. 24 bytes on 64-bit; first field → consistent cast.
#[repr(C)]
pub struct NodeHeader {
    pub node_type:    NodeType,   // 1 byte; redundant with tag but safe for match
    pub num_children: u16,        // current child count; triggers grow/shrink
    pub prefix_len:   u32,        // total logical prefix length; may exceed MAX_PREFIX_LEN (optimistic)
    pub prefix:       [u8; MAX_PREFIX_LEN], // first min(prefix_len, MAX_PREFIX_LEN) bytes stored inline
}

impl NodeHeader {
    /// True if prefix_len > MAX_PREFIX_LEN — lazy bytes not stored; verified at leaf.
    pub fn is_optimistic(&self) -> bool;
    /// Compare key[depth..] against stored inline prefix; returns mismatch byte index or None.
    pub fn check_prefix<'k>(&self, key: &'k [u8], depth: usize) -> Option<usize>;
}
// node4.rs
/// ≤4 children. keys[] sorted ascending; binary search (or branchless linear scan) for find_child.
/// Byte sizes (x86-64): NodeHeader=24 + keys[4]=4 + pad=4 + children[4×8]=32 → 64 bytes.
#[repr(C)]
pub struct Node4 {
    pub hdr:      NodeHeader,
    pub keys:     [u8; 4],
    _pad:         [u8; 4],
    pub children: [NodePtr; 4],
}

impl Node4 {
    pub fn find_child(&self, byte: u8) -> Option<NodePtr>;
    pub fn add_child(&mut self, byte: u8, child: NodePtr);    // maintains sorted order
    pub fn remove_child(&mut self, byte: u8) -> Option<NodePtr>;
    pub fn is_full(&self) -> bool;   // num_children == 4
    /// Grow into Node16, consuming self; called by insert when is_full().
    pub fn grow(self) -> Box<Node16>;
}
// node16.rs
/// ≤16 children. keys[] sorted; SIMD search via art-simd::node16_search (cfg-dispatched).
/// Byte sizes: NodeHeader=24 + keys[16]=16 + children[16×8]=128 → 168 bytes (pad to 192 for cache-line).
#[repr(C, align(64))]
pub struct Node16 {
    pub hdr:      NodeHeader,
    pub keys:     [u8; 16],
    pub children: [NodePtr; 16],
}

impl Node16 {
    /// Delegates to art_simd::node16_search(keys, num_children, byte) — SIMD or scalar fallback.
    pub fn find_child(&self, byte: u8) -> Option<NodePtr>;
    pub fn add_child(&mut self, byte: u8, child: NodePtr);
    pub fn remove_child(&mut self, byte: u8) -> Option<NodePtr>;
    pub fn is_full(&self) -> bool;     // num_children == 16
    pub fn is_sparse(&self) -> bool;   // num_children < 5
    pub fn grow(self)   -> Box<Node48>;
    pub fn shrink(self) -> Box<Node4>;
}
// node48.rs
/// ≤48 children. child_index[byte] → slot index (0xFF = empty slot); children[slot].
/// Byte sizes: NodeHeader=24 + child_index[256]=256 + children[48×8]=384 → 664 bytes.
#[repr(C)]
pub struct Node48 {
    pub hdr:         NodeHeader,
    pub child_index: [u8; 256],   // 0xFF = no child for that key byte
    pub children:    [NodePtr; 48],
    free_slots:      u64,         // bitmask of available slots (popcount ≥ 48 - num_children)
}

impl Node48 {
    pub fn find_child(&self, byte: u8) -> Option<NodePtr>;   // child_index[byte] != 0xFF → children[idx]
    pub fn add_child(&mut self, byte: u8, child: NodePtr);   // allocate free slot; set child_index[byte]
    pub fn remove_child(&mut self, byte: u8) -> Option<NodePtr>;
    pub fn is_full(&self)   -> bool;   // num_children == 48
    pub fn is_sparse(&self) -> bool;   // num_children < 17
    pub fn grow(self)   -> Box<Node256>;
    pub fn shrink(self) -> Box<Node16>;
}
// node256.rs
/// Direct 256-pointer array. O(1) find/add/remove; always correct NodeType for a 256-child node.
/// Byte sizes: NodeHeader=24 + children[256×8]=2048 → 2072 bytes.
#[repr(C)]
pub struct Node256 {
    pub hdr:      NodeHeader,
    pub children: [NodePtr; 256],
}

impl Node256 {
    pub fn find_child(&self, byte: u8) -> Option<NodePtr>;   // children[byte].is_null() check

    pub fn shrink(self) -> Box<Node48>;
}
// leaf.rs
/// Terminal node. Stores the FULL key (required for optimistic-prefix verification at traversal end).
/// Owns key bytes via Box<[u8]>; owns value V. No interior mutability.

// lib.rs (art-simd)
/// Search `keys[0..n]` for `byte`. Returns the child slot index, or None.
/// Dispatched at compile time: SSE2 (x86 baseline), AVX2 (feature = "avx2"), scalar (fallback).
/// Contract: result must equal the scalar fallback for all inputs.
#[inline(always)]

// node16_sse.rs

pub fn node16_search_sse2(keys: &[u8; 16], n: usize, byte: u8) -> Option<usize>;

/// Scalar: iterate keys[0..n]; return first match index. Identical semantics; used on non-x86.
pub fn node16_search_scalar(keys: &[u8; 16], n: usize, byte: u8) -> Option<usize>;

11.4 art-concurrent — ArtOlc + Ebr

// version.rs
/// Per-node version word embedded in NodeHeader (replaces _pad).
/// Bit layout: [63:2] = counter (increment on each write); [1] = lock bit; [0] = obsolete bit.
/// Obsolete = node freed by a writer; reader must restart if it observes obsolete.
pub struct Version(AtomicU64);

impl Version {
    pub fn read(&self) -> u64;                                    // Acquire load
    pub fn is_locked(v: u64) -> bool;    // v & 0b10 != 0
    pub fn is_obsolete(v: u64) -> bool;  // v & 0b01 != 0
    /// CAS lock bit: 0 → 1. Fails if already locked or obsolete.
    pub fn try_write_lock(&self) -> Result<u64, ()>;
    pub fn write_unlock(&self, increment: bool);                  // clear lock bit; if increment, bump counter
    pub fn mark_obsolete(&self);                                  // set bit 0; called by EBR before free
}
// olc.rs
/// Concurrent ART with Optimistic Lock Coupling.
/// SAFETY guarantees: lock-free reads (no reader ever blocks); writers couple parent→child locks.
/// Send + Sync: reads share no mutable state; writes are serialised per node via Version CAS.
pub struct ArtOlc<V: Send + Sync> {
    root:    NodePtr,       // AtomicPtr<NodePtr> for root-replace under write lock
    ebr:     Ebr,
    len:     AtomicUsize,
}

impl<V: Send + Sync> ArtOlc<V> {
    pub fn get(&self, key: &[u8]) -> Option<&V>;           // lock-free read; restart loop
    pub fn insert(&self, key: &[u8], value: V) -> Option<V>; // OLC write path
    pub fn remove(&self, key: &[u8]) -> Option<V>;
}

impl<V: Send + Sync> ArtOlc<V> {
    /// Read-side: snapshot version before descending into child.
    fn read_lock_or_restart(node: &NodeHeader) -> Result<u64, Restart>;
    /// Validate version unchanged since snapshot; else signal Restart.
    fn check_or_restart(node: &NodeHeader, version: u64) -> Result<(), Restart>;
    /// Escalate a read lock to a write lock via CAS on Version; else Restart.
    fn upgrade_to_write_lock_or_restart(node: &NodeHeader, version: u64) -> Result<(), Restart>;
}

struct Restart; // zero-size sentinel; triggers loop iteration
// ebr.rs
/// Epoch-Based Reclamation: ensures no reader is mid-traversal on a node when it is freed.
/// Three epochs cycle; a thread pins its local epoch before reading; freed nodes retire into
/// the epoch's list and are collected only when all threads have advanced past that epoch.
pub struct Ebr {
    global_epoch: AtomicU64,
    // per-thread slots via thread_local! — not shown (OS thread model)
}

impl Ebr {
    pub fn pin(&self) -> EbrGuard<'_>;               // enter quiescent section; pin local epoch
    pub fn retire(&self, ptr: NodePtr, guard: &EbrGuard); // defer free until epoch advances twice
    fn try_collect(&self);                           // advance global epoch if all threads pinned ≥ current
}

pub struct EbrGuard<'ebr> { /* holds local epoch; releases on drop */ }

File: art-trie/src/trie256.rs (full implementation, not smoke-only). TrieNode<V> holds children: Box<[Option<Box<TrieNode<V>>>; 256]> plus value: Option<V> (terminus marker); Trie256<V> wraps root: TrieNode<V> + len: usize. Allocate the 256-slot array via unsafe { Box::<[...; 256]>::new_zeroed().assume_init() } — a stack-resident [None; 256] would spend 2 048 bytes of stack before boxing (Pitfall 1).

  • insert(key: &[u8], value: V) → Option<V>: walk bytes; on byte b, recurse into children[b], allocating a new TrieNode if None; at the key's end, swap node.value and return the old value.

art-trie/src/radix.rs — RadixTree<V>

Node layout:

struct RadixNode<V> {
    edge: Box<[u8]>,          // compressed edge label (empty for root)
    children: Vec<(u8, Box<RadixNode<V>>)>,  // sorted by first byte of child's edge
    value: Option<V>,
}

Key algorithms:

  • find_child(node, key_bytes) — compare node's edge against key prefix; on match recurse with remainder; on mismatch return None.
  • insert — walk to longest match; three cases: (a) exact edge match → recurse or set value; (b) edge is prefix of key → recurse into child or create child; (c) mismatch at byte i → split: create new inner node with edge[..i], old node gets edge[i+1..], new leaf gets key[i+1..], first-bytes become child discriminators.
  • remove — post-order: remove leaf, merge single-child inner nodes (collapse one-child chains) to restore path-compression invariant.
  • range / prefix_iter — in-order DFS; reconstruct key by appending edge labels on the way down.

art-trie/src/patricia.rs — Patricia<V>

struct PatriciaNode<V> {
    bit: u32,                 // bit position to branch on (MSB-first)
    left:  Option<Box<PatriciaNode<V>>>,   // bit == 0
    right: Option<Box<PatriciaNode<V>>>,   // bit == 1
    key: Option<Box<[u8]>>,
    value: Option<V>,
}
  • insert: walk using bit_at(key, node.bit) until node.bit >= key_len_bits or node.bit >= next.bit (upward link); find diverging bit position; insert new branch node at that position.
  • Upward-link detection (classic Patricia invariant): if next.bit <= current.bit, we have reached a leaf back-pointer — compare stored key to resolve match vs collision.
  • remove: find predecessor of the node referencing this node; rewire; handle root-is-leaf edge case.

Shared infrastructure:

  • art-trie/src/lib.rs re-exports both types; stats() on RadixTree returns RadixStats { node_count, leaf_count, height, avg_edge_bytes }.

  • Node16 children array: 16-byte alignment on keys[16] enables a single 128-bit load in Phase 9 (_mm_lddqu_si128); use #[repr(C, align(16))] or explicit align_of assert.
  • Box<[u8]> for Leaf::key — one heap allocation per leaf; in Phase 10 this moves to an arena slab; the interface stays identical.
  • grow_to_node16 copies 4 children + header; cost is ~64 bytes; amortized over the node's lifetime (each node grows at most once per type step).

4.8 Edge Cases

  • Single-byte key [b]: root is a Node4 with one child which is a Leaf; get([b]) must return the value, get([b,0]) must return None.
  • Key length 0 (empty key): root node's value slot — a root-is-leaf case; must not confuse with root being an inner node with 0 children.
  • Inserting 17 keys into a single level: 16 fit in Node16; 17th requires grow to Node48 (Phase 5); Phase 4 should panic or return Err on the 17th to signal the boundary cleanly.
  • Key byte 0x00 as a valid child discriminator: ensure keys[] compare uses u8 equality, not C-string semantics.
  • Node4 with num_children == 0 after all removals: must be collapsed (single-child chain collapse deferred to Phase 7; Phase 4 may leave empty inner nodes temporarily).

Pessimistic prefix (prefix_len ≤ 8): on descent, memcmp(hdr.prefix[..min(prefix_len,8)], key[depth..]) → match/mismatch position; mismatch → split_node.

Optimistic prefix (prefix_len > 8): skip without comparing stored bytes; at the leaf, call prefix_mismatch comparing key vs leaf.key to detect a true divergence. If divergence found at position p < prefix_len, retroactively split: split_node inserts a new inner node at depth+p. any_leaf = cheapest reachable leaf (first-child traversal), stored in prefix.rs as fn find_any_leaf(ptr: NodePtr) -> &Leaf.

Lazy expansion: NodePtr tag for NodeType::Leaf used at any tree position (not just terminal). insert path: if current NodePtr points to Leaf and its key matches prefix → update value; if diverges → expand_lazy which creates a Node4 with both leaves under it, sets NodeHeader.prefix to the common bytes, adjusts prefix_len.

Prefix split algorithm (split_node):

  1. Allocate new Node4.
  2. New node's prefix = hdr.prefix[..mismatch_pos], prefix_len = mismatch_pos.
  3. Old node's prefix shifts by mismatch_pos+1; prefix_len -= mismatch_pos+1; partial key byte = hdr.prefix[mismatch_pos].
  4. add_child(new_node, old_partial_byte, old_ptr).
  5. add_child(new_node, new_key[depth+mismatch_pos], new_leaf).
  6. Parent NodePtr updated to new node.

art-art/src/insert.rs — pub fn insert<V>(root: &mut NodePtr, key: &[u8], value: V, depth: usize) -> Option<V>

Algorithm (recursive / iterative with explicit stack):

  1. root is Leaf → expand_lazy (Phase 6) or overwrite if keys equal.
  2. root is inner → check_prefix(hdr, key, depth):
    • Mismatch at pos p → split_node (Phase 6), then re-insert; return None.
    • Full match → depth += hdr.prefix_len.
  3. find_child(node, key[depth]):
    • Some(child) → recurse into child with depth+1.
    • None → add_child(node, key[depth], make_lazy_leaf(key, value)); if node full → grow first (Phase 5 transitions), then add_child.
  4. Return displaced value if duplicate.

art-art/src/remove.rs — pub fn remove<V>(root: &mut NodePtr, key: &[u8], depth: usize) -> Option<V>

Algorithm:

  1. root is Leaf → compare full key; match → take value, set root = NodePtr::null(); else None.
  2. Inner node: check_prefix → mismatch → None. Match → depth += prefix_len.
  3. find_child(node, key[depth]) → recurse with parent reference kept.
  4. After recursive call removes leaf: remove_child(node, key[depth]).
  5. Shrink: if num_children drops below threshold → shrink (Phase 5).
  6. Path collapse: if num_children == 1 after shrink → merge remaining child into parent:
    • If child is inner: new_prefix = [node.prefix | key_byte | child.prefix]; new_prefix_len = node.prefix_len + 1 + child.prefix_len; set parent to child with updated header.
    • If child is Leaf: parent slot = that leaf directly (lazy-leaf restored).
  7. Prefix re-merge: when new_prefix_len > MAX_PREFIX_LEN, switch to optimistic: keep only first 8 bytes, update prefix_len; leaf's full key will verify at read time.

  1. Leaf → full-key compare → Some(&leaf.value) or None.

In-order traversal algorithm:

  1. Push root; descend always to leftmost child (byte 0 in Node256, first slot in Node4/16/48).
  2. On each frame: append hdr.prefix[..min(prefix_len,8)] to key_buf; if optimistic, prefix bytes >8 are NOT appended now (reconstructed from leaf).
  3. At Leaf: yield (key_buf as reconstructed, &leaf.value); pop frame; backtrack.
  4. On backtrack: truncate key_buf by the bytes appended for that node; advance child_idx to the next child byte in sorted order.

Key reconstruction for optimistic prefix: when prefix_len > 8, the stored 8 bytes are appended; the remaining prefix_len - 8 bytes come from the leaf's key[depth..depth+(prefix_len-8)]; emit the full key from leaf.key directly — simpler and correct.

range(lo: Bound<&[u8]>, hi: Bound<&[u8]>) implementation:

  • Seek to lo: descend ART finding the first leaf ≥ lo (or > lo for Excluded). Seek uses find_child for exact bytes; on a node where no child matches exactly, take the next larger child byte (lower-bound scan).
  • hi enforced lazily: each next() call checks leaf.key against hi; return None when exceeded.
  • pub struct RangeIter<'a, V>(Cursor<'a, V>, Bound<Cow<'a,[u8]>>, Bound<Cow<'a,[u8]>>);

prefix_iter(prefix: &[u8]) implementation:

  • Seek to the subtree rooted at the node where prefix is exhausted; iterate the entire subtree.
  • If prefix descent hits a mismatch → empty iterator.
  • Implemented as range(Included(prefix), Included(prefix_upper_bound(prefix))) where prefix_upper_bound increments the last byte (overflow-safe: if all 0xFF, range is open-ended up to subtree boundary).

successor(key: &[u8]) -> Option<(&[u8], &V)>: range(Excluded(key), Unbounded).next(). predecessor(key: &[u8]) -> Option<(&[u8], &V)>: reverse cursor or binary search on a Node's children — implement via a ReverseCursor mirroring Cursor but descending rightmost-first.

OrderedMap<V> trait impls added in lib.rs:

fn range(&self, lo: Bound<&[u8]>, hi: Bound<&[u8]>) -> RangeIter<'_, V> { ... }
fn prefix_iter(&self, prefix: &[u8]) -> PrefixIter<'_, V> { ... }

art-art/src/seek.rs (new): fn seek_lower_bound(root: &NodePtr, key: &[u8]) -> Cursor — drives descent choosing ≥ key[depth] at each level; handles prefix comparison during descent (must advance past prefix bytes without key bytes consumed).

11.7 Performance Concerns

  • Read path: ~3–5 atomic loads (version reads) per level; no CAS on read path → scales with readers.
  • Write path: 2 CAS per node modified (lock + unlock); parent+child coupling = 4 CAS per insert.
  • Restart rate: expect < 1% under 80/20 read/write mix; measure in bench and report.
  • SeqCst loads on version can be downgraded to Acquire + Release on unlock after careful memory-model analysis (document the ordering argument).
  • Node Version field adds 8 bytes to NodeHeader (was 16, now 24); re-verify size_of assertions from Phase 10.
  • Cache-line alignment (Phase 10) ensures version + prefix live in the same cache line as keys for Node4/Node16.

11.8 Edge Cases

  • Concurrent grow (Node4 → Node16) while reader traverses: reader reads old Node4 pointer; writer sets Node4.obsolete, installs Node16; reader's check_or_restart detects version change → restart with new Node16.
  • Delete last child → node collapse: writer locks parent + child, removes child, sets child obsolete, unlocks parent with bumped version; reader restarts and sees collapsed tree.
  • Root replacement: root is a NodePtr; wrap root in an AtomicPtr + its own Version; treat root as a virtual parent.
  • Zero-length key (&[]): valid; insert into root as a leaf; version protocol unchanged.
  • Concurrent inserts of the same key: last writer wins (overwrite); both CAS sequences succeed serially; insert returns Some(old_value) for the loser.

Unsafe-Layout Analysis

  • All *mut () dereferences in art-art gated behind NodePtr::as_node4() / as_node16() / … which assert the tag.

Concurrency Threat Surface (OLC-Specific)

A reader thread snapshots version = node.version.load(Acquire), spins/restarts if the lock bit is set, reads the node's fields, then restarts if a re-read of node.version no longer matches the snapshot. A writer thread acquires the lock via CAS(version, v, v | LOCK_BIT), mutates the node, and releases with version.store(v + 2, Release) (bumping the counter). EBR ties the two together: the writer calls ebr.retire(ptr) for deferred free, readers bracket their critical section with ebr.pin() / ebr.unpin() (quiescent state), and the epoch advances only once all threads have unpinned.

Invariants: (a) no field of a locked node is visible to readers post-check; (b) EBR epoch advance requires all readers to complete their critical section; (c) obsolete bit (bit 0) set before unlink so readers detect stale root.

FM-1: Wrong Iteration Order (P0)

  • Symptom: range() / prefix_iter() / in-order traversal returns keys out of monotonic order; differential test vs BTreeMap diverges.
  • Root Cause: (a) KeyEnc produces non-order-preserving bytes (e.g., little-endian u64); (b) in-order traversal skips a subtree (off-by-one in Node4 sorted key scan or Node256 loop); (c) prefix-split inserts new leaf at wrong branch.
  • Detection: memcmp_order property test; differential fuzzer (ART vs BTreeMap on same op sequence); artdb viz dumps tree; manual inspection of sorted-key lists.
  • Auto-Recovery: None — iterator returns incorrect data silently.
  • Manual Recovery: (1) artdb viz --dot > tree.dot to visualize structure; (2) bisect with reduced key set; (3) check KeyEnc::encode output for the offending key pair; (4) add targeted unit test; fix + re-run property tests.
  • Long-Term Mitigation: memcmp_order test is a release gate (CI blocks merge on failure); differential fuzzer runs for 60 s in CI.

FM-2: get-after-insert Returns None (P0)

  • Symptom: insert(k, v) returns None (no prior value); subsequent get(k) returns None.
  • Root Cause: (a) Prefix-split creates inner node but leaf pointer placed at wrong child slot; (b) add_child for Node4 / Node16 does not shift sorted keys correctly; (c) lazy-expansion leaf not promoted when second key diverges.
  • Detection: Invariant test: for every inserted key, get(key) == Some(value); run after every insert in correctness suite.
  • Auto-Recovery: None.
  • Manual Recovery: (1) artdb viz — locate missing leaf; (2) trace insertion path with RUST_LOG=art=trace traversal hook; (3) inspect NodeHeader.prefix_len and branch byte at divergence point; (4) compare against expected child slot.
  • Long-Term Mitigation: Phase 7 correctness suite; property test: prop_get_after_insert with random keys; differential vs BTreeMap.

FM-3: Memory Corruption / Segfault (P0)

  • Symptom: SIGSEGV; wrong value returned; debug_assert fires on tag check; Miri reports UB.
  • Root Cause: (a) NodePtr tag mismatched — dereferencing Node4 as Node16; (b) Node48::child_index[b] >= 48 (slot not initialized to 0xFF); (c) double-free of leaf on remove; (d) Box<[u8]> in Leaf<V> freed while NodePtr still reachable.
  • Detection: Miri in CI (primary); debug_assert_eq!(ptr.tag(), NodeType::Node4) at every cast; valgrind/sanitizers in optional CI job.
  • Auto-Recovery: None — undefined behavior.
  • Manual Recovery: (1) Reproduce under cargo +nightly miri test; (2) debug_assert narrows to exact call site; (3) inspect NodePtr construction / grow path for tag-assignment omission; (4) check Node48 init loop sets all 256 slots to 0xFF.
  • Forensic Artifact: Miri error trace; RUST_BACKTRACE=full on debug_assert panic.
  • Long-Term Mitigation: Encapsulate all unsafe in NodePtr::{as_nodeN, drop_nodeN}; zero new unsafe paths without Miri green.

FM-4: Node-Type Band Violation (P1)

  • Symptom: Node4 with 5 children (overflow, no grow triggered); Node16 with 1 child (missed shrink); histogram shows wrong distribution.
  • Root Cause: add_child returns without calling grow() when num_children == capacity; remove_child decrements but skips shrink() threshold check.
  • Detection: debug_assert!(self.hdr.num_children <= CAPACITY) after every add_child; art stats node-type histogram drift; invariant-check pass in test suite.
  • Auto-Recovery: None at runtime; the operation silently corrupts structure.
  • Manual Recovery: Identify grow/shrink call site in add_child / remove_child; add threshold unit tests for each transition boundary (4→16, 16→48, 48→256 and reverses).
  • Long-Term Mitigation: Phase 5 transition tests; fuzz insert/delete with capacity-boundary key sets.

FM-5: Optimistic-Prefix Mis-Verification (P1)

  • Symptom: get(k) returns Some(v) for a key k2 ≠ k (false positive match); or None for a key that exists (false negative on prefix mismatch).
  • Root Cause: prefix_len > MAX_PREFIX_LEN path skips inline comparison and goes straight to leaf full-key check, but the leaf's Box<[u8]> key is truncated or the offset arithmetic is wrong.
  • Detection: Property test: prop_no_false_positives — insert disjoint keys, verify get for keys not inserted returns None; prop_get_after_insert.
  • Auto-Recovery: None.
  • Manual Recovery: Trace descent: log prefix_len, MAX_PREFIX_LEN, leaf key bytes; compare key[depth..] vs leaf.key[depth..]; check offset in optimistic-verification branch.
  • Long-Term Mitigation: Phase 6 tests specifically for prefix_len > 8; include keys engineered to exceed MAX_PREFIX_LEN.

FM-6: Concurrent Torn Read / Use-After-Free (P0)

  • Real-world precedent: MySQL InnoDB (Oracle, 2012) disclosed a use-after-free in its buffer pool page hash table when a page-frame pointer was accessed after the frame had been evicted and reallocated; the defect had the same root cause as an EBR gap — a reader holding a stale pointer while the writer's reclamation raced ahead of the reader's critical section (CVE-2012-2122 adjacent; public InnoDB bug report #63704).
  • Symptom: Reader returns garbled value; segfault in concurrent test; loom detects data race.
  • Root Cause: OLC check_or_restart not called after reading multi-word field; EBR epoch not advanced before reclaim; writer stores Version with wrong ordering.
  • Detection: cargo test --features loom exhaustive-schedule checks; TSAN in CI optional; stress test (8 threads, 1M ops, 30 s).
  • Auto-Recovery: OLC restart loop handles transient torn reads; EBR prevents UAF structurally.
  • Manual Recovery: (1) Reproduce with loom — prints the failing schedule; (2) check all multi-field reads are bracketed by version snapshot + check_or_restart; (3) verify Acquire/Release ordering on Version atomic; (4) confirm ebr.pin() called before any pointer dereference in reader path.
  • Long-Term Mitigation: Loom tests for every OLC read path; EBR is mandatory (not optional) for concurrent variant.

FM-7: Infinite OLC Restart Livelock (P2)

  • Symptom: Reader thread spins indefinitely; throughput → 0; OLC restart counter unbounded.
  • Root Cause: Writer holds lock across blocking I/O or lock starvation under high write contention.
  • Detection: OLC restart-rate metric > threshold (e.g., >10k restarts/s sustained); watchdog in artdb bench.
  • Auto-Recovery: Exponential backoff on restart (spin → yield → park after N retries).
  • Manual Recovery: Profile writer critical-section length; reduce write batch size; check for nested lock acquisition (deadlock variant).
  • Long-Term Mitigation: Phase 11 design: writer critical section = pointer swap only, no allocation inside lock; backoff policy documented.

FM-8: Memory Bloat (P2)

  • Symptom: memory_bytes() >> expected; art stats shows mostly Node256 nodes with few children; height taller than key-length floor.
  • Root Cause: Lazy expansion not triggered (single-leaf chains materialised as inner nodes); prefix not compressed (split logic creates degenerate inner node with prefix_len = 0).
  • Detection: Node-type histogram in art stats; fill-factor check (num_children / capacity); compare memory_bytes() vs BTreeMap baseline.
  • Auto-Recovery: None at runtime.
  • Manual Recovery: artdb viz to identify low-fill nodes; trace insert path for pathological key set; verify lazy-expansion condition in single-child insert.
  • Long-Term Mitigation: Fill-factor invariant test; memory regression bench vs BTreeMap.

FM-9: Duplicate Child Key in Node4/Node16 (P3)

  • Symptom: Two entries in Node4.keys for the same byte; find_child returns first match, second unreachable → leaked node.
  • Root Cause: add_child does not check for pre-existing key before inserting.
  • Detection: debug_assert!(find_child(node, byte).is_none()) before add_child in debug; invariant scan in art stats.
  • Auto-Recovery: None.
  • Manual Recovery: Identify call site that bypasses find_child check; add precondition assertion.
  • Long-Term Mitigation: Encapsulate add_child to always call find_child first in debug builds.

FM-10: SIMD/Scalar Node16 Divergence (P1)

  • Symptom: Node16::find_child returns different results depending on whether the simd feature is enabled; property test (INV-12) fails on one CI target but not the other; a "phantom child hit" returns a wrong NodePtr for a byte never inserted.
  • Root Cause: The SIMD movemask is not masked against num_children before trailing_zeros, so uninitialized bytes in keys[num_children..15] participate in the comparison (MM7); alternatively, the scalar fallback and SIMD path disagree on tie-breaking when num_children == 0.
  • Detection: INV-12 property test (1000 random states × 256 candidate bytes, SIMD vs scalar); art-simd bench divergence counter; differential CI job running both --features simd and --no-default-features.
  • Auto-Recovery: None — a silent wrong-value bug.
  • Manual Recovery: (1) Reproduce with --no-default-features vs default build on the same fixture; (2) inspect the mask construction in node16_sse.rs for a missing & ((1 << num_children) - 1); (3) add the failing (keys, num_children, byte) triple as a regression fixture.
  • Long-Term Mitigation: INV-12 is a mandatory CI gate from Phase 9 onward; both feature configurations run in the CI matrix (simd_off job, §"Build & Release Engineering" CI Matrix).

Incident Response Runbooks

"Scans out of order"

  1. artdb viz --dot | dot -Tsvg > tree.svg — visual inspection.
  2. artdb scan --all --dump-keys → pipe to sort -c to find first inversion.
  3. Identify key pair (a, b) where a > b in output; run artdb encode a b to show byte representations.
  4. If encode(a) < encode(b) but scan returns a before b → traversal bug (Phase 8 / FM-1 path).
  5. If encode(a) > encode(b) → KeyEnc bug; run memcmp_order property test.
  6. Fix → re-run differential fuzzer for 5 min before merge.

"Memory higher than expected"

  1. artdb stats --node-histogram → check Node256 fill factor; if < 20%, premature Node256 promotion.
  2. Check Node48 → Node256 grow threshold (should be 48, not lower).
  3. artdb viz --depth 3 → identify subtrees with single children (lazy expansion not triggered).
  4. Profile with heaptrack or dhat to find allocation hot spots.

"Concurrent throughput collapses"

  1. artdb bench --concurrent --stats → read olc_restart_count per second.
  2. If > 10k restarts/s: check writer critical section for blocking ops (alloc inside lock?).
  3. Enable backoff: ArtOlc::with_backoff(BackoffConfig::default()).
  4. If EBR lag > 2 epochs: check thread pinning; ensure ebr.unpin() called promptly after read.

KeyEnc Encoding Normative Spec (Versioned)

Type Encoding Version
u32 4-byte big-endian v1
u64 8-byte big-endian v1
i64 8-byte big-endian, sign bit flipped (x ^ 0x8000_0000_0000_0000) v1
f64 8 bytes: if MSB=0, flip all bits; if MSB=1, flip only MSB (IEEE total order) v1
str / &[u8] as-is + 0x00 terminator (ensures no key is prefix of another at value level) v1
Composite (A, B) encode(A) ++ encode(B) (concatenation; components must be fixed-width or terminated) v1

Normative property: memcmp(encode(a), encode(b)) == a.cmp(b) for all a, b in the type's ordering.

Breaking change policy: Any change to an encoding byte layout (e.g., endianness fix, different bit trick) is a major semver bump (2.0.0). Rationale: (a) in-memory trees built with v1 encodings contain v1-encoded keys; iterating the same tree with v2 KeyEnc would produce wrong order; (b) if persistence is ever added (deferred phase), on-disk key bytes are tied to the encoding version — a v1 tree is not readable by a v2 library without migration. Callers must re-encode + re-insert all keys on a major bump.

Adding new key types: implement KeyEnc for the new type in a minor release; existing types and their encodings are unaffected. No OrderedMap signature changes required.

Iteration Order and Ordered-Map Semantics

  • In-order (ascending by KeyEnc bytes) iteration is a stable guarantee across all releases.
  • range(lo, hi) with any Bound combination returns keys in ascending encoded order — stable.
  • prefix_iter(prefix) returns all keys where encode(key) has prefix as a byte prefix, in ascending order — stable.
  • Successor / predecessor semantics: range(Excluded(k), Unbounded).next() = smallest key > k — stable.

Concurrency Contract

  • ArtOlc<V> guarantees lock-free reads: a reader thread is never blocked by a writer holding a lock; it may restart but never deadlocks.
  • Linearizability: each get / insert / remove appears to take effect at a single point in time; concurrent reads see either the pre-image or post-image of a write, never a partial state.
  • EBR safety: no NodePtr accessed through the public API is ever freed while a reader holds an Ebr pin (RAII Guard).
  • These are not changed by enabling or disabling simd / avx2 feature flags.

Persistence-Format Versioning (Deferred)

  • The current codebase is in-memory only — no on-disk format exists.
  • If a persistence phase is added, the serialized format will embed the KeyEnc version (v1, …) as a header field, and the art-core version as a separate field.
  • A v1 on-disk tree is not loadable by a v2 library (different encoding) without a migration tool — this is a defined breaking change, not a silent incompatibility.
  • Until persistence is implemented, this section is a forward declaration only; no stability promise applies to any serialization format.

Hot Paths and Cache Behavior

  • Descent loop (Art::get): per-level: load NodePtr → decode tag → load node header (prefetch prefix) → compare prefix bytes → find_child(byte). Cache footprint per step: Node4 = 48 B (fits 1 cache line); Node16 = 160 B (3 lines, but SIMD loads 16 bytes aligned); Node48 = 304 B (~5 lines); Node256 = 2 KB (32 lines — only traversed in dense sub-trees).
  • find_child per type: Node4 linear 4-compare branchless; Node16 SIMD 1 _mm_cmpeq_epi8 + movemask + tzcnt; Node48 single array dereference; Node256 direct pointer load.
  • Branch predictability: Node4/16 miss-branch unpredictable on random keys; Node48/256 are branchless — this is the key reason high-fanout nodes win on random workloads.
  • Prefetch: insert _mm_prefetch of next node pointer before descending; measurable gain on 1M+ random key workloads.

Profiling Protocol

  • perf stat -e cache-misses,branch-misses,instructions,cycles on get_dense_u64 + get_sparse_u64.
  • Flamegraph (cargo flamegraph --bench art_bench): identify % in find_child vs prefix compare vs allocation.
  • valgrind --tool=cachegrind on deterministic 100k-op harness; report D1mr (L1 data read misses) per op.
  • Target: get_dense_u64 < 2 L1 misses/op average; get_sparse_u64 < 5 (tree deeper in cache misses due to random access).

Memory Density

  • Node4 = 48 B; Node16 = 160 B; Node48 = 304 B; Node256 = 2064 B.
  • Adaptive selection keeps average node size proportional to actual children: measured node-type histogram after 1M u64 inserts expected ~60% Node256, ~25% Node4 (near leaves), ~10% Node16, ~5% Node48 (distribution shifts with key density).
  • Cache residency win: ART for 1M u64 keys ≈ 30–50 MB; BTreeMap ≈ 48–64 MB; smaller footprint → higher L3 hit rate → lower latency.

Allocation Analysis

  • Get: zero allocations; pure pointer-chase descent.
  • Insert: at most one node allocation (grow or new inner node on prefix split); use slab/arena (Phase 10) to avoid GlobalAlloc overhead per insert.
  • Slab allocator: per-node-type free-lists; SlabAlloc<Node4>, SlabAlloc<Node16>, etc.; allocate in 4 KB pages; amortizes system-call overhead.
  • Arena mode: bulk-load path (artdb load subcommand): pre-allocate arena proportional to key count; zero-free during load, single bulk free on drop.

OLC Read Cost

  • OLC adds 2 atomic loads (read Version before + after) + a branch (restart?) per node level.
  • Single-thread overhead vs non-concurrent Art: ~5–15 ns/op on a 10-level tree (measured target).
  • Under 8-reader / 0-writer load: near-linear scaling (lock-free reads); 8 threads ≥ 6× throughput vs single thread.
  • Under 6-reader / 2-writer load: restart rate < 1% at moderate write throughput; restart spikes on bulk-load concurrency.

Tail Latency

  • grow (Node16→Node48): allocates new Node48, copies 16 children, frees old node → ~200 ns spike; amortized rare.
  • Prefix split on insert: allocates 1 new inner node + adjusts pointers → ~150 ns spike.
  • OLC restart: full descent redo → 1–3 µs in worst case; measured p99 vs p50 in olc_mixed bench.

Scalability Analysis

Cost vs n (key count)

  • Height = ⌈key_len_bytes / 1⌉ worst-case for single-byte span; in practice bounded by key byte-length, not n. For fixed-width u64 keys: height ≤ 8 regardless of n. Lookup cost = O(key_len), independent of n — ART does not degrade as n grows unlike O(log n) BTreeMap.
  • Memory growth: O(n × avg_node_size / avg_fanout) → sublinear in n for dense key spaces (Node256 amortizes 256 children per node). Sparse: closer to O(n) (many Node4 leaves).

Cost vs Key Length

  • Descent steps = key_len_bytes; each step = 1 find_child + 1 prefix-compare (≤ 8 bytes inline).
  • Long keys (e.g., 1 KB URLs): 1000-step descent → ~70–150 µs per lookup; mitigate with key truncation (hash suffix if suffix has no ordering requirement) or limiting MAX_KEY_LEN.
  • Optimistic prefix: long shared prefixes stored as prefix_len only (no extra bytes in header) — height reduction, but leaf verification adds ~1 random memory access.

Concurrent Read Scalability (ArtOlc)

  • Lock-free reads: no shared mutable state on read path; scales near-linearly with reader threads.
  • Measured target: 8 readers → ≥ 6× throughput vs single reader (overhead: 2 atomic loads per level + restart branch).
  • Writers serialize only on nodes in the touched path (lock coupling parent→child); unrelated subtrees fully concurrent.
  • Restart rate under write contention: < 1% at ≤ 10% write mix; rises steeply above 50% write mix (not the intended workload — see ROWEX for write-heavy).

Memory Scaling

  • BTreeMap: fixed ~48 B/key overhead (B-tree node + allocation metadata); growth linear.
  • ART adaptive: dense regime ~8–10 B/key effective (Node256 amortizes over 256 children); sparse regime ~30–50 B/key (many Node4 nodes with 1–2 children). Crossover: ART wins on memory at n > ~10k for typical mixed distributions.
  • EBR retired-node accumulation: proportional to concurrent writer throughput × epoch lag; bounded by max_retired_per_epoch config; default epoch advance every 1M ops.

EBR Reclamation Scaling Under Churn

  • High-churn workload (delete-heavy): retire list grows until all threads announce quiescent state; at 8 threads + 1M deletes/s, epoch lag ≤ 2 epochs → peak unreclaimed memory ≤ ~10 MB for Node4-heavy trees.
  • Scaling ceiling: epoch advance requires all threads to check in — 100+ threads with long quiescent intervals can delay reclamation; mitigate with hazard-pointer fallback or bounded grace periods.

Mental Models & First Principles

These mental models compress expert-level insight that is non-obvious from the data structures alone. Each is numbered MM1..MMn. The "Bug class without it" column names the failure mode that appears when this model is absent from the implementor's head.

# Mental Model What It Predicts Bug Class Without It Resolving §
MM1 Byte-trie depth = key length, not key count. Unlike a BST or B-tree whose height grows with n, ART height is bounded solely by key_len_bytes. For fixed-width u64 keys, height is always ≤ 8 regardless of n. Lookup latency is constant in n but linear in key length; no warm-up regression as the tree fills. "ART is getting slower as we insert more keys" — symptom misread as O(log n) degradation; root cause is key-length growth (e.g., URLs replacing u64). §4 System Constraints, Scalability Analysis (Cost vs n)
MM2 Tags live in pointer alignment bits, not in the struct. Every heap pointer on a 64-bit system is 8-byte aligned, leaving bits [2:0] free. NodeType is stored there, not in a header field. sizeof(NodePtr) == sizeof(*mut ()) — no overhead. Dereferencing requires stripping the tag first. NodePtr used directly as *mut Node4 without masking → misaligned read → UB on every dereference; MIRI flags immediately, hardware may trap or silently corrupt. §11.2, ADR-12, Phase 4
MM3 Prefix compression is a contract between writer and reader: pessimistic is safe, optimistic is fast. Pessimistic stores up to 8 inline bytes and compares them on every traversal step. Optimistic stores only prefix_len and verifies the full prefix only at the leaf. Optimistic saves memory and speeds inner-node traversal but defers mismatch detection to the leaf; an off-by-one in prefix_len is never caught until leaf comparison fails. "get returns None for a key that was definitely inserted" — caused by prefix_len set to the partial-match length instead of the full shared-prefix length during a split; leaf verification catches the bug but the fix requires correcting the split logic. §11.2 NodeHeader, Phase 6, ADR-14
MM4 Grow/shrink thresholds are asymmetric by design to prevent thrashing. Node4 grows to Node16 at exactly 4 children; it shrinks back from Node16 only at <5 children. The 1-child hysteresis band means a single insert+delete sequence does not toggle the node type. A key at the exact boundary (4 children, add one, remove one) leaves the node as Node16 rather than bouncing back to Node4. Correctness is unaffected; allocator churn is suppressed. Without the band: benchmark at threshold capacity shows 100× slowdown due to grow/shrink cycle on every alternating insert/delete; profiler shows 80% time in Box::new. §11.2 grow/shrink thresholds, Phase 5, ADR-17
MM5 OLC correctness requires version-before-read, not version-after-read. A reader snapshots the version word before it reads any field from the node, then validates the version after all reads are complete. Reading version after the first field opens a TOCTOU window. Any read of node fields that is not bracketed by (snapshot v, read fields, check v == v') is unsafe even if the individual reads appear atomic. "Stale child pointer crash": reader reads num_children after the version check, node is grown/replaced by writer between reads; reader follows a freed node. Caught by loom but invisible in normal testing. §11.4 Version, Phase 11, ADR-20, INV-9
MM6 EBR reclamation requires a minimum of three epochs, not two. With two epochs, a reader pinned at epoch E could hold a pointer to a node retired at epoch E, which a collector advancing to E+1 would free. A third epoch guarantees the retiring thread's epoch has been fully traversed before collection. The retire-list entry must survive until the global epoch advances by ≥ 2 past the retirement epoch; only then is it safe to free. "Use-after-free under sustained read pressure": two-epoch EBR frees a node while a long-running reader still holds it. Manifests as random value corruption under load; masked by GC pauses in managed runtimes, fatal in Rust without EBR. Phase 12, ADR-22, INV-10, §12.2
MM7 SIMD lane-mask truncation is mandatory. _mm_movemask_epi8 produces a 16-bit mask for all 16 lanes, but a Node16 may have num_children < 16. Bits beyond num_children in the mask correspond to uninitialized key bytes and must be zeroed before tzcnt. Without masking: if keys[num_children..15] happen to contain the search byte (garbage data), tzcnt returns a false-positive slot index; find_child returns a wrong child pointer. "Phantom child hit": lookup returns a wrong value for a byte not present as a child key; only reproducible when the uninitialized key slot byte coincidentally matches the query; depends on allocator behavior. Phase 9, §11.3, ADR-18

std::collections::BTreeMap chose maximally simple correctness over raw lookup speed. It has no unsafe code, predictable O(log n) behavior, and composes safely with Rust ownership. It wins when the key set is small (< 10k), key types are complex (non-byte-comparable), or the team cannot afford the unsafe surface. This blueprint rejects it as the production index because it cannot reach sub-microsecond lookup or scale reads linearly with threads (Leis ICDE 2013 §7).

WiredTiger SkipList (used in MongoDB 4.x for in-memory indexes) prioritizes write concurrency via per-level CAS. It wins for write-heavy workloads (> 50% writes under concurrent load) where OLC restart rates would degrade throughput. WiredTiger's skip list does not provide prefix compression, so memory usage is higher for common-prefix key spaces. This blueprint rejects it because the target workload is read-dominant (§4).

RocksDB SkipList MemTable adds epoch-based memory management on top of a similar concurrent skip list. It wins when the index is fronting an LSM tree (keys are frequently compacted/discarded) and when the language runtime provides a GC or explicit memory region lifetimes. Rust EBR matches most of the safety guarantees with lower overhead. This blueprint does not target an LSM architecture.

PostgreSQL B+-tree (nbtree) is optimized for disk-backed ordered indexes, amortizing random I/O across 8 KB pages with buffer pool caching. It wins when the index cannot fit in RAM, when update-in-place semantics are required, or when MVCC is built into the storage model. ART's node granularity (64 B – 2 KB) is inappropriate for disk-backed storage; this blueprint is an in-memory-only design by ADR-04.

Back-of-Envelope Capacity Model

All numbers are derived step-by-step from the System Constraints table (§4). Variables: n = key count, L = avg key length bytes, f = avg fanout.

Derived numbers:

C1 — Node count (inner nodes):

inner_nodes ≈ n / (avg_fanout - 1)

For n=10M keys, avg_fanout=16 (Node16 dominates a random-distribution workload): 10M / 15 ≈ 667k inner nodes.

C2 — Memory for inner nodes:

inner_bytes = inner_nodes × weighted_node_size
weighted_node_size ≈ 0.40×64 + 0.35×192 + 0.15×664 + 0.10×2072 ≈ 391 B

(Weights: Node4=40%, Node16=35%, Node48=15%, Node256=10% — typical mixed workload, Leis ICDE 2013 §6.) 667k × 391 B ≈ 261 MB inner node memory.

C3 — Memory for leaves:

leaf_bytes = n × (24 + L + sizeof(V))

For n=10M, L=16 B avg key, sizeof(V)=8 B: 10M × 48 B = 480 MB leaf memory.

C4 — Total index memory:

total_memory ≈ inner_bytes + leaf_bytes = 261 MB + 480 MB ≈ 741 MB

Fits within the §4 constraint of "≤ 2× BTreeMap baseline" (BTreeMap: ~10M × 48 B = 480 MB, so 741/480 ≈ 1.54×).

C5 — Lookup latency budget:

lookup_latency ≈ L × (1 cache_miss + find_child_cost)

For L=16, cache miss = 100 ns (DRAM), find_child for Node16 SIMD ≈ 3 ns: 16 × (100 + 3) ns ≈ 1.6 µs worst case (all DRAM misses). Hot path (cache resident): 16 × 3 ns = 48 ns. Target: ≤ 500 ns per §4 (achievable when upper tree levels are L1/L2 resident).

C6 — EBR retire-list peak memory:

peak_retired ≈ write_rate × epoch_lag × node_size

For 1M deletes/s, epoch lag 2, avg node size 391 B: 1M × 2 × 391 B = 782 MB/s × 2 = ~1.6 GB peak if epochs stall. Under normal operation (epoch advances every 1M ops, 8 threads, all checking in within 1 ms): peak ≈ 1M ops × 391 B = 391 MB — acceptable; configurable via max_retired_per_epoch.

C7 — SIMD throughput gain (Node16):

speedup = scalar_cycles / simd_cycles = 16 / 2 = 8×

Scalar: 1 comparison/cycle × 16 comparisons = 16 cycles. SSE2: _mm_cmpeq_epi8 (1 cycle) + _mm_movemask_epi8 (1 cycle) + tzcnt (1 cycle) = 3 cycles. Net speedup on Node16 find_child: ~5× (including load, mask, branch).

C8 — OLC restart rate under write contention:

restart_rate ≈ write_fraction × (traversal_steps / lock_hold_time_ratio)

For 10% write fraction, 8-level traversal, lock held for ~50 ns per node: restart_rate ≈ 10% × 8 × (50 ns / mean_read_ns). At 48 ns reads: ≈ 10% × 8 × 1 ≈ 0.8%. Measured target from §4: < 1% under ≤ 10% write mix — consistent.

C9 — Height ceiling:

height_max = key_len_bytes_max

For u64 keys: height = 8 (fixed). For 256-byte string keys: height = 256. Constraint: §4 sets MAX_KEY_LEN = 1024 B → absolute height ceiling = 1024 levels.

C10 — Node4 cache-line fit:

sizeof(Node4) = sizeof(NodeHeader) + keys[4] + _pad[4] + children[4×8]
             = 24 + 4 + 4 + 32 = 64 B = 1 cache line

This is a hard design invariant (ADR-13, P-cache-line): confirmed by assert_eq!(size_of::<Node4>(), 64) in Phase 4.

C11 — Concurrent reader scalability:

throughput_N_readers ≈ N × throughput_1_reader × (1 - restart_overhead)

For N=8, restart_overhead ≈ 0.8%: 8 × single_reader × 0.992 ≈ 7.94×. Target §4: ≥ 6× at 8 readers — satisfied with 1.9× margin.

C12 — Worst-case memory for adversarial keys:

adversarial_nodes ≈ n × key_len_bytes (one Node4 per byte, no sharing)
memory_adversarial = n × key_len_bytes × 64 B

For n=1M, key_len=16: 1M × 16 × 64 B = 1 GB — exceeds practical RAM. Mitigation: enforce MAX_KEY_LEN and monitor Art::stats() for pathological fanout.

Hard Questions (Self-Examination)

Each question requires synthesis of ≥2 sections. The "Resolving §" column names where to find the answer (or the starting point for deriving it). These are staff-engineer-level questions; a correct answer requires not just recall but cross-section reasoning.

  1. Why does prefix_len in NodeHeader need to be a u32 rather than a u8, even though MAX_PREFIX_LEN = 8? (Resolves §11.2 NodeHeader + Phase 6 optimistic prefix) A u8 (max 255) could represent lengths up to 255 bytes of shared prefix. But a u32 is required because prefix_len stores the logical full length of the shared prefix, which can exceed 255 bytes for long string keys under optimistic prefix mode. A 256-character URL prefix would overflow a u8.

  2. If two concurrent readers both read the same node version and both see version = 42 before reading, and a writer upgrades and bumps the version to 44 between the two readers' validation checks, what happens? (Resolves §11.4 Version + Phase 11 OLC + INV-9) Both readers validate 42 == 42 (their snapshot). The writer has already completed by the time they validate; neither restarts. This is safe — OLC only requires that the version did not change during a single reader's traversal of that node, not across multiple readers.

  3. Why do we store the full key in Leaf<V> rather than only the suffix below the leaf? (Resolves §11.2 Leaf + Phase 6 lazy expansion + ADR-14) With optimistic prefix compression, the traversal descends to the leaf without fully verifying the path's shared prefix. The leaf's full key is needed to retroactively verify the entire path's prefix at the end of traversal. Storing only the suffix would prevent detecting a mismatch caused by a wrongly-split shared prefix.

  4. What is the minimum number of epochs needed by EBR, and why does adding a 4th epoch not improve safety? (Resolves §12.2 + INV-10 + MM6) Three epochs are the minimum. Epoch transitions require all threads to advance past epoch E before nodes retired at E are freed. Four epochs add latency without improving safety — the guarantee is already tight at three: retire at E, collect only when global epoch ≥ E+2, which requires two full epoch advances (all threads check in twice). A 4th epoch would only delay collection further without closing any new race window.

  5. In the SIMD node16_search, why must the mask be shifted by n bits before tzcnt, not by 16 - n bits? (Resolves §11.3 + Phase 9 + MM7) _mm_movemask_epi8 produces a 16-bit mask where bit i is 1 if lane i matched. Lanes n..15 are uninitialized key bytes. To exclude them, we AND the mask with (1 << n) - 1, which zeroes all bits ≥ n. This is "shift n bits from the right" not "16 - n from the left" because we want the lower n bits, not the upper.

  6. What invariant guarantees that OLC readers never observe a torn write to a 64-bit pointer? (Resolves §11.4 ArtOlc + Phase 11 + ADR-21) x86-64 guarantees that naturally-aligned 8-byte loads and stores are atomic (Intel® 64 and IA-32 Architectures Software Developer's Manual Vol. 3A §8.1.1). NodePtr is 8 bytes and all heap allocations are ≥8-byte aligned (guaranteed by Rust's global allocator). Combined with the version-based OLC protocol, no torn pointer can be observed: even if a writer replaces a child pointer mid-read, the version check will catch the update and trigger a restart.

  7. Why are the grow and shrink thresholds not symmetric (e.g., grow at 4, shrink at 3 instead of grow at 4, shrink at 4)? (Resolves §11.2 grow/shrink thresholds + MM4 + Phase 5 ADR-17) If grow and shrink used the same threshold, any workload that alternates insert/delete at exactly the boundary would toggle the node type on every operation — O(n) allocations for O(1) logical ops. The 1-child hysteresis band (grow at capacity, shrink at capacity - 1) means one net-remove is needed after a grow before a shrink fires. This matches the Leis 2013 paper §4 recommendation.

  8. Explain why ART's memory usage per key is worse than BTreeMap for sparse u64 key spaces, yet better for dense spaces. (Resolves §4 + Comparative Architecture Table + C4 Back-of-Envelope) For dense sequential u64 keys, upper-level Node256 nodes amortize 2072 bytes over 256 children ≈ 8 B/child — better than BTreeMap's ~48 B/key. For sparse random u64 (e.g., 1000 keys spread over [0, u64::MAX]), the tree is extremely shallow (8 levels) but each level has mostly Node4 nodes with 1–2 children. 1000 keys × 8 levels × 64 B/Node4 ≈ 512 KB vs BTreeMap 1000 × 48 B = 48 KB — ART uses 10× more memory. Dense wins; sparse loses. §4 constrains the use case to assume ≥ 50% fanout average.

  9. What happens if prefix_len overflows during a split? What is ArtError::PrefixOverflow for? (Resolves §11.1 ArtError + Phase 6 + §4 MAX_KEY_LEN) prefix_len is a u32, max ~4 billion. With MAX_KEY_LEN = 1024, prefix_len can never overflow in practice. PrefixOverflow is a defensive error for the case where a buggy caller bypasses MAX_KEY_LEN enforcement and passes a key longer than u32::MAX bytes — structurally impossible with the constraint, but the error is retained for API surface completeness and future-proofing.

  10. If we remove the deny(unsafe_code) attribute from art-core and art-trie and allow unsafe there, what specifically breaks? (Resolves Phase 0 ADR-03 + §7 INV-3 + ADR-02) The two safe crates (art-core, art-trie) serve as a correctness baseline for differential testing. If unsafe leaks in, a bug in a raw pointer operation in art-trie could appear as a false-negative in differential tests (both the ART and the oracle happen to corrupt in the same way). The isolation guarantee — that any mismatch between art-trie (safe) and art-art (unsafe) is a bug in art-art — collapses.

  11. Why does the conformance suite require testing with b"" (empty key)? (Resolves Phase 0.5 Pitfalls + §7 + Phase 4 edge cases) The empty key b"" is a valid ART key — it represents the "root value" (a value stored at the tree root, not associated with any byte sequence). If insert iterates key.iter() and exits immediately on empty key without storing a value, root.value is never set. This is a common off-by-one: the loop terminates before the terminal "store value" step. The conformance fixture explicitly tests this boundary.

  12. What is the computational cost of Art::stats() and when should it NOT be called? (Resolves §11.2 ArtStats + Performance Engineering + Phase 4 deliverable) stats() requires a full O(n) tree traversal counting all node types and summing byte sizes. This is equivalent to iterating all keys. It should not be called on hot paths, in benchmarks, or in production under load. Its intended use is debugging, capacity planning, and test assertions. Calling it in a benchmark introduces O(n) overhead to an otherwise O(key_len) operation.

  13. Why can't ArtOlc implement &mut self insert/remove if it is to be Send + Sync? (Resolves §11.4 ArtOlc + Phase 11 ADR-20 + §7 INV-9) &mut self requires exclusive access, which would serialize all writes — defeating the purpose of OLC. ArtOlc uses AtomicUsize for len and internal unsafe + atomic operations for node mutations, presenting a &self API for both reads and writes. This is the standard Rust pattern for concurrent data structures: interior mutability with safety guaranteed by the synchronization protocol rather than the borrow checker.

  14. What would happen if EBR's retire is called without a pin guard active? (Resolves §11.4 Ebr + Phase 12 + MM6) Without a pin, the calling thread has no announced local epoch. The global epoch could advance immediately, potentially collecting the just-retired node before all readers have finished with it. This is a use-after-free bug. The retire signature takes guard: &EbrGuard precisely to enforce (via Rust lifetimes) that the caller holds a pin at the time of retirement.

  15. If you had to add a 5th key type to KeyEnc (e.g., Decimal128 — a fixed-point decimal), what must the new encode output satisfy, and which existing tests would immediately verify correctness? (Resolves §5 Required Reading IEEE 754-2008 + Phase 1 + Phase 13 differential testing) The output must satisfy: memcmp(encode(a), encode(b)) == a.cmp(b) for all Decimal128 values. Required: encode negative values before positive, zero in its canonical position, and handle the sign and exponent fields so that the byte string order matches decimal numeric order. Existing tests: art-trie/tests/oracle.rs differential test immediately detects ordering bugs — any key insertion that yields wrong range-scan order (vs BTreeMap with native Decimal128 ordering) fails.

  16. Describe a scenario where pessimistic prefix is strictly better than optimistic prefix, even for long common prefixes. (Resolves Phase 6 ADR-14 + ADR-15 + MM3) When get requests for non-existent keys are the dominant workload (false-lookup-heavy, e.g., a cache miss detector). With optimistic prefix, a non-existent key with a long shared prefix descends to a leaf and pays the leaf-verification random memory access (~100 ns) before returning None. With pessimistic prefix (≤8 inline bytes), a mismatch is detected at the first non-matching prefix byte during descent — an L1-resident comparison — without reaching the leaf at all. For purely-existent-key workloads, optimistic is faster; for mixed or negative-dominant, pessimistic wins.

  17. Why does Node48 use child_index[256] (u8 per byte value) instead of a sorted 48-entry array like Node4/Node16? (Resolves §11.2 Node48 + Phase 5 ADR-17 + Comparative Architecture Table) At 48 children, a sorted linear scan (48 comparisons) or even binary search (6 comparisons) is slower than a single O(1) direct-indexed lookup. child_index[byte] is a single cache-line-resident byte load (256 bytes = 4 cache lines; the specific byte is on one of them). SIMD cannot efficiently vectorize a 48-entry sorted search with variable-size keys. The design matches the paper's analysis: 16-entry threshold is the sweet spot for SIMD; beyond that, direct indexing wins.

Alternative Architectures (Roads Not Taken)

Alt-1: B+-Tree (disk-oriented balanced tree)

Show the original text diagram
             [50 | 100 | 150]                 ← inner node (fanout B=4 shown)
            /    |     |     \
   [10|20|30] [60|70|80] [110|120|130] [160|170|180]  ← leaf nodes (linked list)

Regime where it wins: When the index cannot fit in RAM; when update-in-place + ACID guarantees are required; when the system is disk-backed (SSD or HDD) and 8 KB page granularity amortizes I/O cost. PostgreSQL's nbtree, MySQL InnoDB, and SQLite all use B+-trees precisely because the page = block device sector alignment is the dominant performance constraint.

Real system: PostgreSQL nbtree (src/backend/access/nbtree); MySQL InnoDB clustered index.

Why this blueprint rejects it: ART targets in-memory-only operation (ADR-04). B+-tree node sizes (4–64 KB) are dictated by disk I/O granularity, not CPU cache lines. An in-memory B+-tree with 64-byte node sizes degenerates toward a sorted array with O(B) scan cost. ART's byte-at-a-time descent cannot be expressed in a B+-tree structure.

Alt-2: Skip List (probabilistic ordered structure)

Show the original text diagram

Level 2:  [Head] ────── [20] ─────────────── [70] ──── [Tail]

Regime where it wins: When concurrent write throughput matters more than read throughput; when the key type has an arbitrary comparator (no byte-comparable encoding needed); when implementation simplicity is paramount. WiredTiger (MongoDB) uses a concurrent skip list for its in-memory ordered index precisely because per-level CAS enables lock-free writes, and write workloads dominate OLTP.

Real system: WiredTiger wt_skip_list_t (src/include/skip.h in the MongoDB source tree); Redis zset sorted set.

Why this blueprint rejects it: Target workload is read-dominant (§4). Skip-list read throughput is O(log n) — worse than ART's O(key_len) for large n. No prefix compression: skip-list nodes store full key copies, doubling memory for common-prefix workloads. No SIMD opportunity on the traversal path.

Alt-3: Hash Trie (HAMT — Hash Array Mapped Trie)

Show the original text diagram
            [root bitmap: 0b0101_1010]
           /         |          \
    [subnode]    [subnode]    [leaf: "hello" → 42]
      ...           ...

Regime where it wins: When key ordering is never needed — only point lookups; when hash distribution is better than byte distribution (adversarial key sets); when the trie must support persistent/functional semantics (structural sharing). Clojure's PersistentHashMap and Scala's HashMap use HAMT for immutable maps.

Why this blueprint rejects it: Ordered range scans and prefix scans are load-bearing requirements (§4, OrderedMap trait). HAMT's hash-based dispatch destroys key order; range scans require full-tree traversal. This blueprint's primary value proposition over a plain HashMap is the ordered iteration and prefix-scan capability.

Glossary

Term Definition
trie Ordered tree where each node represents a prefix of a key; children keyed by the next byte (or bit for PATRICIA); height = key length in bytes/bits.
radix tree Compressed trie where chains of single-child inner nodes are collapsed into edge labels; reduces height + node count.
PATRICIA Binary radix tree (Practical Algorithm To Retrieve Information Coded In Alphanumeric); branching on individual bits; each node stores the bit-position tested.
prefix The sequence of bytes shared by all keys in a subtree; stored in NodeHeader.prefix (pessimistic) or implied by prefix_len (optimistic).
edge label In RadixTree, the byte sequence on a compressed edge between two inner nodes; replaces a chain of single-child trie nodes.
path compression Collapsing a sequence of single-child inner nodes into a single edge label or header prefix; reduces traversal depth to O(key_len).
pessimistic prefix Path-compression mode: up to MAX_PREFIX_LEN (8) bytes stored inline in NodeHeader.prefix; compared byte-by-byte on every traversal step; always correct.
optimistic prefix Path-compression mode: prefix_len may exceed 8; extra bytes NOT stored in header; correctness verified at leaf's full key on lookup; avoids memory overhead for long shared prefixes.
lazy expansion A single-descendant path is NOT materialized as inner nodes; the Leaf is placed directly. An inner node is created only when a second key diverges (split-on-insert).
adaptive node An ART inner node whose internal representation (key array + child array) is chosen based on actual child count; one of Node4/Node16/Node48/Node256.
Node4 ART inner node; up to 4 children; keys: [u8; 4] (sorted) + children: [NodePtr; 4]; lookup = linear scan (branchless). Shrink from Node16 when child count drops to 3.
Node16 ART inner node; 5–16 children; keys: [u8; 16] (sorted) + children: [NodePtr; 16]; lookup = SIMD _mm_cmpeq_epi8 + movemask. Grow from Node4 at 5, shrink from Node48 at 12.
Node48 ART inner node; 17–48 children; child_index: [u8; 256] maps key byte to slot (0xFF = empty) + children: [NodePtr; 48]; O(1) lookup by index byte.
Node256 ART inner node; 49–256 children; children: [NodePtr; 256]; direct index by key byte; O(1) unconditional. Shrink to Node48 when count drops to 37.
fanout Number of children an inner node currently holds; determines which adaptive node type is used.
span Number of key bits (or bytes) consumed per level; ART span = 8 bits (1 byte) per level, giving up to 256-way branching.
partial key The single byte (span=8) at a given depth that selects which child pointer to follow in an ART inner node.
leaf Leaf<V> { key: Box<[u8]>, value: V } — terminal node storing the complete original key (needed for optimistic-prefix verification) plus the associated value.
inner node Any non-leaf node (Node4/Node16/Node48/Node256) that routes traversal; holds a NodeHeader and a child array.
node header NodeHeader { node_type, num_children, prefix_len, prefix: [u8; MAX_PREFIX_LEN] } — common prefix of every ART node; stored at the start of every node struct for uniform access.
tagged pointer NodePtr(*mut ()) — low bits (or a header byte) encode NodeType, eliminating a separate type tag field and enabling O(1) type dispatch on pointer read.
binary-comparable key A byte string produced by KeyEnc such that memcmp(encode(a), encode(b)) == a.cmp(b); enables ART to serve as an ordered index via byte-wise traversal.
order-preserving encoding KeyEnc contract: u64 → big-endian 8 bytes; i64 → flip sign bit then big-endian; f64 → IEEE total-order transform; str → raw bytes + 0x00 terminator (no key is a prefix of another).
find_child fn find_child(node: NodePtr, byte: u8) -> Option<NodePtr> — dispatches to node-type-specific lookup (linear, SIMD, index, direct).
add_child fn add_child(node: &mut NodePtr, byte: u8, child: NodePtr) — inserts a partial-key → child mapping; triggers grow when node is full.
remove_child Removes a partial-key mapping; triggers shrink when below the lower capacity threshold.
grow Node-type upgrade: Node4→Node16, Node16→Node48, Node48→Node256; triggered when num_children reaches the node's capacity. Old node freed after copying.
shrink Node-type downgrade: Node256→Node48, Node48→Node16, Node16→Node4; triggered when num_children drops below threshold (e.g., Node48 → Node16 at 12 children).
in-order traversal Depth-first, byte-ascending child visitation across all adaptive node types; produces keys in sorted (binary-comparable) order.
range scan OrderedMap::range(lo, hi) — in-order iteration restricted to keys in [lo, hi]; relies on binary-comparable encoding for correctness.
prefix scan OrderedMap::prefix_iter(prefix) — descends to the subtree rooted at prefix, then full in-order traversal of that subtree.
successor Smallest key strictly greater than a given key; derived from in-order traversal with early termination.
predecessor Largest key strictly less than a given key; derived from reverse in-order traversal.
SIMD dispatch In art-simd: Node16 key-byte lookup using _mm_cmpeq_epi8(key_vec, target) + _mm_movemask_epi8 + trailing_zeros; falls back to scalar when SSE2 unavailable.
movemask _mm_movemask_epi8 — collapses 16 comparison results (one per byte lane) to a 16-bit bitmask; trailing_zeros on the mask gives the matching child index in O(1).
slab / arena allocator Pool allocator for fixed-size ART nodes; eliminates per-node malloc overhead; nodes of each type (Node4, Node16, …) allocated from a typed slab.
optimistic lock coupling ART-OLC concurrency scheme: readers never lock; they capture a node's Version before descending, re-verify after reading; retry if changed. Writers CAS the lock bit, couple parent→child locks during structural changes.
ROWEX Read-Optimized Write EXclusion — a related ART concurrency scheme (Leis et al. DaMoN 2016); referenced for context; art-concurrent implements OLC.
version counter Version(u64) per node; bit 0 = obsolete, bit 1 = locked, bits 2..63 = even counter incremented on each write; readers detect concurrent modification via counter change.
obsolete bit Bit 0 of Version; set when a node is replaced (e.g., after grow/shrink); causes any reader holding a reference to restart.
restart Reader detects Version mismatch or obsolete bit → discards all read results, returns to root, retries traversal from scratch.
epoch-based reclamation (EBR) Ebr in art-concurrent: global epoch + per-thread local epoch + retire lists; a node is truly freed only after all threads have passed through a quiescent state past the epoch in which it was retired.
quiescent state A point in a thread's execution where it holds no references to shared ART nodes; threads report quiescent states to advance the global epoch.
ABA ABA problem: a pointer is freed, reallocated at the same address, making a stale CAS succeed spuriously; prevented in art-concurrent by EBR (node not reused until all readers are past the retirement epoch).
OrderedMap<V> Trait in art-core; implemented by Trie256, RadixTree, Patricia, Art<V>, and ArtOlc<V>; uniform surface for get/insert/remove/range/prefix_iter.
KeyEnc Trait in art-core; single method encode(&self, out: &mut Vec<u8>); implementors: u32, u64, i64, f64, &str, composite tuples.
