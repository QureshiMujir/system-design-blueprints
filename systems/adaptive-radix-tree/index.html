In one paragraph

This is an in-memory sorted index, written as a Rust library (Art<V>) with a small command-line tool (artdb) (§1, §3). Keys are byte strings, and the tree branches on one byte at a time. Each node picks a small or large child table to match its real number of children: the adaptive radix tree, or ART (§1, P1). It answers point, range and prefix queries, so it is a real ordered map and not only a hash-map stand-in (§1). The program that embeds it runs it (§1). The headline design target is a point get under 100 ns in cache (M1, §4).

The problem, concretely

You want a sorted in-memory index that answers range queries such as "every key from ant up to bee" (§8.8) and prefix queries (§1). A hash map cannot do either (§4). A balanced tree can, but its height grows with the number of keys (§4, MM1). The obvious trie fixes the height: one level per key byte. But each node of a plain 256-way trie holds 256 child slots whether it needs them or not (§3, Trie256). The blueprint's own six-key example (ann, ant, anti, be, bee, beet) needs 9 such nodes at about 2048 B each, "total inner ≈ 18 KB for 6 keys" (§8.1). P1 states the scaled-up version of the waste: a fixed 256-slot node everywhere costs about 2 GB wasted at 1 M keys, against about 30 MB with adaptive nodes (P1).

There is also a correctness trap. If ant and anti are stored as raw bytes, ant is a byte prefix of anti, and two distinct keys share a whole traversal path. The design adds a 0x00 terminator to strings for this reason (§8.2, ADR-09). Finally, signed integers and floats do not sort correctly as raw bytes, and a wrong encoding "silently reverses the ordering of negative values" with no error (P2). The design answers three pressures: memory proportional to real fanout, byte order equal to logical order, and height set by key length, not key count (P1, P2, P10).

How it works, end to end

The blueprint's own diagram (§3, "Canonical structure"), drawn from its text version and coloured by role:

Follow one get through those boxes:

  1. Encode. The caller's value goes through the KeyEnc trait in art-core, which produces bytes whose memcmp order equals the logical order (§3, §8.2, P2). A key longer than MAX_KEY_LEN (2048 B) is refused with ArtError::KeyTooLong, and no public operation panics (§4).
  2. Read the root pointer. The root is a NodePtr: a pointer whose low 3 bits carry the node's type (ADR-12, §8.3). Reading the tag tells the code which of Node4, Node16, Node48, Node256 or Leaf it is looking at (§3, INV-8).
  3. Check the prefix, then pick the child. The NodeHeader holds up to 8 shared bytes, compared on the way down (§8.5). find_child(node, byte) then dispatches by type: linear scan for Node4, SIMD search in art-simd for Node16, an index table for Node48, direct indexing for Node256 (§8.6).
  4. Reach a Leaf. The leaf stores the complete key, which is compared against the query. That is what makes long hidden prefixes safe (P4, INV-5, §8.5).
  5. Concurrent variant. In art-concurrent, ArtOlc<V> wraps steps 2 to 4 in a version check at every node, and restarts from the root if anything changed (§3, P6, INV-9). Nodes the writers unlink are freed later by the Ebr domain (§3, P7).

Art<V> is !Send + !Sync and ArtOlc<V> is Send + Sync, so mixing them is a type error (§3, Trust boundaries). The baselines Trie256, RadixTree and Patricia live in art-trie and exist to measure height and memory before adaptivity is added (§3, §1).

The core ideas

Idea 1: make byte order equal logical order (§8.2, P2, INV-1)

Plain words: if you turn every key into bytes whose dictionary order is the real order, then walking the tree in byte order gives sorted output with no comparison function. The encoding rules (§8.2):

Type Rule
u32, u64 big-endian bytes
i64 flip bit 63, then big-endian
f64 if bit 63 is set flip all 64 bits, otherwise flip only bit 63
str UTF-8 bytes, then a 0x00 terminator
composite concatenate the parts in declaration order

The blueprint's worked proof for i64 (§8.2): raw -3 is 0xFFFF_FFFF_FFFF_FFFD, which becomes 0x7FFF_FFFF_FFFF_FFFD after the flip. 0 becomes 0x8000_0000_0000_0000 and 1 becomes 0x8000_0000_0000_0001. So the byte order is -3 < 0 < 1. For strings, "ant" is 61 6E 74 00, so it is no longer a byte prefix of "anti" (§8.2).

Idea 2: four node sizes that grow and shrink (§8.3, §8.4, INV-2, P1)

Plain words: a node with 3 children should not pay for 256 slots. The tree keeps four node types and moves a node up or down as children come and go (adaptive nodes). Bands and layouts (§8.3, §8.6):

Node Children How find_child works Size (§8.3)
Node4 1–4 linear scan of sorted keys[4] 64 B, 1 cache line
Node16 5–16 SIMD search of sorted keys[16] 168 B, 3 lines
Node48 17–48 child_index[256] byte table, then children[48] 664 B, 11 lines
Node256 49–256 children[byte] directly 2072 B, 33 lines

Growing is a three-step trace (§8.4, §8.7): when a full Node4 gets a fifth child, allocate a Node16, copy the 4 keys and children, insert the new one. Node16 to Node48 happens at 16 plus an insert, and Node48 to Node256 at 48 plus an insert (§8.4).

The blueprint disagrees with itself about when nodes shrink, and it does not say which version wins:

  • §8.4's table shrinks Node16 to Node4 at 2 children, Node48 to Node16 at 5 and Node256 to Node48 at 17 ("capacity_lower - 1"); T9 also describes a 2-child gap (§8.4, T9).
  • §3 and §11.2 shrink at < 5, < 17 and < 49, matching INV-2's bands; MM4 also says < 5.
  • §5.4 gives < 5, < 13 and < 37; the glossary gives 3, 12 and 37; Q7 of the hard questions says grow at 4, shrink at 3 (§5.4, Glossary, Hard Questions, Q7).

All versions agree on the purpose: grow and shrink points differ so insert/delete at the boundary does not rebuild the node every time (MM4, T9). A debug_assert! fires if a node leaves its band (P13).

Idea 3: path compression and lazy expansion (§8.5, P3, INV-3, INV-4)

Plain words: if every key below a node shares the same next few bytes, store those bytes once in the node instead of spending one node per byte (path compression). Three tools (§8.5):

  • Pessimistic prefix: up to MAX_PREFIX_LEN = 8 bytes sit in NodeHeader.prefix and are compared on every step, so it is always correct.
  • Optimistic prefix: when the shared prefix is longer than 8, prefix_len is stored but only the first 8 bytes are. The hidden tail is skipped on the way down and verified against the leaf's full key at the end. A mismatch means the key is absent, not that the tree is corrupt (§8.5, INV-4).
  • Lazy expansion: a path with only one key below it is just a Leaf hung off the parent. An inner node is created only when a second key diverges (§8.5, P3).

The blueprint's worked prefix split (§8.5): the tree holds antidote as a lazy leaf under a, n, t. Insert antelope. (1) Walk to the leaf antidote. (2) Compare byte by byte from position 3: i against e differs. (3) Make a new Node4 with an empty prefix holding i leading to antidote and e leading to antelope, and put it where the old leaf was (§8.5). The full six-key insertion trace is in §8.7.

Idea 4: a 16-way search in one instruction (§3, §8.6, INV-12, MM7)

Plain words: a Node16's 16 key bytes fit exactly in one 16-byte register (ADR-18). The CPU compares the query byte against all 16 at once and returns a bit mask; the first set bit is the child slot (SIMD, here SSE2). The steps (§3): broadcast the query byte, _mm_cmpeq_epi8 against keys[0..16], _mm_movemask_epi8 to get the mask, AND with (1 << num_children) - 1, then trailing_zeros.

MM7 calls the AND mandatory (MM7). A node with fewer than 16 children has stale bytes in its unused slots, and without the AND one of them can match the query and return a "phantom child" (MM7, FM-10). INV-12 requires the SIMD path and the scalar fallback to return identical answers (INV-12). The blueprint describes the scalar fallback two ways: a linear scan in §3, §4, §11.3 and INV-12, but a binary search in §8.6, P11 and Phase 9 (§21).

Idea 5: readers that never take a lock (§3, P6, INV-9, MM5)

Plain words: each node carries a version number. A reader notes the version, reads the node, then checks the version again. If it changed, a writer touched the node, so the reader throws its work away and starts over from the root (optimistic lock coupling, OLC). The version word is (§3): bit 0 = obsolete, bit 1 = write-locked, bits 2 to 63 = counter. Writers take the lock bit with a compare-and-swap, lock the parent before the child, and bump the counter on release; readers never set a lock bit, so their worst case is a restart loop, not a block (§3). MM5 states the rule that matters: snapshot the version before reading any field and validate after the last read, or a writer can replace the node between reads (MM5).

Idea 6: free memory only when no reader can still hold it (§3, P7, INV-10, MM6)

Plain words: a writer that unlinks a node cannot free it at once, since a lock-free reader might still be standing on it. Freed nodes go on a retire list, and are released only after every thread has passed through a point where it holds no node pointers (epoch-based reclamation, EBR). The design keeps a global epoch cycling through 0, 1, 2 plus a per-thread epoch and retire list; epoch E-2's list is safe to free once all threads have observed E (§3). MM6 says three epochs are the minimum and two are not enough (MM6). Cost: a thread parked inside a read section holds up reclamation, so INV-10 asks for a maximum pin duration (INV-10).

The trade-offs — where engineers disagree

Key representation: encode to bytes, not a comparator (ADR-05)

Chosen: Key(Vec<u8>) plus a KeyEnc trait that makes bytes sort like values, because radix descent works byte by byte and "a comparator cannot drive byte-by-byte descent" (ADR-05). Rejected: store typed keys and pass a comparator. When the rejected choice is right: for a general B-tree-style structure where the comparator is the only ordering tool needed and byte decomposition is unnecessary, such as a skip list or a sorted array (ADR-05).

Adaptive node types instead of one fixed node (ADR-11)

Chosen: Node4, Node16, Node48, Node256 with bands 1–4, 5–16, 17–48, 49–256, because memory per node should follow the number of children (ADR-11, P1). Rejected: a fixed 256-wide node, a binary search tree, or a hash node. When the rejected choice is right: a fixed Node256 wins for maximally dense key spaces, where every byte value is present at every level and type-dispatch costs more than the memory it saves. A hash node wins when keys are random and no range queries are needed (ADR-11).

Prefix strategy: inline plus verify-at-leaf (ADR-14)

Chosen: pessimistic prefix up to 8 B plus optimistic prefix beyond it, verified at the leaf; this adds "one leaf comparison, not full-tree re-traversal" (ADR-14). Rejected: pessimistic-only with truncation, which cannot tell apart keys that share more than 8 bytes. When the rejected choice is right: with uniformly short keys (8 B or less), where the extra leaf dereference of optimistic checking adds cache misses that inline comparison avoids (ADR-14). A related case from the hard questions: a workload dominated by lookups of absent keys favours pessimistic prefixes (Hard Questions, Q16).

Concurrency: optimistic lock coupling (ADR-20)

Chosen: OLC: per-node version counters, lock-free reads, restart on conflict, with a "lower implementation complexity than ROWEX" (ADR-20). Rejected: ROWEX (deferred), a global RwLock<Art>, or a pure lock-free CAS design. When the rejected choice is right: ROWEX for write-heavy loads (over 30% writes, ADR-20) where OLC reader restarts hurt throughput; a global RwLock for one writer and few readers; lock-free CAS on hardware with transactional memory (ADR-20). ADR-21 repeats the ROWEX case with a different figure: sustained writes over 50% (ADR-21).

Memory reclamation: epochs (ADR-22)

Chosen: EBR: low read-path overhead and "simpler than hazard pointers for tree traversal" (ADR-22). Rejected: hazard pointers, reference counting (Arc), or leaking on delete. When the rejected choice is right: hazard pointers when threads can stay in a read section indefinitely and must not block reclamation; Arc for a simple single-threaded prototype where the refcount cost does not matter (ADR-22).

Roads not taken

B+-tree (Alternative Architectures, Alt-1): wins when the index cannot fit in RAM or needs update in place with ACID guarantees, because 8 KB pages amortise disk I/O. Rejected because ART targets in-memory-only operation and its byte-at-a-time descent cannot be expressed in a B+-tree. Alt-1 cites ADR-04 for the in-memory decision, but the persistence deferral is ADR-23 (Alt-1, ADR-04, ADR-23).

Skip list (Alt-2): wins when concurrent write throughput matters more than reads, when keys have an arbitrary comparator, or when simplicity is the goal. Rejected because the target workload is read-dominant (§4) and skip-list reads are O(log n) with no prefix compression.

Hash array mapped trie (Alt-3): wins when ordering is never needed, when hashing spreads adversarial keys better, or when immutable structural sharing is wanted. Rejected because range and prefix scans are load-bearing here and hashing destroys key order.

Deferred features (Deferred Features Register): ROWEX (ADR-21), persistence, WAL and mmap (ADR-23), AVX-512 (ADR-18), distributed sharding and MVCC are all left out of scope.

What must never be false

  • INV-1: in-order traversal yields ascending memcmp order; caught by a property test over range(..) and a differential test against BTreeMap::iter() (§7).
  • INV-2: num_children stays in its type's band; caught by debug_assert! in add_child (§7, P13).
  • INV-3: a node's stored prefix matches every key below it; caught by re-traversing all keys (§7).
  • INV-4: a hidden prefix tail (prefix_len > 8) is checked against a leaf's full key; caught by fuzzing keys that share more than 8 bytes (§7).
  • INV-5: every Leaf holds the complete encoded key; caught by a unit test with a long key (§7).
  • INV-6: get after insert finds the value, after remove finds None; caught by random-sequence tests against BTreeMap (§7).
  • INV-7: no two children share a key byte and Node4/Node16 keys ascend; caught by debug_assert! on consecutive pairs (§7).
  • INV-8: a NodePtr's tag matches the node's node_type; caught by Miri and debug_assert_eq! (§7).
  • INV-9: an ArtOlc reader sees a consistent snapshot or restarts; caught by loom, stress tests and a per-thread restart counter (§7).
  • INV-10: a retired node is freed only after every thread active at retirement passes a quiescent state; caught by AddressSanitizer, Miri and loom (§7).
  • INV-11: height never exceeds the longest key in bytes; caught by artdb stats height (§7).
  • INV-12: SIMD and scalar Node16 search agree; caught by a property test over 1000 random nodes × 256 bytes and a divergence counter that must read zero (§7).

What breaks in production

  • FM-1, wrong iteration order. Symptom: range() or prefix_iter() returns keys out of order, or a differential test diverges. Root cause: a KeyEnc that is not order-preserving (little-endian u64), a skipped subtree, or a leaf placed on the wrong branch. Detection: the memcmp_order property test and the differential fuzzer. Recovery: none at runtime, so the iterator returns wrong data silently; bisect with artdb viz, fix, and keep memcmp_order as a release gate (FM-1).
  • FM-3, memory corruption or segfault. Symptom: SIGSEGV, wrong value, a tag-check assertion or a Miri report. Root cause: a mismatched NodePtr tag, a Node48::child_index[b] >= 48, a double-free of a leaf. Detection: Miri in CI, debug_assert_eq! on tags. Recovery: none (undefined behaviour); reproduce under Miri and audit the grow path (FM-3).
  • FM-5, optimistic-prefix mis-verification. Symptom: get(k) returns a value for a different key, or None for a present one. Root cause: the leaf-key check uses a truncated key or the wrong offset. Detection: prop_no_false_positives and prop_get_after_insert. Recovery: trace prefix_len against the leaf bytes and fix the offset (FM-5).
  • FM-6, torn read or use-after-free under concurrency. Symptom: garbled values, a segfault, or a loom data race. Root cause: check_or_restart not called, the epoch not advanced before reclaim, or wrong atomic ordering. Detection: loom and stress tests. Recovery: restarts cover transient torn reads; EBR covers use-after-free; reproduce with loom and audit every multi-field read (FM-6).
  • FM-7, restart livelock. Symptom: readers spin and throughput falls toward zero. Root cause: a writer holding a lock too long, or starvation under heavy write contention. Detection: restart rate above a threshold (the example is 10k restarts/s sustained). Recovery: exponential backoff (spin, yield, park); keep the writer critical section to a pointer swap (FM-7).
  • FM-10, SIMD and scalar disagree. Symptom: results change with the simd feature, or a phantom child appears. Root cause: the movemask is not masked with num_children. Detection: the INV-12 property test on both CI feature configurations. Recovery: disable the simd feature until fixed (FM-10, INV-12).

Threats worth knowing (Threat Model): T1 a huge key makes the spine deep, answered by the KeyTooLong cap (T1). T3 a wrong user KeyEnc silently breaks range queries, answered by a release-gate property test (T3). T7 use-after-free when a writer frees a node a reader stands on, answered by EBR (T7). T9 insert/delete churn at a node-type boundary, answered by asymmetric thresholds (T9). T11 unbounded growth, which the library cannot stop; the caller sets the limit using memory_bytes() (T11).

How it compares

  • BTreeMap (Rust standard library) chose simple, safe correctness and has no unsafe code. That fits small key sets (under 10k), key types that are not byte-comparable, or teams that cannot afford an unsafe surface. This blueprint instead aims for sub-microsecond lookups and read scaling across threads (Comparative Architecture Table).
  • WiredTiger skip list (MongoDB) chose per-level compare-and-swap for concurrent writes, with no prefix compression. That fits write-heavy loads over 50% writes, where OLC restarts would hurt; this design assumes a read-dominant workload (Comparative Architecture Table, §4).
  • RocksDB skip-list MemTable adds epoch-based memory management to a similar skip list. That fits an index in front of an LSM tree where keys are compacted away; this blueprint does not target that architecture (Comparative Architecture Table).
  • PostgreSQL nbtree B+-tree is built for disk, amortising I/O over 8 KB pages with a buffer pool. It wins when the index cannot fit in RAM or update-in-place and MVCC are needed; ART's 64 B to 2 KB nodes suit memory, not disk. The table says this follows "by ADR-04", but ADR-04 is the OrderedMap trait and the in-memory-only decision sits in ADR-23 (Comparative Architecture Table, ADR-04, ADR-23).

Questions to test yourself

  1. Why does prefix_len in NodeHeader need to be a u32 rather than a u8, even though MAX_PREFIX_LEN = 8? — Hint: the NodeHeader struct in §8.3 and the optimistic prefix in §8.5.
  2. Why do we store the full key in Leaf<V> rather than only the suffix below the leaf? — Hint: §8.5, INV-4, INV-5 and ADR-16's last column.
  3. What is the minimum number of epochs needed by EBR, and why does adding a 4th epoch not improve safety? — Hint: §3 Ebr, MM6 and INV-10.
  4. What would happen if EBR's retire is called without a pin guard active? — Hint: §3 Ebr, P7 and INV-10.
  5. Describe a scenario where pessimistic prefix is strictly better than optimistic prefix, even for long common prefixes. — Hint: ADR-14's last column and §8.5.

If you only remember three things

Make the key's bytes sort like its values and the tree needs no comparator: byte-by-byte descent gives point, range and prefix queries, with height set by key length instead of key count (P2, MM1). Pay for each node only by its real fanout, with four node sizes, shared prefixes stored once, and a lone key kept as a bare leaf (P1, P3, ADR-11). Concurrency comes from version-checked reads that restart and from epochs that delay frees, while all unsafe code stays inside art-art and art-concurrent (P5, P6, P7).

Words used here

  • Trie: a tree where each level consumes the next piece of the key (§1, Glossary).
  • PATRICIA: a binary radix tree that tests one bit per level (§8.1, Glossary).
  • Adaptive node: an inner node whose child table is sized to its real child count (P1).
  • Binary-comparable key: bytes whose memcmp order equals the logical order (§8.2, P2).
  • Pessimistic prefix: up to 8 shared bytes stored in the node and always checked (§8.5).
  • Optimistic prefix: a longer shared prefix whose hidden tail is checked only at the leaf (§8.5).
  • Lazy expansion: a single key below a point stays a bare leaf until a second key arrives (§8.5).
  • Tagged pointer: a pointer whose low 3 bits hold the node type (ADR-12, §8.3).
  • Optimistic lock coupling: read without locking, validate the version, restart on change (P6).
  • Epoch-based reclamation: delay frees until no reader can still hold the node (P7, INV-10).
  • Quiescent state: a moment when a thread holds no references to shared tree nodes (Glossary).
