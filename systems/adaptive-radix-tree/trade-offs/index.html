Decisions (§9) · 29 ADRs

ADR-01

Implementation language

Chosen

Rust 2021, MSRV 1.78

Rejected

C/C++, Go, Java

When the rejected choice is right

C/C++ wins when integrating into an existing codebase where Rust FFI boundary costs are prohibitive (e.g., hot per-call overhead in a C++ query engine). Go wins for teams where GC pause is acceptable and developer velocity matters more than cache-line density. Java wins in JVM-only environments targeting HotSpot JIT optimization of pointer-chasing rather than manual layout.

Why: Precise layout control + unsafe-encapsulation; exhaustive enums for node dispatch; atomics discipline for OLC; no GC

ADR-02

Workspace structure

Chosen

6 crates: art-core / art-trie / art-art / art-simd / art-concurrent / art-cli

Rejected

monorepo single crate; external crate split

When the rejected choice is right

A single crate is correct when the team is small, the entire library is always shipped together, and compile-time matters more than modularity — e.g., an embedded firmware project with a single binary target. External crate split wins when the SIMD or concurrent module is maintained by a different team and must version independently.

Why: Separation of stable vocab (core) from evolving impl; no_std boundaries enforced per crate; independent versioning

ADR-03

Core crates ABI

Chosen

no_std + alloc (art-core, art-trie, art-art, art-simd, art-concurrent)

Rejected

std throughout

When the rejected choice is right

std throughout wins when the library is exclusively deployed in userspace Linux/macOS applications and the team wants std::io/std::thread convenience directly in library code without a separate CLI wrapper.

Why: Embeddable in kernel/firmware contexts; forces explicit allocator discipline; no hidden OS dependencies

ADR-04

Public index trait

Chosen

OrderedMap<V> (get/insert/remove/range/prefix_iter)

Rejected

impl-level duck typing; raw function pointers

When the rejected choice is right

Duck typing wins in a scripting or dynamically-typed embedding context (e.g., an FFI where the caller selects the implementation at runtime via a vtable they construct). Raw function pointers win in a C-interop boundary where Rust trait objects cannot cross the FFI.

Why: Uniform contract across Trie256/RadixTree/ART/ArtOlc; testable via single generic suite

ADR-05

Key representation

Chosen

Key(Vec<u8>) + KeyEnc trait for order-preserving encoding

Rejected

store typed keys + pass comparator

When the rejected choice is right

Typed keys + comparator wins for general B-tree implementations where the comparator is the only ordering primitive needed and byte decomposition is unnecessary (e.g., a skip list or sorted array).

Why: Radix traversal is byte-by-byte; memcmp-order must equal logical order; a comparator cannot drive byte-by-byte descent

ADR-06

u32/u64 encoding

Chosen

big-endian to_be_bytes()

Rejected

little-endian; varint

When the rejected choice is right

Little-endian wins only if the keys come from a little-endian on-disk format and a memcpy-based encode is preferable to byte-swapping. Varint wins when minimizing wire-format bytes matters more than fixed-width trie height (e.g., a Protobuf-encoded key store).

Why: Big-endian places MSB first → lexicographic byte order equals numeric order with no extra logic

ADR-07

i64 encoding

Chosen

flip MSB then big-endian

Rejected

offset-binary (add 2^63); zigzag

When the rejected choice is right

Offset-binary (add 2^63) is equivalent and wins when the transform must be done in SQL-level expressions that cannot use XOR. Zigzag wins when the distribution of values is strongly clustered near zero and variable-length encoding is the goal (e.g., Protobuf signed integers).

Why: Flip-MSB maps all negatives to [0x00…, 0x7F…] and positives to [0x80…, 0xFF…]; single XOR, no branch

ADR-08

f64 encoding

Chosen

IEEE total-order bit trick (neg: flip all bits; pos: flip MSB only)

Rejected

convert to string; normalize to rational

When the rejected choice is right

String conversion wins when human-readable keys are required and byte overhead is not a concern. Rational normalization wins when exact arithmetic equality (not IEEE total order) is the semantic — e.g., a symbolic math engine where 0.1 + 0.2 == 0.3 must be true.

Why: Preserves IEEE 754-2019 totalOrder including NaN/±Inf; 8 B fixed width; O(1)

ADR-09

str encoding

Chosen

UTF-8 bytes + 0x00 terminator

Rejected

length-prefixed; null-padded to fixed width

When the rejected choice is right

Length-prefixed wins when keys can contain embedded 0x00 bytes (arbitrary binary blobs) or when prefix-free property must hold for variable-length binary data. Fixed-width wins when all keys are bounded by a known maximum and constant key length simplifies index arithmetic.

Why: Ensures no key is a byte-prefix of another; terminator byte cost = 1; no fixed-width waste

ADR-10

Composite keys

Chosen

Concatenate KeyEnc outputs in declaration order

Rejected

tuple keys with comparator

When the rejected choice is right

Tuple keys with a comparator wins in a SQL-engine setting where the key schema is dynamic and components must be addressed by column index rather than byte position, or when components include variable-width numeric types that do not have a prefix-free encoding.

Why: Concatenation preserves per-field order if each component encoding is prefix-free or same-width

ADR-11

Adaptive inner-node types

Chosen

Node4 / Node16 / Node48 / Node256 with capacity bands 1–4 / 5–16 / 17–48 / 49–256

Rejected

fixed-width node (always 256); binary search tree; hash node

When the rejected choice is right

Fixed Node256 wins for maximally dense integer key spaces (e.g., all 256 byte values present at every level) where the type-dispatch overhead exceeds the memory savings. A hash node wins when keys are random and unordered access dominates with no range queries needed.

Why: Per-node memory ∝ actual children; four types match the paper's empirical fanout distribution

ADR-12

NodePtr tagging scheme

Chosen

Low 3 bits of aligned pointer encode NodeType

Rejected

separate type byte at pointer+0; fat pointer (ptr+tag pair)

When the rejected choice is right

Separate type byte at pointer+0 wins on platforms where pointer compression is active (e.g., 32-bit targets, pointer tagging unavailable, or when low-bit assumptions are invalidated by a custom allocator returning sub-8-byte-aligned memory). Fat pointer wins when NodeType must be visible in a debugger without decoding tag bits.

Why: Zero overhead: 8-B-aligned allocations always have 3 free low bits; no extra memory word; decode in O(1)

ADR-13

MAX_PREFIX_LEN

Chosen

8 bytes inline in NodeHeader

Rejected

4 bytes (too short for common prefixes); 16 bytes (bloats Node4 past cache line)

When the rejected choice is right

4 bytes wins when the workload is dominated by short keys (e.g., 4-byte IPv4 addresses) and the L1 footprint of Node4 is critical. 16 bytes wins for workloads with long common prefixes (e.g., filesystem path trees where 16 bytes covers most shared directory prefixes) where reducing pessimistic-to-optimistic fallback is worth the larger Node4.

Why: 8 B keeps Node4 at exactly 64 B (1 cache line); covers the majority of real-world prefix lengths

ADR-14

Prefix strategy

Chosen

Pessimistic (inline ≤8 B, always verified) + optimistic (prefix_len > 8, tail skipped, verified at leaf)

Rejected

Pessimistic-only with truncation

When the rejected choice is right

Pessimistic-only wins when the workload has uniformly short keys (≤8 B) and the additional leaf dereference for optimistic verification would introduce cache misses that pessimistic inline comparison avoids.

Why: Truncation would lose the ability to distinguish keys sharing a prefix longer than 8 B; optimistic adds one leaf comparison, not full-tree re-traversal

ADR-15

Lazy expansion

Chosen

Yes — single-descendant paths defer inner-node materialization

Rejected

always materialize; always expand

When the rejected choice is right

Always-materialize wins when bulk-load is the primary workload and predictable tree structure (no lazy-to-inner-node upgrades mid-batch) simplifies parallel construction.

Why: Reduces node count for sparse keys; cost = one Leaf-vs-key comparison on insert of second key

ADR-16

Leaf key storage

Chosen

Leaf stores the FULL original Box<[u8]> key

Rejected

store only a suffix; store nothing (rely on header prefix)

When the rejected choice is right

Suffix-only wins when keys are guaranteed to be short (≤8 B) — no optimistic prefix ever triggers — and memory density is critical. Relying on header prefix alone is correct only when pessimistic-only mode is used and all key lengths are bounded by MAX_PREFIX_LEN.

Why: Optimistic-prefix verification requires comparing against the full key; without it, false positives possible

ADR-17

Node48 child_index design

Chosen

[u8; 256] mapping key_byte → slot (0xFF = empty), plus [NodePtr; 48] children

Rejected

bitmap + compact list; hash map

When the rejected choice is right

A bitmap wins when memory density matters more than cache-line locality and POPCNT is cheap (e.g., AVX-512 VPOPCNTQ for multi-node scans). A hash map wins when the child-count band is very narrow and the 256-byte index overhead is unacceptable (e.g., a 16-bit PATRICIA tree where each byte is precious).

Why: O(1) lookup via direct index; 256 B fits 4 cache lines; avoids sorting overhead vs Node16

ADR-18

Node16 SIMD

Chosen

SSE2 baseline (_mm_cmpeq_epi8 + _mm_movemask_epi8); AVX2 via target_feature

Rejected

AVX-512; scalar binary search only

When the rejected choice is right

AVX-512 wins on server-class CPUs where the wider register enables processing two Node16 children in one instruction, or for Node48 scan acceleration. Scalar binary search wins on microcontrollers or WASM targets where SIMD is absent and branch prediction on 16 sorted elements is reliable.

Why: SSE2 is universally available on x86-64; 16-byte key array fits exactly in one XMM register; scalar fallback for non-x86

ADR-19

Node allocation

Chosen

Slab/arena allocator per node type

Rejected

Box::new per node (global allocator)

When the rejected choice is right

Per-node Box wins in short-lived trees (e.g., per-request query plan trees) where setup overhead dominates and the allocator's per-object fragmentation is irrelevant at the scale used.

Why: Per-node Box causes heap fragmentation + allocation overhead at each grow/shrink; slab keeps same-type nodes contiguous → cache friendliness

ADR-20

Concurrency model

Chosen

Optimistic Lock Coupling (OLC) — per-node version counters, read-lock-free traversal, restart on conflict

Rejected

ROWEX (read-optimized write exclusion, deferred); global RwLock<Art>; lock-free CAS-only

When the rejected choice is right

ROWEX wins for write-heavy workloads (>30% write ratio) where OLC reader-restart rate degrades throughput; global RwLock wins for single-writer / few-reader configs where simplicity outweighs read scalability; pure lock-free CAS wins in HTM-equipped systems where hardware transactional memory can absorb all conflicts.

Why: OLC: readers never block, writers couple parent→child locks; lower implementation complexity than ROWEX; global RwLock serializes all reads; pure lock-free requires SMR everywhere

ADR-21

ROWEX

Chosen

Deferred (noted in art-concurrent; not in scope for Phase 11–12)

Rejected

implement now

When the rejected choice is right

ROWEX wins when the write throughput requirement exceeds what OLC can sustain — specifically, workloads with sustained >50% write ratio and low acceptable restart rate, such as real-time sensor ingestion where every insert is latency-sensitive.

Why: ROWEX adds per-operation protocol complexity; OLC achieves the read-scalability goal with less code

ADR-22

Safe memory reclamation

Chosen

Epoch-Based Reclamation (EBR) — global epoch + per-thread local epochs + retire lists

Rejected

Hazard pointers; reference counting (Arc); leak-on-delete

When the rejected choice is right

Hazard pointers win when threads have unbounded quiescent-state intervals (e.g., long-running read transactions that must not block reclamation); Arc wins for simple single-threaded prototypes where refcount overhead is irrelevant.

Why: EBR: low overhead on read path (no per-pointer registration); simpler than hazard pointers for tree traversal; Arc: atomic refcount per node defeats cache-line sharing

ADR-23

Persistence

Chosen

Deferred (optional future phase, not in Phase 0–13 scope)

Rejected

WAL + mmap now

When the rejected choice is right

WAL + mmap wins when the index must survive process restart without a full reload from a secondary store — e.g., an embedded time-series DB that cannot afford reconstruction time.

Why: This is the in-memory index primitive; durability belongs to project 67 (B-Tree) / 68 (LSM)

ADR-24

Differential test oracle

Chosen

std::collections::BTreeMap

Rejected

custom reference impl; sorted Vec

When the rejected choice is right

A custom reference impl wins when ART must implement semantics not expressible by BTreeMap (e.g., multi-value keys, MVCC snapshots, or encoded-byte ordering that differs from BTreeMap's Ord). Sorted Vec wins for tiny corpora (< 1k keys) where simplicity of the oracle matters more than performance.

Why: BTreeMap is ordered, well-tested, and exposes the same ordered-map interface; directly comparable to ART's OrderedMap

ADR-25

Fuzzing + concurrency testing

Chosen

cargo-fuzz (libFuzzer) for op sequences; loom for concurrent schedule exploration

Rejected

manual stress tests only; TSAN

When the rejected choice is right

Manual stress tests + TSAN win when the loom state space is too large to be tractable (>4 threads, long op sequences) and probabilistic testing is sufficient for the risk tolerance; TSAN alone wins for quick sanity checks in CI where loom's runtime is prohibitive.

Why: loom exhaustively explores valid interleavings under the C++ memory model used by Rust atomics; TSAN is probabilistic

ADR-26

Benchmarks

Chosen

criterion for latency/throughput; compare vs std::BTreeMap, std::HashMap, and ART paper reported numbers

Rejected

custom microbench harness

When the rejected choice is right

A custom microbench harness wins when Criterion's overhead (warm-up iterations, statistical sampling) distorts the measurement for sub-100-ns operations, or when the CI environment cannot install Criterion's transitive dependencies.

Why: criterion: statistical rigor, outlier detection, HTML reports; direct comparison answers "does this implementation achieve paper-level performance"

ADR-27

MSRV

Chosen

1.78

Rejected

latest-stable-only; 1.65

When the rejected choice is right

Latest-stable-only wins for in-house tools with no external consumers where keeping up with new language features matters more than downstream compatibility. MSRV 1.65 wins when targeting long-term-support Linux distributions (RHEL 8/9) whose packaged Rust is far behind current stable.

Why: 1.78 stabilizes std::simd foundations and #[target_feature] improvements needed for SIMD dispatch; wide distro support

ADR-28

Dependency policy

Chosen

Minimal: criterion (bench), loom (concurrency test), cargo-fuzz (fuzz); no art-tree/blart runtime dep

Rejected

pull in art-tree or blart as impl reference

When the rejected choice is right

Pulling in blart as a runtime dependency wins if the goal is a wrapper library or a fork rather than an original implementation — e.g., when rapid prototyping matters more than attribution-free ownership.

Why: Reference crates are consulted for design, not linked; keeps the library self-contained and the impl genuinely from-scratch

ADR-29

Licensing

Chosen

MIT OR Apache-2.0 (SPDX dual)

Rejected

MIT only; proprietary

When the rejected choice is right

MIT-only wins for maximum simplicity when Apache-2.0 patent clauses are unacceptable to legal teams in large enterprises. Proprietary wins when the ART implementation is a commercial differentiator and source distribution must be restricted.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: B+-Tree (disk-oriented balanced tree)

             [50 | 100 | 150]                 ← inner node (fanout B=4 shown)
            /    |     |     \
   [10|20|30] [60|70|80] [110|120|130] [160|170|180]  ← leaf nodes (linked list)

Regime where it wins: When the index cannot fit in RAM; when update-in-place + ACID guarantees are required; when the system is disk-backed (SSD or HDD) and 8 KB page granularity amortizes I/O cost. PostgreSQL's nbtree, MySQL InnoDB, and SQLite all use B+-trees precisely because the page = block device sector alignment is the dominant performance constraint.

Real system: PostgreSQL nbtree (src/backend/access/nbtree); MySQL InnoDB clustered index.

Why this blueprint rejects it: ART targets in-memory-only operation (ADR-04). B+-tree node sizes (4–64 KB) are dictated by disk I/O granularity, not CPU cache lines. An in-memory B+-tree with 64-byte node sizes degenerates toward a sorted array with O(B) scan cost. ART's byte-at-a-time descent cannot be expressed in a B+-tree structure.

Alt-2: Skip List (probabilistic ordered structure)

Level 3:  [Head] ─────────────────────────── [70] ──── [Tail]
Level 2:  [Head] ────── [20] ─────────────── [70] ──── [Tail]
Level 1:  [Head] ─ [10] ─ [20] ─ [40] ──── [70] ─ [90] ─ [Tail]

Regime where it wins: When concurrent write throughput matters more than read throughput; when the key type has an arbitrary comparator (no byte-comparable encoding needed); when implementation simplicity is paramount. WiredTiger (MongoDB) uses a concurrent skip list for its in-memory ordered index precisely because per-level CAS enables lock-free writes, and write workloads dominate OLTP.

Real system: WiredTiger wt_skip_list_t (src/include/skip.h in the MongoDB source tree); Redis zset sorted set.

Why this blueprint rejects it: Target workload is read-dominant (§4). Skip-list read throughput is O(log n) — worse than ART's O(key_len) for large n. No prefix compression: skip-list nodes store full key copies, doubling memory for common-prefix workloads. No SIMD opportunity on the traversal path.

Alt-3: Hash Trie (HAMT — Hash Array Mapped Trie)

            [root bitmap: 0b0101_1010]
           /         |          \
    [subnode]    [subnode]    [leaf: "hello" → 42]
      ...           ...

Regime where it wins: When key ordering is never needed — only point lookups; when hash distribution is better than byte distribution (adversarial key sets); when the trie must support persistent/functional semantics (structural sharing). Clojure's PersistentHashMap and Scala's HashMap use HAMT for immutable maps.

Real system: Clojure PersistentHashMap, Scala HashMap, rpds::HashTrieMap in Rust.

Why this blueprint rejects it: Ordered range scans and prefix scans are load-bearing requirements (§4, OrderedMap trait). HAMT's hash-based dispatch destroys key order; range scans require full-tree traversal. This blueprint's primary value proposition over a plain HashMap is the ordered iteration and prefix-scan capability.
