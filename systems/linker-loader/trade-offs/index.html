Decisions (§9) · 25 ADRs

ADR-01

Core language

Chosen

Rust 2024, #![forbid(unsafe_code)] outside 3 crates

Rejected

C++ (bfd/lld lineage); pure C

When the rejected choice is right

A team with deep existing BFD/lld C++ expertise and no Rust ramp-up budget; a from-scratch C linker on an embedded host with no Rust std/core port

Why: Ownership discipline for Mmap-borrowed lifetimes + zero-cost sum types for RelocKind/WinningDef (P4)

ADR-02

Primary output format

Chosen

ELF (Linux/BSD)

Rejected

Mach-O primary; PE/COFF primary

When the rejected choice is right

Targeting macOS or Windows as the primary platform, where Mach-O/PE-COFF becomes the write path

Why: Linux/BSD is the deployment target; Mach-O/PE are read-only conformance surfaces (§1, §21)

ADR-03

Architecture priority order

Chosen

x86_64 → AArch64 → RISC-V

Rejected

AArch64-first; RISC-V-first

When the rejected choice is right

An embedded RISC-V-only fleet with no x86_64 deployment target in its roadmap

Why: Matches user demand and conformance-corpus availability at authoring time

ADR-04

Output construction strategy

Chosen

mmap MAP_SHARED + direct write

Rejected

In-memory Vec<u8> buffer + single write

When the rejected choice is right

Output targets that are not regular mmap-capable files (pipes, sockets) — buffer+write is the documented fallback

Why: Only architecture that hits the wall-clock target (mold/wild lineage, §5 Papers)

ADR-05

Symbol-table concurrency structure

Chosen

Sharded RwLock<HashMap>, 64 shards

Rejected

Single global Mutex; lock-free hash with hazard pointers

When the rejected choice is right

A link with far fewer than 64 live symbols, where shard overhead exceeds contention savings — collapses to 1 shard under --threads=1 (P2)

Why: Saturates a 16-core box without false sharing; lock-free hash costs more code than the win justifies at our scale (§20.1)

ADR-06

CLI argument parsing

Chosen

clap + hand-rolled ld-compatible flag table

Rejected

Roll-your-own parser

When the rejected choice is right

A greenfield tool with no compatibility requirement to existing ld flag surfaces

Why: Flag compatibility with ld/gold/lld invocations is a hard adoption requirement

ADR-07

mmap/syscall crates

Chosen

memmap2 + nix

Rejected

Raw libc FFI

When the rejected choice is right

A #![no_std] context (the loader, §18) where neither crate is usable — hence ADR-13

Why: Safest API surface (memmap2) plus an auditable syscall layer (nix)

ADR-08

In-memory symbol hashing

Chosen

ahash (non-cryptographic)

Rejected

SipHash (std default); FNV

When the rejected choice is right

Any hash exposed externally or security-relevant (build-id, content-addressing) — SHA-256 there (ADR-15)

Why: Faster than SipHash on the hot resolver path; never used for a persisted/security-relevant hash

ADR-09

LTO codegen backend

Chosen

LLVM bitcode via inkwell

Rejected

Hand-rolled IR; GCC LTO plugin format

When the rejected choice is right

A toolchain that only ever compiles with GCC — the GCC LTO plugin ABI is the right target there

Why: Bitcode codegen requires LLVM; inkwell is the most stable Rust binding available

ADR-10

ThinLTO summary format

Chosen

Follow LLVM's published summary format

Rejected

Invent a new summary format

When the rejected choice is right

A toolchain built around a non-LLVM IR (e.g. a research compiler's own bytecode) needs its own summary format matched to that IR

Why: Reuses the ecosystem's contract (P9) instead of teaching users a bespoke format

ADR-11

Licensing

Chosen

Apache-2.0 OR MIT (linker); MIT-only (loader)

Rejected

GPL-3.0; BSD-2-Clause only

When the rejected choice is right

A project mandated to copyleft-protect derivative work (e.g. a GPL-licensed distro's patch policy)

Why: Matches the Rust ecosystem default; the loader avoids patent-grant complexity as a libc-adjacent runtime component

ADR-12

Loader runtime environment

Chosen

#![no_std], custom bump allocator

Rejected

Full std, malloc-backed

When the rejected choice is right

A "loader helper" invoked by an already-running, already-linked process — std is fine there

Why: The loader runs before libc's allocator initialises; std assumes an initialised runtime

ADR-13

_start trampoline implementation

Chosen

Per-architecture inline assembly

Rejected

Pure Rust #[naked] (unstable); linker-script-only entry

When the rejected choice is right

A boot protocol where the kernel hands off in an already-Rust-compatible state (some embedded RTOS conventions)

Why: The first ~16 instructions run before the stack/registers are in any Rust-assumable state

ADR-14

DWARF handling

Chosen

Re-emit existing DWARF with adjusted offsets

Rejected

Full from-scratch DWARF writer; strip all debug info

When the rejected choice is right

A tool whose primary purpose is debug-info transformation itself (a DWARF-optimising tool)

Why: We offset-adjust what the compiler already emitted; we do not synthesise DWARF (§20)

ADR-15

Build-ID algorithm

Chosen

SHA-1 over output, build-id field zeroed

Rejected

MD5; random UUID; SHA-256

When the rejected choice is right

A greenfield ecosystem with no legacy tooling depending on SHA-1 — BuildIdKind::Sha256 is offered as an opt-in

Why: Matches ld.bfd convention; crash-reporting symbol servers already depend on it

ADR-16

Reproducibility default

Chosen

--reproducible implied; --no-reproducible opt-out

Rejected

Reproducibility opt-in

When the rejected choice is right

A workflow intentionally embedding a build timestamp for support-ticket triage, with no reproducibility requirement

Why: Reverses the historical opt-in default deliberately (P1)

ADR-17

Symbol versioning

Chosen

GNU/Solaris extension (verdef/verneed)

Rejected

No versioning support

When the rejected choice is right

A fully static-linked fleet with no shared libraries in the loop — support present but unexercised

Why: Required for compatibility with glibc and most production .sos

ADR-18

IFUNC resolver policy

Chosen

Supported, documented call-time policy (post-relocs, pre-init-array)

Rejected

Unsupported / reject at parse time

When the rejected choice is right

A hardened/embedded target that forbids indirect-function dispatch by certification policy — --reject-ifunc covers it

Why: glibc/musl rely on IFUNC for memcpy/strlen dispatch; rejecting breaks real binaries

ADR-19

Observability

Chosen

OpenTelemetry tracing spans per pipeline phase

Rejected

Ad hoc eprintln! timers

When the rejected choice is right

A resource-constrained CI runner where OTel export overhead is unacceptable — --trace=none keeps local timing only

Why: Spans are the runbook for "why is my link slow" (§25, §29)

ADR-20

Build reproducibility tooling

Chosen

sccache + Nix flake

Rejected

Plain cargo build; Bazel

When the rejected choice is right

A single-maintainer prototype phase where hermetic infra is premature — locked down by Phase 0 exit (§12.3)

Why: Reproducible builds across maintainer machines, matching the product's own value proposition

ADR-21

Conformance golden references

Chosen

lld + mold output comparison

Rejected

ld.bfd as golden; no golden comparison

When the rejected choice is right

Auditing historical ld.bfd-only quirk compatibility specifically — ld.bfd golden wins for that narrow audit

Why: ld.bfd is too slow to gate CI; lld/mold are actively maintained live references

ADR-22

WebAssembly scope

Chosen

Read-only, deferred to Phase 10 stretch

Rejected

Full Wasm linking now; no Wasm at all

When the rejected choice is right

A project whose primary target is the Wasm ecosystem — full Wasm linking belongs in its own Phase 0

Why: The Component Model is still moving; chasing it in §12–§21 risks churn (§36)

ADR-23

LD_AUDIT scope

Chosen

Read-only hooks now; trampolines deferred

Rejected

Full audit interface now; no audit interface

When the rejected choice is right

A security-tooling fork whose entire purpose is PLT-call interception

Why: Read hooks land cheaply; la_pltenter/la_pltexit need trampolines, a larger and riskier surface (§23 T9)

ADR-24

Cross-platform build hermeticity

Chosen

Nix flake, no host-glibc assumptions

Rejected

Docker-only; host-native builds

When the rejected choice is right

A team already standardised on Docker CI with no Nix expertise — Docker-only is the pragmatic regime there

Why: Multiple glibc versions must be tested; Nix gives hermetic toolchains without per-test container overhead

ADR-25

Supply-chain policy enforcement

Chosen

cargo-deny (licenses, advisories, bans)

Rejected

Manual Cargo.lock review only

When the rejected choice is right

A zero-external-dependency vendored build — manual review is sufficient and cargo-deny is a no-op

Why: Automated, CI-gated, catches regressions a manual review misses

35. Alternative Architectures (Roads Not Taken)

Alt-1 — Classic single-threaded ld.bfd-style design.

sequential: read all -> one global mutable symtab -> layout -> reloc -> write(buffer) -> flush

Regime: extremely small links, embedded toolchains, or contexts where a 40-year correctness track record outranks throughput. Real system: GNU ld/bfd. Rejected: fails the mold-competitive wall-clock target (§4, M4) outright at chrome-class scale — the sequential design has no path to closing a 15-minute-to-7-second gap without a rewrite.

Alt-2 — Incremental/resident linker daemon.

client CLI <-> Unix socket <-> resident daemon (warm symtab + parsed-object cache across invocations)

Regime: interactive edit-compile-link loops in an IDE, where process-startup and re-parse cost dominates over pure link-algorithm cost. Real system: the closest embodiments are Bazel's persistent-worker protocol and javac --server-style daemons; no ELF linker ships this exact shape at authoring time. Rejected: a stateful daemon adds crash-recovery and cross-client cache-invalidation burden disproportionate to this project's reproducible-batch-CLI goal (P1, P3) — every invocation must be independently reproducible, which a warm, order-dependent cache complicates.

Alt-3 — LTO-integrated / whole-program linker with no separate link phase.

source -> whole-program IR -> single monolithic pass: codegen + layout + emit

Regime: closed-world, single-producing-compiler targets with no separate-compilation requirement. Real system: the Go toolchain's cmd/link operating over a closed IR world; embedded/JIT "linkers" that never see object-file boundaries. Rejected: incompatible with this project's open-world requirement — arbitrary .o/.a from any compiler (§1 scope) — a whole-program IR assumes one producing compiler, which clang+rustc+archived-third-party-.a inputs violate by construction.

Alt-4 — In-kernel / loader-less design (fully static, no separate PT_INTERP handoff).

kernel execve -> binfmt_elf -> _start directly (no userspace loader, no DT_NEEDED)

Regime: fully static (or static-PIE) deployments where dynamic linking is refused by policy — distroless/scratch containers, some embedded firmware. Real system: the Linux kernel's own fs/binfmt_elf.c path for static binaries, and musl's static-PIE self-relocation stub (§5 Reference Implementations). Rejected: forfeits shared-library memory sharing across processes and security-patch-without-relink, both required by this project's target users (§1) who explicitly need .so production and consumption.
