78 — Linker and Loader

Project Number: 78

Project Name: Linker and Loader

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build (1) a from-scratch static linker lk consuming ELF relocatable objects (.o) and archives (.a), emitting position-independent executables (PIE) and shared objects (.so) for Linux and BSD (x86_64, aarch64, riscv64gc), deterministic, bit-reproducible, and internally parallel; and (2) a runtime dynamic loader lk-ld.so (an ld.so-equivalent) that mmaps program headers, resolves DT_NEEDED, lazily binds the PLT, sets up TLS, and transfers control to _start. The linker additionally reads (never writes) Mach-O and PE/COFF objects at conformance level, and reads WebAssembly modules as a stretch surface (deferred, PhaseDeferred("§36")).

Phase-0 deliverable (numbered modules):

  1. lk_elf — ELF64 LE reader for ET_REL objects (§13).
  2. lk_archive — System V ar reader (§13).
  3. lk_core::resolver — global symbol table stub; strong/weak/common resolution lands in full at §14.
  4. lk_driver — CLI argument parsing, lk-inspect elf subcommand (§12).
  5. lk_test_kit — fixture builder and golden-file harness (§12).
  6. conformance/relocs/x86_64/inputs/ — seed corpus of 200 recorded objects (§13).

System boundaries — provides: ELF64 parse/emit; x86_64/aarch64/riscv64 relocation processing; static linking to PIE/EXE/DSO; --gc-sections/ICF; ThinLTO/FullLTO orchestration (not codegen); a userspace dynamic loader with lazy PLT binding, TLS (LE/IE/GD/LD), symbol versioning, IFUNC, read-only LD_AUDIT hooks. Delegates: object-code generation (clang/rustc/LLVM); IR optimisation inside LTO (LLVM via inkwell); libc itself (glibc/musl consumed, not authored); kernel-level ASLR/page tables (Linux/BSD kernel). Does NOT provide: a C/Rust compiler; a Mach-O or PE/COFF writer; a debugger; a disassembler beyond lk-inspect's structural dump; ELF32 output; Windows-native execution.

Non-goals: every historical relocation type (pre-2000 SVR4 relocations dropped); a GUI; incremental compilation (only incremental linking); a package manager.

Deployment model: a single CLI binary (lk) plus a side-installed loader (lk-ld.so, installed at /opt/lk/lib/lk-ld.so.1, never overwriting /lib64/ld-linux-x86-64.so.2); invoked from build systems as a drop-in cc -fuse-ld=lk replacement.

Target users/operators: toolchain engineers building custom link pipelines; performance engineers needing faster iterative links than ld.bfd/gold; systems researchers studying ELF/loader internals; CI operators needing reproducible, auditable link output.

What later phases unlock: §16 (layout) unlocks real PIE output; §18 (loader) unlocks running produced binaries without the system loader; §19 unlocks multi-architecture and LTO; §20 unlocks the mold-competitive wall-clock target; §21–§22 unlock conformance parity and audit-readiness.

Recommended language: Rust (2024 edition), #![forbid(unsafe_code)] outside three crates: lk_writer::mmap (the mmap/pwrite syscall surface, P3/P14), lk_arch_*::reloc::arith (relocation arithmetic kernels touching raw bytes), and lk_loader_start (#![no_std] _start trampoline, inline assembly). Rationale: the newtype-per-concept principle (P4) and the sharded-lock symbol table (P2, ADR-05) both lean on the borrow checker to make whole bug classes (unit confusion, use-after-free of Mmap-borrowed data, data races on the global table) compile-time errors — a from-scratch linker's dominant bug source. Rejected: C++ (ties crate boundaries to the BFD/lld inheritance of mutable global state, ADR-01); pure C (no ownership discipline for the Mmap-borrowed lifetime graph, no zero-cost sum types for RelocKind/WinningDef, ADR-01); Go (GC pauses conflict with the mmap-writer's need for predictable msync timing; weaker unsafe story for the mmap surface).

Prerequisites: System V ABI for x86_64/aarch64 (calling convention, PLT/GOT contract); ELF specification ch.4 (sections) and ch.5 (program headers, relocations); the distinction between a translation unit, a relocatable object, an archive member, an executable, and a shared object; the execve → _start → main process-startup lifecycle; intermediate Rust (lifetimes, trait objects, reasoned unsafe); fluency reading objdump -dr, readelf -aW, nm, lddtree output.

Estimated timeline: Phase 0 (§12) — 1 week. Full system (§12–§22) — 13 weeks on the core path; 5–6 months including the god-level conformance and audit passes (Appendix B).

Deferred features (each PhaseDeferred("§36"), registered in §36 with a specific building-phase anchor): WebAssembly module reading; Mach-O/PE/COFF write paths; LD_AUDIT la_pltenter/la_pltexit trampolines; TLSDESC dynamic relocations; WebAssembly Component-Model linking.

2. Why Build This

A linker is the most under-explained tool in the toolchain: every engineer uses one daily, few can describe its algorithm. This project is the direct path from "I have written C/Rust for years" to "I can read the relocation table at the back of psABI-x86_64.pdf and predict, byte for byte, what the linker emits" (§8, §15). Once internalised, the rest of the toolchain — compilers, debuggers, sanitizers — stops being mysterious: objdump -dr output reads like prose.

The dynamic loader is the runtime-side mystery. execve does not enter main; it enters the loader (§18), which walks program headers, mmaps PT_LOAD, recursively resolves DT_NEEDED, builds the symbol-resolution scope, allocates TLS, fixes the GOT, and only then jumps to _start. By §18 you will have written every step and will know why LD_DEBUG=all (glibc) emits the trace it does.

Performance is the third reason. ld.bfd links a Chrome-class binary (~2 GB debug info, ~50M relocations) in ~15 minutes; gold in ~90s; lld in ~30s; mold/wild in 5–7s (§4, §32). The gap between 15 minutes and 7 seconds is architectural, not a constant-factor tweak: parallel symbol resolution, parallel relocation application, mmap-based output construction, sharded symbol hashing (§20, §31 MM3). §20 closes this gap to within 1.5x of mold on 16 cores (M4, §29).

Cross-links: shares the "consume a binary format, build a graph, emit bytes deterministically" shape with a container-image builder (OCI layer graph) and a Bazel-equivalent build system (dependency DAG); shares the "userspace runtime that must bootstrap itself before its own runtime is ready" shape with any #![no_std] kernel-adjacent project. Calibration: a working §18 loader is evidence of System V ABI mastery equivalent to a graduate "linkers and loaders" course compressed into 8 weeks of engineering.

What Mastery Looks Like

  • Read any R_X86_64_*/R_AARCH64_* relocation's psABI formula and hand-compute its patched bytes without a reference (§15, Phase 3).
  • Explain why .tbss/.tdata + PT_TLS produce four distinct TLS access models and pick the cheapest one from a disassembly (§16.4, Phase 4).
  • Trace a dlopen failure to one of: missing DT_NEEDED, symbol-version mismatch, or RTLD_GLOBAL scope collision, from LD_DEBUG=all output alone (§18, Phase 6).
  • Predict, from the ADR-04 mmap-writer decision, why --icf=all and --gc-sections change output filesize but not the wall-clock-dominant phase (§17, §20, Phase 5/8).
  • Diagnose a non-reproducible build to one of: embedded timestamp, non-deterministic archive-symbol ordering, or unpinned LTO summary hash (§22, Phase 10).
  • Design a new ArchBackend (§11.6) for an unsupported ISA without touching lk_core (§19, Phase 7).
  • Explain, from first principles, why -z now -z relro closes the GOT-overwrite exploit class and why lazy binding cannot be retrofitted with the same guarantee (§16.3, §23 T6).

Loader-specific flow (§18), a separate process/address-space from the static linker above: mmap PT_LOAD segments -> resolve DT_NEEDED (recursive, cycle-safe) -> bind PLT (lazy or BIND_NOW) -> allocate TLS (DTV + per-module blocks) -> jump to _start.

Box paragraphs. CLI Drivers — the only externally-facing trust boundary; every byte from argv, response files, and input files is treated as untrusted until validated (§23 T1). Driver Layer — classifies inputs by magic byte, never by file extension; resolves -L/-rpath/sysroot before any file is opened, so search-path logic has no dependency on reader state. Static Link Pipeline — a streaming pipeline: each stage produces an immutable artefact consumed by the next; the only cross-stage mutable state is the global symbol table, built once at §14 and read-only thereafter (I7). Dynamic Link Pipeline — runs in its own process at execve time, never inside the linker; it is a state machine with five reachable ObjectStates (I10). Object Reader — every InputFile variant borrows from an Mmap owned by the driver; the persistence boundary is the mmap itself, never a copy. Symbol Resolver — the one place mutable shared state exists (I7); protected by 64 shards (ADR-05). Layout Engine — a pure function of the resolved symbol table and LinkOptions (P11); no relocation is applied until this stage settles. GC + ICF — two dual passes over the same reachability graph (§17, MM7). Relocator — per-architecture arithmetic kernels behind the ArchBackend trait (§11.6, P7); no shared mutable state across output sections, so this stage parallelises per-section (§20.1). Output Writer — the single owner of all mmap/pwrite calls (P3, P14); the build-id is a pure function of the final bytes with its own field zeroed (I14). LTO — the only stage that hands control to an external toolchain (LLVM via inkwell, ADR-09) before returning ELF objects to the normal pipeline. Loader — a #![no_std] self-relocating program (MM4) that never shares runtime state with the static linker beyond the object-format contract they both implement (P6).

6. Design Principles

  • P1 — Determinism is not a feature; it is the floor. Two invocations with identical inputs and flags produce byte-identical output (I3). Tradeoff: forbids "first finished wins" merges anywhere, including under LTO (P8). Operational implication: the reproducibility matrix (§22, M13) gates every release. Violated: a random tie-break in symbol resolution silently reorders .bss common-symbol placement across runs, breaking downstream symbol-server matching.
  • P2 — Parallelism is the architecture, not a flag. Inputs are read in parallel; resolution runs as a sharded-lock pass (ADR-05); relocations apply per output section in parallel; the writer pwrites in parallel into one mmap. --threads=1 is a degenerate case, not a separate code path. Tradeoff: every shared structure needs a concurrency story from day one. Operational implication: §20.1's parallelism table is load-bearing documentation, not an afterthought. Violated: a "temporary" global mutex added under deadline pressure silently caps the whole pipeline at 1 thread's throughput.
  • P3 — The output file is the truth. The linker mmaps the output MAP_SHARED at predicted size, writes directly, msyncs on close (ADR-04). Tradeoff: requires accurate size prediction before any byte is written. Operational implication: lk_writer owns 100% of the process's mmap/pwrite calls (P14). Violated: falling back to a Vec<u8> buffer silently doubles peak RSS and breaks the M6 ceiling.
  • P4 — One type per concept. A SymbolNameId is not a String; a SectionIndex is not a u32; a FileOffset is not a VirtualAddr (§11.1). Tradeoff: verbose generic bounds. Reward: unit-confusion bugs (subtracting a SectionIndex from a FileOffset) fail to compile. Violated: a raw u64 GOT offset silently accepted as a VirtualAddr produces a wrong-by-a-constant relocation that only manifests at runtime.
  • P5 — Errors carry the input range that produced them. Every Diagnostic embeds file path, section index, and byte range (§11.8). Tradeoff: every fallible call threads provenance. Operational implication: a user sees libfoo.a(bar.o):.text+0x140: R_X86_64_PC32 truncated, never a bare relocation overflow. Violated: bare error strings turn every bug report into a multi-round triage.
  • P6 — The dynamic loader is a separate program, not a library. lk links against nothing; lk-ld.so is a self-relocating ET_DYN whose _start bootstraps before the kernel's auxiliary vector is fully consumable (MM4). Tradeoff: no code sharing at runtime between linker and loader, only at source level. Violated: linking loader code against std silently assumes an initialised allocator that does not exist yet (§18.3).
  • P7 — Architecture support is a switchable backend. A new architecture implements ArchBackend (§11.6) and registers at build time. Tradeoff: every arch-specific optimisation must fit the trait's shape. Reward: adding riscv32 is a self-contained crate, not a lk_core patch. Violated: hard-coding x86_64-specific GOT-offset math inside lk_layout blocks every other architecture's layout.
  • P8 — Reproducibility extends through LTO. ThinLTO summary imports are deterministic; module hashes are stable; bitcode link order is input order (§19.3). Tradeoff: no "first module ready" scheduling shortcut. Violated: sorting ThinLTO summaries by wall-clock arrival time instead of module hash reintroduces host-dependent output.
  • P9 — The conformance suite is the API. A relocation type absent from conformance/relocs/ is not supported, regardless of source-code claims (§27, MM8). Tradeoff: every feature ships with fixtures before it ships to users. Violated: shipping R_X86_64_TLSDESC support with no fixture means the first user hitting it is the first test.
  • P10 — Security defaults are on by default. PIE, RELRO, BIND_NOW, no-execute stack are default; the insecure variant requires an explicit flag (§23). Tradeoff: slightly larger/slower output by default. Violated: defaulting to a writable GOT after init reopens the T6 exploit class for every user who does not know to pass -z now.
  • P11 — Layout is a pure function of the resolved symbol table and options. No relocation processing observes an unfinished layout (I7); §16 never mutates the symbol table. Tradeoff: forces a hard phase barrier between §14 and §16. Violated: a "fast path" that starts relocating before layout settles produces GOT offsets computed against a stale plan.
  • P12 — Synthetic sections are requested, not directly written. .got/.plt/.dynsym/etc. are recorded as GotRequest/PltRequest events by the relocator (§15.4) and materialised once by the layout engine (§16.1). Tradeoff: an extra indirection layer. Reward: parallel relocation processing never serialises on a shared GOT-allocation lock (extends P3 to synthetic data).
  • P13 — Diagnostics are structured data first, text second. Diagnostic (§11.8) is the single source of truth; TextRenderer/JsonRenderer are downstream (§11.5, §19.5). Tradeoff: every error site constructs a struct, not a format! string. Violated: an eprintln! outside the render layer bypasses --diag-format=json, breaking tooling integrations.
  • P14 — No phase blocks on I/O it does not own. All mmap/pwrite calls belong to exactly one crate, lk_writer (P3); every other crate operates on borrowed slices. Tradeoff: crates that "just need to write one debug file" must route through lk_writer or a narrowly scoped exception. Violated: a resolver-side debug dump that opens its own file handle races the writer's ftruncate/mmap sequence under --threads>1.

8. Domain Model

8.1 ELF Container Model

An ELF64 file is: a fixed 64-byte header, an optional program-header table (absent in ET_REL), a section-header table, and section bodies. The header layout:

Offset Field Size Meaning
0x00 e_ident[0..4] 4 Magic 0x7F 'E' 'L' 'F'
0x04 e_ident[EI_CLASS] 1 1 = 32-bit, 2 = 64-bit
0x05 e_ident[EI_DATA] 1 1 = LE, 2 = BE
0x10 e_type 2 ET_REL/ET_EXEC/ET_DYN/ET_CORE
0x12 e_machine 2 EM_X86_64=62, EM_AARCH64=183, EM_RISCV=243
0x18 e_entry 8 Entry virtual address (0 for ET_REL)
0x20 e_phoff 8 Program-header table file offset
0x28 e_shoff 8 Section-header table file offset
0x38 e_phnum/e_shnum/e_shstrndx 2 each Header counts + string-table index

8.2 Section & Program Header Layout

Elf64_Shdr (64 bytes): sh_name(4) · sh_type(4) · sh_flags(8) · sh_addr(8) · sh_offset(8) · sh_size(8) · sh_link(4) · sh_info(4) · sh_addralign(8) · sh_entsize(8). Elf64_Phdr (56 bytes): p_type(4) · p_flags(4) · p_offset(8) · p_vaddr(8) · p_paddr(8) · p_filesz(8) · p_memsz(8) · p_align(8).

8.3 Symbol Table Model

Elf64_Sym (24 bytes): st_name(4) · st_info(1, bind<<4 | type) · st_other(1, visibility) · st_shndx(2) · st_value(8) · st_size(8). Resolution precedence (§14.2): STB_GLOBAL > STB_WEAK > STB_LOCAL-never-global > SHN_COMMON-tentative > undefined; STB_GNU_UNIQUE behaves as STB_GLOBAL for resolution; STT_GNU_IFUNC resolves to WinningDef::Ifunc.

8.4 Relocation Model

Elf64_Rela (24 bytes): r_offset(8) · r_info(8, symbol index in high 32 bits, type in low 32 bits) · r_addend(8, signed). A representative subset of the x86_64 table:

Type Field Size Formula Notes
R_X86_64_64 64-bit S + A Absolute
R_X86_64_PC32 32-bit signed S + A − P PC-relative
R_X86_64_PLT32 32-bit signed L + A − P Via PLT stub at L
R_X86_64_GOTPCREL 32-bit signed G + GOT + A − P GOT-indirect load
R_X86_64_GOTPCRELX 32-bit signed as GOTPCREL, relaxable to LEA when local+in-range Linker relaxation (§15.2)
R_X86_64_TPOFF32 32-bit signed S + A − TLS_offset Local-Exec TLS
R_X86_64_GOTTPOFF 32-bit signed G + GOT + A − P (GOT slot filled by loader) Initial-Exec TLS
R_X86_64_TLSGD 32-bit signed G + GOT + A − P (two GOT slots: DTPMOD64,DTPOFF64) General-Dynamic TLS
R_X86_64_RELATIVE 64-bit B + A (B = load bias) Dynamic-only, self-relocation
R_X86_64_IRELATIVE 64-bit resolver return value IFUNC dynamic

Worked example. Resolve R_X86_64_PLT32 for a call printf@plt at .text offset 0x20, output section .text at vaddr 0x401000 (so P = 0x401020), printf's PLT stub at L = 0x401300, addend A = -4 (x86 call disp is relative to the instruction's end): value = L + A − P = 0x401300 − 4 − 0x401020 = 0x2DC. Patch bytes at offset 0x20 (little-endian 32-bit): DC 02 00 00. Range check: 0x2DC fits signed 32-bit — pass.

8.5 GOT/PLT/Dynamic Section Model

The x86_64 PLT entry is a fixed 16-byte instruction sequence:

.plt[i]:  jmp *got.plt[i+3](%rip)   ; steady state: direct jump to resolved target
          push $i                   ; first call: index for the resolver
          jmp .plt[0]               ; common resolver stub
.plt[0]:  push got.plt[1](%rip)     ; loader-private linkage-map pointer
          jmp *got.plt[2](%rip)     ; loader's _dl_runtime_resolve

.dynamic (DT_* entries, Elf64_Dyn: d_tag(8) + d_val/d_ptr(8)) carries DT_NEEDED, DT_SONAME, DT_RPATH/DT_RUNPATH, DT_HASH/DT_GNU_HASH, DT_PLTGOT, DT_JMPREL, DT_RELA/DT_RELASZ, DT_INIT_ARRAY, DT_VERSYM/DT_VERDEF/DT_VERNEED, DT_FLAGS_1.

8.6 TLS Model

PT_TLS holds p_filesz (= .tdata size), p_memsz (= .tdata+.tbss), p_align. Four access models, increasing indirection/decreasing linker-time-binding: Local-Exec (offset from %fs:0 known at link time) → Initial-Exec (GOT-held offset, filled at load time) → General-Dynamic (__tls_get_addr(modid, offset) call, supports dlopen) → Local-Dynamic (GD-style call amortised across same-module accesses).

8.7 Loader State Machine

ObjectState: Mapped → RelocsApplied → InitArrayCalled → Running → Detached (I10). Boot sequencing (§18.3) walks this once per LoadedObject, breadth-first across the DT_NEEDED DAG (I11).

8.8 Malformed-Input & Failure-Path Examples

Malformed ELF: e_shoff = 0x50000 but file size 0x400 → ElfParseError::SectionHeaderOffsetOutOfBounds { offset: 0x50000, file_size: 0x400 }, rendered as bad.o: e_shoff 0x50000 exceeds file size 0x400 (truncated or corrupt section header table) — never a panic (§13.6).

Missing symbol: a reference to undefined_func from .text+0x10 in bad.o, satisfied by no input, archive, or shared library → Diagnostic code lk0012: undefined reference to 'undefined_func', referenced from bad.o:.text+0x10; no shared library provides it (pass --allow-shlib-undefined to suppress) (P5, I12).

11. Core Schema & Types

All types are signatures only (no method bodies), per the No-Code Rule.

11.1 Identity newtypes

pub struct InputFileId(u32);       // Copy, Eq, Hash — owned by the driver's input list
pub struct SectionIndex(u32);      // Copy, Eq, Hash — file-relative, never cross-file

Ownership: all Copy; no allocation. Mutation: immutable once constructed. Concurrency: Send + Sync trivially. Persistence: none — recomputed per run. Serialization: Serialize/Deserialize for the incremental-cache OutputPlan (§20.2). Compatibility: adding a variant is additive; changing the underlying integer width is a breaking ADR.

11.2 ElfFile

pub struct ElfFile<'mmap> {

    pub path: PathBuf,
    pub mmap: &'mmap [u8],
    pub header: ElfHeader,

Ownership: borrows 'mmap from the driver-owned Mmap (never 'static in real code). Mutation: immutable after parse (§13.1). Concurrency: Send + Sync; read by multiple resolver threads. 14. Phase 2 — Symbol Resolution

Symbol resolution is the heart of every linker. By the end of this phase, an ordered list of relocatable objects, archives, and shared objects folds into a global symbol table whose every entry has a WinningDef consistent with the SysV ABI resolution rules plus the GNU/Solaris extensions (P9, §5 Books #3).

14.1 Objectives

  • Implement the archive crawl (--start-group/--end-group, --whole-archive) bounded at 16 iterations (I13).
  • Implement the 8-rule resolution precedence (§14.2) over a sharded RwLock<HashMap> (ADR-05).
  • Reach a fixed point before any layout code runs (I7, P11 — the barrier is structural).

14.2 Detailed Implementation Steps

  1. Walk InputSpecs in order; for each .o, fold its symbol table into GlobalSymbolTable (§11.4); for each .a, consult the archive's symbol index and pull members that satisfy a currently-undefined global, repeating until no new pulls (I13 bounds this at 16 iterations, with a warning at iteration 12).
  2. Implement the resolution precedence: STB_GLOBAL > STB_GLOBAL is a multiple-definition error (rule 1); STB_GLOBAL beats STB_WEAK (rule 2); STB_WEAK beats undefined (rule 3); two STB_WEAKs — first by InputFileId order wins (rule 4, deterministic per P1); SHN_COMMON tentative definitions materialise the largest-and-most-aligned if nothing concrete appears (rule 5); STB_GNU_UNIQUE resolves as STB_GLOBAL (rule 6); STT_GNU_IFUNC becomes WinningDef::Ifunc (rule 7); versioned symbols key by (SymbolNameId, Option<SymbolVersion>) (rule 8).
  3. Shard the table across 64 RwLocks keyed by ahash(SymbolNameId) (ADR-05); acquire one shard lock per input file's fold pass, not per symbol, to amortise lock overhead (§20.4 pitfall).
  4. For .so inputs, record defined symbols as "shared definitions" — gating --no-undefined and feeding §16's dynamic-symbol writer, without becoming a static WinningDef::Strong.
  5. Implement --whole-archive/--no-whole-archive as a per-InputSpec flag (not global), matching real invocations like -Wl,--whole-archive,libfoo.a,--no-whole-archive,libbar.a.
  6. After folding, walk every RefSite against a WinningDef::Undefined entry; under default flags this is an error (P5-shaped diagnostic); --allow-shlib-undefined permits it only when a .so shared definition exists.
  7. Emit lk_core::resolver::resolve(inputs, opts) -> Result<GlobalSymbolTable, Vec<Diagnostic>> — the fixed-point barrier that §16 depends on (I7, P11).

14.3 Deliverable

conformance/resolution/ (80 fixtures: one per rule-by-rule positive/negative case, archive-crawl edge cases, the four GNU extensions) all pass; lk-inspect symbols prints the resolved table deterministically.

14.4 Acceptance Criteria

  • 80/80 conformance/resolution/ fixtures pass.
  • Resolver output is byte-identical across --threads=1, --threads=4, --threads=16 runs on the same inputs (I3 exercised early).
  • --start-group convergence enforced at ≤16 iterations with a named diagnostic on the 17th (I13).

14.6 Pitfalls

  • STB_LOCAL symbols never enter the global table — a bug here makes objdump output look correct while breaking links where a local shadows a global elsewhere.
  • SHT_GNU_versym maps a symbol-table index to a version index, not a SymbolVersion directly; join the two in the resolver, not at parse time (keeps the parser architecture-agnostic).
  • Unsorted BSD ar symbol indices (old Apple ar) break binary-search satisfaction checks; detect sortedness and fall back to linear scan.
  • STB_GLOBAL in a relocatable object is not the same as a public dynamic symbol — visibility (STV_HIDDEN) gates dynamic-symbol-table entry independently (§16).

14.7 Performance Concerns

The sharded RwLock (ADR-05) trades a small per-shard contention cost for parallelism; pre-bucketing symbols by shard before acquiring any lock avoids repeated lock/unlock churn per symbol (§20.4). The archive crawl is worst-case quadratic in member count under --start-group — I13's 16-iteration cap is the performance guardrail, not just a correctness one.

14.8 Edge Cases

  • A symbol defined STB_WEAK in two different archive members pulled in by different --start-group rounds — resolution order must stay deterministic (rule 4) regardless of pull order.
  • An .so shared definition shadowed by a later static definition — the static one wins for the link, but the .so's presence still affects --no-undefined bookkeeping.
  • A versioned symbol referenced without a version specifier — falls back to the base (unversioned) version per rule 8.

14.9 Failure Analysis

A resolution bug's blast radius is total — every downstream phase reads the (wrong) GlobalSymbolTable. Detection is primarily the 80-fixture conformance suite plus differential testing against lld/mold on the same inputs (§27). Recovery: the fixed-point barrier (I7) means a bad resolve never partially leaks into layout — the link aborts cleanly with diagnostics rather than producing a corrupt binary.

14.10 Operational Notes

lk-inspect symbols --format=json is the primary debugging surface for "why did my symbol resolve this way" support requests; it prints WinningDef plus every RefSite per symbol, directly answering the most common resolver bug report.

15. Phase 3 — x86_64 Relocations

Relocations are the part of the spec every tutorial skims. The full table is in psABI-x86_64.pdf's appendix (§5 Books); by the end of this phase every entry we support has arithmetic, a range check, and a fixture.

15.1 Objectives

  • Implement ArchBackend for X86_64 (§11.6) covering every static relocation type we support (all except the TLSDESC family, deferred — §36).
  • Implement the R_X86_64_GOTPCRELX/R_X86_64_REX_GOTPCRELX linker-relaxation (rewriting mov foo@GOTPCREL(%rip), %rax to lea foo(%rip), %rax when safe).
  • Produce diagnostics that name file, section, and byte range for every overflow (P5).

15.2 Detailed Implementation Steps

  1. Implement the arithmetic for the always-supported set: Abs64(S+A), Pc32(S+A-P), Plt32(L+A-P), GotPcRel(G+GOT+A-P) per §8.4's table — each behind ArchBackend::apply_reloc (§11.6, P7).
  2. Implement range checks per field width: 32-bit fields signed-check via i32::try_from; report Diagnostic lk0023 naming symbol, section, file, and computed value on overflow (P5, I1).
  3. Implement R_X86_64_GOTPCRELX relaxation as a two-pass process: pass 1 marks relaxation candidates (local symbol, ±2 GiB range) without shrinking sections; pass 2 lays out the new (shrunk) section size once every candidate is known — order-sensitive, so single-pass relaxation is explicitly rejected (§15.6).
  4. Implement TLS relocation arithmetic per model (§8.6): TpOff32(LE), GotTpOff(IE, GOT-slot-filled-by-loader), TlsGd(GD, two GOT slots for DTPMOD64/DTPOFF64).
  5. Route GOT/PLT allocation through GotRequest/PltRequest events (P12) rather than direct synthesis — the relocator never mutates .got/.plt directly, decoupling parallel per-section relocation from a single shared allocation.
  6. Distinguish RELA (addend in the relocation entry, used exclusively by x86_64) from REL (addend as the existing field value, used by i386 archive members we may encounter) — never assume file-wide relocation-entry format.

15.3 Deliverable

15.6 Pitfalls

  • The addend is signed 64-bit even in a 32-bit field; compute in 64-bit, range-check at the end, never truncate early.
  • Sign extension is type-specific: R_X86_64_32S is signed, R_X86_64_32 is unsigned — the range check and the diagnostic's sign differ by one bit.
  • A relocation against an undefined weak symbol is not an error — the value is zero; document this to defuse the "why does my code call address 0" recurring question.
  • Relaxation is order-sensitive across a section (§15.2 step 3) — naively shrinking a section during a single relaxation pass invalidates later relocations' offsets in that same section.
  • TLSDESC dynamic relocations (R_X86_64_TLSDESC/R_X86_64_TLSDESC_CALL) are deferred (PhaseDeferred("§36")) — a fixture that exercises them should produce a clear "unsupported, tracked at §36" diagnostic, not a panic.

15.7 Performance Concerns

Per-relocation work is O(1) arithmetic plus one bounds check (§33 #3 shows this is not the wall-clock-dominant cost even at chrome-class scale); the relaxation pre-pass adds a linear scan per section but runs once, not per-thread-contended.

15.8 Edge Cases

  • A relocation site within 8 bytes of a section boundary — the relaxation rewrite must not read past section_data's end when peeking preceding bytes.
  • A GOTPCRELX candidate whose symbol is local but exactly at the ±2 GiB boundary — treat as non-relaxable (fail closed).
  • Mixed RELA/REL sections within the same input file (only via foreign/archived i386 objects) — reader must key relocation-entry format per-section, not per-file.

15.9 Failure Analysis

A relocation-arithmetic bug corrupts a specific instruction's operand — the symptom is usually a crash at a call site far from the actual bug. Detection: the per-type conformance fixtures plus differential testing against lld's disassembly output on the same inputs. Containment: ArchBackend isolation (P7) means an x86_64 arithmetic bug cannot corrupt AArch64/RISC-V output.

15.10 Operational Notes

The lk0023 truncation diagnostic's format (§15.2 step 2) is documented in docs/runbooks/reloc-truncated.md and is stable — external tooling may parse it; changing its shape is a docs/adr entry.

16. Phase 4 — Layout, GOT/PLT, Segments

Phase 4 decides the output executable's shape. By its end, every input Section belongs to an OutputSection, every OutputSection has a VirtualAddr and FileOffset, and every OutputSegment is provisioned (§11.3, P11).

16.1 Objectives

  • Deterministically group input sections into output sections and output sections into PT_LOAD/PT_* segments (§11.3).
  • Materialise synthetic sections (.got, .plt, .dynsym, .dynstr, .gnu.hash, .rela.dyn, .rela.plt, .eh_frame_hdr) from the GotRequest/PltRequest events recorded at §15 (P12).
  • Implement RELRO/BIND_NOW and the four-model TLS layout (§8.6).

16.2 Detailed Implementation Steps

  1. Group input sections by output-section name (.text*→.text, .rodata*→.rodata, etc.); within each group, sort by (InputFileId, SectionIndex) for determinism (I3, P1), sub-sorted by alignment for packing.
  2. Compute cumulative offsets honouring each input section's addralign; compute synthetic-section sizes from the GotRequest/PltRequest counts (P12, §15.2 step 5).
  3. Assemble OutputSegments (§11.3) by SectionFlags: R-X (.text, .plt, .rodata, .eh_frame), R-- (.dynsym, .dynstr, .rela.dyn), RW- (.data, .bss, .got); segment boundaries page-align to max(p_align, page_size) (I2).
  4. Implement -z relro: make .got/.dynamic/.init_array/.fini_array (and .got.plt under -z now) read-only-after-relocation via a PT_GNU_RELRO header the loader mprotects post-relocation (§18.3 step 10); default on for PIE (P10).
  5. Implement -z now (DT_BIND_NOW): every .got.plt entry resolved at load time, no lazy stub ever executed; default for PIE outputs (P10, ADR closing T6).
  6. Implement TLS layout (§8.6): .tdata/.tbss sizes and PT_TLS's p_filesz/p_memsz/p_align; verify LE-model offsets match at link time what §18 will consume at load time (I6).
  7. Emit lk_layout::plan(global_table, inputs, opts) -> Result<OutputPlan, Vec<Diagnostic>> only after §14's fixed point (I7, P11) — this is the hard phase barrier.

16.6 Pitfalls

  • PIE base address depends on the loader's ASLR; emit e_type = ET_DYN with p_vaddr starting at 0, never a fixed guess.
  • .eh_frame_hdr is a binary-search index over .eh_frame FDEs; building it requires parsing every FDE to extract initial_location — lld calls this "scan-eh-frame" and it is non-trivially expensive on a large link (§20.4 ties this to DWARF-merge cost).
  • SHF_GROUP/COMDAT keep/discard decisions must be unanimous across a group's members (§17.1) — partial discard here breaks group invariants before §17 even runs.
  • A fully-relaxed link can leave .got empty — the writer must skip emitting a PT_LOAD for a zero-size synthetic section rather than emitting a degenerate one.

16.7 Performance Concerns

Layout is a single barrier-synchronised pass (P11) — its cost is dominated by the input-section sort (§16.2 step 1), which is O(n log n) in section count and parallelises per output-section group. RELRO/BIND_NOW add no runtime cost to the linker itself; their cost is paid by the loader at mprotect time (§18, M8).

16.8 Edge Cases

  • A linker-script override changing the default .text*→.text mapping (deferred script support notwithstanding, the grouping algorithm must accept an override table without restructuring).
  • TLS alignment exceeding the page size (rare but legal) — PT_TLS's p_align must still be honoured exactly.
  • A COMDAT group whose sections span more than one input file member reference (via --whole-archive) — group unanimity (I8-adjacent) still applies.

16.9 Failure Analysis

A layout bug's most common symptom is a segment-overlap crash at load time, far from the actual planning bug. Detection: I2's overlap check runs on every fixture in CI, not just as a runtime assertion. Recovery: layout is fully re-derivable from the frozen GlobalSymbolTable (P11) — a layout bug never requires re-running resolution, only re-running lk_layout::plan.

16.10 Operational Notes

lk-inspect layout --json is the primary tool for diagnosing "why is my binary this size" and "why did RELRO not cover X" support questions; its segment map is the same data structure §20's benchmarks report against (benchmarks/results/).

17. Phase 5 — GC, ICF, Archives Revisited

Two passes shrink the output without changing semantics: garbage collection of unreferenced sections (--gc-sections) and identical code folding (--icf=safe/--icf=all). Both run after relocations decode (§15) and before layout finalises sizes (§16), operating on the same section-relocation graph (MM7).

17.1 Objectives

  • Implement GC as a reachability worklist over the relocation graph (I8).
  • Implement ICF as a hash-then-verify fold over canonicalised section content (I9).
  • Revisit archive-crawl interactions: --whole-archive and --start-lib/--end-lib both flip crawl discipline and interact with GC.

17.2 Detailed Implementation Steps

  1. Seed the GC worklist: the entry section, every linker-script KEEP(...), .init_array/.fini_array, every SHT_NOTE, .eh_frame (conservatively kept whole by default), and every SHF_RETAIN section.
  2. Pop a section, mark Keep; for every relocation in it, follow the symbol to its defining section and push if not already Keep; COMDAT groups keep unanimously (§16.6); iterate to fixed point (I8).
  3. After GC, drop every Discard section and its relocations from the layout input (§16 never sees discarded sections).
  4. Implement ICF: compute a canonical hash per section with relocations replaced by a placeholder keyed to the symbol's resolved offset relative to a canonical base; group by hash.
  5. Verify each hash-matching group byte-by-byte plus relocation-by-relocation before folding (I9 — hash match is necessary, not sufficient); pick the lexicographically lowest (InputFileId, SectionIndex) as survivor; redirect references.
  6. --icf=safe folds only sections whose address is never compared (no &function taken); --icf=all folds aggressively, trusting the caller has audited pointer-comparison code (documented risk, §17.6).
  7. Revisit archive semantics: --whole-archive pulls every member unconditionally (fine under GC — unreferenced pulled sections are simply GC'd later); --start-lib/--end-lib members are retained only if referenced (interacts with GC directly, not via the archive-crawl fixed point of §14).

17.3 Deliverable

lk_gc::run(plan) -> Plan is idempotent and reduces to the reachable subgraph; lk_icf::run(plan, mode) -> Plan deduplicates per §17.2; a reproducibility fixture asserts lk hello.o libc.a -o hello --gc-sections --icf=all is byte-identical across two runs (I3 exercised under GC/ICF specifically).

17.4 Acceptance Criteria

  • GC+ICF reduce a non-trivial C++ binary's output size by ≥5% (M12).
  • Zero I8 violations (no Discard-marked section referenced by kept output) across the fixture corpus.
  • Zero I9 violations (every ICF fold passes the byte+relocation verifier) across the fixture corpus.

Fixture Purpose Expected Output

gc-icf/gc-ehframe-sealant/ .eh_frame-referenced-but-otherwise-dead section Kept (conservative default)
gc-icf/icf-verify-reject/ Hash collision, content differs Fold rejected, both sections retained (I9)

17.6 Pitfalls

  • --icf=all folds two functions with identical bodies; user code doing if (foo == bar) gets an implementation-defined answer per the C/C++ standard's "not observable through identity" carve-out — most users never read that paragraph; document in the runbook.
  • .eh_frame is the GC "sealant": an otherwise-unreferenced section is often referenced only from an FDE; the conservative default keeps .eh_frame whole, the aggressive --gc-sections=eh-frame-aware mode parses FDEs and GCs them in lockstep (documented performance/correctness tradeoff).
  • ICF on PC-relative architectures requires the canonical-form computation to normalise both the relocation offset and the symbol's distance from the site — a bug here folds two sections that look identical but compute different addresses.
  • Archive semantics from --whole-archive vs --start-lib/--end-lib are easy to conflate; they interact with GC differently (§17.2 step 7) and a test suite must cover both independently.

17.7 Performance Concerns

GC's worklist is O(sections + relocations); ICF's hash-then-verify keeps the expensive byte-comparison off the common (non-colliding) case. On a Chromium-class link, ICF alone saves ≈8% of output size (empirically consistent with M12's ≥5% floor) at a CPU cost dominated by the verifier pass on hash-colliding groups only.

17.8 Edge Cases

  • A COMDAT group partially referenced by --start-lib semantics and partially by --whole-archive in the same link.
  • A section that becomes foldable only after another fold changes its canonical-hash inputs (iterative fixed point required, not a single pass).
  • An SHF_RETAIN section with zero actual relocation references — kept per policy even though GC alone would discard it.

17.9 Failure Analysis

An over-aggressive ICF fold is the highest-risk failure mode here: it does not crash the linker, it silently changes program behaviour for pointer-identity-dependent code (§24 FM-11). Detection is necessarily user-facing (§27's differential testing catches semantic drift only if the fixture exercises pointer comparison explicitly). Containment: --icf=safe is the conservative default; --icf=all requires an explicit opt-in with a documented risk.

17.10 Operational Notes

benchmarks/results/ records GC/ICF size-reduction percentages per release, gating M12; a regression below 5% on the tracked non-trivial C++ binary opens a Sev-2 issue (not Sev-0 — it's a quality regression, not a correctness one).

18. Phase 6 — Dynamic Linking, PLT/GOT, Runtime Loader

Phase 6 is where the linker becomes a loader. Three sub-deliverables: (1) the static linker emits a dynamic image (PIE/.so) with full dynamic-linking metadata; (2) lk-ld.so reads such an image, mmaps it, resolves its symbols; (3) PLT lazy binding works end to end (P6).

18.1 Objectives

  • Emit .dynamic, .dynsym/.dynstr, .gnu.hash, .rela.dyn/.rela.plt, versioning sections (§8.5).
  • Implement lk-ld.so as a self-relocating #![no_std] ET_DYN (ADR-12, ADR-13, MM4).
  • Implement the full loader boot sequence (§8.7, I10, I11) ending in a jump to _start.

18.2 Detailed Implementation Steps

  1. Emit dynamic-image metadata per §8.5: PT_INTERP (default /lib64/ld-linux-x86-64.so.2, configurable via --dynamic-linker); .dynamic with DT_NEEDED/DT_SONAME/DT_RPATH/DT_RUNPATH/DT_HASH/DT_GNU_HASH; .dynsym/.dynstr restricted to STV_DEFAULT/STV_PROTECTED symbols (§14.6 pitfall).
  2. Emit .plt/.plt.got/.got.plt per the 16-byte x86_64 PLT-stub layout (§8.5); wire .rela.plt (R_X86_64_JUMP_SLOT) and .rela.dyn (R_X86_64_RELATIVE/GLOB_DAT/COPY/IRELATIVE).
  3. Implement lk_loader_start::_start (ADR-13, inline assembly per architecture): self-relocate first — walk the loader's own .dynamic, apply every R_X86_64_RELATIVE against the loader's runtime base — only after this can Rust code run (MM4, P6).
  4. Implement the 11-step boot sequence: read the auxiliary vector (AT_PHDR/AT_PHENT/AT_PHNUM/AT_ENTRY/AT_BASE/AT_RANDOM); locate the executable's program headers; mmap each PT_LOAD, mprotect per segment flags; walk PT_DYNAMIC for DT_NEEDED et al.; recursively load dependencies with cycle detection via LoadedObjectId (I11); build the resolution scope (main exe, then DT_NEEDED in declaration order, then BFS over transitive deps); apply .rela.dyn; apply .rela.plt if DF_BIND_NOW else wire the lazy resolver; allocate TLS (TlsBlock, §11.9) and build the DTV; mprotect the PT_GNU_RELRO region read-only; call DT_INIT_ARRAY in order; jump to the entry point.
  5. Implement symbol-versioning lookup: GNU-hash the name, walk the .gnu.hash bucket chain, and on a versym match prefer (name, requested_version) else (name, base_version).
  6. Implement IFUNC resolution: R_X86_64_IRELATIVE points at a resolver function; the loader calls it after .rela.dyn/.rela.plt but before DT_INIT_ARRAY (ADR-18) — the resolver must not depend on TLS or global state initialised later (§18.6, §36).
  7. Implement the read-only LD_AUDIT hooks (la_objsearch, la_objopen, la_symbind64) per ADR-23; la_pltenter/la_pltexit trampolines are deferred (PhaseDeferred("§36")).
  8. Ensure LD_PRELOAD, LD_LIBRARY_PATH, LD_AUDIT are cleared from the environment before any user code runs when the loader detects a setuid binary (§23 T9).

18.3 Deliverable

lk produces a PIE that runs correctly under stock glibc's ld-linux-x86-64.so.2; lk-ld.so runs an unmodified PIE produced by lk and matches glibc's loader behaviour on every conformance/loader/ fixture; LD_DEBUG=all produces a glibc-format-compatible trace.

18.4 Acceptance Criteria

  • 100% of conformance/loader/{basic-pie,multi-needed,tls-multimodule,ifunc,audit}/ fixtures pass under lk-ld.so.
  • Loader first-fault latency ≤ 1 ms on a hot page cache (M8).
  • ObjectState transitions verified monotonic (I10) on every fixture via --check-invariants build.
  • Zero DT_NEEDED cycles left unhandled (I11) — the cyclic fixture resolves via the documented shared-placeholder strategy (§18.10).

18.5 Conformance Fixtures

Fixture Purpose Expected Output

18.6 Pitfalls

  • The auxiliary vector's layout is precise (argc, argv, envp, auxv, end-of-stack); an off-by-one here is a stack-corruption bug that looks like a random crash, not an auxv bug.
  • TLS allocation uses mmap, never malloc — the loader has no working allocator until libc's own init runs; lk_loader::alloc's bump allocator (ADR-12) is the only one available pre-init.
  • DT_RPATH searches before LD_LIBRARY_PATH; DT_RUNPATH searches after — this ordering difference is the single most common loader bug report ("I set DT_RUNPATH and LD_LIBRARY_PATH overrode it").
  • LD_PRELOAD must apply before any DT_NEEDED loads, or a preload library cannot intercept _init in its dependencies.
  • R_X86_64_COPY relocations copy a shared library's canonical data-symbol storage into the executable's .bss — a bug here duplicates apparent global state between executable and library.
  • LD_AUDIT's la_pltenter/la_pltexit trampolines are out of scope for this phase (PhaseDeferred("§36"), ADR-23) — a fixture exercising them must produce a documented "unsupported hook" diagnostic, never silently no-op.

18.7 Performance Concerns

Self-relocation (step 3) must complete before any allocation — its cost is a fixed, small number of R_X86_64_RELATIVE entries in the loader's own image, not user-input-dependent. TLS allocation is the per-thread-creation hot path (M9's ≤10 µs budget); the bump allocator's simplicity is deliberate — a general-purpose allocator here would blow the budget.

18.8 Edge Cases

  • A setuid binary with a DT_RUNPATH pointing outside system paths — secure-execution mode must refuse it (§23 T9).
  • A dlopen'd module whose TLS allocation exceeds the static TLS reservation — must fail cleanly, not corrupt adjacent DTV entries (§24 FM-9).
  • An IFUNC resolver that (incorrectly) references TLS — the loader must not crash; document the constraint and, where feasible, detect and reject at link time (§15.6-adjacent).
  • A version-mismatch (memcpy@@GLIBC_2.34 requested, only GLIBC_2.17 present) — a specific, named diagnostic (§24 FM-8), not a generic segfault.

18.9 Failure Analysis

Loader bugs are the highest-severity class in this project — a bug here crashes every program the loader touches. Detection: the full conformance/loader/ suite plus LD_DEBUG=all-format trace comparison against glibc on every fixture. Blast radius containment: ObjectState monotonicity (I10) means a failed transition aborts the process rather than continuing in a half-initialised state.

18.10 Operational Notes

LD_DEBUG=all output mirrors glibc's format for tooling compatibility (§18.3 step 4's docstring cites this explicitly); the DT_NEEDED-cycle recovery strategy (a shared placeholder object with deferred DT_INIT_ARRAY execution until the cycle resolves) is documented in docs/runbooks/dynamic-loader-debug.md and is the anchor for Deferred Register row "LD_AUDIT trampolines" (§36).

19. Phase 7 — AArch64, RISC-V, Link-Time Optimisation

Phase 7 expands beyond x86_64 (P7's payoff) and lands LTO orchestration (ADR-09, ADR-10).

19.1 Objectives

  • Implement ArchBackend for AArch64 covering the static subset (~60 of ~90 psABI-aarch64 types) plus common dynamic ones.
  • Implement ArchBackend for Riscv64 including the HI20/LO12 relocation-pairing discipline and R_RISCV_RELAX.
  • Orchestrate LLVM bitcode LTO (full and Thin) without hand-rolling codegen (ADR-09).

19.2 Detailed Implementation Steps

  1. Implement AArch64 arithmetic (§5 Books #5): R_AARCH64_ABS64/PREL64/PREL32 (straightforward); R_AARCH64_ADR_PREL_PG_HI21 — (page(S+A) - page(P)) >> 12 where page(x) = x & ~0xFFF, patching an adrp's 21-bit immediate; R_AARCH64_ADD_ABS_LO12_NC patching an add's 12-bit immediate; R_AARCH64_CALL26/JUMP26 patching a 26-bit signed branch offset.
  2. Implement RISC-V arithmetic (§5 Books #6): R_RISCV_HI20/LO12_I/LO12_S, R_RISCV_PCREL_HI20/PCREL_LO12_I/PCREL_LO12_S, R_RISCV_CALL/CALL_PLT, R_RISCV_JAL/BRANCH; R_RISCV_PCREL_LO12_I references the site of the paired PCREL_HI20, not the symbol — the relocator must linearise a per-section pass to find the pairing (breaks the "relocations are independent" assumption used elsewhere).
  3. Implement R_RISCV_RELAX/R_RISCV_ALIGN relaxation, mirroring the GNU-toolchain-emitted relaxation sequences the conformance corpus exercises.
  4. Wire ThinLTO: detect bitcode inputs by magic; parse !llvm.module.flags-derived summaries; build a function-level cross-module-inlining summary; hand the "thin-link plan" to LLVM via inkwell (ADR-09), which emits per-module ELF objects consumed by the normal §13–§18 pipeline.
  5. Wire full LTO: merge all bitcode inputs into one LLVM module, run LLVM's optimisation pipeline, emit one ELF object, link normally.
  6. Preserve determinism through LTO (P8): bitcode link order is input order; ThinLTO summaries sort by module hash, never by arrival time; -fwhole-program-vtables is gated behind an explicit flag.
  7. Tag LTO-promoted symbols (internal linkage promoted to external for cross-module inlining) distinctly from originally-external symbols in the resolver (§14.2), so the dynamic-symbol writer (§18.2) never leaks a promoted-internal symbol into .dynsym (§24 FM-12).

19.3 Deliverable

conformance/relocs/aarch64/ and conformance/relocs/riscv/ are green; lk links a hello-world for aarch64-unknown-linux-gnu and riscv64gc-unknown-linux-gnu end to end, verified under QEMU-user; --lto=thin/--lto=full link a small Rust workspace producing a correctly executing binary.

19.4 Acceptance Criteria

  • 100% pass on both new architecture conformance suites (§27 gate, phase-scoped).
  • LTO-linked binary executes correctly and its output is reproducible (I3) across two builds with --lto=thin.
  • No LTO-promoted symbol appears in .dynsym unless explicitly --export-dynamic-symbol-list-allowed (§24 FM-12 closed).

19.5 Conformance Fixtures

Fixture Purpose Expected Output

19.6 Pitfalls

  • Forgetting AArch64's >> 12 page-granularity shift on ADRP is the single most common bug when porting x86_64-shaped relocation code.
  • RISC-V's HI20/LO12 pairing breaks the "relocations are independent, apply in any order" assumption baked into §15/§16 — the RISC-V relocator's per-section pass must run before, not interleaved with, generic per-relocation dispatch.
  • LTO's internal→external symbol promotion inflates the resolver's apparent external-symbol set; failing to tag promoted symbols leaks them into the dynamic-symbol table (§24 FM-12).
  • LLVM bitcode-format versions drift between LLVM releases; pin the version in Cargo.toml and document the compatibility window (docs/adr/ADR-09).

19.7 Performance Concerns

RISC-V's linearised per-section relocation pass (step 2) is a small constant-factor regression versus x86_64/AArch64's independent-relocation parallelism, but stays within a section (still parallel across sections, §20.1). ThinLTO's cross-module summary import is the long pole on an LTO-heavy link; summary parsing is parallelised per input module.

19.8 Edge Cases

  • A RISC-V relocation pair split across a relaxation boundary (the paired HI20 gets relaxed away before its LO12 is processed) — must be detected and handled, not silently mis-paired.
  • A ThinLTO summary referencing a module that GC (§17) would otherwise discard — LTO's cross-module view must run before GC's reachability analysis, not after.
  • An AArch64 CALL26/JUMP26 target beyond ±128 MiB — out-of-range, requires a linker-generated veneer (documented as a known gap tracked alongside §36 if not yet implemented).

19.9 Failure Analysis

An AArch64/RISC-V arithmetic bug is isolated by ArchBackend's trait boundary (P7) — it cannot corrupt x86_64 output. An LTO symbol-promotion leak (§24 FM-12) is detected by a dedicated conformance fixture checking .dynsym contents against an expected allowlist.

19.10 Operational Notes

docs/reloc-tables/{aarch64,riscv}.md document every supported relocation type with its formula, mirroring docs/reloc-tables/x86_64.md from §15 — kept in lockstep so a new contributor finds the same shape across architectures.

20. Phase 8 — Parallelism, Incremental Linking

Phase 8 is the performance phase. The architecture has been parallel-aware since §12 (P2); this phase lands the actual thread pool and the incremental-link cache that close the gap to mold (§4, M3, M4).

20.1 Objectives

  • Land the rayon-based work-stealing pool per the parallelism table below.
  • Land --incremental with a fingerprint-keyed on-disk cache.
  • Hit M10 (≥14x speedup at 16 threads) and M5 (≤2s incremental-cache relink) on the chrome-class benchmark.

20.2 Detailed Implementation Steps

  1. Parallelise per the table (P2): ELF reading — one task per input file, no synchronisation; symbol resolution — one task per input file, sharded RwLock (ADR-05); GC/ICF — section-level worklist, atomic keep flags; layout — per-output-section, barrier before/after (P11); relocation apply — per-output-section, no synchronisation (sections are independent post-layout); output writing — per-output-section pwrite into one shared mmap (P3); DWARF merging — per compile-unit, atomic per-section offset.
  2. Use rayon for the work-stealing pool, crossbeam channels for the few genuine producer-consumer pairs (notably the LTO bitcode pipeline, §19.2); thread count defaults to available_parallelism(), capped by --threads.
  3. Implement --incremental: key a per-output cache by hash(every input file's contents + link options); on a hit, reuse the previous OutputPlan and rewrite only sections whose inputs changed.
  4. Store the cache in .lk-cache/ (configurable via --incremental-cache-dir); each entry: OutputPlan as JSON, a section-index map, and the patched output as a sparse file.
  5. Pre-bucket symbols by shard before acquiring any RwLock — acquire a shard once per input file's fold pass, not once per symbol (§14.7 performance note, closes a lock-churn pitfall).
  6. Parallelise the DWARF merge per compile unit, copying abbrev tables per unit and merging after — never serialise on a single shared abbrev table (the standard mistake, §20.6).
  7. Verify reproducibility (I3) holds under parallelism: two runs at --threads=1 and --threads=16 on identical inputs must produce byte-identical output — this is the concrete test that P1 and P2 do not conflict.

20.3 Deliverable

--threads=N scales linearly to min(N, num_input_files) on the llvm-class benchmark; --incremental reduces a single-source-file edit-and-relink on the chrome-class benchmark to under 2 seconds; the reproducibility fixture passes with parallelism on, independent of thread count.

20.4 Acceptance Criteria

  • ≥14x speedup at 16 threads on chrome-class vs 1 thread (M10).
  • ≥1.4x additional speedup from 16→32 cores, sub-linear accepted (M11).
  • Incremental single-file relink ≤2s on chrome-class (M5).
  • I3 holds: --threads=1 and --threads=16 outputs are byte-identical on every fixture in conformance/reproducibility/.

20.5 Conformance Fixtures

Fixture Purpose Expected Output
reproducibility/thread-count-matrix/ 1 vs 4 vs 16 threads, same inputs Byte-identical output (I3)
benchmarks/chrome_class.rs Cold + incremental wall-clock Meets M4/M5 thresholds
benchmarks/llvm_class.rs Thread-scaling curve Meets M10/M11 thresholds
incremental/single-file-edit/ Cache hit correctness Only changed sections rewritten; output matches a full cold relink

20.6 Pitfalls

  • Sharded RwLocks are not free; acquiring per-symbol instead of per-input-file dominates the resolver pass with lock overhead — pre-bucket first (§20.2 step 5).
  • pwrite into a MAP_SHARED mmap is well-defined on Linux/macOS but not universally portable; document supported targets and the ADR-04 fallback (buffer + write_all) explicitly.
  • The DWARF merge is the long pole on a debug-info-heavy link; serialising on a shared abbrev table (the standard mistake) erases the per-compile-unit parallelism gain — copy-then-merge instead.
  • An incremental-cache hit on a stale cache (e.g. a changed compiler flag not folded into the fingerprint) produces a silently wrong output (§24 FM-10) — the fingerprint must cover every option that affects bytes, not just input file contents.

20.7 Performance Concerns

This entire phase is the performance concern; §33's back-of-envelope model (relocation-apply cost ≈47ms parallel floor at chrome-class) shows relocation application is not the bottleneck — I/O (reading + writing ~2GB) and symbol resolution's lock traffic dominate, which is where §20.2's design choices (mmap-based I/O, sharded pre-bucketing) target their engineering effort.

20.8 Edge Cases

  • A link with more threads requested than input files — clamp to num_input_files, do not spawn idle workers that only add scheduling overhead.
  • An incremental cache directory shared (incorrectly) across two different projects — the fingerprint must include an absolute-path-independent project identity to avoid cross-project cache poisoning.
  • A crash mid-write to the incremental cache (e.g. kill -9) — the cache must be validated (checksum) before trusting a hit, never partially consumed (§24 FM-10).

20.9 Failure Analysis

A parallelism-introduced non-determinism bug (I3 violation) is the highest-value bug class to catch here — detected by the nightly reproducibility matrix (§22) and the thread-count-matrix fixture in CI on every commit, not just nightly. A stale-incremental-cache bug is detected by a cache-invalidation fixture that changes one compiler flag and asserts a cache miss.

20.10 Operational Notes

OpenTelemetry spans (ADR-19) wrap each pipeline phase from this point on; docs/performance/parallelism-model.md is the runbook answer to "why is my link slow," directly reading the span durations against the §20.2 table.

21. Phase 9 — Mach-O & PE/COFF Conformance

Phase 9 reads non-ELF formats for conformance and inspection tooling only — the linker never produces Mach-O or PE/COFF output (§1, ADR-02; write paths PhaseDeferred("§36")).

21.1 Objectives

  • Implement lk_macho reading Mach-O headers, load commands, sections, symbol/string tables, and the indirect symbol table.
  • Implement lk_pe reading the DOS/PE/COFF headers, optional header, section headers, and the import/export/relocation/resource directories.
  • Never implement a write path for either format (deferred, PhaseDeferred("§36")).

21.2 Detailed Implementation Steps

  1. Parse the Mach-O header (mach_header_64, MH_OBJECT/MH_EXECUTE/MH_DYLIB) and load commands: LC_SEGMENT_64, LC_SYMTAB, LC_DYSYMTAB, LC_LOAD_DYLIB, LC_LOAD_DYLINKER, LC_UUID, LC_CODE_SIGNATURE, LC_FUNCTION_STARTS, LC_DATA_IN_CODE, LC_DYLD_CHAINED_FIXUPS, LC_DYLD_EXPORTS_TRIE, per Apple's Mach-O Runtime Reference (§5 RFCs/Specs) — read-only, never a write path (ADR-02, P6-adjacent format boundary).
  2. Parse sections within segments, the symbol/string table, and the indirect symbol table (used by __la_symbol_ptr/__nl_symbol_ptr).
  3. Explicitly support LC_DYLD_CHAINED_FIXUPS (post-Big-Sur) alongside the older LC_DYLD_INFO_ONLY — reading only the older format silently fails on every modern macOS binary.
  4. Parse the PE/COFF DOS header, PE signature, IMAGE_FILE_HEADER, IMAGE_OPTIONAL_HEADER64, IMAGE_SECTION_HEADERs, the import (.idata), export (.edata), relocation (.reloc), and resource (.rsrc) directories, plus the COFF symbol/string table, per Microsoft's PE Format Specification (§5 RFCs/Specs).
  5. Compute RVA-to-file-offset translation explicitly and separately from ELF's file-offset model — never conflate RVA (relative to image base, from the optional header) with raw file offset (the most common PE bug).
  6. Wire lk-inspect macho/lk-inspect pe to print structured dumps comparable to otool -l/dumpbin /headers.
  7. Build the conformance corpus: 50 Mach-O objects from clang on macOS, 30 PE/COFF objects from MSVC on Windows; round-trip is read + JSON dump + JSON diff against the reference tool's output.

21.3 Deliverable

lk-inspect macho hello.macho and lk-inspect pe hello.exe print structured dumps matching otool -l/dumpbin /headers (post-canonicalisation) on 100% of the conformance corpus.

21.4 Acceptance Criteria

  • 80/80 (50 Mach-O + 30 PE/COFF) conformance fixtures pass (M12-adjacent phase gate).
  • Zero panics on the corpus, including 10 deliberately-corrupted variants per format.
  • LC_DYLD_CHAINED_FIXUPS-only binaries (no LC_DYLD_INFO_ONLY) parse correctly.

21.6 Pitfalls

  • Reading only LC_DYLD_INFO_ONLY misses every modern (post-Big-Sur) macOS binary — support LC_DYLD_CHAINED_FIXUPS from day one of this phase.
  • Confusing PE's RVA with a raw file offset is the most common PE/COFF bug; always translate through the optional header's image base explicitly.
  • WebAssembly module magic (\0asm) detection belongs to this phase's input-classification layer even though full parsing is deferred (PhaseDeferred("§36")) — the classifier must recognise and cleanly reject it, not misclassify it as a corrupt ELF.

21.7 Performance Concerns

Read-only conformance parsing has no wall-clock budget of its own (it never sits on the hot link path); the concern is keeping the fixture corpus's CI runtime bounded (~80 fixtures, target <10s total).

21.8 Edge Cases

  • A fat/universal Mach-O binary (multiple architecture slices) — the reader selects and reports on one slice explicitly rather than silently picking an arbitrary one.
  • A Wasm module input (\0asm magic) arriving where an ELF/Mach-O/PE was expected — cleanly classified and rejected with a deferred-feature diagnostic (PhaseDeferred("§36")), never treated as a corrupt ELF.
  • A PE file with a corrupted IMAGE_SECTION_HEADER count exceeding the file size — bounds-checked exactly as ELF's e_shnum is (§13.6).

21.9 Failure Analysis

Since these are read-only conformance surfaces, a bug here cannot corrupt an lk-produced binary; blast radius is contained to lk-inspect output correctness. Detection is entirely the 80-fixture corpus plus fuzzing (fuzz/fuzz_targets/, extended to Mach-O/PE readers as a documented follow-on).

21.10 Operational Notes

lk-inspect macho/lk-inspect pe are positioned as parity tools for engineers who need one CLI across three object formats during cross-platform debugging — not as a replacement for otool/dumpbin, which remain the source of truth for their native platforms.

22. Phase 10 — Reproducibility, Conformance Harness, Audits

Phase 10 is the polish phase — and the phase that decides whether the linker is genuinely production-grade or merely impressive.

22.1 Objectives

  • Automate the cross-host reproducibility matrix (M13).
  • Land lk_conformance, the corpus-walking runner that gates every release.
  • Scope and prepare for third-party audit (§23, §28).

22.2 Detailed Implementation Steps

  1. Automate the reproducibility test: build lk from source on host A; run a curated link (lk hello.o libc.a -o hello); record sha256(hello); repeat on host B (different distro, glibc version, filesystem); assert equality (I3, M13); run nightly via .github/workflows/reproducibility.yml, opening a Sev-0 incident on any deviation.
  2. Implement lk_conformance: walk the conformance/ corpus depth-first, build each fixture's input (via Makefile.fixture), run lk with the fixture's flags, compare to expected.json ({exit_code, stdout, stderr, sha256_of_output}), and optionally to golden.bin for byte-identical assertions; emit conformance.report.json with one entry per fixture (Pass/Fail/Deferred(anchor)).
  3. Wire phase gates: §12 gate requires the ELF-round-trip smoke fixture; §16 gate requires every relocs/x86_64/* + tls/{le,ie}/*; §18 gate requires every loader/*; §19 gate requires every relocs/{aarch64,riscv}/* + thin-LTO fixtures; this phase's gate requires 100% pass with a documented, non-growing Deferred count.
  4. Implement the golden cross-check (§27): run lld and mold on identical inputs, record objdump -dr/readelf -aW outputs from all three, diff post-canonicalisation (section/symbol/relocation ordering normalised) — targeting semantic equivalence, not byte-equality with lld/mold (ADR-21).
  5. Fill audits/scope.md: relocation arithmetic per architecture (correctness, range checks); the symbol resolver (rule conformance, unsoundness windows under parallelism); the loader's self-relocation, TLS allocator, _start trampoline; the mmap-based writer (race conditions, partial writes, fsync semantics); the supply chain (deny.toml, pinned versions, CI provenance).
  6. Document the reproducibility-breaking known cause: __DATE__/__TIME__ macros embedded by the user's compiler into inputs — not fixable by the linker; recommend -Wdate-time or --reproducible at the compile step.
  7. Classify and cleanly reject WebAssembly module and Component-Model inputs at this phase's edge (magic-byte detection from §21.6 extended here), always with a PhaseDeferred("§36") diagnostic, never a parse attempt (ADR-22).

22.3 Deliverable

make repro produces byte-identical output across the 3-host matrix; make conformance produces conformance.report.json with zero Fail entries; audits/scope.md is complete and ready for engagement.

22.4 Acceptance Criteria

  • 0 byte differences across the ≥3-host reproducibility matrix, nightly (M13).
  • conformance.report.json shows 100% Pass (0 Fail), with any Deferred entries matching exactly the §36 register (M14).
  • Golden cross-check against lld/mold shows semantic equivalence (post-canonicalisation diff empty) on the full corpus.

22.6 Pitfalls

  • __DATE__/__TIME__ in input objects breaks reproducibility in a way the linker cannot fix — document, do not attempt to patch compiler output.
  • Regenerating the conformance corpus without pinning the reference-toolchain version silently drifts the golden baseline; pin and bump deliberately (conformance/README.md).
  • A Deferred count that grows release-over-release without a corresponding §36 register update is itself a gate failure (M14) — the register and the report must stay in lockstep.

22.7 Performance Concerns

The reproducibility matrix and conformance run are both off the hot link path (CI-only); their own runtime budget is generous (minutes, not the M1–M5 link-latency budgets) but the nightly cadence must stay reliable — a flaky matrix job erodes trust in I3 faster than an actual violation would.

22.8 Edge Cases

  • A host in the reproducibility matrix with a filesystem that reorders directory entries differently (e.g. differing readdir order) — input-file ordering must come from the command line / response file, never from filesystem enumeration order.
  • A WebAssembly module-linking (Component Model) input arriving alongside ordinary ELF inputs in one invocation — rejected per-input, without aborting the rest of a mixed-input link.
  • A conformance fixture whose expected.json pins exact diagnostic wording instead of the diagnostic code — brittle; negative fixtures pin the code (lk00NN) and a message substring only (§15.4).

22.9 Failure Analysis

A reproducibility-matrix failure is always Sev-0 (it undermines the product's core promise, P1); root-causing starts with bisecting which pipeline stage's sort or hash the two hosts disagree on. A conformance regression (Fail count > 0) blocks release entirely — lk_conformance's exit code gates release.yml.

22.10 Operational Notes

conformance.report.json is archived per release for trend analysis (Deferred count over time, per-fixture timing); audits/scope.md and audits/reviews/ carry the third-party engagement record referenced by Appendix B's exit criteria for the audit milestone.

25. Operational Readiness

Metrics. OpenTelemetry counters/histograms per pipeline phase (ADR-19): reloc_apply_duration_ms, resolve_fixed_point_iterations, layout_plan_duration_ms, writer_pwrite_bytes_total, archive_crawl_iteration_count, fuzz_crash_total, repro_mismatch_total (all named in §7/§23/§24 as the enforcing telemetry).

Tracing. One span per §3 architectural box, parented under a single link-invocation trace; --trace=none disables export while retaining local timing (ADR-19).

Structured logging. Every log line is a rendered Diagnostic (P13) or a span event; no bare eprintln! outside the render layer (§11.8).

Dashboards. Grafana (via docker-compose.yml) tracks: wall-clock per benchmark class over time (M1–M5 trend), conformance Deferred count trend (M14), reproducibility-matrix pass streak (M13).

Alerting philosophy. Sev-0: any reproducibility-matrix failure (FM-6), any conformance regression to Fail > 0 (M14). Sev-1: any perf-target regression >10% release-over-release (§29). Sev-2: ICF/GC size-reduction regression below M12's 5% floor.

SLOs. Cold link wall-clock (M1–M4) and loader first-fault latency (M8) are release-gating SLOs, not just dashboards — a release that misses them does not ship.

Incident response. docs/runbooks/triage.md is the entry point; reloc-truncated.md, undefined-reference.md, dynamic-loader-debug.md are the three most-hit runbooks, matching FM-1/FM-2/FM-7-8.

Backup/restore. The only persistent state is .lk-cache/ (incremental cache, §20.2) — restorable by deletion (forces a cold relink, never a correctness issue, only a performance one).

Deployment topology. lk ships as a single static-or-dynamic CLI binary via the release channel (§28); lk-ld.so ships side-by-side, versioned independently (§26).

Canary/rolling-upgrade/rollback. A new lk version is canaried by running the full conformance/ suite plus the reproducibility matrix against the previous version's recorded golden hashes before promotion; rollback is reinstalling the previous binary (stateless CLI, no migration needed).

26. Compatibility & Versioning

Wire compatibility. The ELF/dynamic-section wire format is externally fixed by the SysV ABI (§5 Books) — lk cannot version this independently; conformance against it is absolute, not negotiable.

Storage compatibility. The incremental-cache format (OutputPlan JSON + section-index map, §20.2) is internal and versioned via a cache_format_version field; a version bump invalidates old caches (forces one cold relink, never wrong output).

Schema evolution. Diagnostic's JSON shape (P13) is additive-only (new optional fields); removing or renaming a field is a major-version bump.

API stability. ArchBackend (§11.6) is the primary extension point; adding a required trait method is a breaking change requiring a coordinated update across all three implementations (x86_64/AArch64/RISC-V) and a major version bump.

Migration. A breaking ArchBackend change ships with a migration guide in CHANGELOG.md and a deprecation window of one minor version where both trait shapes are accepted via a default-method shim where feasible.

Deprecation policy. Deprecated CLI flags warn for 2 minor versions before removal; deprecated ArchBackend methods follow the same window.

SemVer policy. lk/lk-ld.so follow SemVer; a MAJOR bump for any wire-format-breaking or ArchBackend-breaking change, MINOR for new architecture/feature support, PATCH for bug fixes.

Rolling-upgrade guarantees. lk-ld.so versions install side-by-side (never overwriting), so a fleet can run mixed loader versions against binaries built for either, as long as each binary's PT_INTERP names its matching loader version explicitly.

27. Testing & Verification Strategy

Unit. Per-crate unit tests for every reader/writer/resolver/layout/relocator function; ties to invariants I1–I14 directly (each has at least one targeted unit test beyond the conformance corpus).

Integration. End-to-end lk invocations across the examples/ directory (hello-c, hello-rust, shared-lib, tls-example, lto).

Property-based. proptest on relocation arithmetic: arbitrary in-range/out-of-range (S, A, P) triples assert the range-check boundary matches the psABI formula exactly (§15.2).

Differential. Golden cross-check against lld/mold (§22.2 step 4, ADR-21) — semantic equivalence, not byte equality.

Fuzzing. cargo-fuzz targets for lk_elf::ElfFile::parse, lk_archive::ArchiveReader, and ArchBackend::apply_reloc, run continuously in CI (kernels.yml); crashes auto-file issues (T1, T2, T11).

Chaos/fault injection. kill -9 mid-write to the output mmap (verifies no partial-write corruption reaches a "successful" exit code); corrupt-then-reload the incremental cache (verifies FM-10's checksum gate).

Deterministic replay. The --threads=1/--threads=16 reproducibility fixture (§20.2 step 7) is a replay test by construction.

Soak. A 24-hour repeated-relink soak of the chrome-class benchmark under --incremental, watching for cache-growth or memory-leak regressions.

Conformance. lk_conformance (§22.2 step 2) is the umbrella umbrella-suite tying every fixture (§12.5–§22.5) to a phase gate.

Performance-regression gating. benchmarks/results/ comparison across releases; >10% regression on any M-table target opens a Sev-1 issue (§29).

Every strategy above ties back to a named invariant (§7) and a named fixture (each phase's N.5) — no test exists without a traceable reason.

30. Scalability Analysis

Constant vs grows. ArchBackend dispatch is O(1) per relocation regardless of input size (P7). The global symbol table grows O(unique symbols); §33 #2 shows this is the dominant memory term at chrome-class scale (≈1.28 GB of the ≈2 GB input). Relocation-apply cost is O(relocations) but parallelises fully per output section (§20.1) and is not the wall-clock bottleneck (§33 #3).

Named bottlenecks, in order. (1) I/O — reading + writing ≈2 GB of input/output dominates wall-clock at chrome-class scale, mitigated by mmap-based zero-copy reads (§13) and the mmap-writer (P3). (2) Symbol-resolution lock traffic — sharded but still the second-largest cost, mitigated by pre-bucketing (§20.2 step 5). (3) DWARF merge — the long pole specifically on debug-info-heavy links (§20.6). (4) Relocation-apply arithmetic — confirmed not a bottleneck by §33 #3's derivation.

Horizontal/vertical scaling. The static linker is a single-process, single-machine batch tool — there is no horizontal-scaling story for one link invocation; vertical scaling (more cores) follows §20.1's table up to the sub-linear ceiling at M11.

Sharding/partitioning. The symbol table's 64-way sharding (ADR-05) is the only partitioning scheme in the system; output-section-level parallelism (§20.1) is a natural partition of the layout, not a designed shard.

Coordination overhead. The only hard synchronisation barrier is §14→§16 (I7, P11); every other stage's coordination is either lock-free-adjacent (sharded RwLock) or embarrassingly parallel (per-section relocation/writing).

Practical ceiling. ≈32 cores per §4/M11 (sub-linear scaling beyond 16, symbol-table contention becomes the limiter). Levers beyond it: increase shard count past 64 (diminishing returns given the ADR-05 tradeoff); move to a genuinely lock-free hash (the rejected alternative in ADR-05, viable once contention data justifies the added complexity); or partition the link itself (out of scope — would require a fundamentally different, incremental/distributed linker, §35 Alt-2).

31. Mental Models & First Principles

  • MM1 — A relocation is a deferred write. Insight: every relocation is "patch this byte range with a value computed later," nothing more. Predicts: relocation application fully parallelises once symbol values are known (§20.1). Bug class without it: serialising relocation application under a false assumption that order matters. Applies at §15, §20.
  • MM2 — The GOT is an indirection contract, not a data structure. Insight: the GOT's slots are allocated at link time but its values are a runtime contract fulfilled by the loader. Predicts why -z now vs lazy binding is a security/latency tradeoff, not two unrelated features. Bug class without it: conflating GOT allocation timing with GOT initialization timing. Applies at §16, §18.
  • MM3 — Determinism is a sorting discipline, not an absence of parallelism. Insight: parallelise freely as long as every merge step sorts by a stable key. Predicts I3 holds under any thread count. Bug class without it: assuming "parallel" implies "nondeterministic," leading to unnecessary serialisation. Applies at §20, P1/P2.
  • MM4 — The loader is a program that hasn't linked itself yet. Insight: lk-ld.so is itself an ET_DYN requiring relocation before its own globals are valid. Predicts why self-relocation must precede any Rust/global-state code. Bug class without it: calling into globals before self-relocation, crashing nondeterministically depending on load address. Applies at §18.3.
  • MM5 — TLS is per-thread virtual memory with a compile-time-chosen indirection cost. Insight: LE/IE/GD/LD are one latency/flexibility tradeoff curve, not four unrelated mechanisms. Predicts which model a given code shape (static executable vs dlopen-able library) should use. Bug class without it: treating TLS models as arbitrary compiler choices rather than a spectrum. Applies at §16.4, §18.
  • MM6 — A symbol table is a last-writer-wins log with typed precedence, not a set. Insight: the multiple-definition/weak/strong rules fall out of one total precedence order (§14.2). Predicts the exact winner for any combination of bind types without special-casing. Bug class without it: ad hoc special-casing for each new bind-type combination instead of one ordered rule. Applies at §14.2.
  • MM7 — ICF and GC are dual passes over the same reachability graph. Insight: GC finds reachable, ICF finds redundant — both walk the same section-relocation graph. Predicts they can share infrastructure (the graph builder) even though their outputs differ. Bug class without it: building two independent, divergent graph representations. Applies at §17.
  • MM8 — A conformance fixture is a frozen bug report. Insight: every fixture encodes one specific failure made permanently impossible to reintroduce. Predicts why the Deferred/Fail count should only shrink, never silently regrow (M14). Bug class without it: treating conformance as a checkbox rather than a living regression firewall. Applies at §22, §27, P9.

gold proved threaded symbol resolution was viable years before mold, but its BFD-adjacent data structures capped how far parallelism could go; it is the historical bridge lk's ADR-05 sharding builds past, not a design to imitate wholesale.

LLVM lld wins where cross-format support matters most (a single linker driver targeting ELF, Mach-O, and COFF output, unlike lk's read-only stance on the latter two, ADR-02) — the right choice for a project that must produce all three formats, not just consume two of them for conformance.

mold wins on raw wall-clock at authoring time and is the direct architectural ancestor of lk's ADR-04 mmap-writer decision; it wins outright whenever reproducibility and memory-safety-by-construction are not requirements and Linux-only deployment is acceptable.

33. Back-of-Envelope Capacity Model

  1. Chrome-class unique symbol references: 50M relocations (§4) ÷ ≈5 relocations-per-symbol-reference (empirical average) ≈ 10M unique symbol references.
  2. Global symbol-table memory: 10M symbols × (SymbolNameId 4B + WinningDef enum ≈24B + Vec<RefSite> overhead ≈24B + hashmap slot overhead ≈40B) ≈ 10M × ≈128B ≈ 1.28 GB resident — consistent with the M6 ≤1.5x-input-size RSS ceiling given a ≈2 GB input.
  3. Relocation-processing CPU cost: 50M relocations × ≈15 ns/relocation (bounds check + arithmetic + write) ≈ 0.75 s single-threaded ÷ 16 threads ≈ 47 ms parallel floor — far under the 30 s M4 budget, confirming (§30) relocation apply is not the wall-clock bottleneck.
  4. GOT size estimate: ≈5% of 10M symbol references need a GOT slot (external data/PLT-adjacent) = 500K entries × 8B = 4 MB GOT.
  5. PLT size estimate: ≈2% of symbol references are external function calls needing a PLT stub = 200K stubs × 16B = 3.2 MB PLT.
  6. Output file size prediction: ≈2 GB input, minus ≥5% GC/ICF reduction (M12), plus tens-of-MB synthetic sections (items 4–5 plus .dynsym/.rela.*) ≈ 1.9–2.0 GB output.
  7. TLS aggregate: assume 200 TLS-using modules × avg 2 KB .tdata/.tbss = 400 KB per-thread TLS aggregate; DTV overhead 200 × 8B = 1.6 KB per thread (M9's budget must amortise this allocation, not per-access cost).
  8. FD budget: chrome-class DT_NEEDED transitive depth ≈150 (§4) × 1 FD each during load = 150 FDs, well under the default 1024 ulimit.
  9. Incremental cache size: OutputPlan JSON + section-index map ≈5–10% of output size ≈ 100–200 MB cache footprint per chrome-class link (§20.2).
  10. Fuzzer replay throughput: cargo-fuzz at ≈10K exec/s/core × 12 CI cores = 120K exec/s → a 10M-execution regression corpus replays in ≈83 s, sizing the CI fuzz-replay gate (§27).
  11. Archive-crawl worst case: 16-iteration cap (I13) × N archive members re-scanned per iteration; for a 500-member archive, worst case ≈8,000 member-scans, bounding FM-4's detection threshold.
  12. .gnu.hash table size: GNU-hash convention sizes buckets at ≈symbol_count/4; for ≈100K exported dynsyms (≈1% of the 10M total, per visibility gating, §14.6) → 25K buckets × 4B = 100 KB hash table.

Every number above is derived from §4's System Constraints table with the formula shown — none is asserted without arithmetic.

35. Alternative Architectures (Roads Not Taken)

Alt-1 — Classic single-threaded ld.bfd-style design.

sequential: read all -> one global mutable symtab -> layout -> reloc -> write(buffer) -> flush

Regime: extremely small links, embedded toolchains, or contexts where a 40-year correctness track record outranks throughput. Real system: GNU ld/bfd. Rejected: fails the mold-competitive wall-clock target (§4, M4) outright at chrome-class scale — the sequential design has no path to closing a 15-minute-to-7-second gap without a rewrite.

Alt-2 — Incremental/resident linker daemon.

client CLI <-> Unix socket <-> resident daemon (warm symtab + parsed-object cache across invocations)

Regime: interactive edit-compile-link loops in an IDE, where process-startup and re-parse cost dominates over pure link-algorithm cost. Real system: the closest embodiments are Bazel's persistent-worker protocol and javac --server-style daemons; no ELF linker ships this exact shape at authoring time. Rejected: a stateful daemon adds crash-recovery and cross-client cache-invalidation burden disproportionate to this project's reproducible-batch-CLI goal (P1, P3) — every invocation must be independently reproducible, which a warm, order-dependent cache complicates.

Alt-3 — LTO-integrated / whole-program linker with no separate link phase.

source -> whole-program IR -> single monolithic pass: codegen + layout + emit

Regime: closed-world, single-producing-compiler targets with no separate-compilation requirement. Real system: the Go toolchain's cmd/link operating over a closed IR world; embedded/JIT "linkers" that never see object-file boundaries. Rejected: incompatible with this project's open-world requirement — arbitrary .o/.a from any compiler (§1 scope) — a whole-program IR assumes one producing compiler, which clang+rustc+archived-third-party-.a inputs violate by construction.

Alt-4 — In-kernel / loader-less design (fully static, no separate PT_INTERP handoff).

kernel execve -> binfmt_elf -> _start directly (no userspace loader, no DT_NEEDED)

Regime: fully static (or static-PIE) deployments where dynamic linking is refused by policy — distroless/scratch containers, some embedded firmware. Real system: the Linux kernel's own fs/binfmt_elf.c path for static binaries, and musl's static-PIE self-relocation stub (§5 Reference Implementations). Rejected: forfeits shared-library memory sharing across processes and security-patch-without-relink, both required by this project's target users (§1) who explicitly need .so production and consumption.

37. Glossary

  • ELF — Executable and Linkable Format; the container format for all lk-produced output.
  • ET_REL — relocatable object file type (.o); has no program headers.
  • ET_DYN — shared-object/PIE file type; base address is not fixed.
  • ET_EXEC — non-PIE executable; fixed base address (not produced by default, P10).
  • PT_LOAD — a program-header entry describing a segment to mmap.
  • PT_DYNAMIC — points at .dynamic, the dynamic-linking metadata table.
  • PT_TLS — describes the thread-local-storage template (.tdata+.tbss).
  • PT_INTERP — names the dynamic loader path the kernel should invoke.
  • PT_GNU_RELRO — marks a region the loader mprotects read-only post-relocation.
  • PT_GNU_STACK — carries the stack's execute permission (default: none, P10).
  • GOT — Global Offset Table; indirection slots for external data/PLT addresses.
  • PLT — Procedure Linkage Table; lazy-binding stubs for external functions.
  • DT_NEEDED — a .dynamic entry naming a required shared library.
  • DT_SONAME — the shared object's own canonical name.
  • DT_RPATH — legacy library search path, searched before LD_LIBRARY_PATH.
  • DT_RUNPATH — modern library search path, searched after LD_LIBRARY_PATH.
  • BIND_NOW — resolve all PLT entries at load time, not lazily.
  • RELRO — Relocation Read-Only; post-relocation mprotect hardening.
  • TLS — Thread-Local Storage; per-thread data with four access models (§8.6).
  • DTV — Dynamic Thread Vector; per-thread table mapping module id → TLS block.
  • IFUNC — indirect function; address resolved by a resolver function at load time.
  • STB_WEAK/STB_GLOBAL/STB_LOCAL — symbol binding classes (§8.3, §14.2).
  • STV_HIDDEN — visibility excluding a symbol from the dynamic symbol table.
  • COMDAT — a section group deduplicated across translation units (§16.6, §17).
  • ICF — Identical Code Folding; deduplicates byte-identical output sections.
  • GC-sections — discards unreferenced input sections (§17.1).
  • LTO — Link-Time Optimisation; cross-module optimisation at link time.
  • ThinLTO — summary-based LTO avoiding a single monolithic IR merge.
  • Bitcode — LLVM's serialized IR format, LTO's input (ADR-09).
  • Build-ID — a content hash embedded in the output for symbol-server matching (ADR-15).
  • Reproducible build — byte-identical output across hosts/runs for identical inputs (I3).
  • ASLR — Address Space Layout Randomization; why PIE base addresses vary per run.
  • PIE — Position-Independent Executable; ET_DYN with an entry point.
  • Symbol versioning — verdef/verneed mechanism disambiguating symbol@VERSION.
  • Archive (ar) — a container of relocatable-object "members" with a symbol index.
  • Thin archive — an ar variant storing paths to members instead of their bytes.
  • Relocation — an instruction to patch a byte range with a computed value (MM1).
  • Addend — the constant term in a relocation's value formula.
  • Auxiliary vector (auxv) — kernel-provided key/value pairs at process start (§18.2).
  • _start — the true process entry point, before main (§18.2).
  • DWARF — the debug-information format merged (not synthesized) by lk (ADR-14).
  • .eh_frame — exception-handling frame data; the GC "sealant" (§17.6, MM7).
  • FDE — Frame Description Entry; one .eh_frame record per function.
  • CFI — Call Frame Information; the semantic content of FDEs.
  • Fixed point — the state where resolution produces no further changes (I7).
  • Sharded lock — a lock split across N partitions to reduce contention (ADR-05).
  • Reachability worklist — the GC algorithm's core data structure (§17.1).
  • LD_PRELOAD — forces a library to the front of the resolution scope.
  • LD_AUDIT — a hook interface observing loader decisions (ADR-23).
  • Symbol interposition — one module's symbol shadowing another's at resolution time (§23 T3).
  • RTLD_GLOBAL/RTLD_LOCAL — dlopen flags controlling a loaded module's symbol visibility to others.
  • Static PIE — a position-independent executable with no dynamic dependencies (§35 Alt-4).
  • GNU_HASH — the modern hash-table format for fast dynamic symbol lookup (§8.5, §33 #12).
